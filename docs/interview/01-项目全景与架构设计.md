# 第 01 期 · 项目全景与架构设计（开场必问）

> **本期结论**：开场 10 分钟，面试官只想确认两件事：你是否真的参与过这个项目，以及你是否理解系统的边界。
> 能否把“单一装配入口”和“状态外置”这两个设计讲清楚，往往能拉开差距。
>
> 对应 JD：Agent 平台研发、智能客服落地、Spring Boot 工程化能力。题量 7（初 2 / 中 4 / 高 1）。

### Q1【初级】用 2 分钟介绍这个项目：它解决什么问题、由哪些模块组成、你负责哪一部分？

**考察点**：表达结构；能否区分运行面与控制面；能否讲出一条完整的主链路。

**参考回答**

- **定位**：这是一个基于 AgentScope Java 2.0.3 的企业级智能客服与 Agent 平台。它把
  “接入 → 身份校验 → 会话恢复 → 知识与工具调用 → 退款审批 → 转人工工单 → CSAT”做成一套可运行的系统，
  同时提供运营控制台，用于管理模型、Agent、MCP、评测、发布和账单。
- **模块**：
  - `customer-work-starter`：可复用的 Agent 基础设施，通过 `@AutoConfiguration` 自动装配。
  - `customer-work-app-server`：客服运行面，端口 8080，提供 HTTP / SSE / WebSocket 和工单能力。
  - `customer-channel`：协议与渠道适配，端口 8081。
  - `customer-admin-server`：控制面，端口 8082，使用独立库 `customer_admin`。
  - 可选的 `gateway`，以及两个 Vue 3 前端。
- **主链路**（H5）：`/ws/user` → `ChatDispatchService`（校验会话归属、判断主体配额、落库）→
  `ChatTurnService.stream` → `CustomerServiceService.chatStream` → 单一客服 `ReActAgent`。
  Agent 构建时由 `AgentGovernanceAssembler` 统一装配治理中间件，运行时调用模型、RAG、业务工具、MCP 和 Skill。
- **推荐的表达顺序**：一句话定位 → 三层结构（接入 / 运行 / 控制）→ 一条主链路 → 自己做过的最难的一件事，
  最好带数据或事故复盘。

**追问**

1. *H5 每条消息为什么只走单 Agent，而不走多 Agent？*
   多 Agent 的一次会诊至少包括“路由 + N 个专家 + 归纳”，模型调用次数和首字延迟都会成倍增加。所以 `/consult`
   是一个独立入口，H5 不会对每条消息都调用它（README 3.2 / 3.3 有说明）。
2. *控制面怎么把配置交给运行面？*
   控制面发布配置到 Nacos 的租户专属 dataId。运行面监听到变更后，先校验 HMAC / contentHash，再原子替换运行配置，
   最后通过 ACK Outbox 回报结果。这是一条单向的配置链路（README 3.4）。

**减分回答**：只罗列技术栈名词；说“用了多 Agent 所以更智能”；分不清哪些能力默认关闭、哪些默认开启。

### Q2【中级】为什么要单独抽出 `customer-work-starter`？哪些东西放进 starter，哪些不放？

**考察点**：Spring Boot 自动装配、SPI 设计、按职责划分代码。

**参考回答**

- **判定标准**：只服务当前业务模块的代码，留在业务模块；可复用的通用能力，下沉到 starter。
  starter 里放模型、记忆、RAG、工具 SPI、治理中间件、审批、工单等基础设施。
- **扩展方式**：业务后端通过 `tool.backend.*` SPI 接入，例如 `OrderBackend`、`AfterSalesBackend`。
  starter 默认提供 Mock 实现，并加上 `@ConditionalOnMissingBean`；下游只要声明同类型的 Bean，就能替换成真实系统，
  工具的外壳代码不用改。
- **持久化统一走 Store SPI 模式**：接口 + InMemory 默认实现 + MyBatis-Plus 实现 + `@ConditionalOnMissingBean`。
  审批、槽位填充、对话阶段、转人工、反馈、工单、用户账户、聊天记录都使用这套模式。
- **两个真实踩过的坑**：
  - starter 里的 `WebFilter` 必须加 `@ConditionalOnWebApplication(type = REACTIVE)`。admin 是 Servlet 栈，
    不加这个条件，admin 就只能整体排除 starter 的自动装配。
  - `customer-channel` 使用 `@SpringBootApplication`，只扫描自己的包，拿不到 starter 里的 `@Component`，
    所以需要的 Bean 要显式用 `@Bean` 声明。

**追问**

1. *为什么 `@ConfigurationProperties` 字段的默认值要写成字面量，而不是引用常量？*
   `spring-boot-configuration-processor` 只从字面量初始化表达式里提取 `defaultValue`。改成常量引用后，
   IDE 提示和配置元数据里的默认值会静默消失。
2. *starter 改完后，下游模块为什么还是旧行为？*
   下游解析的是本地仓库里的 jar，而不是 starter 的工作区代码。需要先对 starter 执行 `mvn install`。

**减分回答**：把业务逻辑也塞进 starter；说不出替换点在哪里；只说“为了复用”，讲不出判定标准。

### Q3【中级】项目文档里反复提到“能力只接在用户不走的那条路上”。这个缺陷复发过几次？最后怎么根治的？

**考察点**：能否识别“同一类问题反复出现”背后的架构问题；是否知道单一入口和自动化检查的作用。

**参考回答**

- **现象**：这个问题一共复发了六次：
  - 语义缓存只接在了非流式链路上；
  - CSAT 邀请挂错了生命周期钩子；
  - 缓存命中后的出站过滤只在流式链路上生效；
  - 知识盲区埋点只覆盖了工具路径；
  - 附件 OCR 内容绕开了 Spotlighter 隔离；
  - `/consult` 整条链路没有任何中间件。
- **根因**：“装配治理能力”这件事分散在多个构建 Agent 的入口里，每个入口各写一遍。改了一处忘了另一处，
  **两边都不会报错**。
- **根治方式**：
  1. 收敛为唯一的装配入口 `AgentGovernanceAssembler.applyTo(builder)`。任何 `ReActAgent.builder()`
     在调用 `build()` 之前都必须经过它。
  2. 新增治理中间件时，只改装配器这一个地方。
  3. `AgentAssemblyAlignmentTest` 直接扫描源码并断言：只要新增一条构建 Agent 的路径却没有调用装配器，测试就会失败。
- **同样的思路在项目里还用在**：`TenantResolver`（租户解析只有一个实现）、`MiddlewareOrders`
  （中间件顺序只有一个定义处）、`ModelProviders.SUPPORTED`（支持的模型厂商清单只有一份）、
  `SharedConstantAlignmentTest`（同一个字面量只允许在一处定义）。

**追问**

1. *为什么用扫描源码的测试，而不是运行时断言？*
   运行时断言依赖具体路径被测试覆盖，而最容易漏掉的恰恰是没人测的那条路径。结构断言则会检查所有路径。
   但它也有局限：扫描文本发现不了“调用了装配器，但装进去的中间件是空的”。`customer-channel` 就出现过这种情况：
   调用了 `applyTo`，但 `ObjectProvider` 一个 Bean 都解析不出来。这类问题要用 `@SpringBootTest` 启动真实容器来断言。
2. *同类链路有几条？* 共七条：`chat()`、`chatStream()`、WebSocket `/ws/user`、`/consult` 多 Agent、
   admin 工作台、`customer-channel`、Harness。只在其中一条上验证通过，不等于问题已经修好。

**减分回答**：“加了一个工具类统一调用”，但讲不出为什么以前会漏、以后靠什么防止再漏。

### Q4【中级】为什么把业务表和管理表拆成两个库？admin 访问客服库为什么必须走 `CustomerWorkFacade`？

**考察点**：数据边界、跨库访问的固定套路，以及不依赖分布式事务的一致性方案。

**参考回答**

- **为什么分库**：运行面数据（会话、工单、消息、知识分片、配额）和控制面数据（RBAC、模型资产、发布任务、审计）
  的生命周期、权限和扩缩容节奏都不同。admin 故障时，客服运行面仍然可以继续服务。
- **`CustomerWorkFacade` 负责一整套固定流程**：惰性建立连接池、连通性探测、首次访问前执行客服端 Flyway 迁移、
  库不可达时转换为业务异常、销毁时关闭连接池。
  - 这套流程以前有 8 个能力域各抄了一份，共约 560 行。新增能力域时最容易漏掉 `@PreDestroy`：漏了不会报错，
    只会在反复重启时慢慢泄漏连接池。
  - 收敛之后，admin 中只有这一处调用 `CrossDbGateways.lazy`。
- **迁移门禁**：admin 排除了 starter 的自动装配，所以必须通过门面接管客服端库的迁移。
  否则缺表、缺列的问题会被推迟到业务 SQL 执行时才暴露为 `Unknown column`。

**追问**

1. *跨库操作怎么保证一致性？*
   项目没有使用分布式事务，而是按业务场景设计补偿和回执：
   - **知识库权限变更**：先在 KB 行锁内同步提交客服库的封锁；封锁失败，就阻止后台写入。
   - **知识发布**：发布结果未知时保留原任务，由 Worker 先核对客服库回执再恢复；禁止重新生成任务，
     以免重复插入 FAQ。
2. *门面访问失败时，为什么不缓存失败状态？* 迁移失败时不能缓存这个门面，下次访问要原样重试，
   否则一次瞬时故障就会让这个能力永久不可用。

**减分回答**：直接回答“用 Seata 做分布式事务”，但讲不出业务上的补偿和回执设计。

### Q5【中级】AgentScope 2.0 的“Agent 无状态、状态外置”是什么意思？项目里会话状态怎么存储、怎么隔离？

**考察点**：理解框架的状态模型；缓存键为什么要包含身份；热更新时状态如何保留。

**参考回答**

- **状态外置**：2.0 版本的 Agent 实例不再自己持有会话历史。框架在 `call` / `streamEvents` 链路中，
  按 `(userId, sessionId)` 自动读写 `AgentStateStore`，项目使用 MySQL 实现。
- **`RuntimeContext` 决定状态落到哪个槽位**：`AgentGovernanceAssembler.contextFor` 把 `userId` 设为可信租户
  （来自 `TenantResolver.resolve`），把 `sessionId` 设为会话 ID。这两个值决定框架内部的状态槽位；
  **如果写成常量，所有用户会共用同一份对话历史**。
- **热 Agent 缓存**：进程内使用有界 LRU（`LinkedHashMap` 按访问顺序排序，并重写 `removeEldestEntry`，上限 1000）。
  它只用来摊薄“按会话装配 Agent”的开销，不存储状态。缓存项被淘汰时，调用 `AgentResourceCloser.closeQuietly` 释放资源。
- **缓存键是 `AgentSessionKey(memorySubject, stateUserId, sessionId)`**：Agent 创建时绑定了长期记忆，
  而 `sessionId` 可以由客户端控制。如果只用 `sessionId` 做键，不同租户、不同用户会复用第一位调用者的记忆代理。
- **热更新**：`flushHotAgents` 只清空热缓存，不动 `StateStore`。之后按“淘汰即重建、状态从 Store 恢复”的路径执行，
  进行中的会话不会丢失上下文。

**追问**

1. *热缓存被淘汰时正在进行的请求怎么办？* 状态在 Store 里，下一次请求会重建 Agent 并自动恢复状态；
   同一会话的并发写入由会话锁串行化（见第 06 期 Q5）。
2. *2.0.3 的乐观并发对这里有什么影响？* 写状态时默认走 CAS（`saveIfVersion`），冲突会被 `OVERWRITE`
   策略静默吸收，详见第 04 期 Q7。

**减分回答**：说“Agent 实例里保存着对话历史，所以要缓存 Agent”。

### Q6【高级】如果要给所有对话链路加一个新能力，例如统一的出站 PII 脱敏，你怎么保证不漏？

**考察点**：能否把前面讲到的经验迁移到一个新需求上；是否清楚流式、缓存命中、非流式三种出口。

**参考回答**（按步骤说）

1. **先列出所有同类链路**：一共七条，见 Q3。
2. **找到能覆盖最多链路的公共位置**：把能力做成中间件，放进 `AgentGovernanceAssembler`，
   在 `MiddlewareOrders` 中声明它的顺序（脱敏的顺序值是 `MASKING = 125`，排在敏感词之内、审计之内，
   这样审计记录的已经是脱敏后的内容）。
3. **找出绕过中间件的出口**：
   - **语义缓存命中**：命中后直接返回缓存答案，**不经过 Agent 中间件链**，必须在命中路径上单独再过滤一遍。
     项目中 `streamCachedAnswer` 和非流式命中路径都会重新执行出站敏感词过滤：写入缓存时合规，不代表现在仍然合规，
     因为词库会变化。
   - **流式输出**：用户实际看到的是 `TextBlockDeltaEvent` 这些增量事件。等最终的 `AgentResultEvent`
     到达时，用户早已读完全文，只修改最终结果是“假生效”。
   - **不走装配器的模块**：admin 排除了 starter 的自动装配，需要单独检查。
4. **加一道自动化检查**：扩展 `AgentAssemblyAlignmentTest`，或者用真实容器测试断言中间件确实被装配。

**追问**：*如果某条链路确实不能挂中间件，比如缓存命中，怎样避免两处实现逐渐不一致？*
把核心逻辑抽成同一个组件，两个出口调用同一份实现。例如流式和非流式过滤都通过 `SensitiveWordStreamGuard` 完成：
流式逐片输入；非流式一次输入全文，再调用 `flush` 输出剩余内容。

**减分回答**：“在 Controller 返回前统一处理一下”。这只覆盖了 HTTP，漏掉了 WebSocket、流式和缓存命中这三类出口。

### Q7【初级】工单用了 7 态状态机。AI 自助和人工坐席之间怎么交接？CSAT 邀请为什么挂在工单终态上？

**考察点**：能否把 Agent 能力和业务流程结合起来；是否知道事件驱动和幂等。

**参考回答**

- **状态**：`AI_SERVING`、`WAITING_AGENT`、`PROCESSING`、`ON_HOLD`、`WAITING_CONFIRM`、`RESOLVED`、`CLOSED`。
  非法流转直接抛错（fast-fail），完整流转图见 README 3.6。
- **分发逻辑**：`ChatDispatchService` 先判断是否命中转人工关键词（`HandoffKeywordDetector`），命中就直接转人工。
  未命中时按工单状态分发：
  - `AI_SERVING`：交给 AI 处理；
  - `PROCESSING` / `ON_HOLD`：转发给已接单的坐席 `/ws/agent`；
  - `WAITING_*`：返回排队或待确认的提示。
- **Agent 侧的转人工**：由 `transferToHuman` 工具完成，而且转人工工具组**不允许通过配置停用**（见第 02 期）。
- **事件与 CSAT**：工单事件通过事务 Outbox 投递。`CsatTicketInviteListener` 在工单进入 `RESOLVED` / `CLOSED`
  时发出幂等邀请。以前邀请只挂在 `endSession` 上，而用户真正的“结束”动作是走工单状态机完成的，并不会调用
  `endSession`。结果是邀请只在空闲超时清理时才发出，分母几乎恒为 0，看板上的三项指标全是 0.0%，而链路完全不报错。

**追问**：*评测和合成监控会话为什么用 `discardSession`，而不是 `endSession`？*
这些会话背后没有真实用户，把它们计入 CSAT，会用一批永远不会有人评分的空邀请稀释回收率。
项目实测时，本机库里的 10 条 CSAT 记录全部来自评测。

**减分回答**：只画状态图，讲不出“状态机和 Agent 之间的衔接点”在哪里。

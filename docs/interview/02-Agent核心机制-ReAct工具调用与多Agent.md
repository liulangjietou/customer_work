# 第 02 期 · Agent 核心机制：ReAct、工具调用与多 Agent 编排

> **本期结论**：Function Calling 这类概念题人人都能答。拉开差距的是四个工程问题：工具的 schema 要花多少 token、
> 工具该串行还是并行、工具失败时由哪一层负责、多 Agent 在什么情况下值得用。本期每道题都落在项目的真实取舍上。
>
> 对应 JD：ReAct / CoT、Function Calling、工具调用失败重试、多智能体协作、Agent 与 Workflow 的区别。
> 题量 8（初 1 / 中 5 / 高 2）。

### Q1【初级】ReAct 循环是怎么运转的？项目中 maxIters 设为多少？轮次用完了会发生什么？

**考察点**：是否理解 Agent 主循环；是否考虑过循环的“出口”。

**参考回答**

- **主循环**：组装上下文 → 调用模型 → 解析出工具调用 → 执行工具 → 把结果回灌给模型 → 判断是否结束。
  模型给出最终答复，或者达到 `maxIters` 上限时，循环结束。
- **项目配置**：客服主 Agent 的 `maxIters` 默认是 10（`AgentProperties`）；多 Agent 编排中的专家默认是 6
  （`MultiAgentProperties`）。
- **轮次用完时**：框架会发出 `ExceedMaxItersEvent`，并让模型自己写一段收尾回复。这段话**不会告诉用户接下来怎么办，
  也不会把人工接进来**；而且项目最初全仓都没有代码消费这个事件，运维看不到。`LoopGuardMiddleware` 补上了这两个缺口：
  1. **轮次耗尽**：记录指标并审计，在收尾回复后**追加**一句“已转人工”的提示（追加而不是替换，
     因为收尾回复里可能有对用户有用的中间结论）；默认还会触发转人工（`handoffOnExhausted = true`）。
  2. **重复调用检测**：同一个工具用相同参数连续调用达到阈值（默认 3 次）时告警。

**追问**

1. *检测到重复调用，为什么只告警而不拦截？*
   拦截需要让模型知道“不要再这样调了”。但中间件修改事件流，**改不了写回 AgentState、下一轮喂给模型的内容**。
   真正能影响模型的是在 `onReasoning` 里注入临时消息，而这种做法的效果取决于模型是否采纳，无法用单测验证。
   项目因此只做检测和告警，不去做一个“看起来有用”的拦截。
2. *Agent 和 Workflow 有什么区别？*
   Workflow 的控制流写在代码里，Agent 的控制流由模型决定。项目中“退款信息收集”没有写成对话分支（Workflow），
   而是做成了工具（Agent），原因见 Q6。
3. *（高阶追问，可以请候选人现场分析）这句“已转人工”的提示，在 H5 流式链路上用户看得到吗？*
   已确认的事实有两条：一是 `LoopGuardMiddleware` 只在 `AgentResultEvent` 上追加提示；二是
   `CustomerServiceService.streamFromAgent` 只要收到过任何正文增量，就不再下发 `AgentResultEvent`。
   所以，如果收尾回复是以增量形式流出的，这句提示就到不了 H5 用户，只有转人工这个动作本身会生效。
   这和项目记录过的“只处理 `AgentResultEvent`，在流式路径上等于没生效”是同一类问题
   （`SelfCorrectionMiddleware` 的做法是在流末尾追加一个增量）。结论要用真实流式链路验证，不能只看单测：
   现有单测只断言了 `AgentResultEvent`。

**减分回答**：只背 Thought / Action / Observation 三个词，讲不出循环结束和出错时的处理。

### Q2【中级】Function Calling 的工具描述应该怎么写？项目的工具描述有哪些讲究？

**考察点**：工具 schema 的设计；把工具描述当作“写给模型的契约”。

**参考回答**

- **生成方式**：用 `@Tool(description)` 和 `@ToolParam(name, description)` 注解，框架据此生成 JSON Schema。
  工具按业务域分组注册（knowledge / order / after_sales / presale / member / complaint / human），
  组描述本身也会消耗 token。
- **描述要写清三件事：能做什么、不能做什么、调用前需要满足什么条件**。项目中的例子：
  - `submitRefund`：“为订单登记待人工复核的退款申请，**不执行支付**。申请受理不代表退款获批或资金到账。”
  - `checkRefundEligibility`：“**发起退款前应先调用此工具**。”
  - `collectRefundInfo`：“把用户这一轮的原话传进来。”`userText` 参数的描述还要求“原样传入，不要改写”。
- **返回文案也是写给模型看的**：直接告诉模型下一步做什么，例如“信息已收齐……接下来请调用退款资格校验工具”。
- **描述是防幻觉的第一道防线**：工具描述写清“不打款”，再配合 `SelfCorrectionMiddleware`
  拦截“已退款”这类说法（见第 05 期），形成两层防护。

**追问**

1. *参数校验放在哪一层？*
   工具入参由 `ToolGuardMiddleware` 统一处理：注入公共参数、钳制数值范围、改写破坏性命令。
   业务后端仍然要做自己的校验，因为模型传进来的任何参数都不可信。
2. *工具执行失败时，应该抛异常还是返回错误文本？*
   能让模型理解和纠正的错误，比如参数缺失或格式不对，应该返回可读的说明，让模型追问用户或自我修正。
   系统级故障交给执行层的超时和降级机制处理（见 Q5）。

**减分回答**：“描述写清楚功能就行”。不写边界，模型就会自己脑补出工具并不具备的能力。

### Q3【中级】工具定义本身也要消耗 token。项目实测是多少？怎么控制？

**考察点**：成本意识；能否先量化问题，再比较不同方案。

**参考回答**

- **先量化**：`ToolSurfaceCostTest` 把全部业务工具的 schema 序列化，按每个 token 约 1.5 个字符粗估。
  结果约为 4 千 token，占 `context.max-token` 默认值 8000 的一半以上（最近一次记录是 24 个工具、约 4346 token、占 54%）。
  这笔开销**在每一轮对话里都要付**。
- **三种收敛办法及代价**：
  1. **按意图静态激活工具组**：意图判错就拿不到需要的工具，模型直接办不了事。而当时的 `fastRouteIntent`
     只返回 `Optional<String>`，没有置信度，判不准时无法兜底。
  2. **用 meta-tool 动态装备工具**：每轮都要先“找工具”再“用工具”，多一次模型往返，首字延迟明显变长。
  3. **保持现状**：每轮都带上全部 schema。
- **项目的选择**：
  - 在部署级别静态停用不需要的工具组（`customer-work.tool-surface.disabled-groups`）。运维清楚自己有没有这块业务，
    所以不存在判错风险。
  - **转人工组即使写进停用清单也会被拒绝**（`ToolRegistrar.normalizeDisabled` 会打错误日志并忽略这一项），
    因为配置文件里不应该出现一个能把用户困在智能体里的开关。
  - 接入带置信度的 Jev 意图判定后，按轮收窄工具面（`JevToolScopeMiddleware`）：低于置信度门槛或判为 other 时不收窄。
- **护栏**：`toolCountStaysBounded` 要求工具数不超过 30 个，超出时要先回答“这些工具是否每轮都必须暴露给模型”。
  这个测试曾经漏算过工具：可选依赖 `SlotFillingService` 没有注入，新增的工具就没被统计进去。
  所以护栏本身也要覆盖可选依赖。

**追问**：*收窄工具面时，为什么改的是 `ReasoningInput.tools()`，而不是 Toolkit 的激活组？*
带 StateStore 时，框架会用会话状态中的 `activatedGroups` **全量覆盖** Toolkit 的激活组。如果改激活组，
收窄结果会被持久化，下一轮继续生效，项目就因此出现过“业务工具组被整体清空”的问题。
`ReasoningInput.tools()` 只决定本次模型调用能看到哪些工具，不写回任何状态。

**减分回答**：“工具越多 Agent 越强”；或者直接回答“上 meta-tool”，但说不出它对首字延迟的代价。

### Q4【高级】AgentScope 2.0.1 把 Toolkit 的默认执行模式改成了并行，项目为什么显式改回串行？

**考察点**：能否识别框架升级带来的隐性行为变化；能否从审批、上下文传播和计量三个角度分析并行的风险。

**参考回答**

- **结论**：`ToolkitConfigs.sequential()` / `sequentialWith(...)` 显式设置 `parallel(false)`，
  **把“行为变更”和“版本升级”拆开处理**。这条改动写在 release notes 的 “Refactored” 段落，而不是 Breaking Changes 里，
  实测 `defaultConfig()` 的 `parallel` 已经是 `true`。
- **并行不安全的地方不在工具实现本身**（工具都是无共享状态的 `Mono`），而在于业务语义和治理语义：
  1. **审批交错**：模型在一轮里同时发起“查订单”和“发起退款”，审批拦住了退款，查询却已经执行完。
     如果审批被拒，另一个工具已经产生的副作用无法回滚。
  2. **上下文传播**：并行意味着工具跑在不同线程上，需要显式传播 `TenantContext` / `QuotaSubjectContext` 的位置会变多。
     而“异步回调要显式恢复租户上下文”这个坑，项目已经复发过一次。
  3. **计量口径**：`AgentCallTimingMiddleware` 是 token 的唯一记录点，并行后分段耗时的统计口径会变化。
- **注意区分两个概念**：“一轮发起多个工具调用”不等于“并行执行”。`ActingInput.toolCalls()` 本身就是一个列表，
  模型一轮可以发起多个调用，这和串行还是并行无关。

**追问**：*如果业务确实需要并行，你会怎么做？*
按有无副作用给工具分类：只读工具允许并行，写操作串行执行，并把审批放在最前面。线程切换处显式传播上下文。
计量按 `toolCallId` 聚合。最后把并行化当成一个独立变更，单独评估、单独回归。

**减分回答**：“并行更快，当然应该并行”。

### Q5【中级】工具调用失败或超时怎么处理？重试应该放在哪一层？

**考察点**：分层容错、幂等、降级方向。

**参考回答**

- **执行层**：`ToolkitConfigs.sequentialWith` 显式配置超时：`timeoutMs` 默认 15 秒，重试 `maxAttempts` 默认为 1，
  也就是不重试。框架默认的 `TOOL_DEFAULTS` 是 5 分钟超时、不重试，对客服对话来说 5 分钟等于没有超时。
- **重试为什么默认关闭**：框架的重试对整个工具集统一生效，不区分幂等性。而客服工具里有“发起退款”“创建工单”
  这类操作，重试一次就会多执行一次；超时往往意味着请求已经到达下游，只是响应慢。
- **业务层**：资金类操作走审批执行。`PendingApprovalService` 取得执行租约后调用执行器，幂等键固定为审批单号，
  fencingToken 用来阻止旧 worker 回写状态（见第 05 期 Q5）。执行失败时状态记为 `EXECUTE_FAILED`，由巡检重试。
- **模型层**：`FailoverModel` 负责候选模型切换和熔断（见第 08 期）。
- **降级方向要逐个判断**，项目里三处降级就有三种方向：
  - WebSocket 广播失败：退回“离线”语义，不打断主链路；
  - 调度锁拿不到：照常执行，因为跳过会让超时审批永远没人处理；
  - 受管知识库依赖缺失：显式失败、不降级，因为降级会退回演示文本，而运营会误以为知识库在生效。

**追问**：*下游退款接口超时了，怎么知道到底有没有退款？*
不能靠重试来确认结果，要查询回执或者按幂等键查询。审批状态和执行状态分开记录，执行结果不明确时进入巡检，
下游必须持久化消费记录并按审批单号去重。

**减分回答**：“失败就重试三次”。

### Q6【中级】“退款信息收集”为什么做成工具，而不是在对话链路里加一个表单状态机？

**考察点**：理解 Agent 范式的边界；判断什么交给模型、什么交给代码。

**参考回答**

- **结论**：做成工具（`RefundIntakeTools.collectRefundInfo`），整个过程仍然在 ReAct 范式之内：
  模型自己决定何时收集信息、何时切换话题，权限、审计、超时这些能力也都自动具备。
- **加分支的问题**：在 `ChatDispatchService` 里判断“这是退款意图，切换到表单模式”，等于给对话加了一个状态机。
  用户会被锁在表单里，中途问别的问题就答不了，而且和 `DialogStageMiddleware` 的职责重叠。
- **和“让模型自己追问”相比，工具多做了三件模型做不好的事**：
  1. **跨轮次持久化**：进度保存在 `cw_slot_filling_progress` 表里；模型只能靠对话历史记住进度，历史一旦被裁剪就忘了。
  2. **格式校验**：用正则抽取订单号，模型不会把“上次那个单”当成订单号。
  3. **不漏项**：必填项由表单定义保证。
- **刻意不在这个工具里直接发起退款**：否则会绕开资格校验这道关口。
- **依赖注入方式**：`@Autowired(required = false)` 的 setter 注入，而不是加构造参数，因为 `new ToolRegistrar(...)`
  有四个调用点，加参数会引起连锁修改。

**追问**：*对话阶段状态机（`DialogStage`）踩过什么坑？*
`GREETING` 阶段的提示词曾写着“暂不调用业务工具”，而阶段推进的信号恰恰是“模型发起了业务工具调用”。
结果会话永远停在接待阶段，其余四个阶段的提示词一次都没用上。教训是：**提示词写的内容和代码里的装配要一起检查**。

**减分回答**：“用 Workflow 更可控”，但说不出用户被锁在表单里的代价。

### Q7【高级】`/consult` 多 Agent 编排是怎么实现的？路由、并发、超时和归纳分别怎么设计？

**考察点**：多智能体编排的工程细节；Reactor 并发；局部故障隔离。

**参考回答**（`MultiAgentOrchestrator`）

- **流程**：路由 → 并行会诊 → 归纳；另有 `sequential` 模式，让问题依次经过订单、售后、知识三个专家，逐步细化。
- **三级路由**：
  1. **规则快路由** `fastRouteIntent`：关键词**只命中一个**意图时直接路由；命中多个或没有命中，交给下一级。
     这一步不调用模型。
  2. **Jev 结构化决策**：只采信高置信度的结果。
  3. **LLM 路由**：由 RouterAgent 输出结构化的 `IntentResult`；路由失败时把问题发给全部专家。
- **并行执行**：`Flux.fromIterable(tasks).flatMap(task -> task.subscribeOn(boundedElastic), maxConcurrency)`，
  `maxConcurrency` 默认 8。每个专家单独设置超时（默认 60 秒）；超时或异常只返回一个占位结果，不拖垮整体。
- **归纳**：多于一个专家且开启归纳时，由 ReducerAgent 去重、消解冲突、统一口径；归纳失败则退化为直接拼接。
- **意图没有专家认领**（other 或未知意图）时，发给全部专家，宁可多问几个也不要答不上来。
- **开关必须真的生效**：`enabled` 字段以前全仓没有代码读取，设成 `false` 什么也关不掉。“配了不生效”的开关比没有开关更危险。

**追问**

1. *为什么每个任务都要 `subscribeOn(boundedElastic)`？*
   `agent.call` 底层可能是阻塞调用。不切换线程的话，`flatMap` 的并发只是“订阅并发”，实际执行仍然是串行的。
2. *和 HarnessAgent 的 subagent 有什么区别？*
   subagent 由主智能体在 ReAct 循环里自己逐个创建，本质上是串行的，也无法用代码控制并发；
   需要可控并行时，才走这个编排器。

**减分回答**：“多 Agent 就是多个 Prompt 轮流跑”；或者说不出单个专家失败时怎么隔离。

### Q8【中级】用 Agent 做结构化意图分类有什么已知限制？项目怎么兜底？

**考察点**：结构化输出的可靠性；一次性 Agent 的资源管理；Reactor 阻塞检测。

**参考回答**（`CustomerServiceService.classifyIntent`）

- **隔离**：使用一次性的独立 Agent，并使用独立的 sessionId（`"intent:" + sessionId`），避免污染真实会话的记忆。
  用 `Mono.using` 确保这个 Agent 用完一定被关闭。
- **框架限制**：结构化输出走的是框架的备用工具路径：`generate_response` 被当成普通工具交给模型，
  框架不会用 `tool_choice` 强制模型调用（agentscope-java #1852 / #1699）。如果模型这一轮没调这个工具，
  `hasStructuredData()` 就是 `false`。在提示词里要求“必须调用”只能提高命中率，不能保证 100% 生效。
  未命中时返回 `other` 作为兜底结果，并记录指标 `customerwork.intent.classify.errors`。
- **线程问题**：只要注册了覆写 `onSystemPrompt` 的中间件，`agent.call()` 内部就会同步 `block()`。
  在 `reactor-http-nio` 线程上 `block()` 会抛出 `IllegalStateException`。解决办法是用
  `Mono.defer(...).subscribeOn(boundedElastic())`，把 Agent 的创建和调用整体挪到弹性线程池。

**追问**：*意图分类的准确率怎么评估？*
用 `IntentEvalRunner` 做离线的确定性评测；`fastRouteIntent` 是纯函数，可以直接复用。
质量类评测则需要 LLM-as-Judge（见第 08 期）。

**减分回答**：“让模型输出 JSON，再用正则解析就行”，没有考虑模型不按格式输出时怎么兜底。

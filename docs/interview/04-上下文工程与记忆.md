# 第 04 期 · 上下文工程与记忆

> **本期结论**：上下文工程要回答的问题是：每一次模型调用，放什么进去、放多少、放在哪里、什么时候丢掉。
> 项目在这方面有四个值得深挖的实现：预算裁剪必须放在最内层、裁剪不能拆开工具调用和它的结果、
> 召回内容只临时注入不写回历史、会话状态用乐观并发写入。回答这四个问题，基本就能说明候选人是否真的做过长会话。
>
> 对应 JD：上下文工程、长短期记忆、长会话压缩、Harness（上下文管理与任务状态）。
> 题量 7。

---

### Q1 上下文工程和 Prompt Engineering 有什么区别？项目里一次模型调用的上下文由哪几部分组成？

**考察点**：概念是否清楚；能否说出上下文各部分的来源和顺序。

**参考回答**

- **区别**：Prompt Engineering 关注“把一段提示词写好”。上下文工程关注每次调用**动态组装**什么内容，
  包括来源、数量、位置和淘汰时机。
- **项目中的组成**：
  1. **系统提示词**：优先使用 Nacos 下发的版本，没有时用内置版本。两种情况都会追加 `runtimeFacts`，也就是当前日期等运行期事实。
     这样做的原因是：模型的训练知识有时间滞后，如果不注入当前日期，模型可能把一个合法的订单号判断为“未来日期、不合逻辑”，从而拒绝查询。
  2. **对话阶段片段**：`DialogStageMiddleware` 根据会话所处阶段追加聚焦指令（状态机式的动态组装）。
  3. **工具 schema**：可以按轮收窄，见第 02 期 Q3。
  4. **历史消息**：由 StateStore 恢复。
  5. **长期记忆召回**和 **RAG 召回**。
  6. **临时提醒**，例如任务清单。
- **顺序由 `MiddlewareOrders` 统一定义**。靠近模型的上下文组装层从外到内依次是：
  `JEV_ESCALATION 90` → `DIALOG_STAGE 80` → `JEV_TOOL_SCOPE 75` → `KNOWLEDGE_INJECTION 70` →
  `DYNAMIC_OPTIONS 60` → `CONTEXT_BUDGET 50`（最内层）。

**追问**：*预算裁剪为什么必须放在最内层？*
裁剪要在知识注入、记忆召回、阶段提示词全部完成之后才能算准。如果放在它们外面，裁完之后内层还会继续往上下文里加内容，预算就失去了意义。
同理，工具面收窄（75）必须排在预算裁剪（50）之外：先收窄工具面，预算才会按收窄后的工具面计算。

**减分回答**：“上下文工程就是把 Prompt 写长一点”。

### Q2 长会话的上下文越来越长，项目怎么处理？`ContextBudgetMiddleware` 和 Harness 的 Compaction 分别解决什么问题？

**考察点**：确定性裁剪和模型压缩各有什么取舍；是否了解项目在这个问题上的演进。

**参考回答**

- **历史问题**：主链路的 `ReActAgent` 最初没有任何上下文裁剪。当时唯一的收敛手段是 Harness 的 `CompactionConfig`，
  但 Harness 默认关闭，用户根本不走那条路径。与此同时，长期记忆召回和 RAG 注入默认都是开启的。
  也就是说，**让上下文变长的能力默认开启，而唯一能收敛上下文的能力接在一条用户不走的路径上**。
- **`ContextBudgetMiddleware`（确定性裁剪）**：
  - 按**消息条数**设上限，默认 `budgetMaxMessages=60`，保留最早的 4 条（`budgetKeepEarliest`）。
  - 策略是“去掉中间、保留两头”：最早的几条通常包含用户诉求的关键背景，比如“我买的是 A 商品”；
    最近的几条是当前话题；中间部分最适合舍弃。
  - system 消息和框架合成的临时消息被固定保留，不参与裁剪。
  - **只修改本次模型调用的输入**，不改动持久化的会话状态。
- **Harness Compaction（模型压缩）**：
  - 由 `ContextMemoryFactory.createCompaction()` 创建，参数是 `triggerTokens = maxToken`（默认 8000）、
    `triggerMessages = 40`、`keepMessages = 10`，调用模型对历史做摘要。
- **怎么取舍**：
  - 压缩要额外调用一次模型，而上下文越长，这次调用就越贵。
  - 确定性裁剪零成本、结果可预测、容易测试，代价是被裁掉的内容这一轮看不到。
  - 两者可以同时使用：Harness 链路做压缩，主链路用预算裁剪兜住上限。
- **当前默认值**：`budgetEnabled`、`compressionEnabled`、`harness.enabled` 都默认为 `true`。
  `CustomerServiceService.resolveAgent` 会根据 `harness.enabled` 在轻量的 `ReActAgent` 和
  带压缩保护的 `HarnessAgent` 之间选择。

**追问**：*按条数裁剪能保证不超过 token 上限吗？*
不能。单条消息很大时（例如一个超长的工具结果）仍然可能超限。这是按条数裁剪的边界。
Harness 提供了“工具结果淘汰”（`toolResultEvictionEnabled`，默认关闭）来处理大工具结果。
答题时应该主动说明这个边界。

**减分回答**：“换一个上下文窗口更大的模型”。这样做成本、延迟都会上升，模型对长上下文的注意力也会被稀释，而且没有回答“治理”这个考点。

### Q3 裁剪上下文时，如果把 `tool_use` 和它对应的 `tool_result` 拆开了，会发生什么？项目怎么避免？

**考察点**：是否了解模型厂商对消息结构的约束；能否写出安全的裁剪算法。

**参考回答**

- **后果**：发给模型的消息里出现了一个孤立的 `tool_result`（前面没有对应的 `tool_use`），多数厂商会直接返回 400。
  早期实现就是按位置用 `subList` 截取首尾，完全不看消息内容。如果按文档建议在生产环境开启，
  长会话的问题会从“上下文超限”变成“整轮请求失败”。
- **解决方法（`groupByToolCallPairing`）**：
  - 把“含有 `ToolUseBlock` 的消息”和紧随其后的“含有 `ToolResultBlock` 的消息”合成一个不可拆分的组，
    裁剪只在组与组之间进行。
  - 如果开头和结尾两段已经用掉了全部组，中间没有可以舍弃的内容，就**原样返回**，而不是切出一个残缺的序列。
- **为什么按“紧随其后”分组，而不是按 id 匹配**：在 ReAct 循环里，工具结果总是紧跟在发起调用的那条消息后面；
  system 消息和合成消息已经被提前取出、固定保留，不会插进这段序列中间。

**追问**：*模型一轮发起了多个工具调用时怎么处理？*
分组规则会把紧随其后的所有 `tool_result` 消息都并入同一组，直到遇到一条不是工具结果的消息为止，所以多个调用结果会一起保留或一起舍弃。

**减分回答**：“保留最近 N 条消息就行”。

### Q4 什么是“瞬态注入”？RAG 召回、任务提醒、隔离标记为什么都不写回会话历史？

**考察点**：是否理解框架内“这次调用的输入”和“持久化的状态”是两回事。

**参考回答**

- **机制**：`onReasoning` 拿到的 `ReasoningInput.messages()` 是框架为**这一次模型调用**临时组装的列表，
  不会写回 AgentState。只有模型最终产出的消息才会进入 `state.contextMutable()`。
  框架自带的 `TaskReminderMiddleware` 就是利用这一点做提醒注入的。
- **好处**：
  - 用户可见的历史记录里永远不会出现召回内容和隔离标签；
  - 旧的召回内容不会在每一轮重复发送，token 不会线性增长；
  - 压缩时不会把这些内容也压进摘要；
  - 注入的消息带有 `Msg.METADATA_SYNTHETIC` 标记，其他组件（比如预算裁剪）能识别出来。
- **对比**：在 `onActing` 里修改事件流，只能改变前端看到的内容，改不了模型下一轮看到的内容。
  这也是间接注入防护必须放在 `onReasoning` 的原因（见第 03 期 Q7）。

**追问**：*瞬态注入有什么代价？*
每一轮都要重新构建。所以 `KnowledgeInjectionMiddleware` 会把本轮第一次的检索结果缓存在 `RuntimeContext` 里，
ReAct 的后续迭代直接复用，一轮只检索一次。另外，需要跨轮记住的信息不能依赖瞬态注入，必须进入状态或记忆。
例如槽位填充的进度就存在 `cw_slot_filling_progress` 表里。

**减分回答**：把召回内容直接拼到用户消息里。这样会污染历史，每轮重复发送，前端还会看到这些内容。

### Q5 项目的记忆分几层？各存在哪里？长期记忆按什么维度隔离？

**考察点**：记忆分层；存储选型；隔离与隐私治理。

**参考回答**

- **短期记忆**：存在 AgentState 中，由框架按 `(userId, sessionId)` 自动持久化到 MySQL。
- **长期记忆的三层结构**：
  - L2：`cw_long_term_memory`；
  - L3：事实日志 `cw_fact_log`；
  - Harness 分层记忆：`cw_harness_memory`。
  三处的 `store-mode` 默认都是 `jdbc`。
- **MySQL 是可信数据源，磁盘只是可重建的缓存**：框架只从 workspace 下的 `MEMORY.md` 文件读取 Harness 记忆，
  所以构建 Agent 之前，`HarnessMemorySyncService` 会先把 MySQL 里的权威副本写到磁盘上。
  否则换机器、重启或清理 workspace 之后，历史记忆对框架来说就等于不存在。
- **隔离维度**：租户 + 已验签的主体 + Agent，由 `MemorySubjectResolver` 解析出 `MemorySubjectKey`。
  热 Agent 缓存的键使用同一套解析规则，保证“缓存复用的范围”和“记忆数据的范围”完全一致。
- **隐私治理**：包括授权同意（`MemoryConsentService`）、查看、导出、删除和按保留期清理（`MemoryRetentionService`）。
  生产环境的隐私闭环以 JDBC 实现为基线。

**追问**：*读取“最近一次”记录时，为什么要按自增 `seq` 排序，而不是按时间戳？*
内存计算很快，连续两次写入可能落在同一毫秒。按时间戳取“上一次”会取错或取不到，在 CI 里必然会踩到这个问题。

**减分回答**：“记忆就是把历史存进 Redis”。

### Q6 长期记忆的召回算法为什么从“按单字统计”改成 bigram？怎么评估召回质量？

**考察点**：中文检索的基本功；评测集是否设计合理。

**参考回答**（`FactRelevanceScorer`）

- **原问题**：原算法统计“查询中的去重字符有多少出现在事实里”。中文里“的、是、我、个”这类虚词几乎出现在每条事实中，
  查询里的虚词越多，越多无关事实会得到分数。实测查询“我的那个是不是耳机的”，召回的前三条是手机尾号、收货地址和支付方式，
  偏偏没有耳机那条。
- **三处改动**：
  1. 按 bigram（相邻两个字）而不是单字匹配；
  2. 过滤掉两个字都是停用词的 bigram，比如“的那”“是不”；
  3. 用查询中有效 bigram 的数量对分数归一化，让长查询和短查询的分数可以比较。
- **整句都是虚词时，直接返回空结果**：硬凑几条无关记忆塞进提示词，比不召回更糟。
- **两个存储实现共用这一套打分逻辑**：切换 `store-mode` 不应该改变智能体读到的记忆。
- **评估上的教训**：用一把混合了两类问题的尺子来衡量，会得出相反的结论。
  - 改用 bigram 后，按总召回率算从 0.80 降到了 0.60，看起来是退步。
  - 但掉下去的全是“忌口”对“过敏”这类没有共同实词的同义改写，旧算法在这些用例上的“召回成功”只是靠虚词碰巧命中。
  - 按“这个策略应该负责的问题”和“本来就超出它能力的问题”分组后，字面组是 1.00，同义组是 0.00，真实情况才清楚。
- **记录现状的测试**：`semanticParaphraseNotYetRecalled` 断言同义改写目前召回不到。注释里写明：
  如果哪天它失败了，说明有人接入了语义召回，这时应该把同义组并入字面组的要求，而不是把断言改回去。

**追问**：*什么时候应该上向量召回？*
当同义改写类的问题在真实流量里占到一定比例时。向量召回的代价是每写入一条事实就要调用一次 embedding，
并且要做数据迁移。决策依据应该是分组评测和线上数据，而不是凭直觉。

**减分回答**：“直接上向量数据库”，说不出当前算法的问题到底出在哪里。

### Q7 AgentScope 2.0.3 给会话状态加了乐观并发控制（CAS），项目为此做了哪些工作？已经有会话锁了，为什么还需要 CAS？

**考察点**：并发控制的纵深；框架升级时的隐性风险；装饰器转发问题。

**参考回答**

- **机制**：`MysqlAgentStateStore.supportsVersioning()` 返回 `true`。框架读取状态时调用 `getVersioned`，
  写回时调用 `saveIfVersion` 做 CAS。
- **依赖一个 `version` 列**：框架在 **Store 的构造器里**自动补这一列；即使 `auto-create=false` 也会执行。
  补列失败会抛出 `Failed to ensure version column`，**应用直接启动失败**。项目用临时库和一个只有 DML 权限的账号实测验证过这一点。
  - admin 库中的状态表归 Flyway 管理，由 `V102` 补列；
  - 客服端的 `agentscope_sessions` 表由框架自己创建。在只有 DML 权限的生产环境，需要手工执行
    `customer-work-agent-state-version-alter.sql`。
- **默认的 `OVERWRITE` 策略会把冲突悄悄吸收掉**：检测到冲突时，重新读取最新版本后直接覆盖，不抛异常，也不打日志。
  因此项目加了指标 `customerwork.agent.state.conflicts`，采集点放在 `AgentResourceCloser` 这个唯一的资源释放入口。
  策略由 `customer-work.agent.state-conflict-policy` 配置，只在 `AgentGovernanceAssembler` 这一处设置。
- **装饰器的坑**：框架给 `AgentStateStore` 新增的三个方法都带有 default 实现。`SandboxSafeAgentStateStore`
  如果不转发它们，**也能编译通过**，但 `supportsVersioning()` 会一直返回默认值 `false`：
  被装饰的 MySQL store 明明支持版本控制，框架却退回到了无版本写入，而升级当天所有测试都是绿的。
  `SandboxSafeAgentStateStoreVersioningTest` 用真实 store 验证：经过装饰器之后，CAS 语义依然成立。

**追问**：*已经有会话锁了，为什么还需要 CAS？*
这是纵深防御。会话锁可能失效：Redis 故障时会降级为进程内锁；租约也可能在长响应处理到一半时过期。
CAS 是最后一道防线。冲突指标长期为 0，说明会话锁在正常工作；如果突然上升，通常意味着 `SessionLock`
已经在 Redis 故障时降级成了进程内锁。

**减分回答**：“有锁就不需要乐观锁”；或者不知道 Java 接口的 default 方法会让装饰器在不报错的情况下丢掉能力。

# 第 05 期 · 安全护栏与治理中间件

> **本期结论**：安全题的分水岭在于候选人是否知道“用户实际看到的是哪一个事件”。项目中大部分安全缺陷不是逻辑写错了，
> 而是护栏挂在了用户不走的链路上，或者作用在了用户看不到的事件上。其次要看候选人能不能讲清护栏自身出故障时
> 选择放行还是拦截，以及为什么。
>
> 对应 JD：提示词注入防护、内容安全、HITL、审计合规、MCP 与工具安全。题量 7（初 1 / 中 4 / 高 2）。

### Q1【中级】项目里有二十多个治理中间件，执行顺序是怎么定的？为什么必须集中声明？

**考察点**：洋葱模型；执行顺序不确定带来的隐患；能否把顺序背后的理由讲清楚。

**参考回答**

- **框架语义**：`MiddlewareBase#order()` 的值越大，优先级越高，位置越靠外。靠外意味着**入站时先执行、出站时后执行**。
  默认值是 1；值相同时保持注册顺序。
- **之前的问题**：24 个中间件全部使用默认值 1，也都没有标注 `@Order`，实际顺序由 Spring 交出 Bean 的先后决定，而这个先后是不确定的。
  于是“先裁剪还是先注入”“审计记下的是脱敏前还是脱敏后的内容”这类问题，答案取决于 Bean 定义的顺序，
  改一行无关代码就可能翻转，而且不会报任何错。
- **现在的分层**（`MiddlewareOrders`，从外到内）：
  1. **准入**：`AGENT_LIFECYCLE` 200。已被撤销的会话必须在进入任何链路之前拦下。
  2. **观测与计量**：可观测 190、租户上下文 180、token 计量 170、终止采集 165、耗时 160、回放快照 155。
     这一层要覆盖内层的全部耗时和 token 消耗，所以必须排在被观测的对象外面。
  3. **审计**：150。审计要记录最终真正发出去的内容，所以排在脱敏和过滤外面，出站时最后执行。
  4. **入站防护**：直接注入防护 140、知识引用采集 137、间接注入防护 135。
  5. **出站过滤**：敏感词 130、PII 脱敏 125。出站时先脱敏、再过滤敏感词，这样敏感词命中记录里保存的片段已经是脱敏后的。
  6. **工具治理**：主体授权 120、人工确认 115、退款风险 112、入参护栏 110。这些都必须在工具真正执行之前完成。
  7. **内容质量**：任务清单 107、循环守卫 105、自我纠错 100。
  8. **上下文组装**：预算裁剪 50 放在最内层（见第 04 期）。
- **自动化检查**：`MiddlewareOrderContractTest` 断言三件事：不允许使用默认值、取值不重复、关键的相对顺序成立。

**追问**

1. *租户上下文为什么排在 180 这么靠外的位置？* 内层所有落库、配额、审计和命中记录都依赖它。缺少租户上下文时，持久层会直接拒绝执行（fail-closed）。
2. *WebFilter 有没有类似的问题？* 有。`SubjectQuotaWebFilter`（`HIGHEST_PRECEDENCE + 30`）必须排在
   `ApiKeyAuthWebFilter`（+10）和 `UserAuthWebFilter`（+20）之后。如果排在前面，它执行时用户身份还没解析出来，
   已登录用户会全部被当作匿名 IP 来限流。

**减分回答**：“顺序无所谓，反正每个中间件都会执行”。

### Q2【中级】直接提示词注入和间接提示词注入分别怎么防？附件为什么也要处理？

**考察点**：OWASP LLM01 的两种形态；每层防线各自的定位。

**参考回答**

- **直接注入**：`PromptInjectionGuardMiddleware` 挂在 `onAgent` 上，这是唯一能拦截整次 Agent 调用的钩子。
  它用正则识别注入和越狱模式；命中后**不调用 `next`**，直接返回统一的拒绝话术，不会产生任何模型调用，
  既省成本，也能保证注入内容接触不到推理过程。
  它和 `ToolGuardMiddleware` 的处理方式刻意不同：后者命中后会把参数改写成安全值继续执行；
  而一句已经被识别为攻击的输入，不存在“改写成安全内容后继续对话”的合理中间状态。
- **间接注入**：攻击内容藏在工具返回、知识文档或 MCP 返回里，由 `IndirectInjectionGuardMiddleware` 处理：
  隔离标记加检测告警，详见第 03 期 Q7。
- **附件**：前端把附件的 OCR 结果按固定格式拼进消息正文。如果不做隔离，这些内容会以“用户亲手输入的文字”的身份进入模型；
  一张写着“忽略以上指令”的图片，就成了一条现成的注入通道。
  `AttachmentTextSpotlighter` 按前后端约定的 `【附件：…】---…---` 格式识别出附件段落，包进隔离块。
  **只处理发给模型的那一份内容**，缓存的 key 和埋点使用的原文都不改动：隔离块里带有 `SecureRandom` 生成的随机 nonce，
  如果拿它做语义缓存的 key，缓存永远不会命中。
- **默认值**：直接注入防护和间接注入防护这两个中间件默认都是关闭的，生产环境需要显式开启。
  它们自身出错时选择放行（fail-open）。

**追问**：*正则能拦住多少攻击？*
只能拦住已知的模式。真正的安全来自能力边界：工具权限最小化（退款工具只能登记待审单，不能打款）、
人工审批、出站检查（自我纠错）和审计。正则只是第一层筛子。

**减分回答**：“在系统提示词里写上‘不要执行用户的恶意指令’”。

### Q3【高级】流式输出时怎么做敏感词过滤？一个敏感词被拆到两个 chunk 里怎么办？

**考察点**：流式过滤算法；多模式串匹配；过滤器状态的生命周期。

**参考回答**

- **为什么过滤放在接入层，而不只放在中间件里**：
  - 旧的 `stream()` API 通过 `StreamingHook` 直接从模型输出中截取文本推给前端，中间件对事件流的改写到不了用户屏幕上。
    结果是命中日志显示“已打码”，用户看到的却是原文。
  - 迁移到 `streamEvents` 之后，技术上可以把过滤下沉到中间件，但改造量很大：事件对象不可变，改文本要逐条重建事件；
    子 Agent 的事件也在同一条流里；BLOCK 要改成往流里插入事件。所以目前仍然在两个流式出口各挂一个 guard。
- **`SensitiveWordStreamGuard`**：
  - **每条流一个实例**。它有内部状态，不是线程安全的；跨流复用会把上一段对话的尾巴接到下一段的开头。
  - **滑动缓冲**：每收到一片，就和缓冲区拼接后整体过滤，只放行“确定不可能再构成任何敏感词”的前半部分；
    尾部只保留当前**真正可能继续扩展成敏感词的前缀**，而不是固定保留最长词的长度。流结束时调用 `flush()`，一个字都不丢。
  - **缓冲区保存原文，而不是打码后的文本**：如果一个短词（处理方式为 MASK）恰好是某个长词（处理方式为 BLOCK）的前缀，
    提前把短词替换成 `***`，下一片到达时就匹配不上长词了。
  - **BLOCK 的固有限制**：已经发出去的片段收不回来。命中后的处理是立即停止后续输出，再补一句安全话术。
    要做到一个字都不泄露，只能整段缓冲后再发送，那就失去了流式输出，这个取舍应该由接入层决定。
- **匹配引擎**：
  - `AhoCorasickMatcher` 是自研的 AC 自动机，构建后不可变，单次扫描复杂度为 O(n + 命中数)，与词表规模无关，天然线程安全。
    词表热更新时构建一个新实例，再原子替换引用。
  - `TextNormalizer` 做三件事：全角转半角、转小写、去掉干扰字符（如 `* . · - _ ~ | /`），
    并保存归一化后文本到原文的下标映射，确保 `敏*感*词` 这种写法也能整段打码。
- **接入 Reactor 的方式**：`mapNotNull(guard::accept)` 加上 `concatWith(Flux.defer(guard::flush))`。
  guard 在 `Flux.defer` 内部创建，保证每次订阅都是一个新实例。

**追问**：*命中上报为什么每条流只报一次？*
缓冲区是累积的。如果每来一片就上报一次，同一处命中会被重复上报很多次，所以用 `maskReported` 标志去重。

**减分回答**：“每个 chunk 用 `contains` 检查一下”。这样跨片的词永远匹配不上，而且不会报任何错。

### Q4【中级】模型对用户说“您的退款已到账”，但系统根本不会打款。怎么拦住这种越权承诺？

**考察点**：用工具调用证据判定答复是否可信；处理流式场景的限制。

**参考回答**（`SelfCorrectionMiddleware`）

- **判定依据来自工具调用的证据**：

  | 本轮调用过的工具 | 回复里说“已退款” | 处理方式 |
  |---|---|---|
  | 调用过 `queryRefundProgress` 等查询工具 | 转述系统里的真实状态 | 放行 |
  | 一个工具都没调用 | 凭空编造 | 拦截 |
  | 只调用了 `submitRefund` | 把“已提交工单”当成了“已打款” | **拦截** |

  第三行最隐蔽：链路上一切正常，工具调用了也成功了，错的是模型对工具语义的理解。
- **工具调用证据从事件流里拿**：`ToolCallStartEvent` 和最终答复在同一条事件流里，并且一定先于答复到达。
  所以不需要借助 Reactor Context 在 `onActing` 和 `onAgent` 之间共享状态，也就不依赖“框架对 `onActing` 的调用落在
  `onAgent` 的 next 链上”这个不可靠的假设。
- **流式场景的限制**：检测到时，前面的文字已经显示在用户屏幕上了。处理方式是立即停止后续输出，
  追加一段**明确否定前文**的澄清，并转人工。关键词跨片匹配由 `StreamKeywordMatcher` 完成。
- **语义补充判定**：关键词只能识别字面表达，“款项已原路返回您的账户”这类同义说法会漏掉。开启 Jev 后，
  如果关键词没有命中、本轮也没有查询过真实状态，再用语义判定问一次。Jev 只能增加拦截，不能放宽已有判定；
  Jev 不可用时，退回纯关键词判定。
- **这条防线以前形同虚设**：只检测然后打一行 `log.info`，默认关闭，而且只检查 `AgentResultEvent`，在流式链路上根本不生效。
  类注释里写着“在未调用退款工具的情况下才判定”，代码里却完全没有这个判断。现在默认开启，
  生产配置 `application-prod.yml` 里也显式开启，并写明了理由。

**追问**：*判定为什么放在最终结果上，而不是每个文本块结束的时候？*
一轮 ReAct 经常有多个文本块，比如先说“我先查一下”再去调用工具。逐块判定会在工具调用前插入阻塞等待，还要多付几次调用费用。

**减分回答**：“在提示词里告诉模型不要说已退款”。

### Q5【中级】项目里的人工介入（HITL）分几层？退款审批是怎么设计的？

**考察点**：人机协作的完整闭环；审批的幂等处理；决策和执行分离。

**参考回答**

- **第一层：工具能力本身受限**。`submitRefund` 只登记待审单，不执行支付，从能力上就不可能直接打款。
- **第二层：权限闸门**。框架的 Permission 系统（`PermissionContextState`，主 Agent 与 Harness 共用）的 ask 规则才是真正的闸门；
  `HumanApprovalMiddleware` 只起观测作用（装配器里的注释写明了这一点）。
- **第三层：审批服务 `PendingApprovalService`**：
  - **决策幂等**：`store.decide` 以原子方式推进状态，重复决策会失败（接口返回 409）。
  - **决策和执行分离**：批准后先取得执行租约，再调用 `ApprovalExecutionHandler`。
    幂等键固定为审批单号，fencingToken 用来阻止旧 worker 回写本地的执行状态。
    执行失败时状态记为 `EXECUTE_FAILED`，已经生效的人工决策不会被回滚。
  - **巡检**：恢复卡住的执行、按 `maxAttempts` 重试；审批超时时，按配置升级为人工处理或者自动拒绝。
- **风险增强**：`JevRefundRiskMiddleware` 判定为高风险时额外转人工。它只做旁路判定，从不拦截或改写工具调用。

**追问**：*为什么审批状态和执行状态要分开记录？*
为了避免“工单显示已批准，钱实际上没动”这种情况被静默吞掉。执行失败必须能被看见，并且能被巡检重试。

**减分回答**：“加一个 `approved` 字段，审批通过就调用打款接口”。

### Q6【高级】MCP 允许挂接任意外部服务器，安全上要防哪些东西？

**考察点**：SSRF、本地进程执行、凭据保护、工具授权、上游契约变化。

**参考回答**

- **执行安全（`McpSecurityPolicy`，远程和 stdio 两种方式共用一套规则）**：
  - 默认只允许公网上的远程 MCP，stdio 方式默认关闭。
  - 企业私网或本机的 MCP 必须显式配置 host 白名单。即使命中白名单，仍然拒绝链路本地地址、云元数据地址、未指定地址和组播地址（防 SSRF）。
  - 域名会被解析成 IP 后逐个校验。URL 不允许带 query 和 fragment。
  - stdio 方式必须同时配置可执行文件白名单和工作目录白名单；启动器会清空继承的环境变量，并固定工作目录。
  - 所有客户端都只能通过 `McpClientFactory` 创建，保证保存配置时的校验和真正执行时使用同一套规则。
- **凭据**：只保存 SecretRef。MCP 的 headers 在配置载荷里只以密文形式出现，消费端先校验 HMAC-SHA256、`contentHash` 和 keyId，然后才解密。
- **授权**：按工具、Agent、渠道、主体多个维度授权（如 `SubjectToolAuthorizationMiddleware`）。
  在后台，MCP 管理属于控制面专属权限（统一由 `ControlPlanePermissions` 定义）。判断标准是：
  凡是能把代码或流量带出本进程的权限，都不授予租户管理员。
- **契约漂移**：`McpContractDrift` 对整个服务器的工具契约做整体快照，再和基线做 diff。
  指纹相同就直接判定无变化；如果指纹相同却比出了差异，说明规范化环节有 bug。
  检测到 `BREAKING` 级别的变化也**只报告、告警，不自动停用**：上游演进是常态，基线本身也可能过期，是否停用由人决定。
- **返回内容**：MCP 的返回结果统一经过间接注入防护的隔离标记处理。

**追问**：*DNS rebinding 攻击怎么防？*
保存配置时和每次建立连接前都要做校验（`validateRemoteUrl` 在这两个时机都会被调用）。
重定向也在出站约束的范围内，只在保存时校验一次是不够的。

**减分回答**：“MCP 是标准协议，接上就能用”。

### Q7【初级】为什么有的护栏出故障时选择放行（fail-open），有的选择拦截（fail-closed）？请举项目里的例子。

**考察点**：能否把“出错时往哪边偏”当成一个设计决策，而不是随手写一个 `catch`。

**参考回答**

- **判断标准**：比较“护栏自己出故障时的代价”和“漏放一次的代价”，哪个更大就往另一边偏。
- **选择放行的例子**：
  - 直接注入防护、间接注入防护、循环守卫：护栏自己出故障，不应该导致整个客服对话不可用。
  - 入站消息去重：计数器故障时按首次投递处理。代价只是重复回答一次；反过来，计数器一挂就所有消息都发不出去。
  - 语义缓存：查询失败视为未命中。缓存只是加速手段。
- **选择拦截的例子**：
  - 持久层缺少租户上下文时直接抛错，否则就是跨租户读写数据。
  - 配额要求降级到备用模型，但没有配置备用模型时，直接拒绝服务（`QUOTA-DEGRADE-FALLBACK-MISSING`），
    否则继续调用主模型会突破管理员设定的预算边界。
  - 内容风控的词库加载失败时，过滤器进入“拦截一切”的状态。
- **还有一种“降级但不放行”**：限流用的 Redis 故障时，降级为进程内计数，而不是直接放行。
  保护类能力不能因为基础设施故障就消失。

**追问**：*滑动窗口计数有误差时，误差应该偏向哪边？*
应该偏向多算，也就是限得偏严一点。少算会让超额请求溜过去；多算只是让用户早几十秒被拦下（见第 07 期）。

**减分回答**：所有地方都 `catch` 住异常然后返回默认值。

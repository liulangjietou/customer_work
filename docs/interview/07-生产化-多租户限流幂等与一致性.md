### Q1【中级】多租户行级隔离是怎么做的？为什么放在拦截器里，而不是在每个 Store 里各自处理？

**考察点**：SaaS 隔离模型；缺少上下文时的默认行为；有意跨租户操作的白名单管理。

**参考回答**

- **机制**：使用 MyBatis-Plus 的 `TenantLineInnerInterceptor` 全局改写 SQL，租户值取自 `TenantContext`（一个 ThreadLocal）。
  中间的业务代码感知不到租户，这正是把隔离放在拦截器、而不是每个 Store 各写一遍的意义：只要有一处漏写，就会串数据。
- **租户值精确比较**：`ExactTenantLineInnerInterceptor` 把条件右侧的租户常量转换成 `BINARY` 再比较。
  租户是身份标识，不能沿用业务文本列那种大小写不敏感的排序规则，否则 `TenantA` 和 `tenanta` 会被当成同一个租户。
- **缺少上下文时直接失败**：持久层读不到租户时抛出异常。这是刻意的设计：宁可报错，也不能在没有租户条件的情况下执行查询。
- **有意的跨租户操作只能走 `CrossTenantOperations`**：它是一个可以 grep 的白名单，合法用途只有三类：
  登录、控制面的跨租户视角（先校验权限）、系统级治理任务。
  刻意不采用“给上下文塞一个代表全局的特殊值”的做法，因为那样“忘记设置上下文”和“故意查询全局”在代码里看起来一模一样，
  一处疏漏就是全量数据泄露。
- **两条约定**：
  - 新建业务表一律带 `tenant_id` 列，不要加进忽略清单。
  - 权限查询用用户所属的租户，数据查询用当前视角的租户。两者混用的话，控制面用户切换视角之后会当场失去全部权限。

**追问**：*打开租户开关之后，哪些场景最容易出问题？*
所有不在 Web 请求里的数据库查询：
- 没有登录态的开放 API：用 token 到租户的映射解决；
- 调度线程：按任务所属租户恢复上下文；
- 启动期的装配代码，比如 `@Bean` 方法和 `@PostConstruct`：A2A 的 `@Bean` 里查询 `ai_agent`，曾经直接导致应用无法启动；
- 异步回调：需要显式恢复租户上下文。

**减分回答**：“每条 SQL 里手动加上 `tenant_id` 条件”。

### Q2【高级】主体级速率配额（按登录用户、匿名 IP、API Key 限流）是怎么设计的？为什么先只读判定、放行之后才记账？

**考察点**：滑动窗口的近似实现；误差应该偏向哪一边；异步链路中如何拿到调用者身份。

**参考回答**

- **两套配额并存，互不替代**：
  - **租户配额**（`TenantQuotaGuard`）回答“这个客户这个月能花多少钱”，按自然日或自然月对齐，要能和账单对上。
  - **主体配额**回答“这个调用者这半小时能用多少”，采用滚动窗口，目的是防滥用，同时限制 token 用量和请求次数。
- **先只读判定、放行后再记账**：`check` 只判断，不写计数；请求放行后才调用 `recordRequest`；
  token 用量在模型调用完成后，由 `AgentCallTimingMiddleware`（token 的唯一记录点）补记。
  这样被拒绝的请求不占额度，持续施压也不会把窗口越推越远。代价是并发时可能少量超额，这是有意的取舍。
- **异步链路里怎么拿到身份**：token 用量要等模型调用结束才知道，那时已经经过了好几次线程切换，方法参数里也没有“用户”。
  所以身份放在 `QuotaSubjectContext` 里，写入时 ThreadLocal 和 Reactor Context **两边都要写**，只写一边会在某类链路上取不到主体。
- **入口顺序**：`SubjectQuotaWebFilter` 的顺序是 `HIGHEST_PRECEDENCE + 30`，必须排在两个鉴权过滤器之后，并且它会自己验证一次 Bearer。
  因为 `UserAuthWebFilter` 只覆盖 `/api/customer/user/**`；如果不自己验证，换一条路径请求，就能从“按人限流”退化成“按 IP 限流”。
- **WebSocket 入口要单独判定**：H5 真正发消息走的是 `/ws/user`，WebFilter 管不到。所以 `ChatDispatchService` 里单独判定，
  资源标识为 `ws:chat`。
- **滑动求和的实现**：`WindowCounter#incrementSlidingSum` 把窗口切成 30 个桶来近似滑动窗口，最坏误差是一个桶的时长
  （30 分钟的窗口约为 1 分钟，也就是 3% 左右）。统计范围落在 `[window, window + bucket)`，误差偏向**多算**，也就是限得偏严。
  桶的计算逻辑放在 `SlidingSumBuckets`，进程内实现和 Redis 实现共用，保证 Redis 故障降级前后的用量能对得上。
- **其他细节**：
  - API Key 只保存 SHA-256 指纹，因为主体标识会进入 Redis 的键、命中表和日志。
  - 查询剩余额度的接口 `/api/customer/user/quota` 不参与判定，否则每查一次就扣一次，额度用完时连剩余多少都看不到。

**追问**：*为什么不逐条记录每次调用的时间戳，做精确的滑动窗口？*
在高 QPS 下，逐条记录会把内存或 Redis 撑爆。分桶之后每个计数键只占常数级空间，用可控的误差换来了有界的资源占用。

**减分回答**：“用 Guava RateLimiter 就行”。它是单机的令牌桶，限不了 token 用量，也无法跨副本共享计数。

### Q3【中级】WebSocket 消息被客户端重发时，怎么保证只处理一次？这个方案是怎么演进的？

**考察点**：幂等键的设计；锁和数据库唯一键各自负责什么；问题排查时先分清“数据丢了”还是“界面没显示”。

**参考回答**

- **问题**：移动网络下 WebSocket 断连是常态，客户端必须能重发。如果服务端不去重，同一句话就会变成两轮完整的对话：
  消耗双份 token，还可能提交两张退款工单、发出两次通知。
- **第一版：短窗口去重**。`InboundMessageDeduplicator` 复用 `WindowCounter.increment`，判断某个键在窗口内是否第一次出现；
  多副本部署时用 Redis 实现。没有 `clientMsgId` 的老客户端直接放行，因为去重是增益，不是安全边界。
- **当前版本：以持久化回执为准**（`ChatDispatchService.acceptUser`）：
  1. 生成确定性的消息号：`"REQ-" + base64url(SHA-256(...))`，输入是租户、会话、发送方类型、发送方 ID 和 `clientMsgId`。
     **每个字段前面加长度前缀**，避免字段拼接时边界混淆导致不同输入得到相同结果。
  2. 获取受理锁 `chat-accept:<租户>:<会话>`。
  3. 先查这条消息是否已经有回执，有就直接回放回执（`REPLAY_RECEIPT`）。
  4. 判定主体配额。
  5. 在同一个库的事务里创建工单并保存用户消息。
  6. 如果事务抛出异常，**再查一次回执**：分布式锁可能已经过期，或者实例发生了切换，最终由数据库唯一键来裁决。
     事务回滚之后，才能看到竞争者已经提交的回执。
  7. 如果同一个消息号对应的内容不一致，返回 `CHAT_MESSAGE_ID_CONFLICT`。
- **模型调用和消息转发都在事务提交之后才执行**。

**追问**

1. *为什么不把模型调用放进事务里？*
   事务里调用外部的慢服务，会长时间占住数据库连接和锁；而且事务回滚也撤销不了模型已经触发的工具副作用。
2. *用户反馈“断线重连后消息丢了”，你第一步查什么？*
   先分清是数据丢了还是界面没显示。项目里实测数据全部已经落库，真正的原因是前端重连后没有重新拉取历史消息。
   解决方式是客户端重连后补拉一次，而不是在服务端做一套离线队列（那需要存储、过期、去重三套机制）。

**减分回答**：“前端做防重复点击就行”。

### Q4【中级】事务 Outbox 解决什么问题？项目里的 Outbox 和死信是怎么设计的？

**考察点**：数据库和消息的双写问题；至少一次投递；失败重试的退避策略。

**参考回答**

- **问题**：业务数据写库和发送事件是两个动作。先提交再发送，进程崩溃时事件会丢；先发送再提交，可能发出一个最终被回滚的变更。
- **Outbox 的做法**（`OutboxService`）：
  - 事件和业务变更写在**同一个数据库事务**里。`publish` 写入失败时必须抛出异常，让外层事务一起回滚。
  - 异步投递时按租约领取到期的消息，每个实例带上自己的 `instanceId`，可配置租约时长和批大小，保证多个实例不会同时处理同一条消息。
  - 按事件类型分发给对应的 handler；同一类型注册了两个 handler 时，启动直接失败。
  - 投递失败按指数退避重试。语义是**至少一次**，所以消费者必须按稳定的事件 ID 做幂等。
- **死信**：
  - 重试次数用完后，状态改为 `ABANDONED`，**不删除**，保留现场以便排查。
  - 退避必须是指数的：下游多半正在重启，密集重试等于自己制造雪崩。
  - 没有注册 handler 的类型直接跳过，**也不累计重试次数**。如果累计，次数会被悄悄耗尽，掩盖“这类事件根本没人处理”这个事实。
- **项目中的例子**：工单事件（推送到 WebSocket、发出 CSAT 邀请），以及运行时配置的 ACK。
  Outbox 投递有 1～2 秒的延迟，所以 H5 的评分卡会再补拉一次。

**追问**：*Outbox 表越来越大怎么办？*
按保留期归档或清理已投递的消息；在状态和下次投递时间上建索引；用积压深度指标
（`DeliveryQueueHealthIndicator` 和相关 gauge）监控投递是否卡住。

**减分回答**：“事务提交之后再发 MQ 就行”。

### Q5【高级】配置热更新链路里，怎么防止旧的 Worker 覆盖新配置？怎么判断一次发布“整批生效”？

**考察点**：fencing token；内容指纹；发布、生效、确认三者的区别。

**参考回答**

- **控制面**：
  1. 配置变更和一条 `PENDING` 状态的发布任务写在同一个业务事务里。
  2. `RuntimePublishWorker` 用独立的调度器扫描任务，不依赖 admin 全局的 `@EnableScheduling`，通过 CAS 抢占任务租约。
  3. 准备阶段读取权威资产，做连通性探测，计算 revision 和 `contentHash`。
     如果内容已经确定发生了变化，任务直接终止（`markContentChangedTerminal`），不再发布过期的内容。
  4. 经过评测门禁（`EvalReleaseGate`）；不通过就标记为 `GATE_BLOCKED`。
  5. 发布前用**行锁做 fencing**，阻止旧 Worker 越过新 Worker 发布；失败则指数退避，重试用尽后标记为 `FAILED`。
- **运行面**：
  1. 只监听租户专属的 dataId（`<主 dataId>-tenant-<租户码>`）。专属配置缺失或被删除时，保留当前的安全配置，
     **绝不回退到主 dataId**，这是为了防止跨租户串配置。
  2. 先校验 HMAC、`contentHash` 和 keyId，再解密密钥。
  3. 新配置不可用时保留最后一份安全配置，回滚缓存代际，回复 `REJECTED`；
     可用时原子替换模型、提示词、MCP 和 `maxIters`，刷新热 Agent，回复 `APPLIED`。ACK 经 Outbox 投递。
- **整批生效的判定**：发布任务入队时**冻结目标实例的清单**，清单之外的 ACK 一律拒绝。
  只有清单里的实例全部回复 `APPLIED`，才算整批生效；否则结果是 `PARTIAL` 或 `FAILED`。
- **回滚**：把旧快照当作一个新版本重新发布，走 maker-checker 审批。历史版本只增不删，任何时候都能说清线上运行的是哪一版。
- **缓存代际**：配置切换时，语义缓存进入新的代际。切换过程中的请求一律视为未命中；
  缓存写入只允许写到请求开始时捕获的那个代际，旧模型返回的结果会被丢弃。

**追问**：*`PUBLISHED` 状态为什么不等于配置已经生效？*
它只表示 Nacos 已经接收了这份配置。各个实例是否真的应用成功，要看 ACK 的汇总结果。

**减分回答**：“往 Nacos 里改一下，监听器自动刷新就行”。

### Q6【中级】从单实例扩展到多副本部署，需要改哪些东西？

**考察点**：识别哪些状态是进程内的；SPI 切换；每种能力故障时往哪个方向降级。

**参考回答**

- **计数器**：`WindowCounter` 从进程内实现切到 Redis 实现（`customer-work.distributed.counter-mode=redis`），
  用于限流、租户配额、主体配额和入站去重。
- **会话锁**：`SessionLock` 切到 Redisson 实现（`session-lock-mode=redis`）。
  使用进程内锁时，要求网关按会话做粘性路由。
- **WebSocket 下行推送**：用户可能连在另一个副本上，所以用 Redis 发布订阅做跨副本广播（`RedissonWsDownstreamBroadcaster`）。
  每个副本启动时生成一个 `nodeId`，收到自己发出的广播直接丢弃，防止消息风暴。
- **调度任务**：用租约（`SchedulerLease`）或 XXL-JOB 协调。拿不到锁时**照常执行**：
  跳过会让超时的审批永远没人处理，而重复执行是可以恢复的。
- **会话状态**：由 MySQL 的 StateStore 和 CAS 版本控制兜底（见第 04 期 Q7）。
- **优雅停机**：`GracefulShutdownService` 实现 `SmartLifecycle`，停止接收新请求，并等待进行中的请求处理完。
  滚动发布时对话不会被截断。
- **Redis 故障时的降级方向**：限流和会话锁降级为进程内实现，**而不是直接放行**，保护类能力不能因为基础设施故障就消失。
  WebSocket 广播失败时退回“对方离线”的语义，不打断主链路。

**追问**：*K8s 清单里，应用服务为什么用 StatefulSet，而不是 Deployment？*
这和 Q5 的“冻结目标实例清单”有关：配置 ACK 要靠稳定的实例 ID 来冻结目标集合，所以应用服务固定为
`customer-work-app-0/1`，由 initContainer 根据序号写入这个实例自己的 instance-id 和 ACK token。
也正因为如此，HPA 的上限目前固定为 2。扩容之前，必须先给新序号准备独立的 token 和身份映射，否则新实例无法可靠地回执。
另外，`terminationGracePeriodSeconds` 必须大于应用自己的优雅停机超时时间，否则正在处理的对话会在停机流程走完之前被 SIGKILL 打断。
admin 服务用普通的 Deployment（见 `deploy/k8s/`）。

**减分回答**：“加机器就行，应用本来就是无状态的”。

### Q7【高级】后台的数据权限（按用户隔离）为什么采用白名单？缺少上下文时为什么不过滤，和租户隔离的做法恰好相反？

**考察点**：在两个隔离维度上取舍方向相反；防止越权修改；如何兼容存量数据。

**参考回答**

- **机制**：角色上配置数据范围（`sys_role.data_scope` 取值为 ALL、TENANT 或 SELF），由 `DataScopeInnerInterceptor` 强制执行。
- **白名单，方向与租户隔离相反**：租户隔离的原则是“能加租户列的表全都加”，漏一张就会串数据。
  而用户维度上，大多数表是租户内共享的配置资产（智能体、知识库、Skill、MCP 等），误把其中一张加入过滤，
  同一租户的成员就无法协作，比如 A 建的智能体 B 用不了；而且**不会报错**，只表现为“数据莫名其妙变少了”。
  所以只有真正属于“某个人的产出物”的表才会进入 `DataScopeTables`。
- **缺少上下文时不过滤**：只有根本没有“人”参与的链路才会缺少数据范围上下文，比如调度线程、异步回调和开放 API。
  如果这时选择报错，后台任务会整体挂掉，而且跨租户那道防线本来就还在。
  **例外**：凭令牌进入的链路背后是一个确定的人，必须用 `DataScopeContext.callAs` 显式恢复身份。
  否则 A 的脚本就能读到 B 录入的站点密码。
- **归属列为 NULL 的数据视为租户内共享**：存量数据没有归属人，如果一并过滤掉，升级当天所有历史记录都会消失。
- **UPDATE 和 DELETE 也要过滤**：如果只过滤列表查询，用户虽然看不到别人的数据，却能凭 ID 修改或删除
  （`updateById` 只按主键定位）。INSERT 不需要过滤，归属列统一由 `MyMetaObjectHandler` 写入。
- **ALL 范围必须同时校验控制面角色**：租户管理员可以自己建角色，如果只看字段值，任何租户都能给自己开出跨租户的口子。

**追问**：*为什么会话的归属不另建一张表？*
框架的状态表无法加列，所以复用已有的 `ai_workspace_session`，由 `WorkspaceSessionGuard` 维护归属，
归属条件直接写在那条 JOIN 里。

**减分回答**：“所有表都加一个 `create_by` 过滤就行”。

# 第 08 期 · 模型路由、成本、评测与系统设计

> **本期结论**：高级岗位的最后一轮，通常会问三类问题：怎么让成本可见、怎么证明改动有效（评测）、能否独立完成整体设计。
> 这三类问题的共同点是，都要用数据说话。候选人如果只能说“感觉效果变好了”“应该能省钱”，基本就过不了这一轮。
> 本期最后一道复盘题，面试官可以用来判断候选人的工程成熟度。
>
> 对应 JD：模型路由与容错、成本控制、Agent 评测（LLM-as-Judge、A/B 测试）、AI 系统设计。题量 7。

### Q1 模型层的弹性是怎么做的？主模型和备用模型怎么切换、怎么熔断？流式输出已经开始之后还能切换吗？

**考察点**：失败转移、熔断和半开状态；流式输出中途失败时怎么处理。

**参考回答**（`FailoverModel` 和 `ModelCircuitBreakerRegistry`）

- **候选模型和顺序**：候选模型有序排列，主模型在前、备用模型在后。每次调用优先使用没有熔断的候选；
  如果全部都熔断了，就退回到使用全部候选，而不是直接拒绝服务。
  例外是被健康状态标记为“硬不可用”的候选，它们不会因为本地熔断候选用完而被重新放行。
- **熔断的规则**：每个候选单独统计连续失败次数，达到阈值就打开熔断，熔断持续一段时间；
  到期后自动进入半开状态，计数清零，并放行一次尝试；调用成功就清零计数。
  这部分是手写实现，没有引入 Resilience4j，因为需要的只是“连续失败计数 + 时间窗口”这点语义。
- **流式输出开始后是否还切换候选**，由 `midStreamFailoverEnabled` 决定，两种选择都有真实的使用场景：
  - 设为 `true`：适合动态智能体运行时。流中途失败时换下一个候选，从头重新发送，宁可内容重复，也要拿到完整回答。
  - 设为 `false`：适合客服主链路。已经吐出部分内容后再换候选，用户会看到“前一个模型的前半段 + 新模型的完整输出”
    拼在一起的错乱文字。所以这时直接把错误向上抛，由上层截断输出并返回兜底文案。
- **强制使用备用模型**：配额进入降级状态时，通过 Reactor Context（`ModelRoutingContext.preferFallback`）要求使用备用候选。
  分级路由模型必须把这个指令继续传给内层的 `FailoverModel`，不能让经济档把请求截走，否则“降级”只是名义上生效了。

**追问**：*熔断的阈值该怎么定？*
依据真实的错误率和恢复时间来定。阈值太低，偶发的超时就会把主模型熔断掉；阈值太高，故障期间会有大量请求白白等待。
需要结合熔断打开次数和候选切换次数这类指标来调整。

**减分回答**：“调用失败就 try-catch，然后换一个模型重试”，没有考虑熔断和流式输出中途失败的情况。

### Q2 怎么实现“简单问题走便宜模型”？路由判断错了会怎样？

**考察点**：分级路由的工程取舍；把判断错误的代价设计成不对称的。

**参考回答**（`TieredRoutingModel` 和 `ModelTierPolicy`）

- **判断放在 Model 层**：这一层只能看到 `messages` 和 `tools`，看不到意图分类的结果。
  意图分类器在 `MultiAgentOrchestrator` 里，而这个类本身就持有 `Model`，如果 Model 层反过来依赖它，就会形成循环依赖。
- **判断依据**：只看对话轮数和最后一条用户消息的长度。**只有单轮而且简短的问题才降级到便宜模型**，其余一律走标准模型。
  这样做的好处是判断错误的代价不对称：判错了顶多是“没省到钱”，而不是“回答质量变差”。
- **能力声明取两档中较弱的一档**：结构化输出是否支持、上下文窗口多大，都按两档中较弱的那个上报。
  因为路由是动态的，如果按主模型的能力上报，某次请求被路由到经济档时会直接失败。
- **经济档失败时**：还没有吐出任何内容时，回退到标准模型；已经吐出内容后，就不再回退，原因和 Q1 相同。
- **用数据证明**：分别统计 `economyCount` 和 `standardCount` 两个计数器，这个功能省了多少钱，靠这两个数来说明。

**追问**：*怎么证明它确实省了钱，同时质量没有下降？*
比较分档调用量与单次调用成本，再按档位分别做质量评测；到线上做实验时，要求达到最低曝光量才下结论
（项目在流量不足时只报告 `INCONCLUSIVE`，不给出结论）。

**减分回答**：“用一个大模型先判断问题难度，再决定用哪个模型”。这样每次请求都多一次模型调用，可能反而更贵。

### Q3 语义缓存在客服场景里有什么风险？项目设置了哪些安全措施？

**考察点**：缓存导致数据泄露的风险；缓存命中路径的完整性；让缓存效果可以被度量。

**参考回答**（`SemanticCacheService`）

- **核心风险是数据泄露**：两个用户都问“我的订单到哪了”，语义高度相似，但正确答案完全不同。
  把 A 的物流信息返回给 B，就是一次安全事故。
- **所有安全判断都收在 `cacheable` 这一个方法里**：
  1. **意图白名单**：默认只缓存 `consult`（政策咨询类）意图。
  2. **个人标识过滤**：问题或答案中出现 6 位以上的连续数字（订单号、手机号、快递单号等）就不缓存。
     政策类数字，比如“7 天无理由”“满 99 包邮”，都在 5 位以内，不会被误伤。
     答案这一侧也要检查一次：意图可能被判错，而答案里带有单号，直接说明这条回答依赖个人数据，比意图判断更可信。
  3. **两层隔离**：表上的 `tenant_id` 由拦截器自动改写，缓存条目上还有一层 `scopeId` 做业务分区。
  4. **语义判断**：开启 Jev 时，写缓存之前再让它判断一次，这一步放在 Embedding 之前，被拒绝时连向量调用也省掉了。
- **两条对话链路都要接入缓存**：以前缓存只接在非流式的 `chat()` 上，而 H5 走的是 WebSocket 流式链路，
  结果真实流量既不会写入缓存，也不会命中缓存。现在流式链路遵循三条规则：
  - 缓存的是**经过出站过滤之后**、用户实际看到的那份文本；
  - 命中缓存时再过滤一遍，因为词库可能已经更新；
  - 用 `doOnComplete` 写缓存，并排除走过兜底逻辑的那次请求。
- **配置代际**：每个请求开始时记录当前的配置代际（`CacheGeneration`）。配置切换期间的查询一律视为未命中；
  写缓存时只能写入请求开始时的那个代际。
- **默认值**：starter 默认不开启语义缓存，示例应用显式开启了。相似度阈值 0.95，TTL 7 天，
  单个租户最多缓存 2000 条（超出时淘汰最久未命中的），每次查询最多比较 200 个候选。
  问题长度限制在 4～200 字：太短的问题（比如“在吗”）很容易误命中，太长的问题几乎不会重复。
- **可度量**：记录候选数是否达到上限，用来判断要不要改成真正的向量检索；记录未命中时的最高分分布，
  用来判断阈值是不是定得太严。

**追问**：*有人认为“新写入的缓存条目永远排不到前面，会被饿死”，这个说法对吗？*
不对。`SemanticCacheEntry.of()` 会把 `lastHitAtMs` 设为写入时间，候选按这个字段倒序排列，所以新条目反而排在最前面。
真正的代价在于 `maxSize` 和 `maxCandidates` 的比例：每次查询只能看到大约一成的缓存。这是接口注释里写明的**有意取舍**：
如果不限制候选数量，查一次缓存可能比直接调用模型还慢。这道题也在考察候选人会不会先核实结论，再动手修改。

**减分回答**：“把所有问答都存进 Redis，相似度超过阈值就直接返回”。

### Q4 这个项目怎么评测 Agent？离线评测、LLM-as-Judge 和回归对比分别是怎么做的？

**考察点**：评测体系的完整性；做效果归因的方法；评测数据集的管理。

**参考回答**

- **离线确定性评测**：`IntentEvalRunner` 负责意图评测，`fastRouteIntent` 是纯函数，可以直接复用。
- **LLM-as-Judge**：`QualityEvalRunner` 让裁判模型从相关性、准确性、完整性三个维度打 1～5 分。
  要求裁判按 `SCORE: <1-5>` 的格式输出，再用正则 `SCORE:\s*([1-5])(?!\d)` 解析，3 分及以上算通过。
  `JudgeModel` 是一个函数式接口，默认复用主对话模型；需要更严格的评测时，可以换成一个更强的模型；
  它的 `version()` 方法用来标识当前使用的是哪个裁判。
- **数据集**：classpath 里的种子数据加上数据库里的增量数据，同一个 ID 以数据库为准，已停用的用例会被剔除。
  **种子数据加载失败时直接抛错**，因为空数据集会得出一份 0 个用例的“满分”报告，这比报错更难发现。
- **回归对比**（`EvalComparison`）：
  - 除了给出总体结论（首次运行、提升、退化、持平、出错），还逐个用例列出**回归**（上次通过、这次失败）和**修复**（上次失败、这次通过）。
    因为准确率从 90% 涨到 92%，背后可能是“修好了 3 个，又弄坏了 1 个”，被弄坏的那个才需要立刻去看。
  - 浮点比较的容差是 0.001；评测集本身有增删时，要先看 `datasetChanged`，这时两次的数据不能直接比较。
  - 裁判不可用时结果标记为 `ERROR`，不能作为发布依据。
- **做效果归因**：`PromptVersionTracker` 为每次评测记录当时提示词的指纹。指标下降时先看指纹有没有变：
  变了，说明是这次提示词改动引入的，去对比两个版本的全文；没变，就不用再逐字看提示词，该去查模型或数据。
- **评测在哪里跑**：评测在客服端执行，admin 只负责触发和展示。因为评测的必须是线上真实使用的那一套组件，
  如果在 admin 另外实现一遍等价逻辑，评测的就只是一个副本。
- **发布门禁**：`EvalReleaseGate` 不通过时，配置不会被发布（见第 07 期 Q5）。

**追问**：*LLM-as-Judge 本身有偏差，怎么控制？*
固定评分标准并记录裁判版本；定期用人工标注数据校准裁判；注意位置偏差和“越长越高分”的偏差；
做前后对比时冻结裁判模型；必要时用一个与被测模型不同家族的模型来当裁判。

**减分回答**：“找几个问题人工试一试，感觉还行就上线”。

### Q5 怎么让 token 成本“看得见”？

**考察点**：计量点要唯一；指标的标签口径要一致；计费不能伪造数据。

**参考回答**

- **计量点唯一**：`AgentCallTimingMiddleware` 是 token 用量的唯一记录点，它能看到完整的一轮调用。
  `ChatTerminalCaptureMiddleware` 负责采集对话的终止原因和实际的 token 用量。
- **指标的标签必须一致**：同名的 meter，标签键的集合必须完全相同。Prometheus 遇到不一致会直接拒绝注册，
  而本地测试常用的 `SimpleMeterRegistry` 不会报错，只是查不到数据。给视觉 OCR 的 token 加上 `source` 标签时，
  对话链路那边也必须一起补上。指标名和标签统一定义在 `TokenMetrics`，跨指标共用的标签键统一定义在 `MetricTags`。
  标签键相当于监控查询的接口，同一个含义用了不同的键，跨指标聚合就会断掉。
- **绕开 Agent 链路的调用也要计量**：视觉 OCR 是一次真实的模型调用，但它不走 Agent 链路。以前连返回的 `usage` 都没读取，
  这部分成本完全看不到。现在通过 `VisionOcrUsageRecorder` SPI 记账：指标一定会记录，配额尽力记录。
- **计费**：实时环节只按 token 拦截；金额走 T+1 账单（`cw_tenant_usage_daily`），按归集时的单价落库，调价不影响历史账单。
  缺少单价、缺少用量或者币种混合时，只标记为“不完整”，**不会伪造一个成本数字**。
- **框架升级也会影响账单**：AgentScope 2.0.3 开始按思考内容（`ThinkingBlock`）的真实长度计算 token，这会直接影响配额和账单金额。

**追问**：*为什么实时环节只拦 token，不拦金额？*
token 在请求时就能准确计量；金额要在归集时查单价、处理币种、做对账。把金额判断放进实时链路，会让实时链路依赖这些查询。

**减分回答**：“看一下模型厂商的账单就知道花了多少钱”。那样无法分摊到租户、渠道和具体功能上，也就不知道哪里可以省。

### Q6 系统设计：设计一个支撑 10 万日活的电商智能客服 Agent 系统（可以参照本项目）。

**考察点**：能否先澄清需求；能否说清分层架构和关键取舍；有没有容量和成本意识；系统怎么持续改进。

**参考回答要点**（按“先澄清需求，再讲架构，再讲取舍，最后讲演进”组织）

1. **澄清需求**：接入哪些渠道、峰值 QPS 多少、首字延迟的 SLA 是多少、预计转人工的比例、合规要求
   （个人信息保护、涉及资金的操作）、是否需要多租户。
2. **分层架构**：
   - **接入层**：网关、鉴权、限流，WebSocket 或 SSE。
   - **对话编排层**：会话锁、幂等受理、工单状态机。
   - **Agent 运行层**：单个主 Agent，加上按业务域分组的工具、RAG 和记忆，外面包一层治理中间件链。
   - **工具层**：业务系统通过 SPI 接入，另外有 MCP 和审批。
   - **知识运营**：文档接入、版本管理、ACL、知识评测。
   - **控制面**：模型资产、提示词版本、发布门禁、带 ACK 的配置下发。
   - **数据层**：MySQL、Redis、向量库、对象存储。
   - **观测与反馈**：指标、链路追踪、审计；把 badcase、CSAT 和知识盲区汇集起来，形成持续改进的闭环。
3. **容量和成本**：每一轮对话的 token 预算是多少（光工具 schema 就约 4 千 token）；模型接口有并发上限，
   超出时要排队和降级；用语义缓存和分级路由降低成本；把流式输出的首字延迟作为核心指标。
4. **关键取舍，每个都要讲出理由**：
   - 用单 Agent 还是多 Agent；
   - 为什么把会话状态外置；
   - 消息怎么做到幂等；
   - 转人工的通道必须始终保留；
   - 涉及资金的操作必须经过人工审批；
   - 每道护栏出故障时选择放行还是拦截。
5. **演进路线**：先用单实例和进程内的 SPI 实现跑起来；需要多副本时，再把计数器、锁、广播切换到 Redis 实现；
   语料规模上来以后，再接入专用的向量库。

**评分参考**

- **必答项**：流式输出、会话隔离、幂等处理、转人工、涉及资金操作的审批、可观测性。
- **加分项**：工具面的成本、护栏的执行顺序、语义缓存的安全措施、评测门禁、配置生效确认。
- **减分项**：一上来就画一个“多 Agent 平台”，说不出单轮对话要调用几次模型、要花多少钱。

### Q7 复盘题：讲一个你在这个项目里遇到的“不报错、但功能静默失效”的问题。你是怎么发现的、怎么根治的、又怎么防止它再次出现？

**考察点**：工程成熟度，包括发现问题的方法、根因分析的深度、防止复发的手段，以及是否诚实地说明还没解决的部分。

**参考回答结构**（STAR 加上“防复发”）

- **可以用的素材**（任选其一深入讲）：
  1. **语义缓存只接在了非流式链路上**：用户实际走的是 WebSocket 流式链路，缓存表一直是空的。
     通过命中率指标发现，根治方法是“两条链路都接入”加上统一装配。
  2. **CSAT 邀请挂在 `endSession` 上**：真实用户结束会话时走的是工单状态机，所以回收率的分母近乎为 0，看板上全是 0.0%。
     改为挂在工单进入终态的事件上，并且评测会话不发邀请。
  3. **提示词里写了一个从没装配的能力**：系统提示词第 8 条一直写着“可借助计划工具拆解为子任务”，
     而框架的任务清单工具从没挂上（其实只需要一行 `enableTaskList()`）。
     教训是：接入一个能力要逐一确认四件事：工具挂上了吗？提示词讲清怎么用了吗？结果用户看得到吗？模型到底用没用，有计数吗？
  4. **Toolkit 的防御性拷贝让子类的重写失效**；或者**装饰器没有转发接口的 default 方法**（见第 06 期 Q7）。
- **面试官重点听四件事**：
  1. **怎么发现的**：是靠指标和数据，还是靠运气？
  2. **根因还是表象**：比如“能力只接在用户不走的那条路上”是一种反复出现的模式，还是一次偶然？
  3. **系统性的修复**：有没有收敛成唯一的入口，有没有加上结构性的自动化检查。
  4. **诚实说明边界**：比如这种自动化检查仍然发现不了“调用了装配器，但装进去的是空的”这种情况，需要用真实容器测试来补。
- **项目里的一句总结可以直接引用**：**注释写的是意图，不是事实**。
  读到“另行配置”“在未走退款工具的情况下”这类注释时，要去代码里确认一遍。

**减分回答**：只讲“修了一个 bug”，讲不出它为什么没有被测试覆盖，也说不出以后靠什么防止它再次出现。

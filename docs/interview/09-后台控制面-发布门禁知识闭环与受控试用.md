# 第 09 期 · 后台控制面：发布门禁、知识闭环与受控试用

> **本期结论**：后台的难点不在增删改查，在于**证据链**：运营看到的每一个“通过”“已生效”“已发布”，背后都要有一份
> 冻结的、可复核的事实。没有冻结，评的就不是要发的那份；没有回执，跨库写入失败后就不知道该不该重做；
> 没有精确的状态分类，同一条任务在三个页面上会显示成三种状态。
> 本期题目都基于后台真实踩过的坑，面试时间有限时可以只挑 Q1、Q3、Q4 三道。
>
> 对应 JD：配置中心与灰度发布、LLMOps / 评测门禁、分布式事务与幂等、后台管理系统。题量 7。
> 本期与[第 07 期 Q5](07-生产化-多租户限流幂等与一致性.md)（配置下发的 fencing 与 ACK）衔接，不重复那部分内容。

### Q1 评测门禁阻断了一次发布，任务状态应该算“进行中”还是“失败”？项目在这里踩过什么坑？

**考察点**：状态机里“等人决定”这一类状态的语义；状态分类为什么只能有一个定义处。

**参考回答**

- **结论**：两者都不是。它是第三类状态，**需要人介入**：不会自己往前走，也不能草草判失败。
  项目在 `RuntimePublishStatus` 上把分类收成三个方法，所有消费方只能调用它们：
  - `isAdvancing()`：`PENDING`、`PROCESSING`（靠 Worker 推进）、`PUBLISHED`、`PARTIAL`（靠实例 ACK 推进）；
  - `needsHumanAction()`：只有 `BLOCKED`；
  - `isSettled()`：`APPLIED`、`SUPERSEDED`、`FAILED`。
- **踩过的坑**：此前三个消费方各自判断，在 `BLOCKED` 上正面冲突：
  1. 调度器的捞取 SQL（`findDueCandidates`）只捞 `PENDING` 和租约过期的 `PROCESSING`，等于把 `BLOCKED` 当终态；
  2. 模型实验页把它算作**失败**；
  3. 改进闭环（`ImprovementCaseService#refreshPublish`）的 else 分支把它当**进行中**，每个扫描周期捞一次、判一次、再排下一次。
  结果是：改进记录永远停在“发布中”；因为走的不是失败分支，`lastError` 恒为空，面板上连错误提示都没有；
  同一行数据在模型实验页却显示“失败”。
- **为什么两种误判都有害**：误判成“进行中”会无限轮询，误判成“失败”会把重评之后本可以继续的发布提前关掉。
- **出口**：`BLOCKED` 只有两个出口，都要人操作：重新评测后放回 `PENDING`（`retryGateBlocked`），
  或者走有审计的紧急豁免（`overrideGateBlocked`）。
- **门禁本身**：`EvalGateEvaluator` 是纯函数，检查绝对阈值、相对回归、关键用例、Judge 异常和候选版本是否匹配。
  Judge 调用异常时的策略由 `JudgeErrorPolicy` 决定，生产推荐 `BLOCK`：Judge 挂了就当作没有证据，而不是当作通过。

**追问**

1. *`FAILED` 归入“已成定局”，但迟到的 ACK 仍然可以把它翻成 `PARTIAL`，这不矛盾吗？*
   不矛盾。`FAILED` 是产品语义上的定局：这一轮发布判定失败。迟到 ACK 属于补报，不代表“它会自己好起来”，
   消费方不应该因此继续轮询。
2. *这类问题怎么预防？*
   和工单的 `TicketStatus#isEnded()` 是同一条约定：**“这个状态还会不会自行推进”只在枚举里回答一次**，
   禁止在各处写 `status == APPLIED || status == FAILED` 这种分类。

**减分回答**：“阻断了就是失败，让用户重新发布一次”。这样会丢掉原任务上冻结的快照和评测结论，也绕开了豁免审计。

### Q2 知识缺口原来有一个“一键补知识”的入口，直接往 FAQ 表里插一条。为什么要关掉它，改成候选闭环？

**考察点**：“发布了”和“有效果”的区别；把知识变更纳入与代码变更同等的治理。

**参考回答**

- **旧入口的问题**：`/fill` 直接插入客服库的 `cw_knowledge`。它回答不了三个问题：
  1. 这条知识**真的能被检索到**吗？线上召回是 `KnowledgeMapper.xml` 的三列 LIKE 匹配加 `LIMIT 5`，
     关键词写得不好，这条知识插进去也永远召不回；
  2. 它会不会**挤掉原本答对的知识**，让别的问题变差？
  3. 出了问题，**是谁、基于哪次复核**加的？
- **现在的闭环**：缺口 → 人工分类复核 → 可编辑候选 → 冻结绑定 → 对照复评 → 发布门禁 → 正式 FAQ 与回执。
  - **分类复核是前置条件**：只有人工把缺口分类为 `KNOWLEDGE` 且复核修订号匹配，才允许保存候选。
    规则引擎的建议、旧编辑器里的分类都不算依据，因为很多“未命中”其实是实时数据（`REALTIME`）、
    依赖故障（`DEPENDENCY`）或流程问题（`PROCESS`），补一条 FAQ 解决不了；
  - **候选只增不改**：正文修订只插入、不覆盖，保存只产生 `DRAFT`，不调用模型、不写 FAQ；
  - **复用已有的改进状态机**：`ImprovementCaseService` 本来就有认领、回归用例、制品绑定、复评和发布，
    候选挂在它下面，没有另建一套平行的治理状态机。
- **旧入口的处理**：明确拒绝并提示改走候选复评发布，而不是悄悄保留。留着它，所有门禁都可以被一个按钮绕过。

**追问**：*为什么不直接在旧入口上加一个“插入后跑一次评测”？*
因为那样评的是已经上线的配置，评测结果出来之前用户就已经在用这条知识了；而且评测失败之后还要再删，
删除本身又是一次没有门禁的线上变更。先评后发，才能让门禁真正拦得住。

**减分回答**：“加个审批流，主管点通过就发布”。审批只能证明“有人同意”，证明不了“这条知识有用、没有副作用”。

### Q3 候选复评怎么证明“评的就是要发布的那一份”，而且效果变好是因为这条知识？

**考察点**：评测的单变量控制；冻结与发布前重新核对；异步评测结果的迟到隔离。

**参考回答**

- **冻结**：`KnowledgeCandidateSnapshotService` 冻结候选修订、来源复核、正式 FAQ 基线语料、加入候选后的语料以及全内容指纹；
  `KnowledgeTrialModelService` 冻结答复模型和评分模型的地址、模型名、端点修订和上下文窗口；
  评测集只能用已审核（`APPROVED`）的 QUALITY 数据集快照，**目标用例必须真实存在于那个审核版本**，只在当前工作集里有不算。
  冻结后的 JSON 与原始行对象脱钩，后面有人改了行，冻结内容也不变。持久化字段里不含密钥、SecretRef 或模型对象。
- **单变量对照**：跑两组评测，**只改变知识语料**，提示词、轮数、模型、用例全部相同。两组结果不进入客服端全局的回归基线。
- **检索必须走真实路径**：`SnapshotKnowledgeBackend` 与线上共用同一段 XML 的三列 LIKE、排序规则、主键升序和前五条规则，
  只是数据源换成冻结的 JSON。候选**不会被无条件拼进提示词**：
  模型主动调用知识工具、候选实际排进前五条，才算召回证据；排在第六条之后的不算。
- **跑的是真实 ReAct**：`KnowledgeCandidateTrialRunner` 真的构造 `ReActAgent`，每条用例独立的 `InMemoryAgentStateStore`、
  独立会话，只注册 `KnowledgeBaseTools` 和冻结检索后端，没有正式 MCP、写工具或缺口统计。
- **通过条件是合取的**：两组 Judge 完整、版本与用例计数一致、目标用例实际召回了候选且评分通过、没有新增失败用例、
  整体评分不下降且达到通过线。
- **迟到结果隔离**：每次复评有执行编号和总截止时间。旧一轮的结果晚到时，编号对不上，直接丢弃。
- **发布前重新核对**：发布时重新读取候选、来源和正式 FAQ，任何有效变化都拒绝沿用旧证据。

**追问**

1. *项目里曾出现“目标用例根本没参评，复评却判了通过”，怎么发生的？*
   早期只检查“失败列表里不包含目标用例”。目标被漏掉时，它当然不在失败列表里，于是判成了 `READY_TO_PUBLISH`。
   修复后要核验运行所绑定的不可变快照：类型、内容指纹、运行计数、失败 ID 的唯一性与归属、**目标是否存在**，全部成立才算。
   这是“用不存在来证明通过”的典型错误。
2. *评测通过了，是不是就说明线上效果变好了？*
   不是。它说明的是：在冻结的审核用例上，加入这条知识没有让结果变差、目标问题答对了。线上效果要靠发布后的真实流量指标确认。
   项目文档里专门写了一句：**知识已发布，不等于线上效果已验证**。

**减分回答**：“把候选拼进 system prompt 跑一遍评测集，分数高了就发布”。这样绕过了检索，证明不了线上召回得到它。

### Q4 候选发布要同时改两个库：后台库推进改进记录状态，客服库插入正式 FAQ。怎么保证不丢、不重复插入？

**考察点**：跨库一致性不靠分布式事务时怎么做；“结果未知”状态的处理；回执模式。

**参考回答**

- **不用 XA，用“单库事务 + 回执 + 可恢复的任务”**：
  1. **客服库一个事务**：正式 FAQ、真实自增主键和一条发布回执在客服库的同一个事务里提交（客服端迁移 V29 新增租户发布锁与回执表）；
  2. **后台库一个事务**：父改进记录与候选的冻结、解冻、完成在后台库的同一个事务里提交；
  3. **两库之间靠任务和回执衔接**：发布由既有的 `ImprovementAutomationWorker` 驱动 `KnowledgeCandidatePublicationService`，
     没有另建发布队列。
- **结果未知时怎么办**：客服库提交成功、后台库回滚了（或者响应丢了），状态保留为 `PUBLISHING`，任务不重新生成。
  下一次 Worker **先按固定任务号去客服库读回执**：有回执就直接完成后台记录，没有才写入。
  **禁止重新生成一个新任务去重试**，否则就会重复插入 FAQ。这个“客服库已提交、后台回滚”的裂缝用真实双库集成测试复现过。
- **确定性冲突与瞬时故障分开**：来源、版本、标题冲突进入终态，不重试；网络和数据库故障才退避重试。
- **防止旧入口插队**：发布 SQL 显式精确匹配租户和来源修订，在 `REPEATABLE_READ` 事务里锁住正式语料范围，再与评测基线比较。
  真实 MySQL 验证过：空库和已有知识库两种情况下，核对窗口内旧 badcase 入口的插入都会被挡住。
  如果只让新入口之间互斥，旧入口照样能穿过检查。
- **防止多人同时操作**：页面先展示确切的候选正文再确认发布，并提交它看到的候选指纹和评测运行号；
  服务端持有父记录锁时比较这两个值，防止旧页面把别人更新过的内容发出去。

**追问**：*回执里为什么要存真实的 FAQ 主键，而不是评测时的“虚拟行号”？*
其它租户会消耗自增编号，评测时推算的行号在真实表里可能对应别人的记录。回执只认客服库事务里拿到的真实主键。

**减分回答**：“先写后台库，再写客服库，失败就回滚”。跨库没有这种回滚，第二步失败时第一步已经提交了。

### Q5 管理员想在正式保存前先“试一下”草稿配置。怎么做到真实调用模型，又不产生任何副作用？

**考察点**：试用环境的副作用边界；“看起来隔离”和“真的隔离”的区别；幂等受理。

**参考回答**

- **先说哪些做法不算隔离**（都是读代码核实过的）：
  - 换一个 sessionId 后复用 `AdminAgentInstanceFactory.buildInnerReActAgent`：它会清除正式运行范围的 MCP 授权缓存、
    注册工具分类，并使用持久化的状态库；
  - 用 `ExecutionModePolicy.PLAN` 当隔离：`ExecutionModeMiddleware.planBlock` 只是改写写工具的字符串参数后**继续调用工具**，
    并不是完全禁止调用。
- **实际做法**：
  - 服务端复用 `AgentService.validateConfiguration` 校验草稿，冻结所选的主备模型或路由策略、Skill 和知识库版本；
  - 独立 ReAct 会话只消费这份快照，不修改正式智能体、工作区会话、全局工具实例或发布任务；
  - **工具白名单**：系统工具只允许核实过的纯计算工具 `devtoolbox`；知识库读固定版本，Skill 只读说明和精确路径的 UTF-8 文本附件，
    不执行脚本；MCP、脚本、业务写操作、子智能体、长期记忆和上下文压缩都不在试用范围，页面上明确显示这些限制；
  - **计量照记，但单独标记**：试用标为 `EVALUATION`，保留调用主体、版本谱系和真实用量，不产生在线实验曝光。
- **受理与回执**：`AgentDraftTrialStore` 在独立事务里先持久受理，**受理成功的那一个**才检查配额并调用模型。
  同一试用标识、相同输入只恢复原回执；内容不同则拒绝。120 秒截止后仍无法确认终态的记录收敛为 `UNKNOWN`，**不自动重放**：
  重放意味着再调一次模型、再花一次钱，而上一次可能已经成功了。
- **主备切换的特殊处理**：首个分片已经输出之后主模型失败，直接判失败，**不切备用模型**。否则用户看到的是
  “主模型的半段 + 备用模型的完整回答”拼在一起。

**追问**：*试用回答得很好，能不能据此直接发布？*
不能。试用只证明“这份配置能跑通、回答看起来对”，不等于质量评测或发布门禁通过。发布仍然走正式保存、评测门禁和 ACK。

**减分回答**：“试用时把 Agent 的 maxIters 调小一点，再加个开关让写工具不执行”。开关漏一处就是真实的退款单。

### Q6 多个标签页同时编辑同一个智能体、保存请求的响应丢了、慢请求的结果晚到——后台怎么保证不互相覆盖？

**考察点**：乐观锁在 Web 表单上的落地；“响应丢失”与“失败”的区别；前端请求的代际。

**参考回答**

- **正式配置用修订号做乐观锁**：编辑页面携带 `X-Agent-Revision`，服务在同一事务里原子地比较并推进修订号，再执行原有的保存链路。
  修订号过期返回 `CONFIG_EDIT_CONFLICT`（30016），不覆盖别人的新内容。老接口不带这个头时保持兼容。
- **个人草稿用“固定 UUID + 期望版本号”**：首次创建 `expectedVersion=0`，之后每次比较当前版本再递增；删除也比较版本，
  防止误删另一个标签页刚保存的修改。
- **响应丢失不等于失败**：写请求超时后，先用同一个 ID 查询，**只有配置内容和关联目标都一致**才确认保存成功；
  确认不了就保留用户输入，不自动重发。直接重发在“其实已经成功”的情况下会制造重复的审计修订。
- **正式保存成功后清理草稿失败**：只提示用户核对，不把已经成功的正式保存再执行一次。
- **前端的迟到响应**：模型 A 的连通性测试很慢，用户已经切到模型 B 并且 B 测试失败，A 的成功结果晚到时会把 B 的失败覆盖掉。
  修复方式是给模型和表单的生命周期加请求序号，旧序号的结果直接丢弃。同一个令牌重新登录、权限变化也会让旧操作的回调失效。

**追问**：*为什么后台读取资源选项时不能用一个 `Promise.all` 一次读完？*
缺少某个资源（比如 MCP）的查看权限时，那一个请求被拒绝会让 `Promise.all` 整体失败，连已经有权限查看的模型选项也一起丢掉。
改成按资源各自读取、各自重试。

**减分回答**：“后端加个 `@Transactional` 就不会互相覆盖了”。事务管的是一次请求内部的原子性，挡不住两次请求之间的“读旧、写新”。

### Q7 “发布检查”页面要告诉运营“当前配置已在线上生效”。这个结论需要满足哪些条件？为什么这么严格？

**考察点**：“已生效”这类结论的证据构成；只读聚合查询的一致性。

**参考回答**

- **必须同时满足**：
  1. 当前正式配置与最近一次发布任务冻结的候选**一致**；
  2. 任务状态是 `APPLIED`；
  3. 任务入队时冻结的**每一个非空目标实例**都回复了确认，而且 ACK 的修订号和内容哈希与候选**精确一致**。
  旧版本、没有目标实例、缺少目标记录的旧任务，一律不显示为“当前全部生效”。
- **只读，不做任何有副作用的动作**：入口要求同时拥有 `agent:view` 和 `eval:view`；
  在同一个数据库快照里聚合正式配置、最新发布任务、评测门禁和 ACK，不发起评测、不做连通性探测、不触发发布。
  渠道关联、任务和 ACK 都显式使用精确的租户条件。
- **为什么这么严格**：这个页面的读者是运营，“已生效”会直接变成他们对客户的承诺。
  只要有一个实例没确认，线上就可能有一部分流量还在跑旧配置。
- **还有一条边界要写给运营看**：比较范围只覆盖发布器实际控制的字段。发布器不控制的能力，不能根据这个页面推断已经在客服端生效。
- **本批修过的一个真问题**：发布渠道表有租户列，但实体没有映射，导致查询混进了其他租户的数据；
  两个只读接口还缺少 `Cache-Control: no-store` 响应头。都是先写失败用例复现，再修复。

**追问**：*`PUBLISHED` 为什么不能显示成“已生效”？*
它只表示 Nacos 接收了配置。实例有没有真的应用成功，要看 ACK 的汇总（见[第 07 期 Q5](07-生产化-多租户限流幂等与一致性.md)）。

**减分回答**：“Nacos 发布接口返回 true 就显示已生效”。

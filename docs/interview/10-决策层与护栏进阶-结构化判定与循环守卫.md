# 第 10 期 · 决策层与护栏进阶：结构化判定、影子模式与循环守卫

> **本期结论**：主模型负责“说什么”，但“要不要转人工”“这条回复是不是在承诺打款”“这组问答能不能缓存”这类判断，
> 交给主模型自己决定并不可靠，写成关键词规则又漏得太多。项目的做法是在 Agent 旁边挂一个**带概率输出的结构化决策层**（Jev），
> 并守住三条纪律：**阈值按误判代价定、外部依赖失败时原样走旧路径、后台影子与线上共用一份判定代码**。
> 本期后两题讲另一类护栏：Agent 转不出来时，怎么让每一种消费方都恰好看到一次“接下来怎么办”。
>
> 对应 JD：Agent 护栏、LLM-as-Judge / 分类器接入、熔断降级、灰度与影子流量、流式输出。题量 7。
> 与[第 05 期](05-安全护栏与治理中间件.md)（中间件顺序与关键词护栏）、[第 06 期 Q4](06-Java并发与响应式流式链路.md)（中间件恰好一个元素）衔接。

### Q1 已经有关键词规则和主模型自己的判断了，为什么还要接一个单独的结构化决策模型？它接在了哪些决策点上？

**考察点**：规则、主模型自判、独立分类器三者各自的短板；决策层与执行层分离。

**参考回答**

- **三种做法的短板**：
  - **关键词规则**：只认字面。“钱应该已经到您卡上了”不含“已到账”，规则拦不住；
  - **主模型自己判断**：转人工完全靠模型决定调不调 `transferToHuman`。用户已经暴怒，模型还在讲政策，链路上没有任何信号；
    而且主模型的判断没有概率输出，没法设阈值、没法统计；
  - **独立分类器**：输出带概率（或置信度），可以按阈值做确定性的动作，也可以离线评估。
- **项目接入的五个决策点**（`JevDecisionService` 统一定义问题文案，阈值在 `TypeSafeProperties`）：

  | 决策点 | 中间件 / 位置 | 动作 |
  |---|---|---|
  | 情绪升级 | `JevEscalationMiddleware` | 最高档且高置信 → 直接建工单转人工；明显不满 → 只提示模型考虑转人工 |
  | 意图 | `JevToolScopeMiddleware` | 高置信时本轮收窄工具面 |
  | 答复闸门 | `SelfCorrectionMiddleware` | 关键词没命中时，用语义判定补拦“声称资金已到账” |
  | 语义缓存写入 | `SemanticCacheService` | 问答只适用于特定用户时不写缓存（排在 Embedding 之前，拒绝时连向量调用也省掉） |
  | 退款风险 | `JevRefundRiskMiddleware` | 高风险时额外拉坐席介入，**不拦截、不改写、不延后退款工具** |

- **一次调用回答两个问题**：情绪和意图在同一次请求里问（官方称为 Speculative Fan-out），结果以 `Mono.cache()` 的形式放进
  `RuntimeContext`。ReAct 循环每迭代一次都会经过中间件，两个决策点并发来取，也只发一次请求，一轮只付一次代价。
- **边界要说清**：退款风险判定只看得到对话文本（用户原话、金额、原因），看不到订单历史、退款频次和账户风险，
  它判的是“文本语义风险”，不是交易风控。退款本来就 100% 生成人工审批单，Jev 不新增任何自动放行路径。

**追问**：*情绪升级为什么分“直接转”和“只提示”两段？*
误判的代价不同。直接转人工占用坐席，还会打断一个本来能自助解决的对话，所以只在最高档、高置信时做；
中间档交给模型结合上下文决定，最终控制权仍在模型手里。

**减分回答**：“让主模型在回复末尾输出一个 JSON 字段 `needHuman: true`”。这仍然是主模型自判，没有概率可用，也会污染用户看到的正文。

### Q2 五个决策点的阈值各不一样：自动转人工 0.85、工具收窄 0.9、答复闸门 0.8、缓存写入 0.3、退款风险 0.6。这些数字是怎么定的？

**考察点**：阈值取决于误判代价的不对称，而不是“越高越准”。

**参考回答**

- **原则**：先问“判错了，哪个方向代价更大”，再决定阈值放在高位还是低位。
- **逐个看**：
  - **工具收窄 0.9（高）**：判错的代价是本轮看不到需要的工具，事办不成；判不准时不收窄，代价只是多花一点 token。
    所以只有非常确定才收窄，判为 `other` 也不收窄；
  - **自动转人工 0.85（高）**：误转会打断对话、占用坐席；中间档另有“只提示”的兜底；
  - **答复闸门 0.8（高）**：误拦的代价是给一条正常回复追加否定澄清并转人工，比较重，取官方建议的高阈值区间；
  - **缓存写入 0.3（低）**：这里的方向反过来了。漏判的代价是把 A 用户的信息返回给 B，远重于少缓存一条。
    所以“只适用于特定用户”的概率**达到 0.3 就不写缓存**；
  - **退款风险 0.6（中）**：漏报的代价是高风险退款静静躺在审批队列里没人管；误报的代价只是坐席多看一眼，取中位。
- **这些值不是终点**：阈值要靠带标签的真实样本校准。项目的后台影子模式（见 Q5）就是为了在不影响线上的前提下，
  积累“线上会怎么判”的数据。

**追问**：*意图的“置信度 0.9”能理解成“90% 的概率判对”吗？*
不能。`Choice` 的 confidence 由概率分布的集中程度计算，**衡量的是一致性，不衡量正确性**。模型可以很一致地判错。
要知道准确率，只能拿带标签的样本去测。

**减分回答**：“统一设 0.8，比较稳妥”。统一阈值等于假设所有决策点误判代价相同，缓存那个点恰好是反方向的。

### Q3 接入 Jev 的情绪打分时，有人按 `score == 最高档` 写了自动转人工，结果上线后一次都没触发。为什么？

**考察点**：读懂第三方返回值的语义；期望值和众数的区别。

**参考回答**

- **原因**：`Score` 返回的 `score` 是**浮点期望值**（各档编号乘以概率再求和，例如 2.95），会落在两档之间，不是整数档位。
  只要最高档的概率不到 100%，期望值就永远小于最高档编号，`score == 最高档` 恒为假。
- **正确做法**：判断“落在哪一档”要看概率分布里**概率最大的档位**，项目里是 `Score#mostLikelyLevel()`。
  自动转人工的条件是：最可能档位是最高档，**并且**置信度不低于 `autoHandoffMinConfidence`（0.85）。
  “提示模型考虑转人工”则用期望值：期望值不低于 2.0（明显不满）且置信度不低于 0.6。两种用法各取所需。
- **另一个容易想当然的地方**：是 / 否类判定（Noul）**没有** confidence 字段，单个概率值就是全部信息。
  照着 Choice 的写法去读 confidence，拿到的是默认值。
- **怎么避免**：这两条都写在 `SystemOneAnswer` 的类注释里，并注明“已对照官方文档核实”。
  接第三方模型服务时，先把返回字段的语义逐个查清，再写判定逻辑。

**追问**：*为什么这个 bug 单测没照出来？*
如果单测的桩直接返回整数 `score = 3.0`，断言当然能过。桩数据要按真实分布来造，例如最高档概率 0.9、次高档 0.1，
期望值就是 2.9，这样才能照出问题。这和“注入 mock 就照不出真实链路”是同一类问题。

**减分回答**：“把判断改成 `score >= 2.5`”。这是用一个拍出来的数去近似分布，没有回答“落在哪一档”这个问题。

### Q4 Jev 是外部服务。它变慢或挂掉时，怎么保证客服对话本身不受影响？

**考察点**：增强能力的失败语义；超时分级；熔断的半开设计；Reactor 空流的陷阱。

**参考回答**

- **传输层契约：永不抛错、永不阻塞**。`SystemOneClient` 规定任何失败（网络、超时、4xx / 5xx、响应非法、熔断打开）
  都表现为 `Mono.empty()`，由实现方记日志和指标。调用方拿到空就原样走旧路径。
  把失败做成“空”而不是异常，调用方就不可能忘记处理。
- **超时分两档**：
  - 安全类决策（转人工、答复闸门、退款风险）3000 ms：宁可多等一会儿，也要本轮生效；
  - 优化类决策（只开了工具收窄时）1200 ms：超时就按“无决策”走原路径，不拖慢对话。
- **必须有熔断**：超时只能保证单次调用不会无限等待，保证不了“Jev 挂掉时对话照样快”。
  没有熔断的话，每一轮对话都要干等满一个超时才降级，用户感知到的是整个客服变慢了。
  `JevCircuitBreaker` 连续失败 5 次打开，30 秒后进入半开。
- **半开只放一个试探**：窗口过后如果放行所有请求，高并发下会有一大批请求同时撞上超时。
  只让抢到 CAS 的那一个去试探，其余继续跳过，试探成功才整体恢复。
  **每个被放行的请求都必须以 `onSuccess`、`onFailure` 或 `onAbandoned` 之一收尾**，
  否则半开态的试探名额会被永久占住，Jev 再也用不上。`onAbandoned` 对应的就是请求被取消（用户断开）的情况。
- **中间件侧**：判定链路必须恰好产出一个元素。空流会让下游永不调用（整轮无回复），
  用 `switchIfEmpty(next)` 兜底又会在下游返回空流时让 Agent 执行两遍。详见第 06 期 Q4。
- **开关的 fast fail**：`customer-work.typesafe.enabled` 默认关；开启时必须配置 API Key，缺失则启动失败，
  不静默降级成“开着开关但从不生效”。

**追问**：*为什么是“连续失败 5 次”而不是按错误率？*
决策调用量随对话量波动，低峰期按错误率统计样本太少、容易抖动。连续失败计数实现简单、语义直观，对“整体不可用”这种场景足够。
如果将来需要识别“部分失败”，再换成滑动窗口错误率。

**减分回答**：“Jev 调用失败就抛异常，由全局异常处理器返回友好提示”。增强能力的故障变成了主链路的故障。

### Q5 运营想在后台看到“同一句话，线上 Jev 会怎么判、会做什么”，但又不能影响线上。影子模式怎么设计？怎么保证决策事件不会漏给 C 端用户？

**考察点**：影子流量的“只判不做”；把“执行动作”和“展示决策”拆成两个维度；从源头消灭泄露面。

**参考回答**

- **两个独立维度**：判定之后“执不执行动作”和“要不要把决策发成可展示的事件”是两件事。`JevRunMode` 把它们组合成三种模式：

  | 模式 | 执行动作 | 发出决策事件 | 用在哪里 |
  |---|---|---|---|
  | `LIVE` | 是 | 否 | C 端线上 |
  | `SHADOW` | 否 | 是 | 后台影子 |
  | `LIVE_TRACED` | 是 | 是 | 后台真实执行 |

- **影子模式不改变模型看到的任何内容**：`SHADOW` 下不建工单、不注入提示、不收窄工具，只展示“线上会怎么做”。
  否则后台看到的回复已经被影子判定影响过，与线上不再可比。
- **后台与线上共用同一份代码**：问题文案、阈值、判定逻辑都在 `JevDecisionService` 和决策对象（`TurnDecision`、`NoulVerdict`）里，
  后台只是换一个运行模式。两边各写一份等价逻辑，迟早会出现“后台看到的和线上不一样”。
- **防泄露：从源头就不产生**。决策事件（`CustomEvent`）是内部实现细节，绝不能出现在用户看得到的事件流里。
  项目没有在 WS、流式、AG-UI、渠道等每个 C 端出口逐个过滤，而是让 starter 自动装配给 C 端的中间件实例**一律是 `LIVE`**，
  只有后台显式构建的实例才会发事件。出口有好几个，逐个过滤迟早漏一个；源头不产生，就没有什么可漏。
- **admin 与客服端读同一组配置键**：影子判定要与线上一致，阈值也必须一致。

**追问**：*为什么影子模式适合用来校准 Q2 里的阈值？*
它能在真实对话上拿到“判定结果 + 概率”，运营再对这些对话做人工标注，就能画出不同阈值下的误判与漏判，
而这个过程对线上零影响。

**减分回答**：“给决策事件加一个 `internal` 标记，前端收到就不显示”。数据已经发到了客户端，抓包就能看到。

### Q6 按意图收窄工具面，为什么改的是本次推理的 `ReasoningInput.tools()`，而不是 Toolkit 的激活组？哪些工具永远不能被收掉？

**考察点**：瞬态修改与持久状态的区别；框架状态覆盖机制；“把用户困住”的底线。

**参考回答**

- **为什么要收窄**：工具 schema 约占上下文预算的一半（`ToolSurfaceCostTest` 固定了这个数字），而且这笔钱**每一轮**都要付。
  此前否决“按意图动态激活”的理由是：意图分类没有置信度，判不准时没法兜底。Jev 的 Choice 自带置信度，这个理由不再成立。
- **为什么不改激活组**：框架会用会话状态里的 `activatedGroups` **全量覆盖** Toolkit 的激活组（见 `DefaultActiveGroupsToolkit`）。
  在这里改激活组，收窄结果会被持久化进会话，下一轮继续生效。项目踩过这个坑：业务工具组被整体清空。
- **`ReasoningInput.tools()` 只决定本次模型调用看得到哪些工具**，不写回任何状态。
  工具本身仍在 Toolkit 里，模型凭历史记录发起调用也照样能执行，不会失败。
- **永远保留的三类工具**：
  1. 当前意图映射到的业务组；
  2. **转人工组**：把它收掉，等于把用户困在智能体里出不来；
  3. 未分组的基础工具，例如 Harness 自带的文件与计划工具。
- **原样透传的情况**：拿不到 Toolkit、收窄后为空、没有任何工具被收掉、置信度低于门槛或者判为 `other`。

**追问**：*项目里还有一个配置层面的“停用工具组”，它和这里的收窄是什么关系？*
静态停用是运维明确知道“我们没有这块业务”，零判错风险；动态收窄是按轮、按置信度的优化。
两者都遵守同一条底线：**转人工组不能被停用**。静态配置里如果有人要停用它，代码直接拒绝并打错误日志，而不是靠文档提醒。

**减分回答**：“意图分类后调用 `toolkit.setActiveGroups(...)` 就行”。下一轮用户换了话题，工具已经没了。

### Q7 Agent 轮次耗尽时，框架会让模型写一段收尾回复。项目要在它后面补一句“已为您转接人工”。怎么保证 WS、SSE、同步接口、AG-UI 的用户都**恰好**看到一次？

**考察点**：流式事件的生命周期；“只改最终结果”在流式路径上的假性生效；改写消息时不要丢元数据。

**参考回答**

- **背景**：`LoopGuardMiddleware` 补的两个洞是：迭代耗尽事件（`ExceedMaxItersEvent`）此前全仓零消费；
  以及没有任何死循环征兆检测（同一工具同样参数重复调用）。耗尽时它记指标、审计，默认自动转人工（`handoffOnExhausted = true`），
  并补一句去向说明。难点在“补”这一步。
- **消费方分两类，各看各的事件**：
  - 流式消费方（WS、SSE、复用流式内核的同步接口、AG-UI）只推 `TextBlockDeltaEvent`，拿到过正文就不再看最终结果；
  - 只读最终结果的消费方（`call()`：IM 渠道、评测、多专家编排）只看 `AgentResultEvent`。
  **只改 `AgentResultEvent` 在第一类上是假性生效**：框架的收尾回复本身就是逐片流式发出的。
- **项目的做法：两处都补，各自恰好一次**：
  1. **流式侧，补在收尾文本块结束之前**：收到 `TextBlockEndEvent` 时，先发一个同 replyId、同 blockId 的增量，再放行块结束事件；
  2. **结果侧，追加到最终消息上**：追加而不是替换，收尾里可能有对用户有用的中间结论。
- **为什么必须在块结束之前**（变异测试实证过）：
  - 块结束后再往同一块追加，真实的 AG-UI 适配器会发出“已结束消息”的 `TEXT_MESSAGE_CONTENT`；
  - 另起一个新块，`AguiService` 落库只取最后一条消息，历史里只剩说明、丢了收尾正文；
  - 外层 `SensitiveWordMiddleware` 按块缓冲，块结束才放行尾巴，块外的增量等不到下一次放行。
- **两个边界情况**：
  - 收尾模型中途失败：框架发了块开始和部分正文，却不会再发块结束。说明补进这个**悬空的块**并替它结束；
    另起新块会让悬空的块永远不结束；
  - 一个正文增量都没出过：流式消费方会用最终结果补全文，说明已经在里面了，不再单独补。
- **改写最终消息不要重建**：框架把 `MAX_ITERATIONS` 等结束原因写在消息元数据里，用 `Msg.builder()` 重建会静默退回 `MODEL_STOP`，
  外层 `ChatTerminalCapture` 填的终止信封和 H5 的“答复尚未完成”状态都会跟着错。只换内容，用 `Msg#withContent`。
- **验证方式**：`LoopGuardRealAgentStreamTest` 用真实 Agent 的事件流断言，而不是只断言 `AgentResultEvent`。

**追问**

1. *重复调用检测为什么按“工具名 + 参数”计数，而且只在恰好达到阈值（默认 3）时告警一次？*
   同一个工具用不同参数连查五个订单是正常业务，只按工具名计数会误报，误报几次之后这个指标就没人看了。
   阈值取 3 而不是 2：模型偶尔因为没读懂工具结果重试一次，是正常的自我修正。超过阈值后每轮都报会把日志刷成噪音。
2. *守卫自身出异常怎么办？*
   fail-open，原样放行事件。它的定位是观测与兜底，不是闸门。
3. *项目里还有哪个中间件没完全按这个标准做？*
   `SelfCorrectionMiddleware` 的 Jev 路径仍是“块结束后补增量”的写法，已记录待另行处理。能主动说出存量缺口，比说“全都修好了”更可信。

**减分回答**：“在 `AgentResultEvent` 里把正文替换成收尾加说明”。流式用户看不到，还可能抹掉结束原因。

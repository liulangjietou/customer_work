# 第 11 期 · 账号安全与对外开放部署

> **本期结论**：把后台从内网开放给公网陌生人，要回答的不是“加几个验证码”，而是四个问题：
> **这个邮箱是不是他的、这个匿名接口会不会变成查询服务、限流拿的 IP 是不是真的、租户管理员拿到的权限会不会越出自己的租户**。
> 项目的共同做法是：安全项不做成可以漏配的开关；判定顺序本身就是安全设计的一部分；残留的风险如实写出来。
> 面试时间有限时可以只挑 Q3、Q5、Q6 三道。
>
> 对应 JD：Spring Security / Sa-Token、认证授权、账号安全、防刷与反枚举、SaaS 权限模型、安全合规。题量 7。
> 与[第 07 期 Q7](07-生产化-多租户限流幂等与一致性.md)（数据权限）、[进阶第 07 期](advanced/07-身份授权合规与治理.md)（身份授权通论）衔接。

### Q1 自助注册为什么强制邮箱验证码，而且连关闭的开关都没有？两道验证码（图形码、邮箱码）分别放在哪一步？

**考察点**：“填了邮箱”和“拥有邮箱”的区别；安全项做成开关的风险；验证码放在副作用发生的地方。

**参考回答**

- **为什么必须验证**：只“填了邮箱”不等于“这个邮箱是他的”。不验证的话，审核结果和后续的密码重置都会发到别人手里。
- **为什么删掉开关**：此前由 `email-required` 和 `email-verification.enabled` 两个默认为 false 的开关控制，只在对外部署下强制。
  这等于把“注册者是否真的拥有那个邮箱”做成了一件可以漏配的事，而漏配不报错。
  现在两个开关都删了，`RegistrationGuard#admit` 无条件核验邮箱验证码；`register-options` 接口也不再返回这两个布尔值。
  返回一个恒为 true 的布尔，等于告诉前端“它可能为假”，后来的人会照着写死分支。
- **代价要一起接受**：自助注册开着时 SMTP 必须可用。`AdminProductionReadinessValidator` 只要看到 `self-service-enabled` 就强制校验邮件配置。
  不想配 SMTP 的实例应该关掉自助注册、由管理员预建账号，而不是关掉验证。
- **两道验证码各在各的位置，不是叠加**：
  - **图形码在“发码”那一步**（`POST /api/auth/email-code`）：服务端替匿名调用者给任意地址发一封信，
    这是唯一会向站外第三方产生副作用的匿名操作，最该先挡住脚本；
  - **邮箱码在“注册”那一步**：手里这份邮箱码已经证明申请人控制着那个邮箱，比图形码强得多，注册时再要一次图形码只是多一个输入框。

**追问**：*`admit` 里的判定顺序是怎样的？为什么？*
分两段：先做无副作用的表单校验（两次密码一致 → 密码强度 → 邮箱必填），再做有副作用的防滥用判定（IP 限流 → 邮箱验证码核验）。
- 表单校验排前面：真人填错一次不该白扣一次注册额度（默认每小时 5 次）；
- **限流排在验证码核验之前**：核验失败会累加一次失败计数，达到上限（默认 5 次）验证码作废。
  如果先核验，攻击者密集试码就能把受害者手里那份有效的验证码提前耗到作废。

**减分回答**：“邮箱验证做成可配置项，内网部署可以关掉”。

### Q2 发送邮箱验证码的匿名接口有四道防线。每一道分别挡的是哪种打法？验证码本身有哪些实现细节？

**考察点**：限流维度与攻击模型一一对应；验证码生命周期的边界处理。

**参考回答**

- **四道防线**：

  | 防线 | 默认值 | 挡的打法 |
  |---|---|---|
  | 图形验证码 | 发码前校验 | 脚本批量调用 |
  | 单 IP 限流 | 窗口内 10 次 | 一个来源换着邮箱轰炸 |
  | 单邮箱冷却 | 60 秒 | 对同一个受害者高频轰炸 |
  | 单邮箱日总量 | 每天 10 封 | “每 60 秒一封、发一整天”（冷却对它完全无效） |

- **验证码签发接口本身也要限流**：`/api/auth/captcha` 是免登录接口，每次调用都要画一张图、写一次 Redis。
  它单独计数（默认每窗口 30 次），不和注册共用一个桶，否则真人换几张图就把注册额度用光了。
- **验证码的四个实现细节**：
  1. **输错不立即作废，但有次数上限**（默认 5 次）：错一位就要重新收信，而每次重发都是一封真实的外部邮件；
     但 6 位数字不限次数是可以直接猜穿的；
  2. **失败计数写回时保持原过期时刻**：否则不断试错就能让验证码永不过期；
  3. **发信失败要清掉刚写入的码**：留着就是一份死码。用户拿不到，下一次重发又被冷却挡住，等于把这个邮箱锁死一个冷却周期；
  4. **通过即销毁**：同一份码不能注册两个账号。
- **发码前先查邮箱是否已被占用**，否则那封信已经发到别人邮箱里了。
- **邮件出口统一**：`AdminMailSender` 一律抛异常，吞不吞由调用方决定。审核通知是旁路，可以吞；验证码发不出去必须让用户当场看到失败。

**追问**：*注册验证码和找回密码验证码能不能共用一个存储键？*
不能。项目用 `EmailCodePurpose` 按用途分键。共用的话两种码可以互相顶替：注册码是任何人对着一个未注册邮箱都能索取的，
拿它去重置同一邮箱下账号的密码就成立了。**但限流键刻意不分用途**：IP 限流、单邮箱冷却和日总量保护的是“收件人不被轰炸”，
与发的是哪种码无关。按用途各给一份，攻击者交替调用两个接口，对同一个受害者的发信量就翻倍了。

**减分回答**：“加个图形验证码就够了”。图形码可以被打码平台绕过，只有一道防线等于没有分层。

### Q3 找回密码是一个匿名接口。怎么防止它被用来探测“某人是不是这里的用户、他的邮箱是不是这个”？

**考察点**：账号枚举的多种侧信道；响应、限流、错误码、副作用四个层面都要含糊；如实说出残留风险。

**参考回答**

- **与注册接口刻意相反**：注册重名时明确提示“用户名已存在”，这是注册页的可用性底线，批量枚举由 IP 限流兜住；
  找回密码则无论邮箱没注册、用户名与邮箱对不上、还是账号根本不能重置，**返回值都完全一样**（都返回验证码有效期）。
- **含糊要贯穿整条链路**，`PasswordResetService` 做了三处：
  1. **先扣额度，再查账号**：`sendCode` 的顺序是图形码 → 扣发信额度 → 查账号 → 发信。
     如果先查账号再扣额度，“有没有被限流”本身就成了存在性探针，文案再含糊也白写。
     为此把 `EmailVerificationService#sendCode` 拆成了 `reserveSendQuota` 和 `issueAndSend` 两步；
  2. **重置时三种失败合并成一个错误码**：账号对不上、验证码错、验证码过期都返回 `PASSWORD_RESET_REJECTED`（30015），连文案都一样；
  3. **不能重置的账号改发一封说明信**：OA 域账号、已禁用账号不在响应里说明原因，而是发信说明。信只有邮箱的主人收得到，响应则是谁问谁得。
- **另外三条细节**：
  - **账号匹配判定排在验证码核验之前**：否则任何人拿一个错的用户名反复提交，就能把受害者手里那份真码的重试次数耗光；
  - **图形码无条件校验**，不看部署形态：注册在内网可以省掉图形码（要过审核、建出来的号没有权限），这里对着的却是一个已存在、多半已获授权的账号；
  - **不对不上的请求也不记用户名和邮箱**：这行日志正是攻击者拿不到、运维也不需要的信息。
- **凭证用验证码而不是重置链接**：“点此重置密码”是钓鱼邮件最常模仿的形态；链接需要一个可靠的对外基础 URL，多域名或反向代理下极易配错，
  配错就是把凭据发向错误的域名；企业邮件安全网关还会预取链接，把一次性 token 静默消费掉。
- **残留的风险要如实说**：当前实现里，匹配成功的账号会**同步**调用 SMTP 发信，匹配失败的请求直接返回。
  两者的**响应时间**有明显差异，理论上可以用计时侧信道区分。修法是把发信改成异步投递（或让所有分支走相同的排队路径），
  让响应时间与账号是否存在无关。能指出这一点，说明候选人理解的是“枚举防护的目标”，而不只是“把文案写成一样”。

**追问**：*重置成功之后还要做哪些事？*
与 `AuthService#changePassword` 逐条一致：递增 `auth_epoch`、撤销既有会话、清零该“账号 + 来源 IP”的登录失败计数，并记操作日志。
**只改密码列、不撤会话**，意味着已经登进去的那个人照旧待在里面，而“怀疑号被盗”恰恰是重置密码最常见的动机。
另外顺带把 `email_verified` 置 1：能收到验证码并填回来，本身就是一次邮箱所有权证明。
这个接口跑在匿名请求里，写库必须自带 `TenantContext.runWith`，否则 `sys_user` 的租户行过滤会直接失败。

**减分回答**：“邮箱不存在时提示‘该邮箱未注册’，用户体验更好”。

### Q4 登录失败锁定，锁的是账号、IP，还是别的维度？被锁期间用户继续尝试怎么处理？

**考察点**：防爆破措施本身被用来做拒绝服务；计数的边界行为。

**参考回答**

- **锁“账号 + 来源 IP”的组合**（`LoginAttemptGuard`，默认 15 分钟内失败 5 次锁定）：
  - 只锁账号：任何人拿一个已知用户名连打几次，就能把真实用户挡在门外，防爆破变成了拒绝服务；
  - 只锁 IP：挡不住分布式撞库，即每个 IP 只试少数几个账号的打法；
  - 组合锁定对两者都有效。代价是同一个 NAT 出口下的多个用户会互相影响，这在对外部署里可以接受。
- **被锁期间只读、不累加**：否则攻击者持续尝试会把锁定期无限延长。
- **成功即清零**：窗口内失败四次、第五次成功的正常用户，不该带着计数继续用；否则他下次偶尔输错一次就被锁。
- **登录侧不区分“账号不存在”和“密码错误”**，统一提示。
- **开关语义**：锁定在内网部署可配；对外部署下强制启用，不看配置项。
  把公网实例的锁定配成关，不应该是一个能配错的选项。

**追问**：*组合锁定挡不住“一个 IP 对一个账号每 15 分钟试 4 次”这种慢速爆破吗？*
单靠它挡不住，要靠纵深：密码强度策略（`PasswordPolicy`）让慢速爆破在有限时间内不可能成功；
登录滑块验证码提高每次尝试的成本；异常登录要有审计和告警。任何单一措施都不是完整的防护。

**减分回答**：“连续输错 5 次锁账号 30 分钟”。

### Q5 限流、验证码绑定、登录锁定都要拿“来源 IP”。服务部署在反向代理后面，IP 从哪里取？`X-Forwarded-For` 能直接用吗？

**考察点**：转发头可以伪造；可信代理链的解析方向；默认值的安全取向。

**参考回答**

- **不能直接用**：转发头由客户端控制。直接取 `X-Forwarded-For` 的第一个值，攻击者每个请求换一个伪造值，
  所有基于 IP 的限流和锁定全部失效。
- **`ClientIpResolver` 的规则**：
  1. **默认不信任转发头**（`trust-forwarded-header = false`），直接取 TCP 连接的对端地址；
  2. 只有**直接连接方命中显式配置的可信代理 CIDR** 时，才读取转发头；
  3. `X-Forwarded-For` 的排列是“客户端, 代理1, 代理2”，所以**从右向左**剥离可信代理，取第一个不可信的地址。
     伪造在最左侧的地址不会被采信；
  4. 任何格式异常、过长、跳数过多，或者整条链都是可信代理时，一律回退到直接连接地址；
  5. IP 与 CIDR 只接受字面量，不做 DNS 查询：DNS 查询既慢，又可能被用来做 DNS 重绑定。
- **为什么是从右向左**：最右边的一跳是离服务最近的代理追加的，只有它可信；越往左越可能是客户端自己写进去的。

**追问**：*K8s 里 Ingress 前面还有云厂商的负载均衡，可信 CIDR 应该配什么？*
配所有会追加转发头的那几层代理的网段（负载均衡出口网段、Ingress Pod 网段）。配少了会把代理地址当成客户端，所有用户共享一个限流桶；
配多了（比如 `0.0.0.0/0`）就退化成“完全信任转发头”。

**减分回答**：“取 `X-Real-IP`，没有就取 `X-Forwarded-For` 的第一个”。

### Q6 后台要开放给公网陌生人自助注册。租户管理员的权限边界怎么划？还有哪些东西必须一起改？

**考察点**：控制面权限的判定标准；多个安全判定的交集；拦截器顺序；租户隔离模型的适用前提。

**参考回答**

- **一个总开关**：`admin.public-deployment.enabled=true` 一次生效三件事：内部运维工具下架（菜单不下发、接口 403）、
  发码强制图形验证码、审核不允许并入 `default` 租户。不逐项勾选，漏配任何一条都是实打实的暴露面。
- **权限边界只有一处定义**：`ControlPlanePermissions`。判定标准是“**租户管理员拿到它，影响面会不会越出自己的租户**”，
  不是菜单挂在哪一级。三类必须收归控制面：
  1. **操作的表不参与租户过滤**：`ai_model_config` 在租户忽略清单里，全平台只有一份，授出去等于让任何一个租户改删所有租户在用的模型配置；
  2. **能把代码或流量带出本进程**：MCP 可以挂任意外部服务端，Skill 包含代码执行，HTTP 工具是现成的 SSRF 面，SQL 客户端能跑任意语句；
  3. **视野是全平台而非本租户**：计费、SLO、死信队列、敏感词库与命中记录、限流规则、编码审计。
  `ControlPlanePermissionsTest` 对此下断言；Controller 仍须叠加 `CrossTenantAuthority`，不能把角色授权配置当成唯一的安全边界。
- **内部工具是两个判定的交集**：“控制面专属”与“对外下架”必须同时成立。只判前者，对外实例上超管仍看得到 SQL 客户端菜单（点进去必然 403）；
  只判后者，内网实例的租户管理员会拿到能跑任意 SQL 的权限。菜单过滤和接口拦截共用 `internalToolFamilies()` 一份清单。
- **拦截器顺序**：`InternalToolGuardInterceptor` 必须排在 Sa-Token 之前（`HIGHEST_PRECEDENCE`）。
  `/api/workbench/agent/**` 是免登录接口（ScriptCat 回调走 `X-Workbench-Token`），排在登录校验之后就永远轮不到它，
  而那恰恰是对外实例上最该堵的一条。
- **注册者不能落进 `default` 租户**：数据权限的 SELF 过滤只覆盖少数“个人产出物”表，智能体、知识库、Skill、MCP、字典、敏感词等
  都是租户内共享的，`sys_user` 也不在白名单里。所以“统一放进一个租户、靠 SELF 隔离”在公网场景下不成立。
  审核必须走“新开租户”路径，复用 `TenantService#create`（内部已包含开通流程）；新租户的角色 ID 由服务端从 `tenant_admin` 反查。
- **存量库的越权授权**由后台迁移 V101 回收：只动 `control_plane=0` 的角色，幂等，空库无操作。

**追问**：*收权限的那次改动打红了两个既有测试，是回归吗？*
不是。那两个测试拿 `billing:view` 当“租户可授予”的样本，它被收归控制面后测试失败，恰恰说明代码判定与 V101 迁移一致地生效了。
处理方式是把其中一个测试的断言反过来写成“V101 应该回收它”。

**减分回答**：“给租户管理员角色少勾几个菜单就行”。菜单不是安全边界，接口和数据才是。

### Q7 后台登录态从内存改存 Redis 之后，Redis 挂了会怎样？为什么不像聊天历史缓存那样退化到别的存储？

**考察点**：鉴权与缓存的失败语义相反；开关与生产基线校验的配合。

**参考回答**

- **为什么改存 Redis**：Sa-Token 默认把登录态放在进程内的 Map 里，服务一重启全部用户被踢下线；多实例部署时各实例也互不认对方签发的 token。
  `AdminSaTokenDaoConfig` 把 token 和 SaSession 换到 Redis，过期交给 Redis 的 TTL（`sa-token.timeout` 默认 24 小时绝对过期，不按活跃续期）。
- **Redis 不可达时 fail-closed**：校验登录态直接抛异常，请求失败。这是登录态该有的安全语义：
  鉴权数据取不到，就不能认定“他已登录”。
- **与缓存旁路刻意相反**：`ChatHistoryCache` 连不上 Redis 就退化为直读 MySQL，因为缓存丢了数据还在，读库结果一样正确。
  登录态没有第二份权威数据，“退化”只能是“放行”或者“另起一套会话”，前者是安全事故，后者会让所有人的登录态不一致。
- **开关只是非生产环境的应急手段**：把 `admin.sa-token.redis-persistent` 置为 false 可以临时退回内存态，
  代价是重启即全员掉线、多实例互不认 token。但 `prod` profile 下的 `AdminProductionReadinessValidator` 要求它必须为 true，
  否则应用拒绝启动。也就是说，**生产上不允许用“关掉 Redis 登录态”来换可用性**，生产的可用性要靠 Redis 自身的高可用（主从 + 哨兵或集群）来保证。

**追问**

1. *项目里还有哪些“Redis 故障时降级到进程内”的做法？为什么它们可以？*
   限流计数和会话串行锁。这两类是保护性能力，降级到进程内之后保护依然存在（只是从全局变成单实例），**不会变成放行**。
   判断标准是：降级之后，安全性是变弱了还是消失了。变弱可以自动降级，消失就必须 fail-closed。
2. *既然生产禁止关掉，为什么还保留这个开关？*
   本地开发和单实例演示不一定有 Redis。开关服务于这些场景，生产门禁保证它不会被带到线上。
   这是“开关 + 生产基线校验”的常见组合：开关给灵活性，门禁给底线。

**减分回答**：“Redis 挂了就先放行，保证可用性”。

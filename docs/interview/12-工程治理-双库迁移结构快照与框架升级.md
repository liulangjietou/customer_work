### Q1 项目有两个库（客服端库、后台库），每个库都有好几条建库路径。schema 是怎么演进的？怎么保证各条路径建出来的库一样？

**考察点**：迁移的唯一真源；已部署迁移不可修改；存量库的“接管版本”判定。

**参考回答**

- **四条建库路径**：Flyway 迁移、`mysql/01` 客服端完整镜像、`mysql/02` 后台迁移镜像（供手工初始化和 CI 建库）、增量 alter 脚本。
  **真源永远是迁移**，其它都是它的副本，必须同步。
- **已部署的迁移禁止修改**，连改注释都不行：Flyway 会校验 checksum，改过的文件会让已执行过它的库拒绝启动。
  要改列注释，就在新迁移里 `ALTER TABLE ... MODIFY COLUMN`。新结构一律新建下一个版本。
- **客服端库由 `CustomerWorkSchemaMigrator` 统一升级**：空库逐版执行全部迁移；早期由旧的 `SchemaInitializer` 或完整镜像建出来的
  非空库，先**按实际结构判定接管版本**（`resolveBaselineVersion`），再补跑后续迁移。
- **纯数据迁移的坑**：接管判定只认结构。只 INSERT、不改结构的纯种子迁移没有结构痕迹，判定不出来就会重跑：
  - **幂等的**（如归一化 UPDATE）可以不补判定，让完整镜像库重跑一次，代价只是多一行历史；
  - **不幂等的**（如 INSERT）必须在 `resolveBaselineVersion` 里补一条**数据判定**，否则重跑撞唯一键直接失败。
  排序规则迁移同理：它也没有结构痕迹，只能拿排序规则本身当判定信号。
- **后台访问客服端库也要过迁移门禁**：后台排除了 starter 的自动装配，必须通过 `CustomerWorkFacade` 在首次访问前执行客服端迁移，
  不能把缺表缺列拖成业务 SQL 的 `Unknown column`。迁移失败不缓存门面，下次访问原样重试。
- **生产由 DBA 执行**：生产 profile 关闭自动迁移（`schema-migration-enabled=false`），DBA 按手工升级 SQL 执行。

**追问**：*加了一张表，`CustomerWorkSchemaMigrationIntegrationTest` 红了，是回归吗？*
不是。它硬编码了“空库迁移后应有 N 张表”和空库、旧库、镜像三种情况下的迁移历史行数。加表、加迁移必然要同步更新这些断言，
这是预期内的断言更新。

**减分回答**：“开发环境用 `ddl-auto=update`，生产手工对一下表结构”。

### Q2 多个分支并行开发，Flyway 版本号经常撞车。项目踩过哪些坑？版本号进入三位数之后又出了什么问题？

**考察点**：共享开发库上的版本号冲突；Flyway 的 future / missing 语义；字典序与版本序。

**参考回答**

- **撞号**：本机开发库是所有分支共用的。一个分支刚 apply 了 V56，另一个分支也写了 V56，启动时 checksum 不一致直接失败。
  约定：新增迁移前先查 `SELECT MAX(version) FROM flyway_schema_history`，并扫一遍各工作树的最大版本号，而不是只看当前分支的文件名。
- **future 突变成 missing**：Flyway 默认忽略“版本号高于本地最高版本”的库内记录（future）。一旦本地分支的版本号超过它们，
  那些记录就从 future 变成 missing，拒绝启动。dev profile 配了 `ignore-migration-patterns: "*:missing"` 容忍切分支的场景，
  **生产 profile 刻意不配**：生产上出现 missing 说明有人跳过或删掉了迁移，必须停下来。
- **本机库被污染时**：用临时库验证自己的迁移和上下文加载，不去动共享库的 history。
- **三位数之后，字典序不再等于版本序**：`mysql/02` 镜像文件名形如 `<版本号>-V<版本号>__xxx.sql`，
  shell glob 和 `ls` 给出的是 `..., 10-V10, 100-V100, 101-V101, 11-V11, ...`，V100、V101 跑在 V11 之前。后果分两种，后一种更阴险：
  - V101 直接报 `Unknown column`，因为它依赖的列 V63 才加；
  - **V100 逐表守卫、表不存在就跳过，于是静默什么都没做**，建出来的库排序规则始终没对齐，而且不报错。
  修复：一律走 `scripts/apply-admin-schema-mirror.sh`（内部用 `sort -V`），CI 也改用它，禁止再写 `for f in *.sql`。
- **漏同步镜像的教训**：后台早期有 7 个迁移没同步到 `mysql/02`，本地走 Flyway 不受影响，CI 从空库灌脚本时在依赖它们的后续脚本上炸掉，
  main 连红了 6 次。

**追问**：*除了 `sort -V`，还有什么办法根治文件名排序问题？*
文件名里的版本号补零到固定位数（例如 `0100`）也能让字典序等于版本序，但已经存在的文件改名会影响历史记录和引用。
用版本号排序是改动最小、不破坏存量的做法。

**减分回答**：“版本号冲突了就把自己的改成下一个号重跑”。这只解决了自己，没解决共享库里已经留下的那条记录。

### Q3 项目把两个库的“结构快照”提交进仓库，并在每次测试时比对。这个快照怎么生成？做门禁时踩过哪些坑？

**考察点**：生成物与真源的等价性；可复现性的正确验证方式；比较的口径。

**参考回答**

- **是什么**：`mysql/schema-snapshot/` 下两份 SQL，回答“这两个库现在长什么样”。它**由迁移产物生成**，手工改它对任何库都不生效。
- **生成源必须是临时空库跑完迁移的产物**，不能 dump 开发机的长期业务库。本机库被并行分支的迁移反复试跑过，
  沉积下来的结构与迁移产物无法区分，直接 dump 等于把污染固化进快照。
- **门禁与生成共用一段逻辑**（`SchemaSnapshotExporter`）：`CustomerWorkSchemaSnapshotTest` 和 `CustomerAdminSchemaSnapshotTest`
  每次都重新迁移一个临时库再比对，不一致时指出是哪张表的第几行。不会出现“脚本生成的和门禁期望的不是一回事”。
- **后台快照还带系统种子数据**（菜单权限树、角色、默认租户、admin 账号等），执行完就是一个能直接登录的库。
  此前它号称能全新建库，建出来却是谁也登不进去的空壳。**导哪些行不由人工清单决定，照实导出迁移产物里的全部数据行**，
  挑子集会让快照与迁移产物不再等价。
- **踩过的三个坑**：
  1. **时间列**：种子表的 `create_time` / `update_time` 都是“迁移执行那一秒”。写死进 INSERT，门禁**每跑必红**，
     而且红的原因与任何人的改动无关，几次之后就没人信这道门禁了。所以导出时跳过 `DEFAULT_GENERATED` 的 `CURRENT_TIMESTAMP` 列；
  2. **验证“可复现”必须建两个独立的库**：同一个库连导两次，时间列取的是同一次迁移的时刻，结果当然一样，那是恒真断言。
     靠变异测试（故意不跳过时间列）才发现它照不出问题，改成两次独立建库后，同一个变异立刻变红；
  3. **差异定位**：只认 `CREATE TABLE` 来定位表名，会把种子段的差异全归到最后一张表上（实测报成 `workbench_token`，
     实际差在 `ai_model_price`）。指着一张不相干的表报错比不报表名更误导。
- **比较两条建库路径时用 `information_schema`，不要 diff `SHOW CREATE TABLE` 文本**：只写 `COLLATE` 不写 `CHARACTER SET` 的列，
  建库后 MySQL 会回吐 `CHARACTER SET utf8mb4`。这只是显示形态，结构其实等价。

**追问**：*用快照建出来的库，应用能直接用 dev profile 启动吗？*
不能。快照建的库没有 `flyway_schema_history`，dev profile 会从 V1 重跑，撞上已存在的表。要以关闭 Flyway 的方式启动（生产 profile 本来就关闭）。

**减分回答**：“用 mysqldump 导一份放仓库里，有变化就手工更新”。

### Q4 线上 JOIN 两张表时报 `1267 Illegal mix of collations`。根因是什么？项目是怎么全量治理的？

**考察点**：MySQL 8 排序规则的继承规则；DDL 的锁行为；迁移的逐表守卫与收尾自检。

**参考回答**

- **根因**：MySQL 8 里，建表语句写了 `DEFAULT CHARSET=utf8mb4` 却不写 `COLLATE`，用的是**字符集的默认排序规则** `utf8mb4_0900_ai_ci`，
  **不是**建库时 `CREATE DATABASE` 指定的规则。只有连 CHARSET 都不写，才继承库的设置。漏写不报任何错，直到某天两张表 JOIN 字符串列时才炸。
- **复发过四次**：两次各 ALTER 一张涉事表；一次在 Mapper 里用 `COLLATE` 字面量绕过；一次用 `CAST(x AS BINARY)` 绕过，
  **代价是 `session_id` 上的索引失效**。都是局部补丁。
- **更深的问题**：迁移写 `DEFAULT CHARSET=utf8mb4`，完整镜像写 `COLLATE utf8mb4_unicode_ci`，同一张表两条路径建出来不一样。
  37 张客服端表的排序规则取决于这个库当初是怎么建的，本机开发库实测就是混合的。
- **全量治理**（客服端 V22、后台 V100）：
  1. **逐表守卫**：已经是目标规则的表跳过。实测 `ALTER ... CONVERT TO` 没有在线选项：`ALGORITHM=INPLACE` 报 1846，
     `ALGORITHM=COPY, LOCK=NONE` 也报 1846，也就是全表重建加 `LOCK=SHARED`（读不阻塞、写阻塞）。无条件 ALTER 等于把每张表都重建一遍，
     包括最不该在业务时间重建的高写入表；高写入表在迁移开头逐张标注，大数据量时走停写窗口或 gh-ost；
  2. **收尾自检**：迁移末尾查一遍 `information_schema`，仍有残留就 `SELECT * FROM __xxx_not_aligned__`，故意引用一张不存在的表让迁移失败，
     而不是留下一个半统一的库。守卫式跳过一旦判错，静默通过比失败难查得多；
  3. **机器防线**：`TableCollationAlignmentContractTest` 回放四条建库路径，断言终态全部是 `utf8mb4_unicode_ci`，新建表漏写 COLLATE 立刻点名。
- **例外是有意的**：租户、主键这类身份标识列用 `utf8mb4_bin`。大小写不敏感的规则会把 `TenantA` 和 `tenanta` 当成同一个租户。
  表的默认规则仍然是 `unicode_ci`，只在列上显式声明。

**追问**：*后台有一次迁移（V112）已经在共享库执行了，事后发现它的表默认排序规则没对齐，怎么办？*
不能改 V112（checksum）。新建 V113，只修改表默认值和普通文本列，**不用整表 CONVERT**：整表 CONVERT 会把身份列也改成 `unicode_ci`，
破坏大小写精确匹配。升级测试保留了含 emoji 的中文回执和大小写不同的两个主键，验证身份列仍然精确匹配。

**减分回答**：“在 SQL 里加 `COLLATE utf8mb4_general_ci` 就不报错了”。

### Q5 框架从 AgentScope 2.0.2 升到 2.0.3，编译通过、全量测试全绿。能不能直接合并？项目的升级方法论是什么？

**考察点**：编译破坏、行为变更、弃用告警三类风险的区别；探针测试；升级后的逐项核对。

**参考回答**

- **结论**：不能只看“编译通过 + 测试全绿”。框架升级的风险分三类，只有第一类会让编译失败：
  1. **编译期破坏**：本次两处都在后台侧（`AgentRunner.stream` 改名为 `streamEvents` 且返回类型变成 `Flux<AgentEvent>`；
     `TaskRepository` 新增的 `public shutdown()` 与项目的包级 `@PreDestroy` 方法撞名）；
  2. **行为变更**：agent 状态加载失败**不再静默替换**为新会话；`ThinkingBlock` 的 token 按真实内容计数（影响配额和账单金额）；
     推理模型把答案放在 `reasoning_content` 时会重试（可能多一次模型调用）。另一个例子是更早的 2.0.1 把 Toolkit 默认改成并行，
     写在 release notes 的 “Refactored” 段落，而不在 Breaking Changes 里；
  3. **弃用告警**：框架把整套 `rag.Knowledge`、`memory.LongTermMemory`、`hook.Hook` 标记为 `forRemoval`。
     逐个反编译对比后确认，**2.0.2 就已经带着这些标记，是上一次升级漏看了**。release notes 没有 Deprecated 段，只有编译告警会说。
- **方法论**：
  - **行为变更和版本升级拆开处理**：关键行为显式固定（如 `ToolkitConfigs.sequential()`），不依赖默认值；
  - **升级后必看 deprecation 告警**，不只看编译是否通过，并在下次升级前查清替代路径；
  - **接口新增 default 方法时检查所有装饰器**：grep 一遍 `implements <框架接口>`，逐个对照新接口的方法列表（细节见第 06 期 Q7）；
  - **用探针测试钉住“框架当前的缺陷”**：`HarnessAgentInterruptForwardingProbeTest` 断言“框架还没修复会话级中断转发”，
    升级当天立刻变红。反编译确认新 API 的实现与项目原来的绕行做法等价后，改用新 API。
    这类探针的失败消息里一定要写清“红了说明什么、该怎么办”，否则后来的人会当成失效断言删掉；
  - **不确定时反编译确认**，不凭 release notes 和记忆下结论。

**追问**：*“全量测试全绿”为什么不足以证明升级安全？*
测试只能验证你写过断言的行为。默认值变化、计费口径变化、装饰器少转发一个 default 方法，都不会让既有断言失败。
装饰器那个例子里，被装饰的 MySQL store 明明支持版本化写入，套上壳之后框架退回无版本写入，升级当天全量是绿的。

**减分回答**：“看一下 release notes 的 Breaking Changes，没有就直接升”。

### Q6 项目里有一批“扫描源码下断言”的测试，比如装配对齐、常量对齐、HarnessAgent 必须释放。为什么用结构断言，而不是运行时断言？它们的代价是什么？

**考察点**：把反复复发的缺陷变成机器防线；结构断言与运行时断言各自能证明什么；护栏本身的覆盖面。

**参考回答**

- **先说它们防的是什么**：

  | 测试 | 防的缺陷形状 |
  |---|---|
  | `AgentAssemblyAlignmentTest` | 新增一条建 Agent 的路径却没调 `governanceAssembler.applyTo`（“能力只接在用户不走的路上”，复发过六次） |
  | `SharedConstantAlignmentTest` | 同一个字面量在多处定义（`"jdbc"` 曾有 28 处） |
  | `HarnessAgentReleaseContractTest` | 测试里真建的 `HarnessAgent` 没有释放 |
  | `MiddlewareOrderContractTest` | 中间件不定 order、取值重复、关键相对次序被打乱 |
  | `YmlTrimEquivalenceTest` | yml 瘦身时误删配置，导致绑定结果变化 |
  | `ToolSurfaceCostTest` | 工具数量和 schema token 开销悄悄上涨 |

- **为什么用结构断言**：有些缺陷**在运行时根本复现不出来**。`HarnessAgent` 不关闭，会话镜像和记忆刷写的后台线程会在测试方法返回后继续写 workspace，
  CI 上偶发 `Failed to delete temp directory`（三轮 CI 炸了两轮，两次挂的还不是同一个用例）。
  实测把释放去掉之后，连“关闭后主动删一次 workspace”这种最直接的运行时断言都照样是绿的，因为本机太快，后台在删除之前就写完了。
  结构断言不依赖时序，建了不释放当场变红。
- **结构断言的局限**：它只能证明“代码里有这个调用”，证明不了“调用之后装进去的东西不是空的”。
  customer-channel 模块确实调用了 `governanceAssembler.applyTo`，但它的 `@SpringBootApplication` 只扫自己的包，
  装配器拿到的 `ObjectProvider` 解析不出任何 Bean。这类装配完整性必须用 `@SpringBootTest` 起真实容器断言（`ChannelGovernanceMiddlewareTest`）。
- **代价**：
  - 扫描有误报，需要白名单，例如 `SharedConstantAlignmentTest` 的 `DISTINCT_CONCEPTS`，每一条都要写明为什么是巧合而不是同一个概念；
  - 护栏自己也会漏：`ToolSurfaceCostTest` 一度没有注入可选的 `SlotFillingService`，新增工具**不计入** token 统计，
    提醒“加工具有代价”的护栏自己漏算了新工具。**建了护栏之后，每次新增同类东西都要回头确认护栏真的覆盖到了。**

**追问**：*“同值常量要合并”这条规则，什么时候不该合？*
判断标准是**概念**而不是值：一处改了值、另一处不跟着改就会出错，才是同一个概念。
`FAILED` 分属五个状态机、三处 `MAX_BACKOFF_SHIFT=10` 分属不同组件的调优参数，合了会让“改 outbox 退避”意外改到死信队列。
还有一个例外：`@ConfigurationProperties` 的字段默认值刻意保持字面量，因为配置元数据处理器只能从字面量里提取 `defaultValue`。

**减分回答**：“写个 Code Review checklist，大家记住就行”。复发六次的问题，说明靠人记不住。

### Q7 全量回归跑出了几个失败。你怎么判断是真回归，还是环境问题？项目里有哪些“伪装成回归”的例子？

**考察点**：回归判定的纪律；控制变量；对自己操作的干扰保持警觉。

**参考回答**

- **原则**：判回归必须在**同等条件**下对比：同样的环境、同样的负载、同一份冻结的源码。“在 main 上单跑那两条通过了”证明不了任何事。
- **项目里真实遇到的伪装**：

  | 现象 | 真实原因 |
  |---|---|
  | 后台十几个验收测试报 `CommunicationsException` / `Connection refused :9000`，starter 的 skip 从个位数跳到 100+ | 本机 MySQL 或 MinIO 容器停了 |
  | 某个测试 “crashed”，退出码 143 | SIGTERM，会话结束把后台 Maven 杀了 |
  | 报 `NoClassDefFoundError` 或“方法应用不到给定类型” | 两个 Maven 进程同时写同一个 `target/`，或者 target 被清理了一半 |
  | 报“对 insert 的引用不明确” | 全量跑到一半时改了源码，编译到的是半成品 |
  | 登录拼图 e2e 用例 5 秒超时 | e2e 和 Maven 全量并行跑，机器过载；空闲复跑全过，耗时从 2.2 分钟回落到 1.3 分钟 |
  | 后台单模块跑报“期望版本 22，实得 21” | 迁移在 starter 里，`-pl` 单跑解析的是本地仓库里陈旧的 starter jar |
  | 宽度用例期望差 ≤1px，实得 1.125 | 亚像素舍入，在 main 上空闲连跑三轮同样每轮失败 |

- **排查顺序**：
  1. 先看失败类型：连接拒绝、超时、进程退出码、类加载错误，多半是环境；断言失败才优先怀疑代码；
  2. 确认外部依赖在线（`docker start` 之后再判）；
  3. 确认没有并发写 `target/` 的进程，也没有在全量期间改源码；
  4. 在 main 上同等负载、同等次数地跑同一批用例对比，偶发问题要多跑几轮；
  5. 真回归则按 bug 流程：先写失败用例复现，再修根因。
- **两个经验**：
  - **全量跑到一半改了源码，这次全量就作废**，只能重跑；
  - **单模块测试照不出跨模块问题**：给 record 加字段后只编译了 starter，结果连续两轮全量都红在 app-server 的测试编译上。

**追问**：*有一条 git 相关的用例在 CI 上偶发“临时目录删不掉”，本机和容器各跑几百轮都复现不了，怎么证明修好了？*
先看 suppressed 异常：是 `NoSuchFileException`，说明是“遍历时列出来了、stat 时已经没了”的竞态，不是权限或残留。
根因是 `git commit` 收尾会 fork 一个后台维护进程，它在 `.git/objects/` 下建锁文件再自行删除，而这个进程不在等待范围内。
复现不了竞态，就证明**根因消失了**：修复前每次 commit 都 fork 维护进程、都产生锁文件，修复后两者都是 0。
“改完跑一轮是绿的”不算证据，那正是这条用例在 CI 上挂之前每天的样子。

**减分回答**：“CI 偶发失败就重跑一下，绿了就合”。

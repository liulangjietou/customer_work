# 进阶第 01 期 · Agent 运行时与 Harness 深入

> **本期结论**：资深候选人要能说清楚：同一个模型，为什么在不同的工程外壳（Harness）里表现差别很大。
> 运行时负责主循环、状态、中断恢复、执行环境和长任务。这些能力决定了 Agent 能不能可靠地完成真实任务。
>
> 题量 12。

### Q1 请画出一个 Agent 运行时的主循环，并标出关键的决策点。

**考察点**：能否把“模型决策”和“工程控制”区分开。

**参考回答**

1. **组装上下文**：系统指令、工具定义、历史、记忆、检索结果、任务状态。**决策点**：放什么、放多少、怎么裁剪。
2. **调用模型**。**决策点**：用哪个模型（路由）、超时时间、失败后是否切换到备用模型。
3. **解析输出**：最终回答，还是工具调用？**决策点**：格式不合法时是重试还是兜底。
4. **执行工具前的检查**：权限、参数校验、是否需要人工审批。**决策点**：拒绝、改写参数，还是暂停等待审批。
5. **执行工具**：超时、重试、幂等。**决策点**：失败时返回什么信息给模型。
6. **把结果写回上下文**：结果过大时截断，外部内容加隔离标记。
7. **判断是否结束**：得到最终回答、达到最大迭代次数、超出预算、用户中断。**决策点**：结束时如何兜底（例如转人工）。

- **核心观点**：模型只负责第 3 步的“想做什么”，其余每个环节都由运行时控制，而且都是可以被治理和观测的切入点。

**追问**：*哪些决策点应该由模型决定，哪些必须由代码决定？* 权限、审批、预算、终止条件必须由代码决定；
调用哪个工具、传什么参数由模型决定，但要由代码校验。

**减分回答**：只画出“调用模型 → 执行工具 → 再调用模型”，没有任何控制点。

### Q2 什么是 Harness？一个成熟的 Harness 应该包含哪些模块？

**考察点**：对“Agent = 模型 + 工程外壳”的理解。

**参考回答**

- **定义**：包在模型外面的工程层，负责让模型能可靠地完成任务。常说“换模型提升能力的上限，打磨 Harness 提升能力的下限”。
- **主要模块**：
  1. **执行环境**：工作区、文件系统、沙箱、代码执行；
  2. **工具接口**：工具注册、权限、参数校验、超时；
  3. **上下文管理**：组装、裁剪、压缩、临时注入；
  4. **生命周期与编排**：主循环、计划、子 Agent、中断和恢复；
  5. **状态与记忆**：会话状态持久化、长期记忆；
  6. **可观测**：链路追踪、指标、回放；
  7. **校验**：输出检查、测试执行、自我纠错；
  8. **治理**：安全护栏、配额、审计。
- **项目对照**：本项目的 `HarnessAgent` 在 `ReActAgent` 之上增加了压缩、计划模式、工作区、子 Agent 和权限，
  见 [项目第 04 期 Q2](../04-上下文工程与记忆.md)。

**追问**：*为什么同一个模型在不同的编码 Agent 产品里表现差异很大？* 因为 Harness 不同：工具设计、
上下文管理、验证循环（例如是否运行测试）的差异，对结果的影响往往比模型差异更大。

**减分回答**：认为 Harness 只是“调用模型的代码”。

### Q3 Agent 执行到一半进程崩溃了，怎么让任务从断点继续？

**考察点**：持久化执行（Durable Execution）。

**参考回答**

- **问题**：长任务可能包含几十步模型调用和工具调用；如果崩溃后从头再来，既浪费成本，又可能重复执行有副作用的操作。
- **做法**：
  1. **检查点**：每完成一步，就把状态（上下文、已完成的步骤、工具结果）持久化；
  2. **步骤幂等**：每个有副作用的工具调用都带上幂等键（例如“任务 ID + 步骤序号”），恢复后重复执行也不会产生重复效果；
  3. **恢复时重放**：从最后一个检查点恢复，已完成的工具调用直接使用保存的结果，不再重新执行；
  4. **可以借助工作流引擎**（例如 Temporal 这类持久化执行框架）来管理重试、超时和恢复。
- **与模型的不确定性相关的注意点**：模型调用本身不是确定性的，恢复时不应该重新调用模型来“重放”已经完成的步骤，
  而应该直接使用保存下来的结果。

**追问**：*被中断的工具调用恢复后该怎么处理？* 需要知道它是否已经真正执行。能查询结果的先查询；不能确定时，
依赖下游的幂等机制安全地重试，或者交给人工确认。

**减分回答**：“崩溃了就让用户重新发起任务”。

### Q4 用户中途打断 Agent（例如点击“停止”或发送新消息），系统应该怎么处理？

**考察点**：中断语义。

**参考回答**

- **取消正在进行的模型调用**：停止流式输出，节省 token。
- **正在执行的工具**：只读工具可以直接取消；有副作用的工具要么等它执行完，要么记录为“状态未知”，后续核对。
- **状态处理**：已经完成的步骤保留在历史中，被打断的那一轮要标记清楚，避免下一轮模型误以为之前的操作已经完成。
- **恢复**：用户继续时，可以选择恢复被中断的工具调用，或者放弃。
- **多实例**：中断请求可能落到另一个实例上，需要通过会话级的状态或消息广播来找到正在执行的实例。

**追问**：*用户在 Agent 执行过程中发送了新消息，应该中断当前任务，还是排队等待？* 取决于产品设计。
客服场景一般排队串行处理，避免并发修改会话状态；编码助手这类场景可以允许插话并调整计划。

**减分回答**：只在前端隐藏输出，后台继续运行。

### Q5 Agent 需要执行模型生成的代码，沙箱应该怎么设计？

**考察点**：隔离与安全。

**参考回答**

- **隔离层级**（从弱到强）：
  - 语言层面的限制（例如受限解释器）：最弱，容易被绕过；
  - 容器：共享宿主机内核，需要配合 seccomp、只读文件系统、非 root 用户等限制；
  - 用户态内核（例如 gVisor）或轻量虚拟机（例如 Firecracker）：隔离更强，适合多租户执行不可信代码。
- **必要的限制**：CPU、内存、磁盘和执行时间的上限；默认禁止网络，需要时使用白名单；不挂载宿主机敏感目录；
  不注入凭据；每次执行后销毁或重置环境。
- **隔离范围**：按会话或按租户隔离，避免不同用户的文件互相可见。
- **审计**：记录执行的代码、输出和资源使用情况。

**追问**：*沙箱需要访问业务数据时怎么办？* 不要把数据库凭据放进沙箱；通过受控的工具接口提供数据，
由沙箱外的服务负责鉴权。

**减分回答**：“用 Docker 跑一下就安全了”。

### Q6 长时间运行的 Agent 任务（数小时）有哪些特殊问题？

**考察点**：长任务的工程设计。

**参考回答**

- **上下文会持续增长**：需要压缩、把中间结果写入外部文件、用子 Agent 隔离探索过程。
- **目标会漂移**：用任务清单和计划文件记录目标与进度，定期回顾。
- **成本不可控**：设置预算上限和进度检查点，超出预算时暂停并请求确认。
- **故障恢复**：检查点和幂等（见 Q3）。
- **人机协作**：在关键节点请求确认，而不是一路执行到底。
- **可观测**：展示当前进度、已用成本、预计剩余步骤。

**追问**：*怎么判断长任务“卡住了”？* 连续多步没有进展（例如重复调用相同工具、测试一直失败）、
成本增长但任务清单状态不变，都是需要干预的信号。

**减分回答**：把长任务当作一次很长的对话来处理。

### Q7 如何设计 Agent 的计划模式（先规划、再执行）？

**考察点**：规划与执行分离。

**参考回答**

- **规划阶段**：只允许只读操作（读取文件、查询信息），输出结构化的计划（步骤、每步使用的工具、预期结果、风险）。
- **审批**：计划由用户或规则审批，涉及高风险操作的步骤单独标注。
- **执行阶段**：按计划逐步执行，每步完成后更新状态；发现前提不成立时回到规划阶段，而不是强行继续执行。
- **好处**：用户能提前纠正方向，降低高风险操作的误操作概率；计划本身也可以作为评测对象。
- **代价**：多一轮交互和模型调用，简单任务不需要。

**追问**：*规划阶段怎么保证“只读”？* 由运行时在权限层面禁止写工具，而不是靠提示词约束。

**减分回答**：“在提示词里让模型先想好再做”。

### Q8 子 Agent 的编排中，有哪些容易被忽视的问题？

**考察点**：多 Agent 的工程细节。

**参考回答**

- **上下文传递**：子 Agent 看不到主 Agent 的完整上下文，交接信息必须完整、明确（目标、约束、已知信息、期望的输出格式）。
- **权限继承**：子 Agent 的权限不应该超过主 Agent；按任务授予最小权限。
- **成本放大**：每个子 Agent 都有自己的多轮调用，总成本可能成倍增加，要有全局预算。
- **失败传播**：一个子 Agent 失败或超时，不能拖垮整个任务，需要隔离并返回占位结果。
- **结果汇总**：多个子 Agent 的结论可能冲突，需要归纳和消解冲突。
- **可观测**：链路追踪要能串起主 Agent 和所有子 Agent 的调用。
- **租户和用户上下文**：子 Agent 在其他线程或进程中运行时，身份信息要显式传递。

**追问**：*子 Agent 是并行好还是串行好？* 独立的子任务并行，存在依赖的串行；并行时要限制并发数，
避免触发模型厂商的限流。

**减分回答**：只关注子 Agent 能不能跑通，不关心成本和失败隔离。

### Q9 Agent 的工作区（文件系统）应该怎么设计？

**考察点**：执行环境的状态管理。

**参考回答**

- **用途**：保存中间产物、计划文件、记忆文件、大体积的工具结果，减少上下文占用。
- **隔离**：按会话或用户隔离目录，防止路径穿越访问到其他工作区或宿主机文件。
- **持久化**：工作区中的文件如果需要长期保存，应以数据库或对象存储作为可信来源，磁盘只作为可以重建的缓存；
  否则换机器、重启后数据就丢了。
- **清理**：设置保留期限和容量上限，避免磁盘被占满。
- **并发**：同一工作区的并发写入需要加锁或按会话串行化。

**追问**：*框架只能从本地文件读取记忆，但你希望记忆存在数据库里，怎么办？*
启动或构建 Agent 前，把数据库中的内容写到本地（水合），运行后再把变化写回数据库；数据库是权威来源。

**减分回答**：直接使用服务器的某个固定目录，所有用户共用。

### Q10 如何在运行时层面实现 Agent 的“自我验证”？

**考察点**：验证循环。

**参考回答**

- **可执行的验证**：编码场景运行测试、编译检查、Lint；数据场景检查 SQL 执行结果是否合理。
- **规则验证**：输出格式校验、关键结论与工具证据的一致性检查（例如说“已退款”时，本轮是否真的查到了退款状态）。
- **模型验证**：用另一个模型或另一次调用评审结果，要注意评审本身也可能出错。
- **失败后的处理**：把验证失败的原因反馈给模型重试，但要限制次数；多次失败后转人工。
- **原则**：优先使用确定性的验证，其次才用模型评审。

**追问**：*验证循环会不会让成本失控？* 会，所以要设置最大重试次数和预算；并且只对关键步骤做验证。

**减分回答**：“让模型自己检查一遍”。

### Q11 Agent 框架升级时，最容易踩哪些坑？怎么降低风险？

**考察点**：依赖治理的经验。

**参考回答**

- **常见的坑**：
  1. **默认行为改变**：例如工具默认从串行改为并行，而且可能不写在“破坏性变更”里；
  2. **接口新增默认方法**：自定义的装饰器不转发也能编译通过，但能力被悄悄关掉；
  3. **API 废弃**：大量接口被标记为即将删除，只会出现在编译警告里；
  4. **行为语义变化**：例如状态加载失败从静默降级改为直接报错，token 计算方式改变影响计费。
- **降低风险的做法**：
  1. 阅读完整的发行说明，并关注编译警告；
  2. 对关键行为写“记录现状”的测试，行为变化时测试失败并给出说明；
  3. 显式配置关键行为，不依赖默认值；
  4. 把升级和功能改动分开提交，全量回归后再合并。
- **项目对照**：[项目第 02 期 Q4](../02-Agent核心机制-ReAct工具调用与多Agent.md)、[项目第 06 期 Q7](../06-Java并发与响应式流式链路.md)。

**追问**：*“记录现状”的测试失败了，应该怎么处理？* 先判断是框架修复了问题还是引入了变化，
再决定是更新断言还是调整代码；测试的失败信息里应该写清楚“失败意味着什么、该怎么办”。

**减分回答**：“编译通过、测试全绿就可以升级”。

### Q12 自研 Agent 框架和使用开源框架，怎么选择？

**考察点**：技术决策能力。

**参考回答**

- **使用开源框架的理由**：开发速度快；社区持续跟进新模型、新协议；有现成的工具、记忆、RAG 组件。
- **自研的理由**：开源框架的抽象不符合业务需要且无法扩展；对性能、稳定性、安全有特殊要求；
  框架迭代太快，破坏性变更频繁。
- **常见的折中**：使用开源框架作为内核，在其上封装自己的抽象层（模型接口、工具后端、存储、治理中间件），
  业务代码只依赖自己的抽象；框架的问题在适配层解决。
- **决策依据**：团队规模和能力、需求的特殊程度、长期维护成本、框架的活跃度和发布节奏。

**追问**：*如果选定的框架停止维护了怎么办？* 有自己的抽象层时，替换的影响范围可控；这正是抽象层的价值所在。

**减分回答**：“开源框架都不好用，我们要自研”，或者反过来完全依赖框架、没有任何抽象。

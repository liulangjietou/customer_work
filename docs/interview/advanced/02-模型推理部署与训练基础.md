# 进阶第 02 期 · 模型推理部署与训练基础

> **本期结论**：资深 Agent 开发不一定要训练模型，但需要能判断“这个问题应该靠模型解决还是靠工程解决”，
> 能和算法团队、运维团队讨论私有化部署、推理性能和微调方案。本期覆盖推理服务、性能优化、微调和对齐的核心概念。

### Q1 私有化部署大模型，推理服务怎么选型？

**考察点**：推理引擎的认知。

**参考回答**

- **常见引擎**：vLLM、SGLang、TensorRT-LLM、TGI，以及面向本地和开发环境的 Ollama、llama.cpp。
- **选型维度**：吞吐和延迟表现；支持的模型和量化格式；是否提供 OpenAI 兼容接口；
  是否支持工具调用、结构化输出（约束解码）；多卡并行能力；社区活跃度和运维成本。
- **Ollama 更适合开发和小规模使用**；生产环境的高并发服务一般选 vLLM、SGLang 这类引擎。
- **应用侧的注意点**：私有模型的工具调用和结构化输出能力通常弱于商业模型，需要单独评测；
  兼容接口返回的元数据（例如上下文窗口）可能不准确。

**追问**：*私有化部署的主要成本在哪里？* GPU 采购或租赁、运维人力、模型升级的成本。
调用量不大时，私有化的单次成本往往高于商业 API。

**减分回答**：“用 Ollama 部署到生产环境”。

### Q2 vLLM 为什么吞吐量高？PagedAttention 和连续批处理是什么？

**考察点**：推理优化的核心原理。

**参考回答**

- **PagedAttention**：借鉴操作系统的分页机制，把 KV Cache 切成固定大小的块，按需分配，不再为每个请求预留最大长度的连续显存。
  显存碎片大幅减少，同时能服务更多并发请求；相同前缀的 KV 块还可以在请求之间共享。
- **连续批处理（Continuous Batching）**：不等一整批请求全部完成，某个请求一结束就把新请求加入批次，
  GPU 利用率更高。传统的静态批处理要等最长的请求结束，短请求会被拖慢。
- **前缀缓存**：相同的前缀（例如系统提示词）只计算一次，后续请求直接复用。

**追问**：*应用层如何配合推理引擎提升吞吐？* 保持提示词前缀稳定，以便命中前缀缓存；控制输出长度；
避免超长上下文的请求挤占显存。

**减分回答**：“因为用了更好的 GPU”。

### Q3 推理延迟由哪几部分组成？怎么优化首 token 延迟？

**考察点**：延迟分析。

**参考回答**

- **组成**：排队时间 + 预填充（处理输入，决定首 token 延迟）+ 解码（逐个生成 token）+ 网络传输。
- **优化首 token 延迟**：
  1. 缩短输入：精简提示词和工具定义、控制历史长度；
  2. 利用前缀缓存；
  3. 降低排队时间：扩容、按优先级调度；
  4. 选择更小或更快的模型；
  5. 应用侧并行化：检索、记忆召回等准备工作并行执行，而不是串行。
- **优化总耗时**：控制输出长度；使用投机解码等推理优化；使用流式输出，改善用户感知的延迟。

**追问**：*投机解码的原理是什么？* 用一个小模型快速生成若干候选 token，再由大模型一次性验证，
验证通过的部分直接采用，从而减少大模型的串行解码步数，输出分布与大模型一致。

**减分回答**：只知道“换更快的模型”。

### Q4 模型量化是什么？对效果有什么影响？

**考察点**：部署成本优化。

**参考回答**

- **定义**：用更低精度的数值表示模型参数（例如从 16 位降到 8 位或 4 位），减少显存占用、提升推理速度。
- **常见方法**：训练后量化，例如 GPTQ、AWQ，以及 GGUF 格式用于 CPU 和本地推理；FP8 等低精度格式在新一代硬件上有原生支持。
- **影响**：通常精度越低，效果损失越大；不同任务的敏感程度不同，工具调用、结构化输出、复杂推理可能比普通对话更敏感。
- **实践**：量化前后在自己的评测集上对比，特别关注工具调用的准确率。

**追问**：*量化对 Agent 场景的风险在哪里？* 工具调用的参数格式和结构化输出更容易出错，这类错误在普通对话评测中不容易发现。

**减分回答**：“量化只是让模型变小，效果不变”。

### Q5 如何估算私有化部署需要多少 GPU？

**考察点**：容量规划的思路。

**参考回答**

- **显存估算**：
  - 模型参数：参数量 × 每个参数的字节数（例如 7B 参数、16 位精度约需 14GB）；
  - KV Cache：与并发数、上下文长度、层数、隐藏维度相关，长上下文、高并发时往往占用很大；
  - 预留运行时开销。
- **吞吐估算**：通过压测得到单卡在目标输入输出长度下的每秒 token 数，再根据峰值的请求量和每次的 token 数计算所需卡数。
- **需要明确的输入**：峰值并发、平均输入和输出长度、延迟要求（首 token 延迟、每秒 token 数）。
- **结论要以压测为准**：公式只用于粗估，不同引擎和参数设置下的实际表现差异很大。

**追问**：*长上下文对容量的影响有多大？* KV Cache 大致随上下文长度线性增长，长上下文会显著降低单卡能支撑的并发数。

**减分回答**：只按模型参数量估算，忽略 KV Cache。

### Q6 SFT、LoRA、全参数微调分别是什么？怎么选？

**考察点**：微调方法的基础。

**参考回答**

- **SFT（监督微调）**：用“输入 - 期望输出”的样本对训练模型，让模型学会特定的格式或行为。
- **全参数微调**：更新所有参数，效果上限高，但需要大量显存和计算资源，还有遗忘原有能力的风险。
- **LoRA**：冻结原模型，只训练插入的低秩矩阵，参数量很小，训练成本低；多个 LoRA 适配器可以共享同一个基座模型，
  按需切换。QLoRA 在量化后的基座上训练 LoRA，进一步降低显存需求。
- **选择**：大多数应用场景用 LoRA 就够了；只有在需要深度改变模型能力且资源充足时，才考虑全参数微调。

**追问**：*Agent 场景微调通常训练什么？* 工具调用的格式和选择、领域意图分类、特定的输出风格；
训练数据往往来自线上成功的对话轨迹。

**减分回答**：“微调能让模型学会我们所有的业务知识”。

### Q7 RLHF、DPO、GRPO 分别是什么？

**考察点**：对齐方法的认知。

**参考回答**

- **RLHF**：先用人类偏好数据训练一个奖励模型，再用强化学习（常用 PPO）优化模型，让它的输出获得更高的奖励。流程复杂，训练不稳定。
- **DPO（直接偏好优化）**：直接用“更好的回答 / 更差的回答”这样的偏好对来优化模型，不需要单独训练奖励模型，实现更简单。
- **GRPO**：一种强化学习方法，对同一个问题生成一组回答，用组内的相对得分作为优势估计，省去了单独的价值模型。
  在数学、代码这类有明确对错判定的任务上效果显著，也常用于推理模型的训练。
- **对应用开发的意义**：了解这些方法，才能判断“这个问题能否通过训练解决、需要准备什么样的数据”。

**追问**：*什么是“可验证奖励”？* 奖励来自可以自动判定对错的规则（例如代码能否通过测试、答案是否正确），
不依赖人工打分，适合规模化训练。

**减分回答**：把所有训练方法都叫作“微调”，说不出区别。

### Q8 什么是 Agentic RL？为什么模型厂商会针对 Agent 能力做专门训练？

**考察点**：前沿趋势的理解。

**参考回答**

- **定义**：在真实或模拟的环境中，让模型完成多步任务（调用工具、浏览网页、写代码），根据任务最终是否完成给予奖励，
  用强化学习提升模型的多步决策能力。
- **为什么需要**：只靠 SFT 学到的是模仿，模型在遇到训练数据以外的情况时容易出错；
  通过与环境交互获得反馈，模型能学会从错误中恢复、合理规划。
- **对应用开发的影响**：
  1. 模型的工具调用和长任务能力持续提升，部分原本需要工程补偿的能力会被模型内化；
  2. 应用应该让工具设计贴近模型训练时熟悉的形式（例如清晰的工具描述、标准的文件和命令操作）；
  3. 企业可以用自己的业务环境和评测集构造奖励，训练专用模型，但成本和门槛较高。

**追问**：*模型能力持续变强，Harness 的价值会降低吗？* 部分工程补偿会变得不再必要，
但权限、审计、成本、业务集成、评测这些工程能力始终需要。

**减分回答**：不了解这个方向。

### Q9 约束解码（Constrained Decoding）是什么？和结构化输出有什么关系？

**考察点**：结构化输出的底层机制。

**参考回答**

- **原理**：生成每个 token 时，根据 JSON Schema 或语法规则，屏蔽所有会导致输出不合法的候选 token，
  从而保证输出一定符合格式。
- **与提示词约束的区别**：提示词约束只是“请求”模型遵守格式；约束解码是在生成过程中强制保证。
- **局限**：只保证格式正确，不保证内容正确；复杂的 schema 可能降低生成速度；部分 schema 特性可能不受支持。
- **私有化部署**：vLLM 等推理引擎支持通过语法约束实现结构化输出。

**追问**：*用了约束解码，还需要做结果校验吗？* 需要。格式正确不代表业务上正确，例如枚举值的含义是否合理、数值是否在合理范围内。

**减分回答**：不知道格式保证是怎么实现的。

### Q10 什么时候应该考虑训练或蒸馏一个专用的小模型？

**考察点**：成本与效果的权衡。

**参考回答**

- **适合的场景**：调用量大、任务固定（例如意图分类、信息抽取、路由判断）、对延迟敏感、有数据合规要求。
- **做法**：用大模型的输出作为标注数据（蒸馏），或者使用人工标注和线上数据，训练一个小模型。
- **前提**：有足够的高质量数据；有评测集能证明小模型的效果达标；有持续更新模型的能力。
- **收益**：成本和延迟大幅下降，可以私有化部署。
- **风险**：业务变化时需要重新训练；可能在长尾的情况上表现变差，需要保留回退到大模型的路径。

**追问**：*怎么判断小模型能否替代大模型？* 在评测集上对比，尤其关注长尾用例；
线上先做影子测试（小模型并行运行但不生效），对比两者的结果差异。

**减分回答**：“小模型效果差，不值得”，或者“所有任务都用小模型”。

### Q11 长上下文模型越来越强，RAG 还有必要吗？

**考察点**：技术趋势的判断。

**参考回答**

- **长上下文的优势**：不需要检索，信息完整，能进行全局的理解和推理。
- **RAG 仍然必要的原因**：
  1. **成本和延迟**：每次都把大量资料放进上下文，成本和首 token 延迟都很高；
  2. **规模**：企业知识库的规模远超任何上下文窗口；
  3. **权限**：需要按用户过滤可见的内容；
  4. **时效性和可追溯**：知识更新后立即生效，并能给出引用来源；
  5. **注意力稀释**：上下文过长时，模型对中间部分的利用效果下降。
- **趋势**：两者结合。先用检索缩小范围，再把较大的相关片段放进长上下文；配合提示词缓存降低重复内容的成本。

**追问**：*什么场景可以直接用长上下文、不做 RAG？* 资料规模小（例如一份合同、一个代码仓库的一部分）、
不需要权限区分、对成本不敏感的单次分析任务。

**减分回答**：“长上下文出来以后 RAG 就过时了”。

### Q12 如何评估一个新发布的模型是否值得切换？

**考察点**：模型升级的决策流程。

**参考回答**

1. **离线评测**：在自己的评测集上对比效果，重点看工具调用准确率、结构化输出成功率、业务关键用例。
2. **性能和成本**：对比首 token 延迟、每秒 token 数、单价、提示词缓存支持情况。
3. **兼容性**：消息格式、工具调用格式、上下文窗口元数据、错误码是否有变化。
4. **影子测试**：线上流量复制一份给新模型，但结果不返回给用户，对比两者差异。
5. **灰度发布**：小流量上线，观察业务指标和错误率。
6. **保留回滚能力**：配置化切换，出现问题时快速切回旧模型。

**追问**：*新模型总体评分更高，但有几个关键用例变差了，怎么办？* 分析这些用例的原因，判断是否可以通过调整提示词解决；
关键用例的回归不应该被总分的提升掩盖。

**减分回答**：“新模型榜单排名更高，直接切换”。

# 进阶第 04 期 · 线上故障排查与性能容量

> **本期结论**：资深工程师和中级工程师最大的区别，在于面对线上问题时有没有系统的排查路径，以及能否用数字做容量规划。
> 本期都是场景题：先给现象，考察排查顺序、止血手段和根因修复。
>
> 题量 12。通用排查框架：确认影响范围 → 止血 → 定位环节（接入、编排、模型、工具、检索、数据）→ 找根因 → 修复并补防线 → 复盘。

---

### Q1 场景：上线新版本后，模型调用成本一天内涨了 3 倍，怎么排查？

**考察点**：成本异常的定位能力。

**参考回答**

1. **确认范围**：是所有租户都涨了，还是某个租户、某个应用、某个入口？是调用次数涨了，还是单次的 token 数涨了？
2. **拆解 token**：输入 token 涨了，还是输出 token 涨了？输入涨了，就看系统提示词、工具定义、历史长度、检索注入的内容有没有变大；
   输出涨了，就看是否出现长篇回答或循环。
3. **看调用次数**：每轮对话的模型调用次数是否增加（例如重试、循环、多 Agent 的扇出、验证循环）。
4. **看缓存**：提示词缓存命中率是否下降（前缀里被加入了变化的内容）；语义缓存是否失效。
5. **看路由**：分级路由是否失效，所有请求都走了贵的模型。
6. **对比版本差异**：结合发布内容定位原因。
- **止血**：回滚版本；临时收紧配额；关闭新增的高成本功能。
- **防线**：按版本和功能统计 token；设置成本异常告警。

**追问**：*如果发现是某个租户被人刷接口导致的，怎么办？* 立即对该主体限流或封禁；检查主体级配额是否覆盖了所有入口（包括 WebSocket）。

**减分回答**：“去模型厂商后台看一下账单”。

### Q2 场景：用户反馈回答质量突然下降，但系统没有任何报错，怎么排查？

**考察点**：“静默失效”类问题的排查。

**参考回答**

1. **量化**：负反馈率、转人工率、知识未命中率、兜底回复比例是否有明显变化，从哪个时间点开始。
2. **对照变更**：这个时间点前后是否有发布、配置变更、提示词修改、模型厂商升级、知识库更新。
3. **看版本指纹**：线上实际生效的提示词版本和模型版本是否发生了变化。
4. **分环节检查**：检索是否还能召回（向量服务是否降级、Embedding 模型是否变化）；工具调用率是否下降（工具是否被意外关闭）；
   中间件是否漏装。
5. **用评测集复现**：在线上的配置下运行评测集，与基线对比，找出回归的用例。
- **常见根因**：模型厂商悄悄更新了模型；配置发布只部分生效；检索服务降级后返回空结果；上下文被错误裁剪。

**追问**：*模型厂商悄悄更新了模型，怎么提前发现？* 固定使用带版本号的模型名称；定期运行评测集作为巡检；
监控结构化输出失败率、工具调用率这类敏感指标。

**减分回答**：“调一下提示词试试”。

### Q3 场景：首 token 延迟从 1 秒涨到了 5 秒，怎么排查？

**考察点**：延迟分解。

**参考回答**

1. **拆分链路耗时**：网关 → 鉴权 → 获取会话锁 → 加载状态 → 检索 / 记忆召回 → 模型排队 → 模型预填充 → 首个 token 返回。
   依靠链路追踪看每一段的耗时。
2. **常见原因**：
   - 会话锁等待（同一会话有未结束的请求）；
   - 检索或 Embedding 服务变慢；
   - 输入变长（历史、检索内容变多），预填充时间增加；
   - 模型厂商排队或限流；
   - 线程池耗尽（阻塞调用占满了线程）；
   - 流式响应被代理缓冲。
3. **止血**：切换到备用模型；缩短上下文；关闭非必要的前置步骤。

**追问**：*链路追踪显示模型调用本身很快，但用户仍然感觉慢，可能是什么原因？* 响应被网关或代理缓冲，没有真正实现流式；
或者下游的处理（过滤、写库）阻塞了发送。

**减分回答**：只会说“模型太慢了，换一个”。

### Q4 场景：Agent 频繁出现“迭代次数用尽”，怎么排查？

**考察点**：Agent 行为问题的分析。

**参考回答**

1. **看轨迹**：是在重复调用同一个工具（工具返回的信息对模型没有帮助），还是在多个工具之间来回尝试（缺少需要的工具或信息）？
2. **看工具结果**：工具是否返回了错误，而错误信息模型看不懂；是否返回了空结果。
3. **看工具描述**：描述是否含糊，导致模型选错工具或传错参数。
4. **看上下文**：历史是否被裁剪，模型忘记了已经做过的事情。
5. **看提示词**：是否有相互矛盾的指令（例如一边要求必须调用工具，一边又禁止调用工具）。
- **修复**：改进工具的返回信息、补充缺失的工具、修正提示词；迭代次数用尽时要有兜底（例如转人工）。

**追问**：*能不能直接把最大迭代次数调大？* 可以作为临时措施，但治标不治本，还会增加成本和延迟。

**减分回答**：直接调大最大迭代次数。

### Q5 场景：发现有用户通过提示词注入，让 Agent 泄露了其他用户的订单信息。怎么处理？

**考察点**：安全事件响应。

**参考回答**

1. **止血**：立即关闭相关工具或功能；封禁攻击者；必要时暂停服务。
2. **评估影响**：通过审计日志找出所有受影响的请求和泄露的数据范围。
3. **找根因**：注入只是触发条件，真正的根因是**工具没有按当前用户的身份做权限校验**：模型传入了别人的订单号，工具就直接返回了数据。
4. **修复**：工具从可信上下文获取用户身份，并校验数据归属；增加注入检测和告警。
5. **合规处理**：按照法规和公司流程通知受影响的用户、上报监管。
6. **复盘**：补充红队测试用例和回归测试。

**追问**：*为什么说修复提示词不是根本解决办法？* 提示词无法百分之百防住注入；只要工具本身按身份做了权限校验，
注入成功也拿不到别人的数据。

**减分回答**：“在系统提示词里加一句不要泄露其他用户的信息”。

### Q6 场景：服务偶发 OOM，怀疑和 Agent 相关，怎么排查？

**考察点**：Java 内存问题在 Agent 场景中的表现。

**参考回答**

1. **获取证据**：配置 OOM 时自动生成堆转储；使用 MAT 等工具分析占用内存最多的对象。
2. **Agent 场景常见的原因**：
   - 缓存无界增长（Agent 实例缓存、会话锁对象、会话活跃时间表只放不删）；
   - 流式响应的内容全部累积在内存里（例如用于写缓存的完整答案）；
   - 超大的工具结果或文件被整体加载到内存；
   - Agent 或 MCP 客户端没有释放（Toolkit 需要显式关闭）；
   - 慢请求堆积，导致同时存活的对象过多。
3. **修复**：给缓存加上限和淘汰策略；淘汰时释放资源；大结果采用流式处理或截断；设置并发上限和超时。

**追问**：*项目中的进程内会话锁为什么要按使用者计数回收？* 早期每遇到一个新会话就创建一个锁对象且从不删除，
长期运行会导致内存泄漏（见 [项目第 06 期 Q5](../06-Java并发与响应式流式链路.md)）。

**减分回答**：“把堆内存调大”。

### Q7 场景：模型厂商全面故障 30 分钟，系统应该如何表现？事后怎么复盘？

**考察点**：依赖故障时的韧性设计。

**参考回答**

- **故障期间的预期表现**：
  1. 熔断器迅速打开，不再让请求等待超时；
  2. 切换到备用厂商的模型（前提是提前配置并定期验证过）；
  3. 备用模型也不可用时，返回明确的降级提示，引导转人工或留言；
  4. 规则类能力（关键词转人工、常见问题缓存）继续工作；
  5. 告警及时通知值班人员。
- **复盘要点**：检测和切换用了多长时间；备用模型的效果和成本如何；有多少请求失败；降级话术是否合适；
  是否需要多厂商常态化分流。

**追问**：*备用模型平时不用，怎么保证故障时能用？* 定期进行健康探测，或者平时分配少量流量给它；
凭据、额度和能力差异都要提前验证。

**减分回答**：“等厂商恢复就好了”。

### Q8 计算题：峰值每秒 200 条用户消息，每条消息平均调用 2.5 次模型，每次输入 3000 token、输出 300 token，需要多少模型额度？

**考察点**：容量规划的计算能力。

**参考回答**

- **每秒模型调用次数**：200 × 2.5 = 500 次 / 秒，即每分钟 30000 次（这就是 QPM / RPM 需求）。
- **每分钟 token 量**：
  - 输入：500 × 3000 × 60 = 9000 万 token / 分钟；
  - 输出：500 × 300 × 60 = 900 万 token / 分钟；
  - 合计约 9900 万 TPM。
- **结论**：这个量级通常远超单个账号的默认额度，需要申请额度、多账号或多厂商分流，并且要优化：
  - 用提示词缓存降低输入部分的成本和延迟（3000 token 里大部分应该是可以缓存的固定前缀）；
  - 减少每条消息的模型调用次数；
  - 对简单问题使用小模型或规则。
- **成本估算**：再乘以输入和输出的单价，按日汇总得到每天的费用，评估是否可接受。

**追问**：*还需要考虑哪些因素？* 流量的峰谷比例、重试带来的额外调用、评测和巡检的调用量、厂商额度的限制维度（按模型或按账号）。

**减分回答**：只算出一个数，说不出可以优化的方向。

### Q9 计算题：一次对话平均 6 轮，每轮上下文平均 8000 token，如何把单次对话的成本降低一半？

**考察点**：成本优化的量化分析。

**参考回答**

- **先拆解成本构成**：8000 token 中系统提示词、工具定义、历史、检索内容各占多少；输出占多少。
- **可选的手段与预期效果**：
  1. **提示词缓存**：固定前缀（系统提示词 + 工具定义）如果占一半，缓存命中后这部分的费用可以大幅降低；
  2. **减少工具定义**：按部署关闭不需要的工具组，或者按意图收窄工具；
  3. **控制历史长度**：裁剪或压缩历史；
  4. **减少检索注入**：只放最相关的片段；
  5. **模型分级**：简单轮次使用便宜模型；
  6. **减少调用次数**：合并工具调用、减少不必要的验证步骤。
- **验证**：每项优化都要在评测集上确认效果没有明显下降。

**追问**：*哪项优化通常性价比最高？* 通常是提示词缓存和精简工具定义，改动小、见效快；但要用实际的数据拆解来确认。

**减分回答**：“换一个便宜一半的模型”。

### Q10 如何为 Agent 服务定义 SLO？

**考察点**：可靠性工程。

**参考回答**

- **可用性**：成功返回有效回答的比例（兜底回复是否算成功，要事先定义清楚）。
- **延迟**：首 token 延迟的 P95 / P99；完整回答的耗时。
- **质量**：可以作为辅助目标，例如负反馈率、转人工率不超过某个阈值。
- **错误预算**：根据 SLO 计算允许的失败量；错误预算消耗过快时，暂停发布新功能，优先修复稳定性问题。
- **依赖**：模型厂商的可用性会直接影响 SLO，需要通过备用模型等方式提升整体可用性。
- **多副本评估**：SLO 需要按全局汇总计算，而不是只看单个实例的数据。

**追问**：*模型厂商的可用性只有 99.5%，你的服务能承诺 99.9% 吗？* 单靠一个厂商做不到，需要多厂商冗余、缓存和降级等手段来提升整体可用性。

**减分回答**：只定义“服务不挂”这一个目标。

### Q11 如何做 Agent 服务的压测？和普通 Web 服务压测有什么不同？

**考察点**：压测方法。

**参考回答**

- **不同之处**：
  1. 真实模型调用的成本高，而且受厂商额度限制，不能随意大规模压测；
  2. 响应时间长、流式返回，需要统计首 token 延迟和完整耗时；
  3. 请求的内容会影响耗时（输入输出长度）。
- **方法**：
  1. **使用模拟模型**：模拟真实的延迟分布和流式返回，压测自身系统的瓶颈（连接数、线程池、锁、数据库）；
  2. **小规模真实压测**：验证模型额度和厂商侧的表现；
  3. **使用真实的请求分布**：根据线上的输入输出长度分布来构造请求；
  4. **关注长连接**：WebSocket 的连接数上限、内存占用和心跳。
- **需要关注的指标**：各阶段的耗时分位数、错误率、线程池和连接池的使用率、内存和 GC。

**追问**：*压测时发现瓶颈在会话锁上，怎么办？* 检查锁的粒度是否正确（应该按会话加锁，而不是全局加锁）、锁的持有时间是否过长；
避免在锁内执行不必要的操作。

**减分回答**：直接用真实模型进行大规模压测。

### Q12 如何建立 Agent 系统的告警体系？哪些告警最重要？

**考察点**：监控的优先级。

**参考回答**

- **最重要的告警**：
  1. 模型调用错误率和熔断；
  2. 首 token 延迟的 P95；
  3. 兜底回复的比例（静默失效的重要信号）；
  4. 成本异常（按小时的 token 量相对基线大幅增长）；
  5. 转人工队列积压；
  6. 安全事件（注入检测命中、越权承诺拦截）的突增；
  7. 消息投递积压（Outbox、死信）；
  8. 状态写入冲突突增（可能意味着会话锁失效）。
- **原则**：告警要可行动（每条告警都有对应的处理手册）；避免噪音（只在首次越过阈值时告警）；按严重程度分级。

**追问**：*为什么“兜底回复比例”很重要？* 很多故障不会报错，系统用兜底文案“正常”返回了，只有这个比例能反映出问题。

**减分回答**：只监控 CPU 和内存。

# 进阶第 05 期 · 数据类 Agent 与知识工程

> **本期结论**：企业里价值最高的 Agent，往往是和数据打交道的：问数（Text2SQL）、文档理解、知识图谱、报表生成。
> 这类 Agent 的难点在于准确性和权限，答错一个数字的代价远高于答错一句闲聊。
>
> 题量 10。

---

### Q1 Text2SQL 的主要难点是什么？怎么提升准确率？

**考察点**：Text2SQL 的核心问题。

**参考回答**

- **难点**：
  1. **找对表和字段**（schema linking）：企业数据库有成百上千张表，字段命名不直观；
  2. **业务口径**：同一个指标在不同部门有不同的计算方式；
  3. **复杂查询**：多表关联、窗口函数、时间范围处理；
  4. **数据库方言的差异**。
- **提升准确率的方法**：
  1. **补充元数据**：为表和字段写清楚业务含义、取值示例、常用关联关系；
  2. **检索相关的表**：先检索与问题相关的表结构，只把它们放进上下文；
  3. **提供示例**：检索相似的历史问题和对应的正确 SQL 作为示例；
  4. **执行校验与修正**：执行 SQL，出错时把错误信息反馈给模型修正；检查结果是否合理（例如结果为空、数量级异常）；
  5. **语义层**：预先定义好指标和维度，让模型选择指标，而不是从零写 SQL；
  6. **追问澄清**：问题有歧义时主动询问用户。

**追问**：*SQL 能执行成功，就说明结果是对的吗？* 不是。语法正确但逻辑错误（例如关联条件错误导致数据重复计算）的情况很常见，
需要结果合理性检查和人工核对的能力（展示执行的 SQL）。

**减分回答**：“把所有表结构都放进提示词，让模型生成 SQL”。

### Q2 Text2SQL 如何保证数据安全？

**考察点**：数据库访问的安全控制。

**参考回答**

- **只读**：使用只读账号；在 SQL 解析层面拒绝所有写操作和 DDL；在只读副本上执行。
- **权限**：根据当前用户的身份自动注入行级和列级的权限条件；敏感字段（手机号、身份证）默认不可查询或脱敏。
- **资源限制**：限制扫描的行数、返回的行数、执行时间；禁止笛卡尔积这类高风险查询。
- **防注入**：用户输入可能诱导模型生成恶意 SQL，所以必须在执行前解析和校验 SQL，不能直接执行模型生成的字符串。
- **审计**：记录谁查询了什么数据。

**追问**：*权限条件应该由模型生成，还是由系统注入？* 必须由系统根据可信身份注入，并在 SQL 解析后强制附加；
不能依赖模型在 SQL 里自己加上权限条件。

**减分回答**：“告诉模型只能生成 SELECT 语句”。

### Q3 企业文档（PDF、Word、扫描件、表格）的解析有哪些难点？

**考察点**：知识入库的质量。

**参考回答**

- **难点**：
  1. **版面**：多栏排版、页眉页脚、脚注会打乱文本顺序；
  2. **表格**：跨页表格、合并单元格，转成文本后容易失去结构；
  3. **扫描件**：需要 OCR，识别错误会直接影响检索；
  4. **图片和图表**：里面的信息需要额外提取；
  5. **格式多样**：不同来源的文档格式差异大。
- **方法**：使用版面分析工具识别标题、段落、表格；表格保留结构（转成 Markdown 或 HTML）；
  扫描件使用 OCR，并评估识别质量；复杂文档可以用多模态模型辅助解析。
- **质量控制**：对解析结果做抽样检查；记录解析失败和质量较低的文档；解析质量直接决定了 RAG 效果的上限。

**追问**：*怎么判断解析质量影响了回答效果？* 把回答错误的案例追溯到对应的文档片段，看问题出在解析、分块还是检索。

**减分回答**：“用 Tika 提取纯文本就行”。

### Q4 知识图谱在 Agent 中有什么用？怎么构建？

**考察点**：结构化知识的应用。

**参考回答**

- **用途**：回答需要多跳推理和关系查询的问题（例如“某个产品的哪些零部件来自某个供应商”）；
  为 RAG 提供实体消歧和关联扩展；为 Agent 提供结构化的业务知识。
- **构建方式**：
  1. 从结构化数据（数据库）直接转换，准确性最高；
  2. 从非结构化文本中用模型抽取实体和关系，需要定义清晰的实体和关系类型，并做人工审核；
  3. 实体对齐和去重（同一个实体的不同名称）。
- **查询方式**：Agent 可以通过生成图查询语言，或者调用封装好的查询工具来使用图谱。
- **代价**：构建和维护成本高，适合关系复杂、准确性要求高的领域。

**追问**：*图谱和向量检索怎么结合？* 先用向量检索找到相关的实体或文档，再沿着图谱的关系扩展相关信息，一起提供给模型。

**减分回答**：认为知识图谱可以替代所有检索方式。

### Q5 如何设计一个“问数 + 生成报表”的 Agent 工作流？

**考察点**：Agent 与工作流的组合。

**参考回答**

1. **理解意图**：识别需要的指标、维度、时间范围、过滤条件；有歧义时追问。
2. **获取数据**：通过语义层或 Text2SQL 查询，经过安全校验后执行。
3. **校验数据**：检查结果是否为空、数量级是否合理、与历史数据的对比是否异常。
4. **分析与可视化**：选择合适的图表类型；需要计算时，在沙箱中执行代码，而不是让模型心算。
5. **生成结论**：结论必须有数据支撑，标注数据来源和口径。
6. **交付**：报表可以编辑和导出，并保留生成过程，方便复查。

- **关键点**：数字计算交给代码执行，模型负责理解和表达；每个数字都要能追溯到查询结果。

**追问**：*为什么不让模型直接计算同比、环比？* 模型做算术容易出错，而且错误难以察觉；用代码计算既准确又可复查。

**减分回答**：让模型读取原始数据后直接写出分析结论。

### Q6 知识的新鲜度和冲突怎么管理？

**考察点**：知识运营。

**参考回答**

- **新鲜度**：为每份文档记录更新时间和有效期；过期或长时间未更新的文档降低排序权重或提醒负责人复核；
  重要的政策类知识设置发布门禁。
- **冲突**：同一问题在不同文档中有不同答案时：
  1. 保留版本和时间信息，让模型优先使用最新的有效版本；
  2. 在建库阶段检测冲突并通知负责人处理；
  3. 回答时如果发现冲突，明确告知用户并引导核实。
- **下线**：旧版本的知识下线后，检索、预览和缓存要同步失效。

**追问**：*谁对知识的准确性负责？* 需要明确每个知识库或文档的负责人，由他们负责审核和更新；技术团队负责工具和流程。

**减分回答**：认为把文档导入一次就完成了，不需要持续维护。

### Q7 如何把业务系统的数据安全地提供给 Agent？

**考察点**：业务集成的方式。

**参考回答**

- **优先封装成工具**：把业务接口封装成职责明确的工具（例如查询订单状态），而不是让 Agent 直接访问数据库。
- **按身份授权**：工具从可信上下文获取当前用户身份，只返回该用户有权查看的数据。
- **精简返回**：只返回回答问题所需的字段，敏感字段脱敏。
- **写操作**：通过审批流程或幂等接口执行，保留审计。
- **可替换的后端**：工具定义与后端实现分离（例如通过 SPI），方便在测试环境使用模拟数据，在生产环境接入真实系统。
- **项目对照**：本项目的 `tool.backend.*` SPI，见 [项目第 01 期 Q2](../01-项目全景与架构设计.md)。

**追问**：*能否直接把内部的 REST API 通过 MCP 暴露给 Agent？* 可以，但要重新审视接口的粒度、返回字段和权限控制；
内部接口往往假设调用方是可信的服务，而不是可能被注入操控的模型。

**减分回答**：给 Agent 一个数据库账号，让它自己查询。

### Q8 如何构建和维护 Agent 的评测数据？可以用合成数据吗？

**考察点**：数据工程。

**参考回答**

- **来源**：线上真实问题（需要脱敏）、历史工单、业务专家编写的用例、badcase。
- **合成数据**：用模型基于知识库或业务规则生成问题和答案，可以快速扩大覆盖范围，特别是长尾和边界情况。
  但合成数据可能与真实分布有差异，需要人工抽检，并与真实数据混合使用。
- **标注**：制定清晰的标注规范；多人标注并计算一致性；有争议的样本由专家裁决。
- **维护**：评测集要有版本；定期根据线上数据更新；删除过期的用例（例如业务规则已经改变）。

**追问**：*用同一个模型生成评测数据并评测自己，有什么问题？* 可能存在偏差（模型更擅长回答自己生成的问题），
最好使用不同的模型生成，或者经过人工审核。

**减分回答**：“用模型生成 1000 条评测数据就够了”。

### Q9 多轮对话中如何可靠地收集结构化信息（槽位填充）？

**考察点**：对话式信息收集。

**参考回答**

- **两种方式**：
  - 让模型自然地追问：灵活，但可能漏问、忘记已经收集的信息、格式不规范；
  - 把表单定义成工具（槽位填充）：必填项由定义保证，格式由规则校验，进度保存在外部存储，跨轮次不会丢失。
- **推荐做法**：把收集过程做成工具，让模型决定何时调用、何时切换话题；工具负责校验格式和记录进度，并告诉模型下一步该问什么。
  这样既保留了对话的灵活性，又保证了信息的完整和准确。
- **不建议**：在对话链路中硬性切换到表单模式，用户会被锁在表单里，中途问别的问题就无法回答。
- **项目对照**：[项目第 02 期 Q6](../02-Agent核心机制-ReAct工具调用与多Agent.md)。

**追问**：*用户提供的信息前后矛盾怎么办？* 以最新的为准并向用户确认；关键信息在提交前统一复述确认。

**减分回答**：“让模型记住用户说过的话”。

### Q10 如何让 Agent 处理大量的结构化数据（例如分析一个 10 万行的表格）？

**考察点**：模型的能力边界与工具的使用。

**参考回答**

- **不要把数据全部放进上下文**：成本高，而且模型处理大量数字的准确率很低。
- **正确做法**：
  1. 让模型查看数据的结构和少量样本；
  2. 模型编写分析代码（SQL 或 Python），在沙箱中执行；
  3. 模型根据执行结果（统计值、图表）进行解读；
  4. 需要时迭代分析。
- **安全和资源**：沙箱限制执行时间和资源；数据文件的访问权限受控。

**追问**：*模型写的分析代码出错了怎么办？* 把错误信息反馈给模型修正；限制重试次数；
对关键结论做一致性检查（例如分组汇总的合计是否等于总数）。

**减分回答**：把表格转成文本放进提示词。

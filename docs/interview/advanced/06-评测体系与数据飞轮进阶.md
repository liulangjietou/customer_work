# 进阶第 06 期 · 评测体系与数据飞轮进阶

> **本期结论**：资深岗位的评测题，考的是“能不能用可信的数据做决策”：离线评测结论是否具有统计意义、
> 线上实验怎么设计、公开 Benchmark 能说明什么、数据飞轮怎么转起来。
>
> 题量 10。

### Q1 常见的 Agent 公开 Benchmark 有哪些？它们各自衡量什么？

**考察点**：了解行业的评测基准。

**参考回答**

- **工具调用**：BFCL（伯克利函数调用排行榜），衡量函数调用的准确性。
- **多轮工具使用与业务规则**：τ-bench，模拟用户与客服 Agent 在零售、航空等领域的多轮交互，要求遵守业务规则，
  并关注多次运行中都能成功的一致性。
- **软件工程**：SWE-bench 系列，让 Agent 修复真实开源仓库中的 issue，以测试是否通过作为判定。
- **通用助手**：GAIA，需要检索、推理和工具使用的综合问题。
- **网页和电脑操作**：WebArena、OSWorld 等，在模拟的网页或操作系统环境中完成任务。
- **正确看待**：公开 Benchmark 只能作为选型参考；业务效果必须用自己的评测集来衡量；还要警惕数据污染（题目已被模型训练过）。

**追问**：*为什么面向客户的 Agent 要特别关注“多次运行都成功”的指标？* 用户每次都会遇到一个随机的结果，
一个只有一半概率成功的 Agent，在用户看来就是不可靠的。

**减分回答**：只看公开榜单的排名来选择模型。

### Q2 评测集只有 200 条，新版本的准确率从 85% 提升到 87%，能说明新版本更好吗？

**考察点**：统计意义。

**参考回答**

- **不一定**：200 条样本下，2 个百分点的差异只相当于 4 条用例，很可能在随机波动范围内。
  准确率的标准误约为 √(p(1−p)/n)，p=0.85、n=200 时约 2.5%，这点差异远不足以得出结论。
- **更可靠的做法**：
  1. **配对比较**：在同一批用例上，看“新版本对、旧版本错”和“新版本错、旧版本对”的数量，用配对检验（例如 McNemar 检验）判断显著性；
  2. **多次运行**：模型输出有随机性，每个用例运行多次，统计通过率；
  3. **扩大样本**或者针对变更相关的用例做重点评测；
  4. **看回归用例**：即使总体提升，也要检查是否有关键用例变差。

**追问**：*线上 A/B 测试需要多少流量？* 取决于基线指标、希望检测到的最小差异和显著性要求，要事先计算样本量；
流量不够时应该报告“结论不确定”，而不是强行下结论。

**减分回答**：“87% 比 85% 高，所以新版本更好”。

### Q3 如何为 Agent 设计线上 A/B 实验？

**考察点**：实验设计。

**参考回答**

- **分流单位**：按用户或会话分流（而不是按请求），保证同一个用户的体验一致，避免会话中途切换版本。
- **指标**：
  - 主要指标：问题解决率、转人工率、满意度；
  - 护栏指标：延迟、成本、错误率、安全事件；
  - 预先定义清楚，避免事后挑选对自己有利的指标。
- **样本量与时长**：事先计算；至少覆盖完整的业务周期（例如包含工作日和周末）。
- **注意事项**：新奇效应；不同租户之间的差异；版本之间的缓存互相影响（语义缓存要按版本隔离）。
- **结论**：达不到最小样本量时标记为“结论不确定”。

**追问**：*什么是影子测试？和 A/B 测试有什么区别？* 影子测试把线上请求复制一份给新版本处理，但结果不返回给用户，
用于在零风险的情况下对比输出差异；它无法衡量用户反馈类的指标。

**减分回答**：“先切 50% 流量看看效果”。

### Q4 什么是数据飞轮？Agent 的数据飞轮怎么建立？

**考察点**：持续改进的机制。

**参考回答**

- **定义**：线上使用产生数据 → 数据用于改进 Agent → 改进后效果更好、使用更多 → 产生更多数据，形成正向循环。
- **建立步骤**：
  1. **采集**：完整记录对话轨迹（输入、检索内容、工具调用、输出）和用户反馈（显式评价、转人工、重复提问）；
  2. **筛选**：找出失败案例和高价值案例；
  3. **标注与归因**：确定失败原因属于哪个环节；
  4. **改进**：补充知识、修改提示词和工具、积累训练数据用于微调；
  5. **验证**：把案例加入评测集，确认改进有效；
  6. **上线观察**：确认线上效果。
- **前提**：数据采集要合规（授权、脱敏）；要有版本和归因信息，才能知道每次改进的效果。

**追问**：*飞轮转不起来的常见原因是什么？* 数据采集不完整（没有记录轨迹）；没有人负责处理 badcase；
改进没有经过评测验证，无法证明有效。

**减分回答**：只是把日志存起来，却从来没有分析和使用。

### Q5 如何用用户的隐式反馈评估 Agent 效果？

**考察点**：反馈信号的设计。

**参考回答**

- **常见的隐式信号**：转人工、重复提问同一个问题、会话中途放弃、复制回答内容、点击引用链接、后续的投诉、问题是否被最终解决（工单状态）。
- **注意**：
  1. 信号有噪声，需要组合使用并结合抽样的人工检查；
  2. 显式评价（例如满意度）的回收率通常很低，要同时记录邀请数和回收数；
  3. 评测、巡检产生的会话不能计入这些信号。
- **应用**：作为线上指标监控；筛选需要人工检查的会话；作为 A/B 实验的评估指标。

**追问**：*满意度评分很高，但回收率只有 5%，说明什么？* 这个分数只代表愿意评价的少数用户，不能代表整体体验，需要结合其他信号判断。

**减分回答**：只看点赞和点踩。

### Q6 LLM-as-Judge 的评分结果如何校准和验证？

**考察点**：评测工具的可信度。

**参考回答**

- **与人工标注对比**：抽取一部分样本同时由人工和裁判模型评分，计算一致性（例如一致率或相关系数）；一致性不够时，改进评分标准或更换裁判模型。
- **稳定性**：同一样本多次评分，检查结果的方差。
- **偏差检查**：交换比较的位置、控制回答的长度，检查是否存在系统性偏差。
- **标准细化**：评分标准写清楚每个分数的具体定义并给出示例。
- **版本管理**：裁判模型和评分标准的任何变化都会影响分数，需要记录版本，并且只比较同一版本下的分数。

**追问**：*裁判模型升级后分数整体上升了，说明被测模型变好了吗？* 不能说明，只是评分尺度变了；跨裁判版本的分数不可比较。

**减分回答**：直接把裁判模型的分数当作真实效果。

### Q7 如何评测 Agent 的安全性？

**考察点**：安全评测。

**参考回答**

- **评测集**：包含提示词注入（直接和间接）、越狱、诱导泄露信息、越权操作、虚假承诺、违规内容等攻击用例。
- **指标**：攻击成功率、正常请求被误拦截的比例（两者需要平衡）。
- **轨迹检查**：不只看回答文本，还要检查是否调用了不该调用的工具、是否访问了越权的数据。
- **持续运行**：每次模型、提示词、工具发生变化时都运行；把线上发现的攻击方式加入评测集。
- **红队**：定期进行人工红队测试，发现新的攻击方式。

**追问**：*安全拦截太严格，影响了正常用户，怎么办？* 同时统计误拦率；对误拦的案例进行分析，优化规则；
对高风险场景偏严格、低风险场景偏宽松。

**减分回答**：只测试几个常见的越狱提示词。

### Q8 如何评估 RAG 系统中每个环节的贡献？

**考察点**：分环节评测与归因。

**参考回答**

- **分环节评测**：
  - 检索：Recall@K、MRR；
  - 重排序：正确片段的排名提升了多少；
  - 生成：在给定正确资料的情况下，回答的忠实度和正确性。
- **消融实验**：分别去掉或替换某个环节（例如关闭重排序、关闭查询改写），看整体效果的变化，从而评估每个环节的价值。
- **成本对比**：每个环节带来的延迟和成本，与它带来的效果提升一起权衡。
- **按问题类型分组**：不同类型的问题，各环节的贡献不同。

**追问**：*查询改写让召回率提升了 3%，但延迟增加了 500 毫秒，要不要上线？* 取决于业务对延迟的要求和召回率提升对最终回答的影响；
也可以只对特定类型的问题启用。

**减分回答**：只看端到端的效果，说不出每个环节的作用。

### Q9 评测结果怎么用于发布决策？

**考察点**：评测与发布流程的结合。

**参考回答**

- **发布门禁**：核心评测集的通过率不低于基线；关键用例不允许出现回归；安全评测必须通过。
- **评测不完整时阻止发布**：例如裁判模型不可用、部分用例执行失败，应该阻止发布而不是放行。
- **记录决策依据**：发布记录中保存评测的版本、结果和对比报告，便于事后追溯。
- **例外流程**：确实需要在门禁未通过的情况下发布（例如紧急修复），需要审批并记录原因。
- **上线后的验证**：灰度期间观察线上指标，确认与离线评测的结论一致。

**追问**：*离线评测通过了，线上效果却变差了，可能是什么原因？* 评测集和线上流量的分布不一致；评测时使用的模拟后端与真实后端的行为不同；
线上配置没有完全生效。

**减分回答**：“评测只是参考，发布还是看感觉”。

### Q10 如何衡量 Agent 带来的业务价值（ROI）？

**考察点**：业务视角。

**参考回答**

- **收益**：
  - 效率：自动解决的比例、节省的人力工时、处理时长的缩短；
  - 体验：满意度、响应时间；
  - 业务结果：转化率、挽回的订单等。
- **成本**：模型调用费用、基础设施、研发与运营人力、人工兜底的成本。
- **单位成本**：每个被解决的问题或每个工单的成本，与人工处理的成本对比。
- **口径**：与上线前的基线或对照组比较；排除季节和活动等外部因素的影响。
- **注意**：只统计“AI 回复了多少”没有意义，要看问题是否真的被解决了。

**追问**：*AI 解决率很高，但转人工后投诉增加了，怎么解释？* 可能 AI 把难处理的问题都转给了人工，或者 AI 的错误回答导致了后续投诉；
需要统计完整链路的结果，而不是只看 AI 环节的指标。

**减分回答**：用“AI 回复的消息数量”来证明价值。

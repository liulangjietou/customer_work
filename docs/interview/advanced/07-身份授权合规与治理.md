# 进阶第 07 期 · 身份授权、合规与治理

> **本期结论**：Agent 会代表用户去操作系统，这带来了新的身份和授权问题：Agent 以谁的身份行动、能做到什么程度、出了问题谁负责。
> 在国内落地还必须了解生成式 AI 相关的监管要求。资深候选人需要能把这些要求转化为具体的技术设计。
>
> 说明：法规条款以官方最新发布的文本为准，本期只讲技术落地要点。
>
> 题量 10。

---

### Q1 Agent 调用业务系统时，应该以谁的身份去调用？

**考察点**：委托授权的设计。

**参考回答**

- **三种方式**：
  1. **服务账号**：Agent 使用一个统一的高权限账号。实现最简单，但无法区分用户，容易越权，**不推荐**用于访问用户数据；
  2. **代表用户**：Agent 携带当前用户的身份和权限去调用，业务系统按用户权限校验。这是最安全的方式；
  3. **委托授权**：用户明确授权 Agent 在一定范围和时限内代表自己执行操作（例如基于 OAuth 的授权和令牌交换）。
- **原则**：
  - Agent 的权限不能超过它所代表的用户；
  - 身份必须来自服务端验证过的上下文，不能来自模型生成的参数；
  - 审计日志要同时记录“哪个用户”和“哪个 Agent”执行了操作。

**追问**：*后台定时运行的 Agent 没有用户在场，以谁的身份执行？* 以任务创建者的身份执行（提交任务时保存身份并在执行时恢复），
或者使用权限严格受限的专用服务账号，并记录审计。

**减分回答**：“Agent 用管理员账号访问所有系统”。

### Q2 用户的身份在 Agent 调用链路中怎么传递才可靠？

**考察点**：上下文传播的工程实现。

**参考回答**

- **入口处建立**：在鉴权过滤器中校验 JWT 或 API Key，把租户和用户身份写入请求上下文。
- **跨线程传递**：响应式链路需要借助 Reactor Context 以及与 ThreadLocal 之间的自动同步机制；
  异步任务需要在提交时捕获身份，在执行时显式恢复。
- **跨服务传递**：调用下游服务时传递身份令牌，由下游重新校验，而不是只传一个用户 ID。
- **缺失时的处理**：访问数据时缺少身份应该直接拒绝，而不是使用默认值。
- **测试**：必须测试真实的跨线程场景，单元测试中的同步回调容易掩盖问题
  （见 [项目第 06 期 Q2、Q6](../06-Java并发与响应式流式链路.md)）。

**追问**：*为什么不能从用户的会话 ID 中解析出租户？* 会话 ID 是客户端可以控制的，攻击者可以伪造一个带有其他租户前缀的会话 ID。

**减分回答**：“把用户 ID 作为参数传给工具就行”。

### Q3 Agent 使用的各类凭据（模型 API Key、业务系统密钥、MCP 凭据）应该怎么管理？

**考察点**：密钥管理。

**参考回答**

- **集中存储**：使用密钥管理服务（KMS、Vault 等），业务表和配置中只保存引用，不保存明文。
- **传输加密**：配置下发时密钥以密文传输，接收方校验签名后再解密。
- **最小权限**：每个密钥只授予必要的权限；不同环境、不同租户使用不同的密钥。
- **轮换**：支持定期轮换，轮换期间新旧密钥同时有效。
- **不泄露**：不出现在日志、错误信息、接口返回和提示词中；不注入代码执行的沙箱环境。
- **API Key 的保存**：用户侧的 API Key 只保存哈希指纹，用于校验和统计。

**追问**：*模型能不能看到业务系统的密钥？* 不能。工具在执行时由服务端注入凭据，凭据永远不应该出现在模型的上下文中。

**减分回答**：把密钥写在配置文件或环境变量里，并且打印在日志中。

### Q4 在国内上线一个面向公众的生成式 AI 服务，需要满足哪些合规要求？技术上怎么配合？

**考察点**：监管要求的技术落地。

**参考回答**

- **主要的法规依据**：《生成式人工智能服务管理暂行办法》、互联网信息服务算法推荐和深度合成的相关管理规定、
  《个人信息保护法》《数据安全法》，以及对 AI 生成内容进行标识的相关规定。
  面向公众提供服务通常需要完成相应的安全评估和备案（例如使用的模型需要已经完成备案）。
- **技术上需要配合的要点**：
  1. **内容安全**：输入和输出的内容审核（敏感词、违规内容），拦截记录留存；
  2. **生成内容标识**：按要求对 AI 生成的内容进行标识；
  3. **个人信息保护**：告知与授权、最小化收集、脱敏、支持查询和删除；
  4. **日志留存**：按要求保存对话和操作日志，便于追溯；
  5. **投诉举报**：提供投诉渠道和处理机制；
  6. **数据出境**：使用境外模型时评估数据出境的合规要求。
- **原则**：合规要求要落实到具体的系统能力上，并作为上线检查项。

**追问**：*使用境外的模型 API 面向国内用户提供服务，有什么风险？* 数据出境合规、模型备案要求、服务可用性，都需要提前评估。

**减分回答**：认为内部技术人员不需要了解合规要求。

### Q5 Agent 的审计日志应该记录什么？

**考察点**：可追溯性设计。

**参考回答**

- **记录内容**：
  - 谁：用户、租户、Agent、渠道；
  - 什么时间、在哪个会话；
  - 做了什么：调用了哪个工具、参数是什么（脱敏后）、结果如何；
  - 为什么：模型的决策依据（可以关联到模型调用记录）；
  - 审批信息：是否经过人工审批，审批人是谁。
- **要求**：审计日志不可篡改（只追加）；敏感信息脱敏；保留足够的时间；支持按用户、工具、时间查询。
- **与普通日志的区别**：审计日志是给合规和安全团队追溯使用的，不能因为日志级别或采样而丢失。

**追问**：*审计日志中记录模型的完整输入输出会有什么问题？* 可能包含大量个人信息，存储成本也高；
一般记录脱敏后的关键信息，完整内容按需保存在权限更严格的存储中。

**减分回答**：“有应用日志就够了”。

### Q6 多租户平台中，租户管理员能授予的权限应该如何限制？

**考察点**：权限边界的设计。

**参考回答**

- **判断标准**：一个权限授予租户管理员后，影响范围会不会超出他自己的租户。
- **必须收归平台（控制面）的权限**：
  1. 操作全平台共享的资源（例如全局的模型配置）；
  2. 能把代码或流量带出本进程的能力（例如挂接任意的 MCP 服务、执行代码的 Skill、任意 SQL 查询、任意 HTTP 请求）；
  3. 能看到全平台数据的视图（例如全局计费、全局日志）。
- **租户管理员只能在自己的租户内管理角色和数据**；跨租户的操作只能由平台管理员执行，并留有审计。
- **防止自我提权**：租户管理员不能给自己创建超出租户范围的角色。
- **项目对照**：[项目第 05 期 Q6](../05-安全护栏与治理中间件.md)、[项目第 07 期 Q7](../07-生产化-多租户限流幂等与一致性.md)。

**追问**：*为什么“执行代码的 Skill”必须收归平台？* 它可以访问服务器资源和网络，影响范围不限于单个租户。

**减分回答**：“租户管理员在自己的租户里拥有所有权限”。

### Q7 如何治理企业内部大量涌现的 Agent 和提示词？

**考察点**：规模化治理。

**参考回答**

- **资产登记**：所有 Agent、提示词、工具、知识库都在平台上登记，有负责人和版本。
- **发布流程**：变更需要经过评测和审批才能上线；支持灰度和回滚。
- **权限控制**：谁能创建、修改、发布；工具和数据的访问需要审批。
- **统一的治理能力**：安全护栏、审计、配额、可观测由平台统一提供，而不是每个 Agent 各自实现。
- **成本分摊**：按 Agent 和部门统计成本。
- **生命周期**：长期不用的 Agent 下线；依赖的模型或工具下线时通知负责人。

**追问**：*各团队自己写的 Agent 不愿意接入平台，怎么办？* 让接入平台的成本足够低（例如提供 SDK 和统一的装配方式）；
同时对访问敏感数据和对外提供服务设置强制性要求。

**减分回答**：“让各团队自己管理”。

### Q8 如何防止 Agent 在对外服务中做出有法律风险的承诺？

**考察点**：业务风险控制。

**参考回答**

- **能力边界**：工具描述写明能力的限制（例如“只登记申请，不代表审批通过”）；系统提示词明确禁止承诺赔偿、退款到账时间等。
- **输出检查**：检测承诺类的表述（例如“已退款”“保证赔偿”），核对是否有工具调用的证据；没有证据时拦截并纠正。
- **流式场景**：已经输出的内容无法撤回，需要立即停止输出，追加明确否定前文的澄清，并转人工。
- **免责提示**：在界面上说明 AI 回答仅供参考，以人工确认的结果为准。
- **审计**：保留完整的对话记录，便于纠纷处理。
- **项目对照**：[项目第 05 期 Q4](../05-安全护栏与治理中间件.md)。

**追问**：*检测承诺类表述只靠关键词够吗？* 不够。同义的表述可以绕过关键词，需要结合语义判断，
但语义判断只能用来增加拦截，不能放宽已有的判定。

**减分回答**：“在提示词里告诉模型不要乱承诺”。

### Q9 用户要求删除自己的所有数据，Agent 平台需要处理哪些地方？

**考察点**：数据删除的完整性。

**参考回答**

- **需要处理的数据**：对话记录、会话状态、长期记忆、事实日志、语义缓存、上传的附件（对象存储）、
  向量索引中的相关内容、日志中可识别的个人信息、备份（按保留策略处理）、发送给第三方的数据（按协议处理）。
- **做法**：
  1. 数据按用户标识组织，便于查找和删除；
  2. 删除操作覆盖所有存储，并验证删除结果；
  3. 给用户明确的删除回执；
  4. 记录删除操作用于审计（记录操作本身，而不是被删除的内容）。
- **设计阶段就要考虑**：新增任何存储用户数据的地方时，同步更新删除流程。

**追问**：*模型厂商那边的数据怎么处理？* 选择不保存数据或不用于训练的服务条款；需要时按照厂商提供的方式申请删除。

**减分回答**：只删除数据库中的对话记录。

### Q10 如何处理 Agent 系统中的第三方依赖风险（模型、插件、MCP 服务、开源组件）？

**考察点**：供应链安全。

**参考回答**

- **模型**：多厂商备份；固定模型版本；评估数据处理条款。
- **插件和 MCP 服务**：接入前做安全评估；运行时限制网络访问和权限；监控契约变化；工具描述和返回内容当作不可信内容处理。
- **开源组件**：依赖扫描和漏洞监控；固定版本；升级时审查变更（尤其是默认行为的变化）。
- **模型文件和数据集**：从可信来源获取并校验完整性；注意投毒风险。
- **退出方案**：关键依赖需要有替代方案，并定期验证可用性。

**追问**：*一个常用的 MCP 服务被发现存在恶意行为，怎么应急？* 立即禁用；通过审计日志评估影响范围；
轮换相关的凭据；排查通过它执行过的所有操作。

**减分回答**：“开源的、大家都在用，所以安全”。

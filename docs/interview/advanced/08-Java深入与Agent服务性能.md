### Q1 Agent 服务的负载有什么特点？对 JVM 调优有什么影响？

**考察点**：负载特征分析。

**参考回答**

- **特点**：请求耗时长（秒级到分钟级）；大量长连接（WebSocket、SSE）；内存中同时存在大量会话的对象（上下文、流式缓冲）；
  CPU 占用相对不高，主要时间在等待外部 IO。
- **对 JVM 的影响**：
  1. 长时间存活的请求对象会晋升到老年代，要关注老年代的增长和 GC 停顿；
  2. 流式处理中会产生大量短生命周期的小对象（每个分片），年轻代的回收频繁；
  3. 选择低停顿的垃圾回收器（例如 G1 或 ZGC），避免 GC 停顿导致流式输出卡顿；
  4. 容器环境中正确设置堆内存占容器内存的比例，为堆外内存（Netty 直接内存）留出空间。
- **关注的指标**：GC 停顿时间、老年代使用率、堆外内存、线程数。

**追问**：*流式输出偶尔会卡顿一下，怎么判断是不是 GC 导致的？* 对照 GC 日志中的停顿时间和卡顿发生的时间点；
同时排除网络、模型厂商和线程池的原因。

**减分回答**：“把堆内存设大一点”。

### Q2 虚拟线程（JDK 21）适合 Agent 服务吗？有什么需要注意的？

**考察点**：新特性的理解。

**参考回答**

- **适合的原因**：Agent 服务大部分时间在等待 IO（模型调用、工具调用、数据库），虚拟线程可以用同步的写法支撑大量并发，代码简单、容易调试。
- **注意事项**：
  1. **线程固定（pinning）**：在 `synchronized` 块中执行阻塞操作会把虚拟线程固定在载体线程上，降低并发能力
     （新版 JDK 正在逐步改善这一点）。长时间持有锁的阻塞代码要改用 `ReentrantLock`；
  2. **ThreadLocal**：虚拟线程的数量可能非常大，每个线程都保存大对象会消耗大量内存；
  3. **下游资源仍然有限**：数据库连接池、模型厂商的并发额度不会因为使用了虚拟线程而增加，仍然需要限流；
  4. **框架支持**：确认使用的库和框架对虚拟线程的兼容性。
- **与响应式的关系**：两者都能解决高并发 IO 问题；已有的响应式系统没必要重写，新系统可以根据团队情况选择。

**追问**：*用了虚拟线程，还需要线程池吗？* 虚拟线程本身不需要池化；但要用信号量等方式限制对下游资源的并发访问。

**减分回答**：“用了虚拟线程就不用考虑并发问题了”。

### Q3 基于 Netty 的 WebFlux 服务，处理流式输出时要注意什么？

**考察点**：网络层的细节。

**参考回答**

- **不能阻塞事件循环线程**：任何阻塞操作（数据库、同步 HTTP、加锁等待）都要切换到弹性线程池，否则会拖慢所有连接。
- **背压**：客户端消费速度慢时，服务端要能感知并控制发送速度，避免在内存中无限堆积数据。
- **连接管理**：设置空闲超时和心跳；客户端断开时取消上游的订阅，停止模型调用。
- **堆外内存**：Netty 使用直接内存，需要监控；ByteBuf 的泄漏会导致堆外内存持续增长。
- **写出的线程**：下游的处理（过滤、写数据库）不要在模型的 IO 线程上执行，避免拖慢读取模型的分片。

**追问**：*怎么排查 Netty 直接内存泄漏？* 开启 Netty 的泄漏检测；监控直接内存的使用量；检查自定义编解码中 ByteBuf 是否正确释放。

**减分回答**：认为 WebFlux 自动解决了所有并发问题。

### Q4 Reactor 的链路出了问题，怎么调试？

**考察点**：响应式编程的调试能力。

**参考回答**

- **问题**：响应式链路的异常堆栈通常只有框架内部的调用，看不出是在哪个业务算子上出的错。
- **方法**：
  1. `checkpoint("描述")`：在关键位置标记，异常时堆栈中会显示这个描述；
  2. `log()`：打印每个信号（订阅、元素、完成、错误、取消），用于定位信号的流转；
  3. 调试模式（`Hooks.onOperatorDebug()` 或 Reactor 的调试代理）：在异常中记录算子组装位置，便于定位，但开销较大，不适合在生产环境全量开启；
  4. 用 `StepVerifier` 编写测试，验证元素顺序、完成信号和错误信号。
- **常见的问题**：忘记订阅导致什么都没执行；空流导致下游从未被调用；在错误的线程上阻塞；
  `doFinally` 在取消和错误时也会执行，导致误判。

**追问**：*为什么 `Mono.fromCallable` 返回 null 会导致问题？* 返回 null 会变成空的 `Mono`，
下游依赖“恰好一个元素”的逻辑就不会执行，而且不会报错（见 [项目第 06 期 Q4](../06-Java并发与响应式流式链路.md)）。

**减分回答**：只会在链路中加 `System.out.println`。

### Q5 Spring Boot 自动装配的原理是什么？在 Agent 基础设施 starter 中如何应用？

**考察点**：Spring 原理与工程实践。

**参考回答**

- **原理**：启动时读取自动配置类的清单（Spring Boot 3 中是 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件），
  根据条件注解（`@ConditionalOnClass`、`@ConditionalOnProperty`、`@ConditionalOnMissingBean` 等）决定是否注册 Bean。
- **在 Agent starter 中的应用**：
  1. 提供默认实现（例如内存存储、模拟的业务后端），并加上 `@ConditionalOnMissingBean`，使用方声明同类型的 Bean 即可替换；
  2. 通过开关属性控制可选能力（例如语义缓存、多租户）；
  3. 区分 Web 类型：只适用于响应式栈的组件要加上 `@ConditionalOnWebApplication(type = REACTIVE)`；
  4. 可选依赖用 `ObjectProvider` 获取，缺失时优雅降级。
- **需要注意**：`@ConfigurationProperties` 的默认值要写成字面量，否则配置元数据中不会显示默认值；
  新增可选 Bean 时要有装配测试，避免 Bean 实际不存在但单元测试（使用 mock）仍然通过。

**追问**：*用了 `ObjectProvider.getIfAvailable()` 的代码，有什么隐藏风险？* Bean 不存在时能力会静默关闭，不会报错。
项目中就出现过语义缓存因为缺少 Embedding Bean 而完全失效的问题，需要装配测试来防护。

**减分回答**：只知道 `@SpringBootApplication` 会自动扫描。

### Q6 如何设计 Java 中的 SPI 扩展点，让使用方可以替换 Agent 的业务后端？

**考察点**：可扩展的架构设计。

**参考回答**

- **接口定义**：面向业务能力定义接口（例如查询订单、提交退款），而不是面向具体的系统。
- **默认实现**：提供模拟实现或内存实现，用于开发和测试，并用 `@ConditionalOnMissingBean` 标注。
- **替换方式**：使用方声明同类型的 Bean 即可覆盖，不需要修改工具的代码。
- **与工具分离**：工具负责面向模型的描述和参数，后端负责业务逻辑，两者独立演进。
- **上下文传递**：接口实现能获取到租户和用户身份（通过可信的上下文），以便做权限控制。
- **原则**：只有在出现第二个真实的实现需求时才引入抽象，避免过度设计。

**追问**：*为什么不直接用 Java 原生的 `ServiceLoader`？* 在 Spring 应用中，借助 Spring 的 Bean 机制更方便使用依赖注入、条件装配和配置；
`ServiceLoader` 更适合不依赖 Spring 的库。

**减分回答**：在工具代码中通过 `if/else` 判断使用哪个后端。

### Q7 高并发场景下，Agent 的会话级缓存应该怎么选型？

**考察点**：缓存设计。

**参考回答**

- **进程内缓存**：用于 Agent 实例、配置这类可以重建的对象。要设置容量上限和淘汰策略（例如 Caffeine），
  淘汰时释放资源（例如关闭 MCP 客户端）。
- **分布式缓存**（Redis）：用于需要跨实例共享的数据（计数器、锁、短期的会话数据）。要考虑网络延迟和故障降级。
- **锁的粒度**：避免在缓存的计算过程中持有全局锁，例如 `Collections.synchronizedMap` 的 `computeIfAbsent` 会在整个构建过程中持有全局锁，
  使用按键加锁的缓存实现更好。
- **缓存键的设计**：必须包含隔离维度（租户、用户），否则会发生数据串用。
- **一致性**：配置更新时通过版本或代际让旧的缓存失效。

**追问**：*缓存了 Agent 实例，但配置更新了，怎么处理？* 清空缓存，让后续请求用新配置重建；
状态保存在外部存储中，重建不会丢失会话。

**减分回答**：使用一个没有容量上限的 `HashMap` 作为缓存。

### Q8 分布式锁在 Agent 场景中的使用要注意什么？

**考察点**：分布式锁的正确使用。

**参考回答**

- **线程绑定问题**：Redisson 的 `RLock` 在释放时会校验持有锁的线程，而响应式链路中加锁和释放可能不在同一个线程，
  会导致释放失败。可以使用 `RPermitExpirableSemaphore` 这类通过许可 ID 释放的机制。
- **租约时长**：必须显著大于一次处理的最长耗时，否则长请求执行到一半就失去了互斥保护；同时要保证实例崩溃后锁能自动过期。
- **故障降级**：Redis 不可用时是降级为本地锁、直接拒绝，还是放行，要根据业务决定。
- **锁不能保证绝对互斥**：租约过期、网络分区都可能导致两个实例同时持有锁，所以关键的写操作还需要乐观并发（版本号）或 fencing token 兜底。
- **项目对照**：[项目第 06 期 Q5](../06-Java并发与响应式流式链路.md)。

**追问**：*什么是 fencing token？* 每次获取锁时得到一个单调递增的令牌，写入时带上令牌，存储端拒绝比当前令牌小的写入，
防止旧的持锁者在锁过期后仍然写入。

**减分回答**：“用 Redis 的 SETNX 就能保证互斥”。

### Q9 如何在 Java 中实现一个高性能的流式敏感词过滤？

**考察点**：算法与工程结合。

**参考回答**

- **算法**：多个关键词的匹配使用 Aho-Corasick 自动机，一次扫描即可找出所有命中，时间复杂度与文本长度线性相关，与词库规模无关。
- **文本归一化**：全角转半角、统一大小写、去除插入的干扰字符，并记录归一化前后的位置映射，以便对原文打码。
- **流式处理**：维护一个缓冲区，只输出确定不会构成敏感词的前缀，保留可能继续扩展成敏感词的尾部，流结束时输出剩余部分。
- **线程安全与热更新**：自动机构建完成后不可变，天然线程安全；词库更新时构建新的实例并原子替换引用，匹配时无需加锁。
- **每条流一个过滤器实例**：过滤器有状态，不能跨流复用。
- **项目对照**：[项目第 05 期 Q3](../05-安全护栏与治理中间件.md)。

**追问**：*为什么缓冲区中保存的是原文，而不是打码后的文本？* 如果短词是长词的前缀，提前打码会破坏长词的匹配。

**减分回答**：用 `String.contains` 逐个检查每个敏感词。

### Q10 如何为 Agent 服务实现优雅停机？

**考察点**：发布过程的稳定性。

**参考回答**

- **步骤**：
  1. 停止接收新请求（从负载均衡中摘除、健康检查返回不可用）；
  2. 等待正在处理的请求完成（设置超时上限）；
  3. 对于长连接，通知客户端重连到其他实例；
  4. 保存需要持久化的状态；
  5. 释放资源（连接池、MCP 客户端、线程池）。
- **Spring 中的实现**：开启 Web 服务器的优雅停机；使用 `SmartLifecycle` 控制组件的停止顺序。
- **Kubernetes**：`terminationGracePeriodSeconds` 必须大于应用自身的优雅停机超时，否则进程会在等待期间被强制终止。
- **长任务**：无法在超时内完成的任务，需要保存检查点，由其他实例恢复执行。

**追问**：*WebSocket 长连接在停机时如何处理？* 发送关闭帧通知客户端，客户端重连到其他实例，并在重连后补拉期间遗漏的消息。

**减分回答**：直接执行 `kill -9`。

### Q11 如何在 Java 中调用大模型 API 并正确处理流式响应？

**考察点**：HTTP 客户端与流式解析。

**参考回答**

- **客户端选择**：使用支持流式响应的 HTTP 客户端（例如 WebClient、JDK HttpClient、OkHttp），或者使用框架的封装。
- **SSE 解析**：按行读取，处理 `data:` 前缀，识别结束标记；注意一个事件可能跨越多个网络数据包，需要缓冲拼接。
- **增量组装**：文本增量直接转发；工具调用的参数是分片返回的，需要按调用 ID 拼接完整后再解析 JSON。
- **超时**：设置连接超时、首个字节超时，以及相邻两个分片之间的空闲超时。
- **取消**：客户端断开时关闭上游连接。
- **错误处理**：流中间可能返回错误事件；HTTP 状态码为 200 也不代表整个流都成功了。

**追问**：*工具调用的参数分片到达，什么时候可以解析？* 等该调用对应的结束信号到达、参数拼接完整之后再解析；
逐片解析会失败。

**减分回答**：把整个响应读完后再一次性解析。

### Q12 如何保证 Agent 服务的代码质量？

**考察点**：工程规范。

**参考回答**

- **测试策略**：确定性逻辑用单元测试；关键链路用真实容器的集成测试（避免 mock 掩盖装配问题）；模型相关的效果用评测集。
- **结构性测试**：扫描源码或反射，确保新增的构建 Agent 的链路都接入了统一的治理能力；确保同一个常量只在一处定义。
- **变异测试**：检查断言是否真的能发现错误。
- **常量与配置**：禁止魔法值，同一个概念只有一个定义处；配置的默认值只在一处声明。
- **代码评审关注点**：新的链路是否接入了治理能力；异步回调中是否恢复了上下文；故障时是放行还是拦截；资源是否被释放。
- **日志规范**：日志带错误码和占位符，不打印敏感信息。

**追问**：*模型相关的代码很难写测试，怎么办？* 把模型调用隔离在接口之后，用模拟模型测试编排逻辑；模型效果交给评测集。

**减分回答**：“Agent 的效果不确定，所以不用写测试”。

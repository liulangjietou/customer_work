### Q1 Agent 技术在过去两年有哪些重要的发展趋势？

**考察点**：行业视野。

**参考回答**

- **从“提示词工程”到“上下文工程”再到“Harness 工程”**：关注点从写好一段提示词，转向管理每次调用的上下文，再到整个运行时外壳的工程化。
- **协议标准化**：MCP 成为工具和数据接入的事实标准；A2A 推动 Agent 之间的互操作；AG-UI 等协议规范 Agent 与界面的交互。
- **模型原生的 Agent 能力增强**：推理模型、针对工具使用和长任务的专门训练，让模型的多步决策能力显著提升。
- **编码 Agent 快速成熟**：从代码补全发展到能够自主完成任务、运行测试、提交代码。
- **GUI 操作**：Computer Use / Browser Use 让 Agent 能操作没有 API 的系统。
- **工程化和治理成为重点**：评测、可观测、安全、成本控制成为企业落地的核心问题。

**追问**：*这些趋势对你的工作有什么影响？* 应该结合自己的实践回答，例如接入 MCP 后工具集成的方式发生了什么变化。

**减分回答**：只能说出几个产品名称。

### Q2 Coding Agent 的架构一般是怎样的？为什么它的落地速度比其他领域快？

**考察点**：典型 Agent 产品的架构理解。

**参考回答**

- **架构**：
  1. 工具：读写文件、代码搜索、执行命令、运行测试、版本控制操作；
  2. 上下文管理：按需读取文件，而不是把整个仓库放进上下文；子 Agent 做大范围探索；上下文压缩；
  3. 项目说明文件：让 Agent 了解项目的约定和命令；
  4. 权限：执行命令、修改文件前的确认机制；
  5. 验证循环：修改后运行测试和检查，失败时继续修复。
- **落地快的原因**：
  1. 有天然的验证方式（编译、测试），能快速判断对错；
  2. 开发者本身就是用户，反馈快；
  3. 训练数据丰富，结果容易评估，适合做强化学习。
- **对其他领域的启发**：为任务建立可验证的检查方式，是提升 Agent 可靠性的关键。

**追问**：*在企业中推广 Coding Agent，需要注意什么？* 代码安全（不泄露到外部）；权限控制；产出的代码仍然需要评审；
建立团队的使用规范和项目说明文件。

**减分回答**：认为 Coding Agent 只是更强的代码补全。

### Q3 GUI Agent（Computer Use / Browser Use）的主要挑战是什么？适合什么场景？

**考察点**：新方向的判断。

**参考回答**

- **挑战**：
  1. **可靠性**：界面变化、加载延迟、弹窗都可能导致操作失败，长流程的成功率会逐步下降；
  2. **成本和速度**：基于截图的方式需要多次视觉模型调用，速度慢、成本高；
  3. **安全**：网页上的内容可能包含注入指令；误操作可能导致购买、删除等不可逆的后果。
- **适合的场景**：没有 API 的旧系统；流程相对固定的重复操作；测试自动化。
- **不适合的场景**：已经有 API 的系统（直接调用 API 更可靠）；涉及资金的高风险操作且无人确认。
- **实践建议**：优先使用 API；GUI 操作用于补充；关键步骤人工确认；在隔离的环境中运行。

**追问**：*与传统的 RPA 相比有什么区别？* RPA 依赖预先录制的固定脚本，界面一变就失效；GUI Agent 能理解界面并动态调整，
但确定性不如 RPA。两者可以结合：稳定的流程用 RPA，需要判断的部分交给 Agent。

**减分回答**：“以后所有系统都可以让 Agent 直接操作界面”。

### Q4 实时语音 Agent 的技术路线有哪些？各有什么优缺点？

**考察点**：多模态交互的理解。

**参考回答**

- **级联方案**（语音识别 → 大模型 → 语音合成）：
  - 优点：每个环节都能单独选型和优化；文本环节可以复用现有的 Agent 能力（工具调用、RAG、安全检查）；
  - 缺点：延迟叠加；丢失语气、情绪等语音信息。
- **端到端语音模型**：
  - 优点：延迟低、对话自然、能感知语气；
  - 缺点：可控性较弱；工具调用、安全审核等能力需要重新评估；调试更困难。
- **共同的难点**：打断处理、嘈杂环境、口音、关键信息的确认、合规录音。
- **选择**：对准确性和可控性要求高的业务（例如客服办理业务）多采用级联方案；对自然交互要求高的场景可以考虑端到端方案。

**追问**：*语音场景中如何做内容安全审核？* 级联方案可以对文本进行审核；端到端方案需要对模型输出的文本转写或音频进行审核，并考虑延迟的影响。

**减分回答**：只知道“语音转文字再转语音”。

### Q5 多模态 Agent 带来了哪些新的机会和风险？

**考察点**：多模态的落地判断。

**参考回答**

- **机会**：理解截图、票据、合同、图表；处理用户上传的图片（例如商品破损照片）；从视频中提取信息。
- **风险**：
  1. 成本：图片和视频的 token 消耗很高；
  2. 安全：图片中的文字可能是注入指令；
  3. 隐私：图片中可能包含身份证、人脸等敏感信息；
  4. 准确性：视觉理解可能出错，关键信息需要核对。
- **落地建议**：先用 OCR 等专用工具提取结构化信息，模型负责理解和判断；对关键字段做校验；敏感信息脱敏；计入成本和配额。

**追问**：*用户上传商品破损的照片申请退款，Agent 能直接判断并同意退款吗？* 可以辅助判断，但涉及资金的决定应该经过规则校验或人工审批。

**减分回答**：认为多模态模型可以直接替代所有的专用识别工具。

### Q6 “模型越来越强，工程上的很多工作会不会被取代？”你怎么看？

**考察点**：技术判断力。

**参考回答**

- **会被取代的部分**：为弥补模型能力不足而做的工程补偿，例如复杂的提示词技巧、为了让模型输出格式正确而做的大量解析和重试、
  部分简单的工作流编排。
- **不会被取代的部分**：
  1. 与业务系统的集成（工具、数据、权限）；
  2. 安全、合规、审计；
  3. 评测与持续改进；
  4. 成本与性能的控制；
  5. 人机协作的流程设计。
- **应对方式**：把工程投入放在长期有价值的部分；让工程设计能随着模型能力的提升而简化（例如用配置控制是否启用某个补偿机制），
  而不是写死在代码中。

**追问**：*你在项目中做过哪些“随着模型变强可以去掉”的设计？* 结合实际回答，例如结构化输出的多级兜底、复杂的查询改写。

**减分回答**：认为 Agent 开发会被完全取代，或者认为模型进步与自己无关。

### Q7 开源模型和闭源模型在企业 Agent 中如何选择？

**考察点**：选型策略。

**参考回答**

- **闭源商业模型**：能力强、更新快、无需运维；但存在数据出境和隐私顾虑、成本随调用量增长、依赖厂商的可用性和额度。
- **开源模型**：可以私有化部署、数据不出内网、可以微调、大规模使用时成本可控；但需要运维投入，能力通常落后于最强的闭源模型。
- **常见的组合策略**：
  1. 敏感数据和高频简单任务使用私有化部署的开源模型；
  2. 复杂任务使用闭源模型；
  3. 通过统一的模型抽象层和路由，按任务和数据敏感程度选择。
- **决策依据**：数据合规要求、调用量和成本、团队的运维能力、在业务评测集上的效果。

**追问**：*开源模型在 Agent 场景中最常见的短板是什么？* 工具调用和复杂指令遵循的稳定性，需要在评测集上重点验证。

**减分回答**：“开源免费，所以用开源”，或者“闭源效果好，所以都用闭源”。

### Q8 你认为 Agent 在企业落地的最大障碍是什么？

**考察点**：对落地问题的认识（开放题）。

**参考回答**（可以从以下几个方面组织）

- **可靠性**：多步任务的成功率会逐步下降，企业需要稳定可预期的结果。
- **集成**：企业系统复杂、接口不统一、权限体系多样，数据质量参差不齐。
- **信任与责任**：出错时谁负责；关键操作需要人工确认，导致自动化程度受限。
- **评估**：难以量化业务价值，缺少评测体系。
- **成本**：规模化后模型调用成本可观。
- **组织**：业务方的期望过高、缺少数据和知识的负责人。
- **应对思路**：从高频、边界清晰、容易验证的场景切入；人机协作而不是完全替代；先建立评测和度量体系；逐步扩大自动化范围。

**追问**：*如果让你在一家传统企业推动 Agent 落地，你会选择什么场景作为起点？* 选择高频、规则清晰、有明确收益、出错代价可控的场景，
例如内部知识问答、工单分类和辅助回复。

**减分回答**：“主要是模型还不够强”。

### Q9 多 Agent 的协作会是未来的主流吗？

**考察点**：对架构趋势的独立判断。

**参考回答**

- **有价值的场景**：任务可以拆解为独立的子任务并行处理；不同子任务需要隔离的上下文和权限；跨组织的 Agent 协作（例如通过 A2A）。
- **需要警惕的问题**：成本和延迟成倍增加；错误在 Agent 之间传播和放大；调试和评测更困难。
  很多被设计成多 Agent 的系统，用单个 Agent 加上合适的工具就能完成。
- **判断**：在单个组织内部，优先使用单 Agent 或主从式的子 Agent；跨组织、跨系统的协作会越来越依赖标准协议。
  是否使用多 Agent，要由具体的需求和评测数据决定，而不是追逐潮流。

**追问**：*怎么证明拆分成多 Agent 是有效的？* 在同一评测集上对比单 Agent 和多 Agent 的效果、成本和延迟。

**减分回答**：“多 Agent 更高级，是未来的方向”。

### Q10 你平时如何跟踪 Agent 领域的技术进展？

**考察点**：学习能力与信息来源。

**参考回答**（给出方法，而不是具体的网站列表）

- **一手信息**：模型厂商和框架的官方文档、发布说明、技术博客；协议的规范文档。
- **论文与评测**：关注重要的论文和 Benchmark 的更新，理解背后的方法。
- **开源项目**：阅读优秀开源项目的代码和设计决策，而不只是使用。
- **实践验证**：新技术先在小范围试验，用自己的评测集验证效果，再决定是否采用。
- **总结输出**：写技术文档或分享，把学到的内容系统化。

**追问**：*最近学到的一个对你工作有实际帮助的新技术是什么？* 结合实际回答，说明为什么有价值、如何落地、效果如何。

**减分回答**：“主要看公众号和短视频”。

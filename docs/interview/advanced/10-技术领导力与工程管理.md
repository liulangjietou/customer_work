# 进阶第 10 期 · 技术领导力与工程管理

> **本期结论**：资深和专家岗位不只看个人的技术能力，还看能否带领团队做出正确的技术决策、推动项目落地、建立工程规范。
> 这类问题没有标准答案，面试官关注的是：有没有真实的经历、决策的依据是否充分、能否反思。
>
> 答题建议：使用 STAR 结构（情境、任务、行动、结果），并补充“如果重来会怎么做”。
>
> 题量 10。

---

### Q1 你如何判断一个业务需求是否适合用 Agent 来解决？

**考察点**：技术方案的判断力。

**参考回答**

- **适合的特征**：
  1. 输入是非结构化的（自然语言、文档）；
  2. 处理路径不固定，需要根据情况做判断；
  3. 有明确的衡量标准，能够评测；
  4. 出错的代价可控，或者可以加入人工确认。
- **不适合的特征**：规则明确、路径固定（用传统的程序或工作流更可靠、更便宜）；要求百分之百准确且没有人工兜底；数据和系统接口不具备。
- **方法**：先做小规模的验证（POC），用评测集证明可行，再决定是否投入。

**追问**：*业务方坚持要用 Agent，但你认为用规则引擎更合适，怎么办？* 用数据说话：对比两种方案的准确率、成本和维护成本；
也可以采用组合方案，规则处理确定的部分，Agent 处理需要判断的部分。

**减分回答**：“所有需求都可以用 Agent 解决”。

### Q2 如何从 0 到 1 搭建一个 Agent 团队和技术体系？

**考察点**：规划能力。

**参考回答**

- **第一阶段（验证价值）**：选择一个高价值、边界清晰的场景；小团队快速做出可用版本；建立最初的评测集；用数据证明价值。
- **第二阶段（工程化）**：沉淀公共能力（模型接入、工具框架、治理中间件、可观测、评测），形成基础设施或平台；制定开发规范。
- **第三阶段（规模化）**：平台化支持更多业务；建立统一的治理（安全、成本、合规）；建立运营闭环（badcase、知识更新）。
- **团队构成**：后端工程师（业务集成、工程化）、算法工程师（模型、检索、评测）、产品经理、业务专家（知识和评测标注）。
- **原则**：先解决具体的业务问题，再抽象平台；不要一开始就做大而全的平台。

**追问**：*什么时候应该把公共能力抽象成平台？* 当出现第二个、第三个真实的业务需求，并且它们确实需要相同的能力时。

**减分回答**：一上来就规划一个大而全的 Agent 平台。

### Q3 如何做 Agent 相关的技术选型决策？请举一个你做过的例子。

**考察点**：决策过程。

**参考回答**（答题结构）

1. **明确要解决的问题和约束**：性能、成本、团队技能、合规、时间。
2. **列出候选方案**，并确定评估维度和权重。
3. **做验证**：用原型和评测数据对比，而不是只看文档和宣传。
4. **评估长期成本**：维护成本、社区活跃度、升级的风险、退出的成本。
5. **做出决策并记录理由**（例如技术决策记录 ADR），说明放弃其他方案的原因。
6. **事后回顾**：决策是否正确，有哪些教训。

- **示例方向**：Agent 框架的选择；向量库的选择；是否自建模型服务；工具执行串行还是并行。

**追问**：*如果选型后发现选错了，怎么办？* 尽早承认；评估迁移成本；有抽象层时迁移更容易；把教训记录下来。

**减分回答**：“大家都在用 X，所以我们也用 X”。

### Q4 如何推动一个 Agent 项目从 Demo 走向生产？

**考察点**：落地推进能力。

**参考回答**

- **明确上线标准**：效果（评测通过率）、安全、稳定性、成本、合规，并与业务方达成一致。
- **补齐工程能力**：容错、可观测、安全护栏、权限、审计、降级。
- **建立评测和反馈机制**：上线前的评测集，上线后的 badcase 处理流程。
- **灰度上线**：先在小范围用户或内部用户中使用，逐步扩大。
- **管理预期**：让业务方理解 Agent 会出错，设计好人工兜底；用数据展示进展。
- **明确责任**：知识由谁维护，badcase 由谁处理，线上问题由谁响应。

**追问**：*Demo 效果很好，但上线后效果明显变差，常见的原因是什么？* Demo 只覆盖了精心挑选的问题；
真实用户的问题更加多样；生产环境的数据和权限与 Demo 环境不同；缺少对长尾情况的处理。

**减分回答**：“Demo 跑通了，就可以上线”。

### Q5 如何在团队中建立 Agent 开发的工程规范？

**考察点**：规范建设。

**参考回答**

- **架构规范**：统一的装配入口；工具设计规范；上下文和记忆的使用规范；护栏在故障时是放行还是拦截需要明确说明。
- **代码规范**：常量和配置只有一个定义处；日志规范（错误码、脱敏）；异步场景中上下文的传递。
- **测试规范**：单元测试、真实容器的集成测试、结构性测试、评测集；变更必须通过评测。
- **发布规范**：提示词和配置的版本化、评测门禁、灰度、回滚。
- **文档规范**：记录设计决策和踩过的坑，供后来的人参考。
- **让规范可执行**：尽量用自动化检查（测试、CI）来保证，而不是只写在文档中。

**追问**：*规范写好了，但大家不遵守，怎么办？* 把关键规范变成自动化的检查（例如源码扫描测试），在 CI 中强制执行；
在代码评审中持续关注。

**减分回答**：“写一份规范文档发给大家”。

### Q6 AI 编码工具在团队中如何使用，才能提效而不降低代码质量？

**考察点**：对 AI 辅助开发的管理。

**参考回答**

- **提效的场景**：样板代码、测试用例、文档、代码理解、重构、排查问题。
- **风险**：生成的代码可能有隐蔽的错误；不了解项目的约定；安全漏洞；开发者对代码的理解下降。
- **管理方法**：
  1. 提供项目说明文件，让 AI 了解项目的约定和常见的坑；
  2. AI 生成的代码同样需要评审和测试，责任在提交者；
  3. 对关键模块（安全、资金）要求更严格的人工审查；
  4. 用自动化测试和结构性检查兜底；
  5. 注意代码和数据的外泄风险，使用企业许可的工具。
- **度量**：关注交付质量和缺陷率，而不只是代码产出量。

**追问**：*AI 生成的代码通过了所有测试，还需要人工评审吗？* 需要。测试可能不完整，也可能被一起修改；
评审还要检查设计是否合理、是否符合项目的约定。

**减分回答**：“AI 写的代码直接合并就行”，或者“完全禁止使用 AI 工具”。

### Q7 讲一个你遇到的最有挑战的 Agent 技术问题，以及你是怎么解决的。

**考察点**：真实的技术深度（行为面试题）。

**参考回答**（答题结构）

1. **背景**：什么系统、什么规模、问题的影响是什么。
2. **困难在哪里**：为什么这个问题难（例如不报错、难以复现、涉及多个团队）。
3. **排查过程**：提出了哪些假设，如何逐一验证。
4. **根因**：问题的本质是什么。
5. **解决方案**：修复了什么；为什么选择这个方案而不是其他方案。
6. **防止复发**：增加了哪些测试、监控或规范。
7. **反思**：如果重来一次，会怎么做。

- **可以参考的素材**：[项目第 08 期 Q7](../08-模型路由成本评测与系统设计.md) 中列出的“静默失效”类问题。

**追问**：*你是怎么确认问题真的被解决了？* 应该有数据或测试证明，而不是“改完之后没再出现”。

**减分回答**：只讲解决方案，讲不出排查过程和根因。

### Q8 你和业务方对 Agent 能做到什么程度有分歧，怎么处理？

**考察点**：沟通与预期管理。

**参考回答**

- **理解业务目标**：业务方真正想解决什么问题，而不是争论具体的功能。
- **用数据沟通**：用评测结果和试点数据展示当前的能力和局限。
- **给出可选方案**：例如“完全自动化能达到 70% 的准确率；加入人工确认后能达到 95%，但效率提升会减少”。
- **分阶段推进**：先实现可靠的部分，再逐步扩大范围。
- **写清楚边界**：Agent 不处理哪些情况、出错时如何兜底。

**追问**：*业务方要求“准确率必须达到 100%”，怎么回应？* 说明 Agent 的输出存在不确定性，无法保证 100% 准确；
讨论通过人工确认、限定范围等方式来满足业务上的可靠性要求。

**减分回答**：“技术上做不到”，却不给出替代方案。

### Q9 如何评估和培养 Agent 开发工程师？

**考察点**：团队建设。

**参考回答**

- **能力模型**：
  1. 扎实的后端工程能力（并发、分布式、数据库）；
  2. Agent 相关的知识（模型特性、工具设计、RAG、上下文工程）；
  3. 评测和数据驱动的思维；
  4. 安全和质量意识；
  5. 与业务沟通、理解业务的能力。
- **面试重点**：让候选人讲清楚项目中的具体取舍和踩过的坑，而不是背诵概念；给出场景让他们设计和排查。
- **培养方式**：代码评审中讨论设计取舍；分享踩坑复盘；让新人从评测和 badcase 分析入手，快速理解系统的真实表现；
  鼓励把经验沉淀成文档和自动化检查。

**追问**：*传统的 Java 后端工程师转型做 Agent 开发，最需要补的是什么？* 对模型不确定性的理解（为什么需要评测、兜底和护栏），
以及上下文工程和工具设计的经验。

**减分回答**：只看候选人会不会用某个框架。

### Q10 如果让你负责一个 Agent 平台未来一年的技术规划，你会怎么做？

**考察点**：战略规划能力（开放题）。

**参考回答**（答题结构）

1. **现状评估**：当前平台的能力、主要问题（例如稳定性、效果、成本、接入效率）、业务方的反馈。
2. **目标**：与业务目标对齐的可衡量目标（例如接入的业务数量、问题解决率、单位成本、稳定性指标）。
3. **重点方向**（示例）：
   - 效果：评测体系和数据飞轮；
   - 效率：降低业务接入的成本（模板、SDK、低代码）；
   - 治理：安全、合规、成本的统一管控；
   - 技术演进：跟进协议标准（MCP、A2A），评估新的模型能力。
4. **优先级与节奏**：按价值和依赖关系排序，分季度制定里程碑。
5. **风险与应对**：模型厂商变化、法规变化、团队能力。
6. **度量与复盘**：定期检查目标的完成情况并调整规划。

**追问**：*资源有限，只能做一件事，你会选什么？* 一般优先选择能直接提升业务价值且可衡量的方向，例如评测体系与 badcase 闭环，
它是所有后续优化的基础。

**减分回答**：列出一堆新技术，没有和业务目标关联。

# 基础补全第 03 期 · 工作流编排与图框架

> **本期结论**：JD 中经常出现 LangGraph、Dify、Coze、Spring AI Alibaba Graph 等关键词，考察的是“用图来编排 Agent 流程”的能力。
> 这类框架的共同核心是：状态、节点、边、检查点和中断。掌握这些概念，就能快速上手任何一个具体的框架。
>
> 说明：各框架的 API 迭代较快，本期只讲通用的概念和设计要点。
>
> 题量 10。

---

### Q1 基于图的 Agent 编排框架有哪些核心概念？

**考察点**：图编排的基本模型。

**参考回答**

- **状态（State）**：在整个流程中传递和更新的数据结构，例如消息列表、已收集的信息、当前步骤。
- **节点（Node）**：一个处理步骤，读取状态、执行逻辑（调用模型、调用工具、执行代码），然后返回对状态的更新。
- **边（Edge）**：节点之间的流转关系，分为固定的边和**条件边**（根据状态决定下一个节点）。
- **状态合并规则**：多个节点更新同一个字段时如何合并，例如消息列表是追加而不是覆盖。
- **检查点（Checkpoint）**：每一步执行后保存状态，支持中断、恢复和回溯。
- **入口和结束**：流程的起始节点和结束条件。

**追问**：*ReAct Agent 能用图来表示吗？* 可以，本质上是“调用模型”和“执行工具”两个节点，加上一条根据是否有工具调用而决定走向的条件边，形成一个循环。

**减分回答**：只能说出“拖拽节点连线”。

### Q2 图编排中的状态应该怎么设计？

**考察点**：状态建模能力。

**参考回答**

- **只放流程需要的数据**：状态过大会增加检查点的存储开销，也容易出现无关字段被意外修改的情况。
- **明确每个字段的合并规则**：列表是追加还是覆盖；并行分支同时修改一个字段时如何处理。
- **区分持久数据和临时数据**：大文件、大体积的检索结果放在外部存储，状态中只保留引用。
- **结构化**：用明确的类型定义状态，而不是任意的键值对，便于校验和维护。
- **可序列化**：检查点需要序列化状态，状态中不能包含不可序列化的对象（例如数据库连接）。

**追问**：*两个并行分支都要往消息列表中添加内容，会冲突吗？* 如果合并规则是追加，就不会丢失；
如果是覆盖，后完成的分支会覆盖先完成的，需要事先定义清楚。

**减分回答**：把所有数据都放在一个 Map 中随意读写。

### Q3 如何在图编排中实现人工审批（Human-in-the-Loop）？

**考察点**：中断与恢复机制。

**参考回答**

- **机制**：执行到需要审批的节点时，流程**中断**，保存当前状态（检查点），把待审批的内容展示给用户；
  用户做出决定（批准、拒绝或修改内容）后，从检查点**恢复**执行，把人工的决定作为输入继续后面的流程。
- **要求**：
  1. 检查点必须持久化（数据库），因为审批可能需要几小时甚至几天；
  2. 恢复时要校验审批的有效性（审批人的权限、是否超时）；
  3. 审批决定要幂等，重复提交不能导致流程执行两次；
  4. 审批超时要有处理策略（自动拒绝或升级）。

**追问**：*审批期间服务重启了怎么办？* 状态保存在持久化的检查点中，重启后收到审批结果，依然能从检查点恢复。

**减分回答**：让线程阻塞等待审批结果。

### Q4 检查点（Checkpoint）有什么用？怎么实现？

**考察点**：流程的持久化。

**参考回答**

- **用途**：
  1. 故障后从断点恢复；
  2. 实现人工审批这类长时间的中断；
  3. 调试：查看每一步的状态，甚至回到某一步修改状态后重新执行（常被称为“时间旅行”）；
  4. 多轮对话：按会话保存流程状态。
- **实现**：每个节点执行完后，把状态和执行位置按“会话 / 线程 ID + 步骤序号”保存到存储中（内存、Redis、数据库）；
  生产环境使用持久化存储。
- **注意**：检查点的数量会不断增长，需要清理策略；状态中不要保存敏感信息的明文。

**追问**：*从某个检查点恢复后重新执行，会不会重复执行有副作用的操作？* 会，所以有副作用的节点要做幂等，
或者记录已经执行过的操作并跳过。

**减分回答**：只在内存中保存流程状态。

### Q5 如何在图中实现并行分支和结果汇总？

**考察点**：并行编排。

**参考回答**

- **分发（Fan-out）**：一个节点之后连接多个节点，同时执行；或者根据数据动态生成多个并行任务（例如对每个文档分别处理）。
- **汇总（Fan-in）**：等待所有分支完成后，由一个节点合并结果。
- **需要考虑的问题**：
  1. 状态的合并规则（见 Q2）；
  2. 某个分支失败或超时时，是整体失败还是用占位结果继续；
  3. 并发数的限制，避免触发模型厂商的限流；
  4. 总的成本和延迟由最慢的分支决定。

**追问**：*汇总节点需要等待所有分支吗？* 默认等待；也可以设置超时，超时后用已有的结果继续，并标记缺失的部分。

**减分回答**：认为并行执行只是为了更快，不考虑失败处理。

### Q6 子图（Subgraph）有什么用？

**考察点**：流程的模块化。

**参考回答**

- **作用**：把一个复杂流程中相对独立的部分封装成子图，作为一个节点嵌入主图。例如把“退款流程”封装成子图，在多个主流程中复用。
- **好处**：模块化、可复用、便于单独测试；子图可以有自己的状态，只把必要的结果返回给主图，控制上下文的大小。
- **多 Agent 的实现**：每个 Agent 可以是一个子图，由主图负责路由和协调。
- **注意**：主图和子图之间的状态映射要清晰；子图中的中断（例如人工审批）需要正确地传递到主图。

**追问**：*子图和普通的函数调用有什么区别？* 子图有自己的状态和检查点，支持中断和恢复，也能在执行记录中单独观测。

**减分回答**：把所有逻辑都放在一张大图中。

### Q7 Dify、Coze 这类低代码平台和代码框架（LangGraph、Spring AI Alibaba Graph）怎么选？

**考察点**：选型判断。

**参考回答**

- **低代码平台**：
  - 优点：上手快，业务人员也能参与；内置知识库、插件、发布和日志；
  - 缺点：复杂逻辑难以表达；版本管理、测试和代码评审不如代码方便；与企业内部系统的深度集成受限；有平台锁定的风险。
- **代码框架**：
  - 优点：灵活，可以使用完整的工程实践（版本控制、测试、CI）；方便深度集成；
  - 缺点：开发成本高，需要工程师参与。
- **选择**：原型验证、简单的场景、业务主导的应用适合低代码平台；核心业务、复杂逻辑、对质量和安全要求高的场景适合代码框架。
  也可以组合使用：平台负责快速试验，成熟后用代码重写。

**追问**：*用低代码平台做的应用，怎么做测试和发布管理？* 利用平台的版本和发布功能；导出配置并纳入版本管理；
通过接口运行评测集。

**减分回答**：“低代码平台不专业”，或者“低代码能解决所有问题”。

### Q8 图编排的流程出错了，怎么处理和调试？

**考察点**：可靠性与可观测。

**参考回答**

- **错误处理**：
  1. 节点级的重试（只对幂等的节点）；
  2. 错误分支：出错时走到专门的处理节点（兜底回复、转人工）；
  3. 全局的超时和最大步数，防止死循环。
- **调试**：
  1. 记录每个节点的输入、输出和耗时；
  2. 从检查点回放某次执行；
  3. 修改某一步的状态后重新执行，验证修复方案；
  4. 可视化执行路径。
- **监控**：统计每个节点的错误率和耗时，找出瓶颈和不稳定的节点。

**追问**：*循环的图（例如 ReAct）怎么防止死循环？* 设置最大迭代次数，并在状态中记录循环次数，超出时走到结束或兜底节点。

**减分回答**：只在最外层 `try-catch`。

### Q9 什么时候用固定的工作流，什么时候用图中的 Agent 节点？

**考察点**：确定性与灵活性的平衡。

**参考回答**

- **固定工作流**：步骤明确、必须按顺序执行、合规要求高的环节，例如身份校验、审批、支付。
- **Agent 节点**：需要理解自然语言、路径不确定、需要根据中间结果决定下一步的环节，例如理解用户诉求、查询信息、回答问题。
- **组合**：外层用固定工作流保证关键步骤必须发生，内层嵌入 Agent 节点处理开放式的任务；
  或者 Agent 作为主控，把确定性的流程封装成一个工具来调用。

**追问**：*能不能举一个组合的例子？* 退款流程：Agent 负责理解诉求和收集信息；资格校验、审批、打款由固定工作流执行；
审批结果再交给 Agent 解释给用户。

**减分回答**：全部用 Agent，或者全部用固定流程。

### Q10 图编排框架和 Temporal 这类持久化执行引擎有什么区别？

**考察点**：技术视野。

**参考回答**

- **图编排框架**：面向 AI 流程，内置了消息、工具调用、模型调用、人工中断等概念，开发效率高；
  在大规模的可靠性保障（分布式调度、长期运行的任务、复杂的重试策略）上相对较弱。
- **持久化执行引擎**：面向通用的长流程业务，提供强大的可靠性保障（自动重试、超时、断点恢复、分布式执行），
  但对 AI 相关的概念没有内置支持。
- **组合方式**：用持久化执行引擎作为底层的可靠性保障，把模型调用、工具调用作为其中的活动（Activity），
  适合需要长时间运行且可靠性要求高的 Agent 任务。

**追问**：*为什么在持久化执行引擎中，模型调用不能放在确定性的流程定义里直接执行？* 流程定义在恢复时会被重放，
必须是确定性的；模型调用是不确定的，要作为活动执行，结果被记录下来，重放时直接使用记录的结果。

**减分回答**：不了解两者的区别。

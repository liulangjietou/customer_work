### Q1 HashMap 的底层原理是什么？在 Agent 服务中使用有什么需要注意的？

**考察点**：经典集合原理。

**参考回答**

- **结构**（JDK 8 及以后）：数组 + 链表 + 红黑树。通过 key 的 hash 值（高 16 位与低 16 位异或，减少冲突）定位数组下标；
  冲突的元素组成链表；链表长度达到 8 且数组容量不小于 64 时转为红黑树，提升查找效率。
- **扩容**：元素数量超过“容量 × 负载因子（默认 0.75）”时，容量翻倍，元素重新分布。
- **线程不安全**：并发写入可能丢失数据；多线程场景使用 `ConcurrentHashMap`。
- **Agent 服务中的注意点**：
  1. 会话级的缓存是并发访问的，不能用 `HashMap`；
  2. 作为缓存使用时必须有容量上限，否则会话越来越多会导致内存溢出；
  3. 作为 key 的对象要正确实现 `equals` 和 `hashCode`（使用 `record` 作为复合键很方便）。

**追问**：*为什么树化阈值是 8？* 在哈希分布良好的情况下，链表长度达到 8 的概率极低；树化主要用来防御哈希冲突严重的极端情况。

**减分回答**：只知道“数组加链表”。

### Q2 ConcurrentHashMap 是怎么保证线程安全的？`computeIfAbsent` 有什么坑？

**考察点**：并发容器原理与使用陷阱。

**参考回答**

- **原理**（JDK 8 及以后）：数组槽位为空时用 CAS 放入节点；槽位不为空时，用 `synchronized` 锁住该槽位的头节点，
  锁的粒度是单个槽位；读操作基本不加锁。元素计数使用分散的计数单元，减少竞争。
- **`computeIfAbsent` 的坑**：
  1. 计算函数执行期间会锁住对应的槽位，**计算函数中不能执行耗时操作**（例如远程调用、构建复杂对象），
     否则会阻塞落在同一槽位的其他操作；
  2. 计算函数中不能修改同一个 Map，否则可能抛出异常或死锁；
  3. 计算函数返回 null 时不会插入值。
- **与 `Collections.synchronizedMap` 的区别**：后者所有操作共用一把锁，`computeIfAbsent` 会在整个计算期间持有这把全局锁
  （见 [项目第 06 期 Q3](../06-Java并发与响应式流式链路.md)）。

**追问**：*需要在缓存未命中时构建一个耗时的 Agent 实例，怎么写更好？* 使用支持按 key 异步加载的缓存（例如 Caffeine）；
或者在锁外构建，再用 `putIfAbsent` 放入缓存，竞争失败的一方释放自己创建的实例。

**减分回答**：“ConcurrentHashMap 所有方法都是线程安全的，随便用”。

### Q3 线程池的核心参数有哪些？调用大模型的线程池应该怎么配置？

**考察点**：线程池原理与 IO 密集型场景的配置。

**参考回答**

- **核心参数**：核心线程数、最大线程数、空闲线程存活时间、任务队列、线程工厂、拒绝策略。
- **执行流程**：线程数小于核心线程数时创建新线程；否则放入队列；队列满了且线程数小于最大线程数时创建新线程；
  都满了就执行拒绝策略。
- **大模型调用的特点**：IO 密集，每次调用耗时数秒甚至更长；并发数受模型厂商的额度限制。
- **配置建议**：
  1. 线程数可以远大于 CPU 核数，但上限要与模型厂商的并发额度相匹配，线程再多也会被厂商限流；
  2. 使用**有界队列**，避免任务无限堆积导致内存溢出和超时；
  3. 拒绝策略要返回明确的“系统繁忙”，而不是静默丢弃；
  4. 线程命名便于排查；
  5. 不同类型的任务使用不同的线程池隔离（模型调用、工具调用、数据库），避免相互影响。
- **为什么不推荐 `Executors` 的工厂方法**：部分方法使用无界队列或不限制线程数，高负载下可能导致内存溢出。

**追问**：*使用了虚拟线程，还需要限制并发吗？* 需要。虚拟线程解决的是线程数量问题，下游资源（模型额度、数据库连接）仍然有限，可以用信号量限流。

**减分回答**：“核心线程数设为 CPU 核数的 2 倍”，不考虑具体的负载特点。

### Q4 CompletableFuture 的回调在哪个线程执行？有什么坑？

**考察点**：异步编程的细节。

**参考回答**

- **规则**：
  1. 不带 `Async` 后缀的方法（例如 `thenApply`）：如果注册回调时 future 已经完成，回调在**当前调用线程**上同步执行；
     否则在完成 future 的那个线程上执行；
  2. 带 `Async` 后缀的方法：在指定的线程池中执行，不指定时使用公共的 `ForkJoinPool`。
- **常见的坑**：
  1. 不指定线程池时使用公共线程池，阻塞的 IO 操作会占满它，影响整个进程中所有使用它的代码；
  2. ThreadLocal 上下文（例如租户）不会自动传递到回调线程；
  3. 测试中如果 future 已经完成，回调在测试线程上同步执行，这时上下文还在，测试会得出错误的结论
     （见 [项目第 06 期 Q6](../06-Java并发与响应式流式链路.md)）；
  4. 异常被包装在 `CompletionException` 中，需要正确处理。

**追问**：*怎么在异步回调中保留租户上下文？* 在提交任务时捕获上下文，在回调中显式设置并在结束后清理；
或者使用能自动传递上下文的包装工具。

**减分回答**：认为 `thenApply` 一定在另一个线程执行。

### Q5 volatile 的作用是什么？双重检查锁为什么需要 volatile？

**考察点**：Java 内存模型。

**参考回答**

- **volatile 的作用**：
  1. **可见性**：一个线程修改后，其他线程能立即读到最新的值；
  2. **禁止指令重排序**：通过内存屏障保证读写顺序。
  它**不保证复合操作的原子性**（例如 `i++`）。
- **双重检查锁**：`instance = new Object()` 包括分配内存、初始化对象、把引用赋给变量三个步骤。
  如果后两步被重排序，另一个线程可能拿到一个尚未初始化完成的对象。加上 `volatile` 可以禁止这种重排序。
- **项目中的例子**：`CustomerServiceAgentFactory` 中的 trace 导出器就使用了 `volatile` 加双重检查的延迟初始化。

**追问**：*happens-before 规则有哪些？* 例如：同一线程内的顺序规则、锁的释放先于后续的加锁、volatile 的写先于后续的读、
线程的启动先于线程内的操作等。

**减分回答**：“volatile 保证线程安全”。

### Q6 synchronized 和 ReentrantLock 有什么区别？AQS 是什么？

**考察点**：锁的原理与选择。

**参考回答**

- **synchronized**：JVM 层面实现，自动加锁和释放，写法简单；JVM 会做锁优化。
- **ReentrantLock**：基于 AQS 实现，需要手动在 `finally` 中释放；支持可中断的加锁、带超时的加锁、公平锁、多个条件变量。
- **AQS（AbstractQueuedSynchronizer）**：用一个状态变量和一个等待队列实现锁和同步器的通用框架，
  `ReentrantLock`、`Semaphore`、`CountDownLatch` 都基于它实现。
- **选择**：简单的互斥用 `synchronized`；需要超时、可中断或多个条件时用 `ReentrantLock`。
- **虚拟线程**：在 `synchronized` 块中执行阻塞操作可能导致虚拟线程被固定在载体线程上，长时间持有锁的阻塞代码更适合用 `ReentrantLock`。

**追问**：*锁在 A 线程获取、在 B 线程释放可以吗？* `synchronized` 和 `ReentrantLock` 都不行，释放时会检查持有者。
响应式链路中需要“按凭证释放”的机制，例如信号量（见 [项目第 06 期 Q5](../06-Java并发与响应式流式链路.md)）。

**减分回答**：只知道一个是关键字、一个是类。

### Q7 ThreadLocal 的原理是什么？为什么会内存泄漏？在线程池中有什么风险？

**考察点**：ThreadLocal 的使用陷阱。

**参考回答**

- **原理**：每个线程内部有一个 `ThreadLocalMap`，以 ThreadLocal 对象为 key（弱引用），保存该线程自己的值。
- **内存泄漏**：key 是弱引用，ThreadLocal 对象被回收后，value 仍然被线程强引用。如果线程长期存活（例如线程池中的线程），
  value 就无法释放。
- **线程池中的风险**：线程会被复用，上一个任务设置的值如果没有清理，会被下一个任务读到，导致**上下文串用**
  （例如把 A 租户的身份带到 B 租户的请求中）。
- **正确用法**：在 `try-finally` 中设置和清理；跨线程传递时显式捕获和恢复。
- **Agent 服务中的应用**：租户上下文、用户身份、请求 ID 通常使用 ThreadLocal；在响应式链路中需要与 Reactor Context 同步
  （见 [项目第 06 期 Q2](../06-Java并发与响应式流式链路.md)）。

**追问**：*子线程能继承父线程的 ThreadLocal 吗？* `InheritableThreadLocal` 可以在创建线程时继承，但线程池复用线程时不会重新继承，
这种场景需要专门的上下文传递工具。

**减分回答**：只知道“每个线程一份副本”。

### Q8 Semaphore、CountDownLatch、CyclicBarrier 分别用在什么场景？

**考察点**：并发工具的应用。

**参考回答**

- **Semaphore**：控制同时访问某个资源的线程数。例如限制对模型厂商的并发调用数，或者实现会话级的互斥（许可数为 1）。
- **CountDownLatch**：一个或多个线程等待其他若干个任务完成，计数只能使用一次。例如等待多个并行的检索任务都完成后再汇总。
- **CyclicBarrier**：多个线程相互等待，全部到达后再一起继续，可以重复使用。在业务代码中较少使用。
- **在 Agent 场景中**：多 Agent 并行调用后汇总结果，在响应式编程中通常用 `Flux.flatMap` 控制并发、`collectList` 汇总，
  在同步编程中可以用 `CompletableFuture.allOf` 或 `CountDownLatch`。

**追问**：*用 Semaphore 限流时，获取许可超时怎么处理？* 返回“系统繁忙”并记录指标，而不是无限等待。

**减分回答**：分不清三者的区别。

### Q9 原子类（AtomicLong）和 LongAdder 有什么区别？

**考察点**：高并发计数。

**参考回答**

- **AtomicLong**：基于 CAS 更新一个变量，高并发时大量线程竞争同一个变量，CAS 失败重试的开销很大。
- **LongAdder**：把计数分散到多个单元中，不同线程更新不同的单元，读取时再汇总。高并发写入的性能更好，但读取的结果不是严格的实时快照。
- **选择**：统计类的计数（例如调用次数、命中次数）用 `LongAdder`；需要精确比较和更新的场景（例如生成序号）用 `AtomicLong`。

**追问**：*Agent 服务中哪些地方适合用 LongAdder？* 各种指标计数，例如拦截次数、缓存命中次数、工具调用次数。

**减分回答**：认为两者完全一样。

### Q10 线上发生死锁或线程卡住，怎么排查？

**考察点**：问题排查。

**参考回答**

- **获取线程转储**：使用 `jstack` 或 `jcmd <pid> Thread.print`，JVM 会自动检测并报告死锁。
- **分析**：找出处于 `BLOCKED` 和 `WAITING` 状态的线程，查看它们在等待什么锁、这个锁被谁持有。
- **Agent 服务中常见的“卡住”**：
  1. 线程池被阻塞调用占满（例如在响应式的事件循环线程上执行了阻塞调用）；
  2. 等待外部服务但没有设置超时；
  3. 会话锁没有释放（例如释放逻辑写在了错误的位置）；
  4. `computeIfAbsent` 中执行耗时操作导致其他线程等待。
- **预防**：所有外部调用都设置超时；固定加锁的顺序；使用带超时的加锁；监控线程池的活跃线程数和队列长度。

**追问**：*响应式应用的线程转储看起来都很正常，但请求就是不返回，可能是什么原因？* 流没有被订阅、空流导致下游从未被调用、
或者在等待一个永远不会到来的信号；需要通过链路日志和 `checkpoint` 排查。

**减分回答**：只会重启服务。

### Q11 CopyOnWriteArrayList 适合什么场景？

**考察点**：并发容器的选择。

**参考回答**

- **原理**：每次写操作都复制一份新的数组，修改后替换引用；读操作不加锁，读取的是某个时刻的快照。
- **适合**：读多写少的场景，例如监听器列表、配置的回调列表。
- **不适合**：写入频繁或元素很多的场景，每次复制的开销很大。
- **类似的思路**：项目中的敏感词自动机也是“构建新实例 + 原子替换引用”，使读取完全不需要加锁。

**追问**：*迭代时修改会抛异常吗？* 不会。迭代器遍历的是创建迭代器时的快照，看不到之后的修改。

**减分回答**：认为它可以替代所有的 List。

### Q12 用 BlockingQueue 实现生产者 - 消费者模式，在 Agent 场景中有什么应用？

**考察点**：经典并发模式的应用。

**参考回答**

- **原理**：生产者向队列中放入数据，消费者从队列中取出数据；队列满时生产者阻塞，队列空时消费者阻塞，天然实现了流量控制。
- **在 Agent 场景中的应用**：
  1. 异步写入日志、审计、命中记录等旁路数据，不阻塞主链路；
  2. 文档入库的流水线：解析、分块、向量化分阶段处理；
  3. 把同步的流式回调转换为可以逐个消费的数据流。
- **注意**：使用有界队列；队列满时的处理策略（丢弃并计数，还是阻塞）要根据数据的重要程度决定；服务停机时要处理队列中剩余的数据。

**追问**：*审计日志的异步队列满了，应该丢弃还是阻塞？* 审计数据通常不能丢，应该降级为同步写入或者持久化到本地；
普通的统计数据可以丢弃并记录丢弃的数量。

**减分回答**：使用无界队列，不考虑队列满的情况。

### Q13 Java 17 和 21 有哪些新特性在 Agent 开发中常用？

**考察点**：现代 Java 的使用。

**参考回答**

- **record**：不可变的数据类，适合作为消息、事件、配置和复合的缓存键，自动生成 `equals`、`hashCode`、`toString`。
- **文本块**：多行字符串，适合编写提示词模板（例如项目中的系统提示词）。
- **switch 模式匹配和 instanceof 模式匹配**：按事件类型分派处理（例如区分文本增量事件和工具调用事件），代码更简洁。
- **sealed 类**：限定类型的子类，适合定义一组固定的事件或结果类型，编译器能检查是否处理了所有情况。
- **虚拟线程**（JDK 21）：用同步的写法实现高并发 IO。
- **注意**：MyBatis 等框架使用 record 作为结果类型时可能无法自动映射（record 没有 setter），需要用普通的类接收结果再转换。

**追问**：*项目中为什么 MyBatis 的查询结果不直接映射到 record？* record 没有 setter，自动映射无法赋值；
项目统一用普通的数据对象接收结果，再转换成领域对象。

**减分回答**：只知道 Lambda 和 Stream。

### Q14 Stream 并行流适合在 Agent 服务中使用吗？

**考察点**：并行计算的适用范围。

**参考回答**

- **原理**：并行流基于公共的 `ForkJoinPool`，把数据分片后并行处理。
- **不适合的情况**：
  1. 处理过程中有阻塞的 IO（例如调用模型或远程接口），会占满公共线程池，影响整个进程；
  2. 数据量小，并行的开销大于收益；
  3. 依赖 ThreadLocal 上下文，并行执行时上下文会丢失。
- **适合的情况**：数据量大、纯 CPU 计算、无副作用的任务，例如对大量向量计算相似度。
- **替代方案**：IO 并发使用专门的线程池、`CompletableFuture` 或响应式编程，并控制并发数。

**追问**：*在并行流中调用模型接口会怎样？* 公共线程池的线程数通常等于 CPU 核数减一，很快会被阻塞的调用占满，
并发能力很低，还会影响其他使用公共线程池的代码。

**减分回答**：“并行流更快，都用并行流”。

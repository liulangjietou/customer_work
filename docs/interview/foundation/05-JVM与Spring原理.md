### Q1 JVM 的内存区域是怎么划分的？Agent 服务中哪些区域最容易出问题？

**考察点**：JVM 内存模型。

**参考回答**

- **线程共享的区域**：堆（对象实例，GC 的主要区域）；元空间（类的元数据，JDK 8 起替代永久代，使用本地内存）。
- **线程私有的区域**：虚拟机栈（方法调用的栈帧）、本地方法栈、程序计数器。
- **堆外内存**：直接内存（NIO、Netty 使用），不受堆大小的限制，但受 `-XX:MaxDirectMemorySize` 等参数控制。
- **Agent 服务中容易出问题的区域**：
  1. 堆：会话缓存无界增长、流式内容全部累积在内存中、超大的工具结果；
  2. 直接内存：Netty 处理大量长连接和流式数据，ByteBuf 泄漏；
  3. 线程：为每个请求创建线程，或者线程池没有上限，导致无法再创建线程。

**追问**：*容器中 JVM 的堆应该设置多大？* 要为直接内存、元空间、线程栈等留出空间，通常用 `MaxRAMPercentage` 按容器内存的比例设置，
而不是把堆设置成接近容器的上限。

**减分回答**：只知道“堆和栈”。

### Q2 常见的垃圾回收器有哪些？Agent 服务应该怎么选择？

**考察点**：GC 的选择。

**参考回答**

- **G1**：把堆分成多个区域，优先回收垃圾最多的区域，可以设置期望的停顿时间，是 JDK 9 之后的默认回收器，适合大多数服务。
- **ZGC**：并发执行几乎所有的回收工作，停顿时间极短（通常在毫秒级以下），适合对延迟敏感、堆较大的服务；
  较新的 JDK 版本中提供了分代模式，进一步提升了性能。
- **Parallel**：追求吞吐量，停顿时间较长，适合批处理任务。
- **Agent 服务的选择**：流式输出对停顿敏感（停顿会导致输出卡顿），同时有大量短生命周期的小对象；
  一般使用 G1 就可以，堆很大或者对延迟要求很高时考虑 ZGC。无论选择哪种，都要用 GC 日志和压测来验证。

**追问**：*Young GC 很频繁，说明什么？* 短生命周期的对象创建得很多，例如流式处理中每个分片都创建新的字符串和对象；
可以减少不必要的对象创建，或者适当增大年轻代。

**减分回答**：只知道 CMS 和“标记清除”。

### Q3 类加载的过程是怎样的？什么是双亲委派？SPI 为什么要打破它？

**考察点**：类加载机制。

**参考回答**

- **过程**：加载 → 验证 → 准备 → 解析 → 初始化。
- **双亲委派**：类加载器收到加载请求时，先委托给父加载器，父加载器无法加载时才自己加载。这样可以保证核心类的唯一性和安全性
  （例如用户无法用自己写的 `java.lang.String` 替换系统的类）。
- **SPI 为什么要打破它**：SPI 的接口由核心类库定义（由启动类加载器加载），实现由应用提供（由应用类加载器加载）；
  父加载器无法“看到”子加载器中的类，因此通过线程上下文类加载器来加载实现类。
- **应用场景**：JDBC 驱动的加载、`ServiceLoader`；Spring Boot 的自动配置也是基于类似的“按约定读取实现清单”的思路。

**追问**：*插件式地加载 Agent 工具（运行时加载新的 jar）要注意什么？* 使用独立的类加载器隔离插件；注意类冲突和资源释放；
严格控制插件的权限。

**减分回答**：说不清类加载器之间的委派关系。

### Q4 OutOfMemoryError 有哪几种？分别怎么排查？

**考察点**：内存问题的排查。

**参考回答**

- **Java heap space**：堆内存不足。开启 `-XX:+HeapDumpOnOutOfMemoryError`，用 MAT 分析占用最大的对象及其引用链。
- **Metaspace**：类的元数据过多，常见于动态生成类过多（例如大量的动态代理或脚本编译）。
- **Direct buffer memory**：直接内存不足，常见于 Netty 的 ByteBuf 泄漏或者大文件的传输。
- **unable to create native thread**：无法再创建线程，线程数过多或者系统限制。
- **GC overhead limit exceeded**：GC 占用了绝大部分时间却回收不了多少内存，通常是堆接近耗尽的前兆。
- **Agent 服务中的常见原因**：见[进阶第 04 期 Q6](../advanced/04-线上故障排查与性能容量.md)。

**追问**：*线上不能随便生成堆转储（会暂停服务），怎么办？* 先把实例从负载均衡中摘除再生成；
或者使用 `jmap -histo` 查看对象统计；平时通过监控内存的增长趋势提前发现问题。

**减分回答**：“把 -Xmx 调大”。

### Q5 为什么 Java 服务刚启动时比较慢？怎么处理？

**考察点**：JIT 与预热。

**参考回答**

- **原因**：
  1. JIT 编译：代码刚开始以解释方式执行，热点代码被编译成本地代码后才变快；
  2. 类加载：首次使用的类需要加载；
  3. 各种缓存还没有建立（连接池、Agent 实例缓存、配置缓存）；
  4. 首次调用外部服务需要建立连接（TLS 握手等）。
- **处理**：
  1. 启动后先预热（发送模拟请求），再接入流量；
  2. 连接池预先建立连接；
  3. 就绪探针在预热完成后才返回成功；
  4. 滚动发布时逐步切换流量。

**追问**：*有没有减少预热时间的技术？* 例如类数据共享（CDS）、提前编译相关的技术；GraalVM 原生镜像启动很快，但对反射和动态代理的支持需要额外配置。

**减分回答**：不知道 JIT 的存在。

### Q6 Spring Bean 的生命周期是怎样的？在 `@PostConstruct` 中访问数据库有什么风险？

**考察点**：Spring 容器原理与启动期的陷阱。

**参考回答**

- **生命周期**：实例化 → 属性注入 → Aware 回调 → `BeanPostProcessor` 的前置处理 → 初始化（`@PostConstruct`、`afterPropertiesSet`、init 方法）→
  `BeanPostProcessor` 的后置处理（例如生成 AOP 代理）→ 使用 → 销毁（`@PreDestroy`、`destroy`）。
- **在 `@PostConstruct` 中访问数据库的风险**：
  1. 此时没有请求上下文，开启了多租户隔离的系统会因为缺少租户信息而查询失败，导致**应用无法启动**；
  2. 依赖的其他 Bean 可能还没有完全初始化；
  3. 耗时的初始化会拖慢启动速度。
- **项目教训**：开启租户隔离后，某个 `@Bean` 方法中查询了数据，导致应用直接无法启动
  （见 [项目第 07 期 Q1](../07-生产化-多租户限流幂等与一致性.md)）。
- **建议**：启动期的查询要显式声明跨租户的访问范围；耗时的初始化放到应用启动完成之后异步执行。

**追问**：*`@PreDestroy` 有什么作用？忘记写会怎样？* 用于释放资源（连接池、线程池、客户端）；
忘记写不会报错，但反复重启或热部署时资源会慢慢泄漏。

**减分回答**：只知道 `@Autowired` 和 `@Component`。

### Q7 Spring 如何解决循环依赖？为什么推荐构造器注入？

**考察点**：容器的实现细节。

**参考回答**

- **三级缓存**：一级缓存存放完全初始化好的 Bean；二级缓存存放提前暴露的早期引用；三级缓存存放创建早期引用的工厂（用于处理 AOP 代理）。
  通过提前暴露还没有完成初始化的 Bean 引用，解决**单例、属性注入**的循环依赖。
- **无法解决的情况**：构造器注入的循环依赖；原型作用域的循环依赖。Spring Boot 2.6 之后默认禁止循环依赖，需要显式开启。
- **推荐构造器注入的原因**：依赖不可变；强制依赖在构造时就能确定；便于编写单元测试；循环依赖会在启动时暴露出来，促使改进设计。
- **可选依赖**：使用 `ObjectProvider` 或 `@Autowired(required = false)` 的 setter 注入，避免构造参数过多，也能降低修改构造函数时的连锁影响。

**追问**：*构造参数太多怎么办？* 说明这个类的职责可能过多，考虑拆分；可选的依赖改用 setter 注入或 `ObjectProvider`。

**减分回答**：说不出为什么构造器注入无法解决循环依赖。

### Q8 Spring AOP 的原理是什么？为什么同一个类中的方法互相调用时注解会失效？

**考察点**：代理机制。

**参考回答**

- **原理**：Spring 为目标 Bean 创建代理对象，在代理中织入切面逻辑。目标类实现了接口时可以使用 JDK 动态代理，否则使用 CGLIB 生成子类；
  Spring Boot 默认使用 CGLIB。
- **自调用失效**：同一个类中，方法 A 调用方法 B，是通过 `this` 直接调用的，没有经过代理，所以方法 B 上的 `@Transactional`、`@Async` 等注解不生效。
- **解决方法**：把方法 B 移到另一个 Bean 中；或者通过代理对象调用。
- **Agent 场景中的应用**：日志、耗时统计、审计、权限校验都可以用 AOP 实现；但模型调用链路上的治理，更适合用框架提供的中间件机制，
  因为中间件能感知推理、工具调用这些 Agent 特有的阶段。

**追问**：*final 方法能被代理吗？* CGLIB 基于继承实现，final 方法无法被重写，所以不能被代理。

**减分回答**：只知道 AOP 是“面向切面编程”。

### Q9 Spring 事务在哪些情况下会失效？在事务中调用大模型有什么问题？

**考察点**：事务的正确使用。

**参考回答**

- **常见的失效情况**：自调用；方法不是 public；异常被捕获没有抛出；抛出的是受检异常（默认只回滚运行时异常）；
  多线程中执行（事务绑定在当前线程上）；数据库引擎不支持事务。
- **在事务中调用大模型的问题**：
  1. 模型调用耗时数秒甚至更长，期间一直占用数据库连接和锁，高并发时连接池会被耗尽；
  2. 事务回滚无法撤销模型调用本身，也无法撤销模型触发的工具副作用。
- **正确做法**：数据库操作放在短事务中；模型调用放在事务之外（通常在事务提交之后）；需要一致性时使用 Outbox 或状态机。
  项目中的消息受理就是“先在事务中保存用户消息，提交后再调用模型”（见 [项目第 07 期 Q3](../07-生产化-多租户限流幂等与一致性.md)）。

**追问**：*事务传播行为 REQUIRED 和 REQUIRES_NEW 有什么区别？* REQUIRED 加入已有的事务，没有时新建；
REQUIRES_NEW 总是新建事务并挂起外层事务，适合记录审计日志这类即使外层失败也要保留的操作。

**减分回答**：在整个对话处理方法上加 `@Transactional`。

### Q10 Spring Boot 的条件装配有哪些常用注解？自动配置的顺序怎么控制？

**考察点**：自动配置的细节。

**参考回答**

- **常用条件**：`@ConditionalOnClass`（类路径中存在某个类）、`@ConditionalOnMissingBean`（容器中没有同类型的 Bean）、
  `@ConditionalOnProperty`（配置项满足条件）、`@ConditionalOnWebApplication`（Web 应用的类型）、`@ConditionalOnBean`。
- **顺序控制**：`@AutoConfiguration` 的 `before` / `after` 属性，或者 `@AutoConfigureBefore` / `@AutoConfigureAfter`。
  `@ConditionalOnMissingBean` 在自动配置中使用才可靠，因为自动配置在用户的配置之后处理。
- **Agent starter 中的应用**：默认实现加上 `@ConditionalOnMissingBean`，让使用方可以覆盖；
  只适用于响应式栈的组件加上 `@ConditionalOnWebApplication(type = REACTIVE)`；
  可选功能用 `@ConditionalOnProperty` 控制开关。
- **测试**：使用 `ApplicationContextRunner`（或者 `ReactiveWebApplicationContextRunner`）测试自动配置在不同条件下的装配结果，
  测试的上下文类型要与真实运行的环境一致。

**追问**：*配置文件中的默认值和 Java 代码中的默认值不一致，以哪个为准？* 以配置文件为准。
所以默认值最好只在一个地方定义（Java 代码中），配置文件只写需要覆盖的值，否则容易出现两处不一致的问题。

**减分回答**：不了解自动配置的原理。

### Q11 Spring WebFlux 和 Spring MVC 有什么区别？Agent 服务应该怎么选？

**考察点**：Web 技术栈的选择。

**参考回答**

- **Spring MVC**：基于 Servlet，每个请求占用一个线程（虚拟线程出现后，这个限制大大降低）；编程模型简单，生态成熟。
- **Spring WebFlux**：基于 Reactor 和 Netty，非阻塞；少量线程就能处理大量并发连接；天然支持流式响应和背压。
- **Agent 服务的选择**：
  - 大量长连接和流式输出（WebSocket、SSE）、高并发的对话服务，适合 WebFlux；
  - 管理后台、以 CRUD 为主的服务，适合 MVC；
  - 两者可以共存于不同的服务中（例如项目中客服端用 WebFlux，管理后台用 MVC）。
- **注意**：WebFlux 中不能阻塞事件循环线程；ThreadLocal 上下文需要特殊处理；同一个组件要同时支持两种栈时，需要按 Web 应用类型区分装配。

**追问**：*MVC 能实现 SSE 吗？* 可以，例如使用 `SseEmitter`；但每个连接会占用资源，大量长连接时要评估容量。

**减分回答**：“WebFlux 性能更好，所有服务都用 WebFlux”。

### Q12 配置的动态刷新怎么实现？有哪些需要注意的地方？

**考察点**：配置中心的使用。

**参考回答**

- **实现方式**：配置中心（例如 Nacos）推送变更，应用监听到变化后更新配置；Spring Cloud 中可以用 `@RefreshScope` 让 Bean 在刷新后重新创建。
- **需要注意的地方**：
  1. **校验**：新配置先校验（格式、签名、内容指纹），不合法时保留旧配置；
  2. **原子替换**：一组相关的配置要一起生效，避免中间状态；
  3. **依赖配置的对象要重建**：例如 Agent 实例绑定了提示词，配置变化后需要清空缓存重建；
  4. **生效确认**：配置中心接收了新配置，不代表每个实例都应用成功，需要实例上报结果；
  5. **敏感配置**：密钥加密传输；
  6. **多租户**：每个租户的配置独立，缺失时不能回退到其他租户的配置。

**追问**：*配置刷新期间，正在处理的请求用哪个版本的配置？* 请求开始时捕获配置的版本，整个请求使用同一个版本；
例如语义缓存会在请求开始时记录配置代际，只允许写入这个代际。

**减分回答**：“改了配置自动就生效了”。

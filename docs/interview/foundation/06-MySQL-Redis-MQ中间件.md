### Q1 MySQL 的事务隔离级别有哪些？InnoDB 如何实现可重复读？

**考察点**：事务与 MVCC。

**参考回答**

- **四个隔离级别**：读未提交、读已提交、可重复读（InnoDB 默认）、串行化。
- **MVCC**：每行数据有隐藏的事务 ID 和回滚指针，旧版本保存在 undo log 中；事务读取时根据 Read View 判断哪个版本可见。
  - 可重复读：事务第一次读取时生成 Read View，之后一直复用，所以同一事务内多次读取的结果一致；
  - 读已提交：每次读取都生成新的 Read View。
- **幻读**：快照读由 MVCC 避免；当前读（`SELECT ... FOR UPDATE`、更新语句）由间隙锁和临键锁避免。
- **Agent 场景**：会话状态的并发更新、工单状态的流转，需要用行锁或乐观锁（版本号）保证正确性，不能只依赖隔离级别。

**追问**：*读已提交和可重复读，哪个更适合高并发的业务？* 读已提交的锁更少、并发更好，很多互联网业务使用它；
配合乐观锁或业务上的幂等来保证正确性。

**减分回答**：说不出 MVCC 的原理。

### Q2 MySQL 索引的原理是什么？哪些情况下索引会失效？

**考察点**：索引与查询优化。

**参考回答**

- **结构**：InnoDB 使用 B+ 树。聚簇索引的叶子节点保存整行数据；二级索引的叶子节点保存主键值，查询其他列时需要回表。
- **常见的失效情况**：
  1. 对索引列使用函数或进行计算；
  2. 隐式类型转换（例如字符串列与数字比较）；
  3. **排序规则或字符集不一致的字段进行比较或关联**；
  4. 联合索引不满足最左前缀；
  5. 以通配符开头的模糊查询（`LIKE '%xx'`）；
  6. 使用 `OR` 连接的条件中有列没有索引；
  7. 优化器判断全表扫描更快。
- **排查**：使用 `EXPLAIN` 查看执行计划，关注 `type`、`key`、`rows`、`Extra`。
- **项目教训**：两张表的字符串列排序规则不一致，关联查询会报错；如果用类型转换绕过，索引就会失效
  （见 CLAUDE.md 中关于建表必须显式指定 COLLATE 的说明）。

**追问**：*覆盖索引是什么？* 查询所需的列都在索引中，不需要回表，性能更好。

**减分回答**：“给每个字段都加上索引”。

### Q3 MySQL 中如何实现乐观锁和悲观锁？在 Agent 场景中怎么选？

**考察点**：并发控制。

**参考回答**

- **悲观锁**：`SELECT ... FOR UPDATE` 锁住行，其他事务等待。适合冲突频繁、必须串行的场景（例如审批的状态推进）。
- **乐观锁**：表中加版本号，更新时带上条件 `WHERE id = ? AND version = ?`，更新行数为 0 表示冲突，需要重试或报错。
  适合冲突较少的场景。
- **CAS 式的状态更新**：`UPDATE ... SET status = 'APPROVED' WHERE id = ? AND status = 'PENDING'`，用于状态机的原子推进，
  保证重复的决策只有一次生效。
- **Agent 场景**：会话状态的写入使用乐观并发（版本号）；审批和工单的状态流转使用条件更新；避免在持有行锁时调用模型。

**追问**：*乐观锁冲突后应该重试还是报错？* 取决于业务：可以自动合并的（例如计数）重试；需要用户确认的（例如审批）返回冲突错误。

**减分回答**：只知道 `synchronized`，不知道数据库层面的并发控制。

### Q4 大表的 DDL 变更（例如加列、修改排序规则）要注意什么？

**考察点**：线上数据库变更。

**参考回答**

- **风险**：部分 DDL 需要重建整张表并加锁，大表上执行会长时间阻塞写入。
- **做法**：
  1. 确认 DDL 是否支持在线执行（Online DDL 的 `ALGORITHM` 和 `LOCK` 选项）；例如修改表的字符集和排序规则通常需要重建表，并阻塞写入；
  2. 大表使用 gh-ost、pt-online-schema-change 这类在线变更工具，或者在停写窗口执行；
  3. 变更脚本要幂等（已经是目标状态的表跳过），并在最后做自检；
  4. 通过 Flyway 这类工具管理迁移版本，已经执行过的迁移脚本不能修改。
- **项目经验**：统一表排序规则的迁移逐表判断，已经合规的表直接跳过，避免无谓的重建，并在最后检查是否有残留
  （见 CLAUDE.md 的相关说明）。

**追问**：*为什么已经执行过的 Flyway 迁移脚本不能修改？* Flyway 会校验脚本的校验和，修改后应用启动时会校验失败；
要调整，只能新增一个迁移。

**减分回答**：直接在生产库上执行 `ALTER TABLE`。

### Q5 Redis 有哪些常用的数据结构？在 Agent 服务中分别怎么用？

**考察点**：Redis 的应用。

**参考回答**

| 数据结构 | Agent 服务中的用途 |
|---|---|
| String | 计数器（限流、配额）、分布式锁、短期缓存 |
| Hash | 会话的元数据、配置快照 |
| List / Stream | 简单的消息队列、事件流 |
| Sorted Set | 按时间窗口的滑动计数、排行榜、延迟任务 |
| Set | 去重（例如已经处理过的消息 ID） |
| Pub/Sub | 跨实例广播（例如 WebSocket 消息推送到持有连接的实例） |

- **注意**：Pub/Sub 不保存消息，订阅者离线期间的消息会丢失，适合可以丢失的实时通知；需要可靠投递时使用 Stream 或 MQ。

**追问**：*用 Redis 实现滑动窗口限流有哪些方式？* 使用 Sorted Set 记录每次请求的时间戳（精确，但占用空间大），
或者按时间分桶计数（近似，但空间固定）。

**减分回答**：只知道用 Redis 做缓存。

### Q6 缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？

**考察点**：缓存的经典问题。

**参考回答**

- **缓存穿透**：查询不存在的数据，缓存中没有，每次都打到数据库。解决方式：缓存空值（设置较短的过期时间）、布隆过滤器、参数校验。
- **缓存击穿**：某个热点 key 过期的瞬间，大量请求同时打到数据库。解决方式：互斥锁（只有一个请求去加载）、热点数据不过期或者提前刷新。
- **缓存雪崩**：大量 key 同时过期或缓存服务宕机。解决方式：过期时间加随机值、多级缓存、限流降级、缓存集群高可用。
- **Agent 场景中的对应**：
  - 语义缓存查询失败时视为未命中，不能影响对话；
  - 大量用户同时问同一个热门问题，缓存未命中时可能同时触发多次模型调用，可以合并相同的请求。

**追问**：*语义缓存和普通的键值缓存有什么不同的风险？* 语义缓存按相似度命中，可能把一个用户的个人信息返回给另一个用户，
需要严格限定可以缓存的内容范围。

**减分回答**：分不清三者的区别。

### Q7 Redis 分布式锁怎么实现？有哪些问题？

**考察点**：分布式锁的正确性。

**参考回答**

- **基本实现**：`SET key value NX PX 过期时间`，value 使用唯一的请求标识；释放时用 Lua 脚本判断 value 是否是自己的再删除，
  避免误删其他客户端的锁。
- **问题**：
  1. **过期时间难以确定**：太短会在业务执行完之前释放，太长会在故障时长时间占用；Redisson 的“看门狗”机制会自动续期；
  2. **主从切换可能丢锁**：主节点写入后还没同步就宕机，新的主节点上没有这把锁；
  3. **与线程绑定**：Redisson 的 `RLock` 释放时校验线程，响应式链路中加锁和释放可能不在同一个线程。
- **兜底**：锁不能保证绝对互斥，关键的写操作还要用乐观锁或 fencing token 兜底
  （见[进阶第 08 期 Q8](../advanced/08-Java深入与Agent服务性能.md)）。

**追问**：*Redis 故障时，锁应该怎么处理？* 根据业务选择：降级为本地锁（单实例内仍然互斥）、拒绝请求，或者放行。
项目中会话锁降级为本地锁，并记录错误日志。

**减分回答**：“用 SETNX 加 EXPIRE 两条命令就行”（两条命令不是原子的）。

### Q8 Redis 的持久化方式有哪些？数据会丢失吗？

**考察点**：Redis 的可靠性。

**参考回答**

- **RDB**：定期生成内存快照。恢复快、文件小，但两次快照之间的数据可能丢失。
- **AOF**：记录每条写命令，可以配置每条命令、每秒或由操作系统决定何时刷盘；每秒刷盘最多丢失约 1 秒的数据。
- **混合持久化**：AOF 重写时以 RDB 的格式保存基础数据，后面追加增量命令，兼顾恢复速度和数据完整性。
- **结论**：Redis 不适合作为唯一的权威存储。
- **Agent 场景**：计数器、锁、短期缓存可以放在 Redis 中；会话状态、审批、工单等需要可靠保存的数据要以 MySQL 为准。

**追问**：*限流计数器因为 Redis 重启而清零，会有什么影响？* 短时间内限流会变宽松，通常可以接受；如果不能接受，需要持久化或者用数据库兜底。

**减分回答**：认为 Redis 的数据不会丢失。

### Q9 Redis 集群模式下有哪些需要注意的地方？

**考察点**：Redis 的高可用与扩展。

**参考回答**

- **数据分片**：Redis Cluster 把 key 分布到 16384 个槽位上，不同的 key 可能在不同的节点。
- **多 key 操作**：涉及多个 key 的命令和 Lua 脚本，要求这些 key 在同一个槽位上，可以用哈希标签（`{}`）让相关的 key 落到同一个槽位。
- **热 key 与大 key**：热点 key 会让单个节点压力过大；大 key 会导致操作阻塞、迁移困难。
- **高可用**：主从复制加哨兵，或者集群模式下的自动故障转移；主从复制是异步的，故障切换时可能丢失少量数据。
- **Agent 场景**：按会话或用户组织 key，避免把所有计数放在同一个 key 上形成热点。

**追问**：*滑动窗口计数用了多个时间桶，放在不同的 key 上会有什么问题？* 在集群模式下，多 key 操作需要保证它们在同一个槽位，
可以用哈希标签把同一个计数对象的桶放在一起。

**减分回答**：不了解集群模式对多 key 操作的限制。

### Q10 消息队列在 Agent 系统中有哪些用途？

**考察点**：异步架构。

**参考回答**

- **异步处理**：文档解析和向量化、长时间运行的 Agent 任务、批量评测。
- **削峰填谷**：高峰期把请求放入队列，按模型额度平稳处理。
- **事件驱动**：工单状态变化后通知用户、发送满意度邀请、更新统计数据。
- **解耦**：审计日志、调用记录、成本统计等旁路数据异步写入。
- **可靠投递**：配合事务 Outbox，保证业务数据和事件的一致性。

**追问**：*对话本身适合放进消息队列异步处理吗？* 实时对话对延迟敏感，一般直接处理；长任务、批量任务、旁路数据适合异步处理。

**减分回答**：“所有请求都放进 MQ”。

### Q11 如何保证消息不丢失？如何保证消息不被重复消费？

**考察点**：消息的可靠性与幂等。

**参考回答**

- **不丢失**：
  1. 生产端：等待 Broker 的确认，失败时重试；业务数据和消息通过事务 Outbox 保证一致；
  2. Broker：消息持久化、多副本（例如 Kafka 设置 `acks=all` 并配置足够的同步副本数）；
  3. 消费端：处理成功后再提交消费位点。
- **不重复处理**：消息队列一般只保证“至少一次”投递，重复是正常的，消费端必须幂等：
  1. 使用业务上唯一的消息 ID，处理前检查是否已经处理过；
  2. 使用数据库的唯一约束兜底；
  3. 状态机的条件更新（只有状态符合条件才处理）。
- **Agent 场景**：模型调用成本高、工具调用可能有副作用，重复消费的代价很大，幂等尤其重要。

**追问**：*消费失败的消息怎么处理？* 按指数退避重试，达到上限后进入死信队列，保留现场并告警，不要直接删除。

**减分回答**：“MQ 会保证消息只投递一次”。

### Q12 如何保证消息的顺序？

**考察点**：顺序消息。

**参考回答**

- **Kafka**：同一个分区内的消息有序。把需要保持顺序的消息（例如同一个会话、同一个工单的事件）用相同的 key 发送到同一个分区；
  消费端单线程处理同一个分区，或者按 key 串行处理。
- **代价**：并行度受分区数限制；某条消息处理失败会阻塞后面的消息。
- **替代方案**：消息中带上版本号或序号，消费端丢弃比当前版本旧的消息，而不是依赖严格的顺序。

**追问**：*工单状态变更的事件乱序了会怎样？* 可能把已经关闭的工单改回处理中。可以在消费时检查状态流转是否合法，
或者按版本号只接受更新的事件。

**减分回答**：认为消息队列天然保证全局有序。

### Q13 分布式事务有哪些方案？Agent 系统中怎么处理跨服务的一致性？

**考察点**：分布式一致性。

**参考回答**

- **常见方案**：
  1. **两阶段提交（2PC / XA）**：强一致，但性能差、存在阻塞；
  2. **TCC**：业务上实现尝试、确认、取消三个操作，侵入性强；
  3. **Saga**：长事务拆成多个本地事务，失败时执行补偿操作；
  4. **本地消息表 / 事务 Outbox**：业务和消息写在同一个本地事务中，异步投递，最终一致；
  5. **Seata 等框架**：提供 AT、TCC、Saga 等模式。
- **Agent 系统中的选择**：大多数场景采用最终一致：Outbox 加幂等消费；跨库的关键操作通过回执和对账保证；
  涉及资金的操作通过审批状态和执行状态分开记录，失败时巡检重试。
- **原则**：模型调用无法回滚，所以在设计上要让有副作用的操作可以查询、可以补偿、可以幂等重试。

**追问**：*为什么不直接用 Seata 的 AT 模式？* 它依赖对 SQL 的解析和全局锁，对跨服务的外部调用（模型、第三方接口）无能为力；
业务上的补偿和回执更可控。

**减分回答**：“用分布式事务框架就能保证一致”。

### Q14 向量数据写入 MySQL 的 JSON 列，在应用层计算相似度，有什么问题？什么时候需要改造？

**考察点**：存储选型的边界。

**参考回答**

- **问题**：每次查询都要读取候选向量并逐条计算相似度，复杂度与数据量成正比；数据量大时，内存占用、查询延迟和数据库压力都会快速增长；
  也无法使用近似最近邻索引。
- **适用范围**：数据量小（例如几千到几万条）、查询量不高的场景，好处是不引入新的组件。
- **需要改造的信号**：查询延迟明显上升；需要比较的候选数经常达到上限；数据量持续增长。
- **改造方向**：通过存储的抽象接口切换到专用的向量数据库或支持向量索引的存储（见[基础补全第 09 期](09-向量数据库与检索引擎选型.md)）。
- **项目对照**：项目的受管知识库和语义缓存都采用了这种方式，并记录了“候选数是否达到上限”的指标作为改造的依据
  （见 [项目第 08 期 Q3](../08-模型路由成本评测与系统设计.md)）。

**追问**：*为什么要先有指标，再决定是否改造？* 没有数据支撑的改造可能是过度设计；指标能说明问题是否真的存在、严重到什么程度。

**减分回答**：“向量就应该存在向量数据库里”，不考虑规模和成本。

### Q1 Spring Cloud Alibaba 包含哪些核心组件？在 Agent 平台中分别怎么用？

**考察点**：微服务组件的应用。

**参考回答**

- **Nacos**：服务注册发现和配置中心。Agent 平台中用于下发模型、提示词、工具等运行时配置，并支持按租户灰度。
- **Sentinel**：限流、熔断、降级。可以用于保护模型调用和工具调用，但 Agent 场景的 token 级配额通常需要自定义实现。
- **Gateway**：统一入口，负责鉴权、路由、限流；需要支持 WebSocket 和 SSE 的透传。
- **Seata**：分布式事务，Agent 场景中较少使用，更多采用 Outbox 加最终一致。
- **RocketMQ**：消息队列，用于异步任务和事件。

**追问**：*网关需要对流式响应做哪些特殊配置？* 关闭响应缓冲；延长超时时间；支持 WebSocket 协议升级；保持长连接。

**减分回答**：只能说出组件的名字。

### Q2 服务之间的调用如何做熔断、降级和超时控制？

**考察点**：服务容错。

**参考回答**

- **超时**：每一次远程调用都要设置超时，包括连接超时和读取超时；超时时间要小于上游的超时，避免上游已经放弃、下游仍在处理。
- **熔断**：错误率或慢调用比例超过阈值时，暂时停止调用，快速失败；一段时间后试探恢复。
- **降级**：返回默认值、缓存数据或友好的提示。
- **隔离**：不同的依赖使用不同的线程池或信号量，一个依赖变慢不会拖垮所有请求。
- **重试**：只对幂等的操作重试，加退避和抖动，并限制总的重试次数，避免重试风暴。
- **Agent 场景**：模型调用的超时时间通常较长，要区分首 token 的超时和整体超时；流式输出中途失败的处理见[进阶第 04 期](../advanced/04-线上故障排查与性能容量.md)。

**追问**：*上游超时 10 秒，下游的模型调用超时 30 秒，会有什么问题？* 上游已经返回失败，下游还在继续调用模型、消耗费用，结果也没有人使用。

**减分回答**：“调用失败就重试”。

### Q3 Agent 服务容器化部署有哪些特殊的注意点？

**考察点**：容器化实践。

**参考回答**

- **JVM 参数**：按容器内存的比例设置堆大小，为直接内存、元空间、线程栈留出空间。
- **优雅停机**：`terminationGracePeriodSeconds` 要大于应用的优雅停机超时，否则正在处理的对话会被强制中断。
- **探针**：存活探针只检查进程是否正常；就绪探针检查依赖（数据库、模型的连通性）并在预热完成后才返回成功；
  不要让探针依赖外部模型的可用性，否则模型厂商故障时所有 Pod 都会被判定为不健康并重启。
- **不在容器本地磁盘保存重要数据**：工作区、上传的文件以数据库或对象存储为准。
- **密钥**：通过 Secret 或外部密钥管理服务注入，不写进镜像。
- **代码执行沙箱**：执行不可信代码时需要额外的隔离，不能直接在业务容器中执行。

**追问**：*存活探针检查了模型厂商的连通性，会发生什么？* 厂商故障时所有 Pod 被判定为失活而反复重启，服务完全不可用，
而实际上本可以降级运行。

**减分回答**：把应用打包进镜像就算完成了容器化。

### Q4 Agent 服务在 Kubernetes 中如何做弹性伸缩？

**考察点**：伸缩策略。

**参考回答**

- **指标选择**：CPU 使用率不能很好地反映 Agent 服务的负载（大部分时间在等待 IO）。更合适的指标是并发会话数、
  正在进行的请求数、队列长度、WebSocket 连接数，需要通过自定义指标来实现伸缩。
- **注意**：
  1. 扩容不能突破模型厂商的额度，瓶颈可能在上游；
  2. 缩容时要优雅停机，长连接需要迁移；
  3. 有状态的组件（例如需要固定实例身份来确认配置生效）需要特殊处理
     （项目中应用服务使用 StatefulSet 固定实例序号，见 [项目第 07 期 Q6](../07-生产化-多租户限流幂等与一致性.md)）。
- **预热**：新实例启动后先预热再接入流量。

**追问**：*为什么扩容后请求的延迟没有下降？* 瓶颈可能在模型厂商的额度或下游的数据库，而不在应用本身。

**减分回答**：“按 CPU 使用率自动伸缩”。

### Q5 如何实现服务的灰度发布？

**考察点**：发布策略。

**参考回答**

- **常见方式**：
  1. **按实例**：先更新部分实例（滚动更新、金丝雀发布）；
  2. **按流量比例**：网关按比例把流量分给新旧版本；
  3. **按用户或租户**：指定的用户或租户使用新版本，便于控制影响范围和收集反馈。
- **Agent 场景中还有“配置灰度”**：代码不变，只把新的提示词或模型配置先下发给部分租户。
- **要求**：新旧版本要兼容（数据库结构、消息格式）；有明确的观察指标和回滚方案；同一个用户的会话不要在新旧版本之间来回切换。

**追问**：*数据库结构的变更怎么配合灰度发布？* 先做向后兼容的变更（例如只加列），新旧版本都能运行；
全部切换到新版本后再清理旧的结构。

**减分回答**：直接全量发布。

### Q6 如何为微服务化的 Agent 系统建立链路追踪？

**考察点**：分布式追踪。

**参考回答**

- **基础**：使用 OpenTelemetry 等标准，在服务之间传递追踪上下文（trace ID、span ID）；每个服务记录自己的 span。
- **Agent 特有的 span**：一次对话中每次模型调用、工具调用、检索、子 Agent 的调用都作为 span，并记录模型名称、token 用量、
  工具名称、结果状态等属性（可以参考 OpenTelemetry 为生成式 AI 定义的语义约定）。
- **异步与响应式**：追踪上下文要在线程切换、消息队列、异步任务之间正确传递。
- **采样**：全量采集成本很高，可以按比例采样，但出错和慢请求要全部保留。
- **隐私**：span 中不要记录完整的提示词和回答原文，或者脱敏后存储在权限受控的系统中。

**追问**：*用户反馈某次回答有问题，怎么找到对应的链路？* 在回答中返回消息 ID 或追踪 ID，并与日志、调用记录关联。

**减分回答**：只依靠日志排查。

### Q7 服务注册与发现的原理是什么？Agent 之间的发现（A2A）和微服务发现有什么不同？

**考察点**：服务发现与 Agent 发现。

**参考回答**

- **微服务发现**：服务启动时向注册中心注册地址和元数据，定期发送心跳；调用方从注册中心获取实例列表并做负载均衡；实例下线或失去心跳时被移除。
- **Agent 发现**：除了地址，还要描述能力（能做什么、接受什么输入、鉴权方式），例如 A2A 协议中的 Agent Card；
  调用方需要根据能力选择合适的 Agent，而不只是选择一个健康的实例。
- **结合方式**：可以把 Agent Card 这类能力描述作为元数据注册到服务注册中心，统一管理。
- **安全**：对外暴露 Agent 的接口需要鉴权、限流和审计，内部的服务发现机制不等于公网的安全边界。

**追问**：*注册中心故障时，服务调用还能继续吗？* 调用方通常会缓存实例列表，短时间内可以继续调用；但新上线的实例无法被发现。

**减分回答**：认为 Agent 发现和微服务发现完全一样。

### Q8 如何设计 Agent 平台的多环境（开发、测试、生产）管理？

**考察点**：环境治理。

**参考回答**

- **配置隔离**：不同环境使用不同的配置命名空间、模型凭据、数据库。
- **模型和成本**：测试环境可以使用更便宜的模型或模拟模型，避免产生大量费用；评测和压测的调用单独计量。
- **数据**：测试环境使用脱敏的数据；生产环境**不能**残留演示数据（Agent 会把演示数据当作真实信息回答用户）。
- **提示词和配置的流转**：在测试环境验证后，通过发布流程推广到生产环境，而不是在生产环境中直接修改。
- **生产环境的安全基线**：例如关闭代码执行、关闭调试接口，并在配置中显式声明，即使默认值也是关闭的。

**追问**：*为什么生产环境的安全配置即使与默认值相同，也要显式写出来？* 表达“生产环境明确要求它是关闭的”，
即使将来有人修改了代码中的默认值，生产环境仍然保持安全。

**减分回答**：各环境共用一套配置和数据。

### Q9 Agent 服务的日志应该怎么规范？

**考察点**：日志治理。

**参考回答**

- **结构化**：使用统一的格式，包含时间、级别、追踪 ID、会话 ID、租户、错误码。
- **错误码**：错误日志带上固定的错误码，便于检索、统计和配置告警。
- **占位符**：使用占位符而不是字符串拼接，避免无谓的性能开销。
- **脱敏**：不记录密钥、完整的提示词和回答原文、个人信息；必要时脱敏后记录。
- **级别**：日志级别要有明确的规范，避免把正常的业务情况记成错误，导致告警噪音。
- **与审计分开**：审计日志要求完整、不可篡改、不能被采样，与普通的应用日志分开存储。

**追问**：*为什么不能在日志中打印完整的用户消息？* 用户消息中可能包含个人信息；日志系统的访问权限通常比业务数据库宽松，会增加泄露风险。

**减分回答**：用 `System.out.println` 或者把整个请求对象打印出来。

### Q10 如何做 Agent 服务的容量规划和成本估算？

**考察点**：资源规划。

**参考回答**

- **应用侧**：根据峰值的并发会话数、每个会话占用的内存、长连接数，估算实例数量和规格；通过压测验证。
- **模型侧**：根据每秒的消息数、每条消息的模型调用次数和 token 数，计算需要的 QPM 和 TPM 额度；
  再结合单价估算每天的费用（见[进阶第 04 期 Q8](../advanced/04-线上故障排查与性能容量.md)）。
- **中间件**：数据库的连接数和写入量（对话记录、审计日志）；Redis 的计数器和锁的 QPS；向量检索的 QPS。
- **余量**：为流量高峰和故障切换预留余量；备用模型的额度也要纳入规划。
- **持续跟踪**：按租户、功能统计实际的用量和成本，与规划对比并调整。

**追问**：*哪一部分的成本通常占比最高？* 通常是模型调用；但大规模私有化部署时，GPU 资源也可能是主要的成本。

**减分回答**：只估算服务器的数量，忽略模型调用的成本。

### Q1 实现一个线程安全的 LRU 缓存。

**考察点**：数据结构、并发、边界条件。

**参考实现**（哈希表 + 双向链表，`get` / `put` 都是 O(1)）

```java
public class LruCache<K, V> {

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    /** 哨兵节点：head.next 是最近使用的，tail.prev 是最久未使用的 */
    private final Node<K, V> head = new Node<>(null, null);
    private final Node<K, V> tail = new Node<>(null, null);

    public LruCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public synchronized V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) {
            return null;
        }
        moveToHead(node);
        return node.value;
    }

    public synchronized void put(K key, V value) {
        Node<K, V> node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        node = new Node<>(key, value);
        map.put(key, node);
        addFirst(node);
        if (map.size() > capacity) {
            Node<K, V> eldest = tail.prev;
            unlink(eldest);
            map.remove(eldest.key);
        }
    }

    private void moveToHead(Node<K, V> node) {
        unlink(node);
        addFirst(node);
    }

    private void addFirst(Node<K, V> node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static final class Node<K, V> {
        final K key;
        V value;
        Node<K, V> prev;
        Node<K, V> next;

        Node(K key, V value) {
            this.key = key;
            this.value = value;
        }
    }
}
```

**简化写法**：继承 `LinkedHashMap`，构造时传入 `accessOrder = true`，重写 `removeEldestEntry` 返回 `size() > capacity`，
再用 `Collections.synchronizedMap` 包装。项目中的热 Agent 缓存就是这样实现的，并在淘汰时释放资源。

**追问**

1. *被淘汰的对象持有资源（例如 MCP 客户端），怎么处理？* 在淘汰时调用释放方法；释放操作最好放在锁外执行，避免阻塞其他线程。
2. *整个缓存用一把锁，高并发下怎么优化？* 分段加锁，或者使用 Caffeine 这类成熟的并发缓存。

**减分回答**：只用 `HashMap` 加一个时间戳，每次淘汰都遍历全部元素（O(n)）。

### Q2 实现一个令牌桶限流器，支持按 token 数量扣减。

**考察点**：限流算法、时间计算、线程安全。

**参考实现**

```java
public final class TokenBucket {

    private final long capacity;
    private final double refillPerNano;
    private double tokens;
    private long lastRefillNanos;

    /**
     * @param capacity        桶容量（允许的突发量）
     * @param refillPerSecond 每秒补充的令牌数
     */
    public TokenBucket(long capacity, double refillPerSecond) {
        if (capacity <= 0 || refillPerSecond <= 0) {
            throw new IllegalArgumentException("capacity and rate must be positive");
        }
        this.capacity = capacity;
        this.refillPerNano = refillPerSecond / 1_000_000_000d;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    /** 尝试扣减 permits 个令牌（例如本次请求预估的 token 数），不足时直接返回 false，不阻塞。 */
    public synchronized boolean tryAcquire(long permits) {
        refill();
        if (tokens >= permits) {
            tokens -= permits;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - lastRefillNanos) * refillPerNano);
        lastRefillNanos = now;
    }
}
```

**要点**：用 `System.nanoTime()` 计算时间差，不受系统时钟调整的影响；按需补充令牌，不需要后台线程。

**追问**

1. *大模型调用在请求前不知道会消耗多少 token，怎么扣减？* 先按预估值扣减或只判断不扣减，调用结束后再按实际用量记账；
   项目中的主体配额就是“先只读判定，放行后再记账”（见 [项目第 07 期 Q2](../07-生产化-多租户限流幂等与一致性.md)）。
2. *多实例部署时怎么做？* 把状态放到 Redis 中，用 Lua 脚本保证“补充 + 扣减”的原子性。

**减分回答**：用一个计数器每秒清零（固定窗口），说不出窗口边界处的突发问题。

### Q3 实现一个按时间分桶的滑动窗口计数器。

**考察点**：滑动窗口的近似实现与空间控制。

**参考实现**

```java
public final class SlidingWindowCounter {

    private final long bucketMillis;
    private final long[] counts;
    private final long[] bucketIds;

    public SlidingWindowCounter(long windowMillis, int buckets) {
        if (windowMillis <= 0 || buckets <= 0) {
            throw new IllegalArgumentException("window and buckets must be positive");
        }
        this.bucketMillis = Math.max(1, windowMillis / buckets);
        this.counts = new long[buckets];
        this.bucketIds = new long[buckets];
        // 初始化为不可能出现在窗口内的桶编号
        Arrays.fill(bucketIds, -buckets);
    }

    /** 增加 amount，并返回窗口内的总量。 */
    public synchronized long addAndGet(long amount, long nowMillis) {
        long currentId = nowMillis / bucketMillis;
        int index = (int) (currentId % counts.length);
        if (bucketIds[index] != currentId) {
            // 这个位置上保存的是过期的桶，重置后复用
            bucketIds[index] = currentId;
            counts[index] = 0;
        }
        counts[index] += amount;
        long total = 0;
        for (int i = 0; i < counts.length; i++) {
            if (currentId - bucketIds[i] < counts.length) {
                total += counts[i];
            }
        }
        return total;
    }
}
```

**要点**：空间固定为桶的数量，与请求量无关；误差最多一个桶的时长。桶越多越精确，但每次求和的开销越大。

**追问**：*误差应该偏向多算还是少算？* 对于限流和配额，应该偏向多算（限得偏严），少算会让超额的请求溜过去。

**减分回答**：用一个列表记录每次请求的时间戳，高并发下内存无限增长。

### Q4 实现一个 SSE（Server-Sent Events）流式响应的解析器，网络数据可能在任意位置被切分。

**考察点**：流式解析、缓冲处理。

**参考实现**

```java
public final class SseParser {

    private final StringBuilder buffer = new StringBuilder();
    private final StringBuilder data = new StringBuilder();

    /** 喂入一段网络数据，返回本次解析出的完整事件（data 字段的内容）。 */
    public List<String> feed(String chunk) {
        List<String> events = new ArrayList<>();
        buffer.append(chunk);
        int newline;
        while ((newline = buffer.indexOf("\n")) >= 0) {
            String line = buffer.substring(0, newline);
            buffer.delete(0, newline + 1);
            if (line.endsWith("\r")) {
                line = line.substring(0, line.length() - 1);
            }
            if (line.isEmpty()) {
                // 空行表示一个事件结束
                if (data.length() > 0) {
                    events.add(data.toString());
                    data.setLength(0);
                }
                continue;
            }
            if (line.startsWith(":")) {
                // 注释行，常用作心跳
                continue;
            }
            if (line.startsWith("data:")) {
                String value = line.substring(5);
                if (value.startsWith(" ")) {
                    value = value.substring(1);
                }
                if (data.length() > 0) {
                    data.append('\n');
                }
                data.append(value);
            }
            // event:、id:、retry: 等字段按需处理
        }
        return events;
    }
}
```

**要点**：没有遇到换行符的部分留在缓冲区中，等待下一段数据；一个事件可以有多行 `data`；
调用方需要识别结束标记（例如部分厂商发送的 `[DONE]`）。

**追问**：*工具调用的参数也是分片返回的，怎么处理？* 按调用 ID 把参数片段拼接起来，等收到该调用的结束信号后再解析 JSON；逐片解析会失败。

**减分回答**：假设每次收到的数据正好是一个完整的事件。

### Q5 在流式输出中检测关键词（例如“已退款”），关键词可能被拆到两个分片中。

**考察点**：跨分片匹配。

**参考实现**

```java
public final class StreamKeywordDetector {

    private final List<String> keywords;
    /** 需要保留的尾部长度：最长关键词长度 - 1 */
    private final int keep;
    private final StringBuilder window = new StringBuilder();

    public StreamKeywordDetector(List<String> keywords) {
        this.keywords = List.copyOf(keywords);
        this.keep = keywords.stream().mapToInt(String::length).max().orElse(1) - 1;
    }

    /** 喂入一个增量，命中时返回命中的关键词。 */
    public Optional<String> feed(String delta) {
        window.append(delta);
        String text = window.toString();
        for (String keyword : keywords) {
            if (text.contains(keyword)) {
                return Optional.of(keyword);
            }
        }
        // 只保留可能与下一片拼成关键词的尾部
        if (window.length() > keep) {
            window.delete(0, window.length() - keep);
        }
        return Optional.empty();
    }
}
```

**要点**：跨两片的关键词，它的开头一定落在上一片末尾“最长关键词长度 - 1”个字符之内，所以只需要保留这么长的尾部。
关键词很多时，用 Aho-Corasick 自动机替代逐个 `contains`。

**追问**

1. *如果检测到之后要拦截输出，而不仅仅是检测，怎么做？* 需要缓冲：只放行确定不会构成关键词的前半部分，保留可能构成关键词的尾部，
   流结束时再输出剩余部分（见 [项目第 05 期 Q3](../05-安全护栏与治理中间件.md)）。
2. *已经发给用户的内容怎么办？* 收不回来，只能停止后续输出并追加澄清。

**减分回答**：对每个分片单独调用 `contains`。

### Q6 实现带指数退避和随机抖动的重试工具。

**考察点**：重试策略的正确实现。

**参考实现**

```java
public final class Retry {

    private Retry() {
    }

    public static <T> T withBackoff(Callable<T> action, int maxAttempts, Duration initialDelay,
                                    Duration maxDelay, Predicate<Exception> retryable) throws Exception {
        long delay = initialDelay.toMillis();
        for (int attempt = 1; ; attempt++) {
            try {
                return action.call();
            } catch (Exception e) {
                if (attempt >= maxAttempts || !retryable.test(e)) {
                    throw e;
                }
                // 全抖动：在 [0, delay] 之间随机等待，避免大量客户端同时重试
                Thread.sleep(ThreadLocalRandom.current().nextLong(delay + 1));
                delay = Math.min(maxDelay.toMillis(), delay * 2);
            }
        }
    }
}
```

**要点**：只重试可以重试的错误（超时、429、5xx），参数错误不重试；限制最大次数和最大等待时间；随机抖动避免重试风暴。
响应式代码中可以直接使用 Reactor 的 `retryWhen(Retry.backoff(...))`。

**追问**

1. *收到 429 并带有 `Retry-After` 头时怎么处理？* 优先按照服务端给出的等待时间重试。
2. *为什么非幂等的操作（例如提交退款）不能直接用这个工具重试？* 超时时请求可能已经执行成功，重试会导致重复执行；需要幂等键配合。

**减分回答**：在循环中立即重试，不等待、不限次数。

### Q7 实现一个最简单的 ReAct 主循环。

**考察点**：Agent 主循环的核心逻辑与边界控制。

**参考实现**

```java
public record ToolCall(String id, String name, String argumentsJson) {
}

public record Message(String role, String content, List<ToolCall> toolCalls, String toolCallId) {

    static Message system(String content) {
        return new Message("system", content, List.of(), null);
    }

    static Message user(String content) {
        return new Message("user", content, List.of(), null);
    }

    static Message assistant(String content, List<ToolCall> calls) {
        return new Message("assistant", content, calls, null);
    }

    static Message tool(String toolCallId, String result) {
        return new Message("tool", result, List.of(), toolCallId);
    }
}

public record ModelReply(String text, List<ToolCall> toolCalls) {
}

public interface ChatModel {
    ModelReply chat(List<Message> messages, Collection<Tool> tools);
}

public interface Tool {
    String name();

    String call(String argumentsJson) throws Exception;
}

public final class SimpleReActAgent {

    private static final int MAX_RESULT_CHARS = 4000;
    private static final String FALLBACK = "抱歉，这个问题我暂时没能处理好，已为您转接人工客服。";

    private final ChatModel model;
    private final Map<String, Tool> tools;
    private final String systemPrompt;
    private final int maxIterations;

    public SimpleReActAgent(ChatModel model, List<Tool> tools, String systemPrompt, int maxIterations) {
        this.model = model;
        this.tools = tools.stream().collect(Collectors.toMap(Tool::name, t -> t));
        this.systemPrompt = systemPrompt;
        this.maxIterations = maxIterations;
    }

    public String run(String userInput) {
        List<Message> messages = new ArrayList<>();
        messages.add(Message.system(systemPrompt));
        messages.add(Message.user(userInput));
        for (int i = 0; i < maxIterations; i++) {
            ModelReply reply = model.chat(messages, tools.values());
            if (reply.toolCalls().isEmpty()) {
                return reply.text();
            }
            // 工具调用消息必须先于工具结果写入，二者成对出现
            messages.add(Message.assistant(reply.text(), reply.toolCalls()));
            for (ToolCall call : reply.toolCalls()) {
                messages.add(Message.tool(call.id(), execute(call)));
            }
        }
        // 轮次用尽：给出明确的去向，而不是一句含糊的道歉
        return FALLBACK;
    }

    private String execute(ToolCall call) {
        Tool tool = tools.get(call.name());
        if (tool == null) {
            return "错误：不存在名为 " + call.name() + " 的工具，请从可用工具中选择。";
        }
        try {
            String result = tool.call(call.argumentsJson());
            return result.length() > MAX_RESULT_CHARS ? result.substring(0, MAX_RESULT_CHARS) + "…（结果已截断）" : result;
        } catch (Exception e) {
            // 把可读的错误交给模型，让它修正参数或换一种方式
            return "工具执行失败：" + e.getMessage();
        }
    }
}
```

**要点**：最大迭代次数和用尽后的兜底；工具不存在或执行失败时返回可读的错误；结果过长时截断；工具调用与结果成对写入历史。

**追问**：*生产环境中还需要补充什么？* 参数校验和权限检查、人工审批、超时、流式输出、状态持久化、重复调用检测、可观测和成本统计。

**减分回答**：没有最大迭代次数，或者工具异常直接抛出导致整个对话失败。

### Q8 实现 RRF（倒数排名融合），合并向量检索和关键词检索的结果。

**考察点**：检索融合算法。

**参考实现**

```java
public final class ReciprocalRankFusion {

    /** 常用取值为 60，用来平滑排名靠前的结果之间的差距。 */
    public static final int DEFAULT_K = 60;

    private ReciprocalRankFusion() {
    }

    /**
     * @param rankings 多路检索结果，每一路按相关度从高到低排列（元素为文档 ID）
     * @param topN     返回的结果数
     */
    public static List<String> fuse(List<List<String>> rankings, int k, int topN) {
        Map<String, Double> scores = new HashMap<>();
        for (List<String> ranking : rankings) {
            for (int rank = 0; rank < ranking.size(); rank++) {
                scores.merge(ranking.get(rank), 1.0 / (k + rank + 1), Double::sum);
            }
        }
        return scores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topN)
            .map(Map.Entry::getKey)
            .toList();
    }
}
```

**要点**：只使用排名，不依赖各路检索的原始分数，因此不需要做分数归一化；在多路中都排名靠前的文档得分最高。

**追问**：*RRF 之后还需要做什么？* 通常再用重排序模型对融合后的前几十条结果精排，再选取前几条交给大模型。

**减分回答**：直接把向量相似度和 BM25 分数相加。

### Q9 计算余弦相似度，并从大量向量中找出最相似的前 K 个。

**考察点**：向量计算与 Top-K 算法。

**参考实现**

```java
public final class VectorSearch {

    public record Scored(String id, double score) {
    }

    private VectorSearch() {
    }

    public static double cosine(float[] a, float[] b) {
        if (a.length != b.length) {
            // 不同维度的向量来自不同的模型，比较没有意义
            throw new IllegalArgumentException("vector dimension mismatch");
        }
        double dot = 0;
        double normA = 0;
        double normB = 0;
        for (int i = 0; i < a.length; i++) {
            dot += a[i] * b[i];
            normA += a[i] * a[i];
            normB += b[i] * b[i];
        }
        if (normA == 0 || normB == 0) {
            return 0;
        }
        return dot / (Math.sqrt(normA) * Math.sqrt(normB));
    }

    /** 用大小为 K 的最小堆保留当前最相似的 K 个，复杂度 O(n log K)。 */
    public static List<Scored> topK(float[] query, Map<String, float[]> candidates, int k) {
        PriorityQueue<Scored> heap = new PriorityQueue<>(Comparator.comparingDouble(Scored::score));
        for (Map.Entry<String, float[]> entry : candidates.entrySet()) {
            double score = cosine(query, entry.getValue());
            if (heap.size() < k) {
                heap.offer(new Scored(entry.getKey(), score));
            } else if (score > heap.peek().score()) {
                heap.poll();
                heap.offer(new Scored(entry.getKey(), score));
            }
        }
        List<Scored> result = new ArrayList<>(heap);
        result.sort(Comparator.comparingDouble(Scored::score).reversed());
        return result;
    }
}
```

**要点**：维度不一致直接报错；零向量的处理；使用最小堆，避免对全部候选排序。

**追问**：*数据量达到百万级怎么办？* 暴力计算的复杂度是 O(n·d)，需要使用近似最近邻索引（HNSW、IVF）；
向量预先归一化后，余弦相似度可以简化为点积。

**减分回答**：对全部结果排序后取前 K 个，且不检查维度。

### Q10 并行调用多个专家 Agent，每个设置超时，失败的返回占位结果，最后汇总。

**考察点**：并发编排、超时与失败隔离。

**参考实现**（`CompletableFuture` 版本）

```java
public interface Expert {
    String name();

    String answer(String question);
}

public final class ExpertFanout {

    private final Executor executor;
    private final Duration timeout;

    /** executor 应为有界线程池，线程数即最大并发数，避免同时向模型厂商发起过多调用。 */
    public ExpertFanout(Executor executor, Duration timeout) {
        this.executor = executor;
        this.timeout = timeout;
    }

    public List<String> consult(String question, List<Expert> experts) {
        List<CompletableFuture<String>> futures = experts.stream()
            .map(expert -> CompletableFuture.supplyAsync(() -> expert.answer(question), executor)
                .orTimeout(timeout.toMillis(), TimeUnit.MILLISECONDS)
                .exceptionally(error -> "【" + expert.name() + "暂时无法回答】"))
            .toList();
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
        return futures.stream().map(CompletableFuture::join).toList();
    }
}
```

**Reactor 版本**（项目中的写法）：

```java
Flux.fromIterable(experts)
    .flatMap(expert -> Mono.fromCallable(() -> expert.answer(question))
        .subscribeOn(Schedulers.boundedElastic())
        .timeout(timeout)
        .onErrorReturn("【" + expert.name() + "暂时无法回答】"), maxConcurrency)
    .collectList();
```

**要点**：单个专家的失败或超时不影响整体；通过线程池大小或 `flatMap` 的并发参数限制并发数；
阻塞的调用必须切换到弹性线程池，否则并发只是形式上的。

**追问**：*`orTimeout` 超时后，后台的调用会停止吗？* 不会自动停止，底层任务可能仍在执行并消耗资源；
需要支持取消的客户端，或者在调用本身设置超时。

**减分回答**：依次串行调用每个专家；或者某个专家出错导致整体失败。

# 基础补全第 09 期 · 向量数据库与检索引擎选型

> **本期结论**：JD 中经常出现 Milvus、Elasticsearch、PGVector 等关键词。面试官想知道候选人能否根据数据规模、查询模式、
> 过滤需求和运维能力做出合理选择，而不是只说“用 Milvus”。
>
> 说明：各产品迭代较快，具体特性以官方文档为准。
>
> 题量 10。

---

### Q1 常见的向量存储方案有哪些？各自适合什么场景？

**考察点**：选型的整体认知。

**参考回答**

| 方案 | 特点 | 适合的场景 |
|---|---|---|
| 专用向量数据库（Milvus 等） | 为大规模向量检索设计，支持多种索引，可以水平扩展 | 数据量大、检索是核心能力 |
| 搜索引擎（Elasticsearch / OpenSearch） | 同时支持全文检索和向量检索，便于做混合检索 | 已有 ES 基础设施、需要关键词加向量的混合检索 |
| 关系型数据库扩展（PGVector 等） | 向量和业务数据在一起，支持事务和 SQL 过滤 | 数据量中等、希望少引入组件 |
| Redis 等内存数据库 | 延迟低 | 数据量小、对延迟要求高 |
| 应用内存或 MySQL 加应用层计算 | 实现最简单 | 原型阶段、数据量很小 |

- **选择依据**：数据量和增长速度；是否需要混合检索；过滤条件的复杂度；对延迟和召回率的要求；团队的运维能力；是否需要与业务数据保持事务一致。

**追问**：*数据量只有几万条，需要专门部署向量数据库吗？* 通常不需要，使用现有数据库的向量能力就足够，少一个组件就少一份运维成本。

**减分回答**：不管什么场景都说“用 Milvus”。

### Q2 带过滤条件的向量检索有哪些实现方式？各有什么问题？

**考察点**：过滤与检索的结合。

**参考回答**

- **先检索后过滤**：先取出最相似的 K 条，再按条件过滤。问题：过滤后可能不足 K 条，甚至为空（例如大部分数据属于其他租户）。
- **先过滤后检索**：先按条件筛选出候选，再在候选中计算相似度。问题：候选很多时退化为暴力计算；无法充分利用向量索引。
- **检索过程中过滤**：在遍历索引的过程中同时判断过滤条件，这是较好的方式，需要向量库支持。
- **按分区隔离**：按租户或类别建立分区或独立的集合，检索时只查对应的分区。适合过滤条件固定、分区数量可控的情况。
- **Agent 场景**：租户、权限、文档状态都是必须的过滤条件，而且必须由服务端强制添加。

**追问**：*租户很多（成千上万），每个租户一个集合可以吗？* 集合太多会带来资源和管理上的开销；通常使用共享集合加租户字段过滤，
大租户可以单独分区。

**减分回答**：没有意识到先检索后过滤会导致结果不足。

### Q3 向量索引的参数怎么调优？

**考察点**：召回率与性能的平衡。

**参考回答**

- **HNSW**：
  - 每个节点的连接数（M）越大，召回率越高，但内存占用和构建时间也越多；
  - 构建时的候选数越大，索引质量越好，构建越慢；
  - 查询时的候选数越大，召回率越高，查询越慢，这个参数可以在查询时动态调整。
- **IVF**：聚类中心的数量和查询时搜索的聚类数；搜索的聚类数越多越准确，也越慢。
- **量化**：用乘积量化等方法压缩向量，节省内存，但会损失一定精度。
- **调优方法**：建立带标准答案的测试集，用暴力检索的结果作为基准，测量不同参数下的召回率、延迟和内存，选择满足要求的平衡点。

**追问**：*召回率 95% 意味着什么？* 与精确检索相比，平均有 5% 的真正最相似的结果没有被找到；需要评估这对最终回答的影响。

**减分回答**：使用默认参数，从不测量召回率。

### Q4 Elasticsearch 如何同时实现全文检索和向量检索？

**考察点**：混合检索的实现。

**参考回答**

- **全文检索**：基于倒排索引和 BM25 打分；中文需要配置合适的分词器（例如 IK 分词器），分词质量直接影响召回。
- **向量检索**：使用向量类型的字段，支持近似最近邻检索（基于 HNSW）。
- **混合检索**：在一次查询中同时执行关键词查询和向量查询，再融合结果（例如 RRF 或加权打分，新版本提供了相关的内置能力）。
- **过滤**：可以在向量检索中带上过滤条件（例如租户、权限）。
- **注意**：向量索引会占用大量内存；写入后需要刷新才能被检索到；索引参数需要根据数据量调整。

**追问**：*中文分词对 RAG 有什么影响？* 分词不准确会导致关键词检索召回不到；专有名词（产品型号、业务术语）需要加入自定义词典。

**减分回答**：只知道 ES 可以做全文检索。

### Q5 BM25 的原理是什么？为什么比简单的词频统计好？

**考察点**：关键词检索的基础。

**参考回答**

- **核心思想**：一个词在文档中出现的频率越高、在整个语料中越少见，这个文档与查询的相关度就越高。
- **相比简单的 TF-IDF 的改进**：
  1. **词频饱和**：词频增加到一定程度后，得分的增长会变缓，避免某个词重复很多次的文档得分过高；
  2. **文档长度归一化**：长文档天然包含更多的词，对其进行惩罚，避免长文档总是排在前面。
- **适用**：精确的关键词匹配，例如订单号、型号、人名、专业术语。
- **局限**：无法理解同义词和语义上的相似。

**追问**：*为什么不能只用向量检索？* 向量检索对精确匹配（编号、型号）效果差；混合检索能兼顾两者。

**减分回答**：说不出 BM25 和词频统计的区别。

### Q6 稀疏向量和稠密向量有什么区别？

**考察点**：向量表示的类型。

**参考回答**

- **稠密向量**：维度固定（例如几百到几千维），每一维都有值，表达语义上的相似性。由 Embedding 模型生成。
- **稀疏向量**：维度很高（例如与词表大小相同），大部分维度为 0，只有与文本相关的少数维度有值，类似于关键词的权重。
  BM25 的结果可以看作一种稀疏表示；也有通过模型学习得到的稀疏向量（例如 SPLADE），能够对词做一定的扩展。
- **结合使用**：同时使用稠密向量和稀疏向量做混合检索，兼顾语义相似和关键词匹配。
- **ColBERT 等多向量方法**：为每个词保留一个向量，检索时做细粒度的匹配，效果好但存储开销大。

**追问**：*学习得到的稀疏向量相比 BM25 有什么优势？* 能够对查询和文档做词的扩展（例如把“手机”扩展到“移动电话”），同时保持关键词匹配的可解释性。

**减分回答**：只知道一种向量。

### Q7 向量数据的更新和删除有什么需要注意的地方？

**考察点**：向量数据的生命周期。

**参考回答**

- **删除**：部分向量索引的删除只是标记删除，需要定期压缩或重建索引才能真正回收空间，并保持检索性能。
- **更新**：通常实现为“删除 + 插入”；文档更新时要删除旧版本的全部分块，再写入新的分块。
- **一致性**：向量库与业务数据库之间没有事务保证，需要以一方为权威数据源，用幂等写入和定期对账保证最终一致。
- **版本切换**：大批量更新时，可以先写入新版本，再原子地切换检索使用的版本，最后删除旧版本，避免检索到新旧混合的数据。
- **权限变更**：撤销权限后，向量库中的元数据也要同步更新，否则仍然可能被检索到。

**追问**：*用户删除了一份文档，但检索结果中仍然出现它的内容，可能是什么原因？* 向量库中的分块没有删除；语义缓存中保存了基于旧内容的答案；
或者删除操作还没有生效（例如索引没有刷新）。

**减分回答**：只关注写入，不考虑删除和更新。

### Q8 Embedding 模型更换后，如何平滑迁移？

**考察点**：模型升级的工程实践。

**参考回答**

- **原因**：不同模型生成的向量不能混用，维度不同时无法比较，即使维度相同，分数也没有意义。
- **迁移步骤**：
  1. 用新模型为全部数据重新生成向量，写入新的索引或集合（与旧索引并存）；
  2. 在评测集上对比新旧模型的检索效果；
  3. 灰度切换检索使用的索引，观察线上指标；
  4. 全部切换后下线旧索引；
  5. 迁移期间的新增数据要同时写入新旧两个索引。
- **保护措施**：检索时检查查询向量和索引的维度是否一致，不一致时跳过而不是返回错误的结果
  （项目对照：`ManagedKnowledge` 中的维度校验，见 [项目第 03 期 Q2](../03-RAG与知识库工程.md)）。

**追问**：*重新生成向量的成本很高，怎么优化？* 批量调用 Embedding 接口；按文档的更新时间分批迁移；优先迁移访问频率高的数据。

**减分回答**：直接在线上替换模型，不重建索引。

### Q9 如何评估向量检索系统的性能？

**考察点**：性能指标与测试方法。

**参考回答**

- **效果指标**：召回率（与精确检索相比）、Recall@K、MRR。
- **性能指标**：查询延迟（P50 / P95 / P99）、QPS、写入吞吐、索引构建时间。
- **资源指标**：内存占用（向量索引通常主要占用内存）、磁盘、CPU。
- **测试方法**：使用真实规模和分布的数据；测试带过滤条件的查询；测试并发读写同时进行的场景；测试数据增长后的表现。
- **容量规划**：内存的估算约为“向量数量 × 维度 × 每个值的字节数”，再加上索引结构的开销（例如 HNSW 的图结构）。

**追问**：*100 万条 1024 维的 float 向量，原始数据大约占多少内存？* 100 万 × 1024 × 4 字节约为 4GB，还要加上索引结构的开销。

**减分回答**：只测试一次单条查询的耗时。

### Q10 在 Java 项目中如何接入向量检索，并保持可替换性？

**考察点**：工程上的抽象。

**参考回答**

- **定义抽象接口**：例如 `VectorStore`（写入、删除、带过滤条件的检索）和 `EmbeddingClient`（生成向量），业务代码只依赖接口。
- **多种实现**：内存实现用于测试；数据库实现用于小规模的场景；专用向量库的实现用于大规模的场景。通过配置切换。
- **框架的抽象**：Spring AI 的 `VectorStore`、LangChain4j 的 `EmbeddingStore` 都提供了类似的抽象，但要注意它们对过滤条件的支持程度。
- **租户和权限的过滤**：在抽象层中强制添加，而不是交给每个调用方。
- **可观测**：记录检索的耗时、返回数量、最高分数、是否为空结果，以及候选数是否达到上限。

**追问**：*什么时候应该从数据库实现切换到专用的向量库？* 当指标显示查询延迟上升、候选数经常达到上限、数据量持续增长时；
有了抽象接口，切换只需要替换实现。

**减分回答**：在业务代码中直接调用某个向量库的 SDK。

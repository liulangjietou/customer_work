### Q1 TCP 三次握手和四次挥手的过程是怎样的？TIME_WAIT 过多会有什么问题？

**考察点**：TCP 连接管理。

**参考回答**

- **三次握手**：客户端发送 SYN → 服务端回复 SYN + ACK → 客户端回复 ACK。三次握手确认双方的收发能力，并同步初始序列号；
  两次握手无法防止已经失效的旧连接请求被服务端误认为新连接。
- **四次挥手**：主动关闭方发送 FIN → 对方回复 ACK → 对方数据发送完后发送 FIN → 主动关闭方回复 ACK，并进入 TIME_WAIT 状态。
  需要四次，是因为 TCP 是全双工的，两个方向需要分别关闭。
- **TIME_WAIT**：持续 2 倍的 MSL（报文最大生存时间），用于确保最后一个 ACK 能到达，并让旧连接的报文在网络中消失。
- **TIME_WAIT 过多**：短连接频繁建立和关闭时（例如调用模型 API 时每次都新建连接），主动关闭方会积累大量 TIME_WAIT，占用端口，
  可能导致无法建立新连接。
- **解决**：使用连接池和 HTTP 长连接复用连接；必要时调整内核参数。

**追问**：*调用大模型 API 时，为什么要复用 HTTP 连接？* 每次新建连接都要经历 TCP 握手和 TLS 握手，会增加几十到几百毫秒的延迟，
还会产生大量 TIME_WAIT。

**减分回答**：说不出为什么需要三次握手，或者不知道 TIME_WAIT 的作用。

### Q2 TCP 如何保证可靠传输？流量控制和拥塞控制有什么区别？

**考察点**：TCP 的核心机制。

**参考回答**

- **可靠传输**：序列号和确认应答、超时重传、快速重传（收到三个重复的 ACK）、按序重组、校验和。
- **流量控制**：接收方通过窗口大小告诉发送方自己还能接收多少数据，防止发送方发得太快、接收方处理不过来。
  它解决的是“发送方与接收方”之间的速度匹配。
- **拥塞控制**：发送方根据网络状况调整发送速度，防止网络过载。包括慢启动、拥塞避免、快速重传、快速恢复等算法。
  它解决的是“发送方与整个网络”之间的问题。
- **与流式输出的关系**：客户端读取慢时，TCP 的接收窗口会变小，服务端的发送缓冲区逐渐被填满；
  应用层需要感知这种情况（背压），而不是在内存中无限堆积待发送的数据。

**追问**：*Nagle 算法对流式输出有什么影响？* Nagle 算法会把小数据包合并后再发送，可能增加流式分片的延迟；
对实时性要求高的场景可以开启 `TCP_NODELAY`（Netty 等框架通常默认开启）。

**减分回答**：把流量控制和拥塞控制混为一谈。

### Q3 HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

**考察点**：HTTP 协议的演进。

**参考回答**

- **HTTP/1.1**：文本协议；支持持久连接；同一个连接上请求需要排队（队头阻塞），浏览器通常对同一域名建立多个连接来并发。
- **HTTP/2**：二进制分帧；在一个连接上多路复用多个请求；头部压缩；服务端推送（实际很少使用）。
  但它仍然基于 TCP，一个 TCP 包丢失会阻塞所有流（TCP 层面的队头阻塞）。
- **HTTP/3**：基于 QUIC（运行在 UDP 之上），解决了 TCP 层面的队头阻塞；连接建立更快；网络切换（例如从 Wi-Fi 切到移动网络）时连接可以迁移。
- **与 Agent 服务的关系**：SSE 在 HTTP/1.1 下每个流占用一个连接，浏览器对同一域名的连接数有上限（通常为 6 个），
  打开多个页面时可能被占满；HTTP/2 下多个 SSE 流可以共享一个连接。gRPC 基于 HTTP/2。

**追问**：*浏览器打开多个标签页都使用 SSE，后面的页面卡住了，可能是什么原因？* HTTP/1.1 下同一域名的连接数达到上限，
新的请求在排队；可以改用 HTTP/2，或者在多个页面之间共享一个连接。

**减分回答**：只知道“HTTP/2 更快”。

### Q4 HTTPS 的 TLS 握手过程是怎样的？

**考察点**：安全传输的原理。

**参考回答**

- **目的**：协商加密算法、验证服务端身份（证书）、生成会话密钥。
- **TLS 1.2 的简化流程**：客户端发送支持的算法和随机数 → 服务端返回选定的算法、随机数和证书 → 客户端验证证书，
  双方通过密钥交换（例如 ECDHE）算出相同的会话密钥 → 之后用对称加密传输数据。完整握手需要 2 个往返。
- **TLS 1.3**：握手减少到 1 个往返，支持会话恢复时的 0-RTT；移除了不安全的算法。
- **证书验证**：检查证书链是否由可信的 CA 签发、域名是否匹配、是否过期或被吊销。
- **与 Agent 服务的关系**：
  1. 调用模型 API 时复用连接，避免重复握手；
  2. 企业内网的代理可能会重新签发证书（中间人代理），Java 程序需要信任代理的 CA 证书，否则会出现证书校验失败；
  3. 绝不能为了“解决”证书问题而关闭证书校验。

**追问**：*为什么在密钥交换后要使用对称加密传输数据？* 非对称加密的计算开销很大，只用于协商密钥；大量数据使用对称加密，性能更好。

**减分回答**：“HTTPS 就是用公钥加密所有数据”。

### Q5 WebSocket 是怎么建立连接的？协议层面有哪些细节？

**考察点**：WebSocket 协议。

**参考回答**

- **建立连接**：客户端发送 HTTP 请求，带上 `Upgrade: websocket`、`Connection: Upgrade` 和一个随机的密钥；
  服务端返回 101 状态码，完成协议升级，之后在同一个 TCP 连接上进行全双工通信。
- **帧**：数据被分为帧传输，有文本帧、二进制帧、控制帧（Ping、Pong、Close）；客户端发送的帧必须使用掩码。
- **心跳**：通过 Ping / Pong 帧检测连接是否存活，防止被中间的代理因为空闲而断开。
- **鉴权**：浏览器的 WebSocket API 不能自定义请求头，常见的做法是在 URL 参数中携带 token，或者建立连接后发送的第一条消息中进行鉴权；
  URL 中的 token 要注意不要被记录到日志中。
- **网关配置**：代理和网关需要支持协议升级，并设置足够长的空闲超时。

**追问**：*WebSocket 断线重连后，如何保证消息不丢、不重复？* 客户端为每条消息生成 ID，重发时沿用；服务端按 ID 做幂等；
重连后客户端补拉断线期间的消息（见 [项目第 07 期 Q3](../07-生产化-多租户限流幂等与一致性.md)）。

**减分回答**：认为 WebSocket 和 HTTP 是完全无关的两个协议。

### Q6 SSE 的协议格式是怎样的？和 WebSocket 相比有什么优缺点？

**考察点**：流式协议的细节。

**参考回答**

- **协议格式**：响应的 Content-Type 为 `text/event-stream`；每个事件由若干行组成，常用的字段有 `data:`、`event:`、`id:`、`retry:`；
  事件之间用空行分隔；以冒号开头的行是注释，常用作心跳。
- **断线重连**：浏览器的 `EventSource` 会自动重连，并通过 `Last-Event-ID` 请求头告诉服务端最后收到的事件 ID，服务端可以据此续传。
- **优点**：基于普通的 HTTP，容易穿透代理和防火墙；实现简单；浏览器原生支持自动重连。
- **缺点**：只能由服务端推送给客户端；`EventSource` 只支持 GET 请求，不能自定义请求头（大模型应用中常改用 `fetch` 读取流来实现 POST 请求）；
  HTTP/1.1 下有连接数的限制。

**追问**：*为什么很多大模型应用的流式接口使用 POST 请求加 SSE 格式？* 请求体需要携带较长的对话内容，而 `EventSource` 只支持 GET；
所以用 `fetch` 发起 POST 请求，再按 SSE 格式解析响应流。

**减分回答**：不知道 SSE 的事件格式和空行分隔的规则。

### Q7 长连接为什么会被莫名其妙地断开？怎么排查？

**考察点**：网络问题的排查。

**参考回答**

- **常见原因**：
  1. 负载均衡、网关、代理的空闲超时（例如 60 秒没有数据就断开）；
  2. NAT 设备的连接表超时；
  3. 服务端或客户端的读超时设置过短；
  4. 服务端发布或重启；
  5. 移动网络切换。
- **排查**：确认断开的时间规律（是否总是在固定的空闲时长后断开）；逐层检查链路上每个组件的超时配置；抓包查看是哪一方发出了 FIN 或 RST。
- **解决**：应用层定期发送心跳（小于链路上最短的空闲超时）；调整网关的超时配置；客户端实现断线重连和消息补拉。

**追问**：*模型思考时间很长，几十秒没有输出，连接被断开了，怎么办？* 在等待期间定期发送心跳（例如 SSE 的注释行或者状态事件），
让连接保持活跃，同时也让前端能展示“正在思考”的状态。

**减分回答**：只会让用户刷新页面。

### Q8 BIO、NIO、AIO 有什么区别？select、poll、epoll 有什么区别？

**考察点**：IO 模型。

**参考回答**

- **BIO（阻塞 IO）**：每个连接由一个线程处理，读写时线程阻塞。连接数多时线程数暴增。
- **NIO（非阻塞 IO + 多路复用）**：一个线程通过多路复用器管理大量连接，只处理已经就绪的连接。Netty 基于此实现。
- **AIO（异步 IO）**：由操作系统完成 IO 后通知应用；在 Linux 上的支持不如 NIO 成熟，实际使用较少。
- **多路复用的实现**：
  - `select`：用位图表示文件描述符，数量有上限（通常为 1024），每次调用都要把整个集合从用户态复制到内核态，并遍历全部描述符；
  - `poll`：用数组，没有数量上限，但仍然需要遍历；
  - `epoll`：在内核中维护关注的描述符集合，就绪时通过回调放入就绪列表，应用只获取就绪的描述符，适合大量连接、少量活跃的场景。
- **与 Agent 服务的关系**：大量 WebSocket 和 SSE 长连接中，同一时刻真正有数据传输的只是少数，epoll 加事件驱动的模型非常适合。

**追问**：*epoll 的水平触发和边缘触发有什么区别？* 水平触发：只要描述符处于就绪状态，每次都会通知；
边缘触发：只在状态发生变化时通知一次，需要一次性把数据读完，效率更高但编程更复杂。

**减分回答**：只知道“NIO 是非阻塞的”。

### Q9 Netty 的线程模型是怎样的？为什么不能在 EventLoop 中执行阻塞操作？

**考察点**：Reactor 模式与 Netty。

**参考回答**

- **Reactor 模式**：由事件循环监听 IO 事件，并分发给对应的处理器。
- **Netty 的主从 Reactor 模型**：Boss 线程组负责接受新连接；Worker 线程组（EventLoop）负责已建立连接的读写。
  每个连接绑定到一个 EventLoop，它上面的所有事件都由这个线程串行处理，避免了并发问题。
- **为什么不能阻塞**：一个 EventLoop 负责很多个连接，如果在处理某个连接时执行了阻塞操作（例如同步调用数据库或模型 API），
  这个线程上的所有其他连接都会被卡住。
- **正确做法**：阻塞操作交给单独的线程池执行（在 Reactor 中使用 `subscribeOn(Schedulers.boundedElastic())`），完成后再回到 IO 线程写出结果。
- **Spring WebFlux 默认基于 Netty**，同样的规则适用。

**追问**：*怎么发现代码中有没有在 EventLoop 上执行阻塞操作？* Reactor 会在非阻塞线程上检测 `block()` 并报错；
也可以借助 BlockHound 这类工具在测试中检测。

**减分回答**：“Netty 性能好，随便写都很快”。

### Q10 什么是零拷贝？在哪些场景中有用？

**考察点**：IO 性能优化。

**参考回答**

- **传统的文件发送**：数据从磁盘读到内核缓冲区 → 复制到用户态的缓冲区 → 再复制到内核的 socket 缓冲区 → 发送到网卡，
  涉及多次数据复制和用户态与内核态之间的切换。
- **零拷贝**：通过 `sendfile`、`mmap` 等系统调用，减少或避免数据在用户态和内核态之间的复制。
  Java 中的 `FileChannel.transferTo` 可以使用 `sendfile`。
- **Netty 中的“零拷贝”**：还包括在用户态避免复制的技巧，例如组合多个缓冲区（`CompositeByteBuf`）、切片（`slice`）、使用直接内存。
- **应用场景**：文件下载、消息队列的数据传输（Kafka 大量使用）、静态资源服务。
- **Agent 场景**：用户上传或下载附件时，可以通过对象存储的预签名地址让客户端直接上传和下载，完全不经过应用服务，比零拷贝更彻底。

**追问**：*Kafka 为什么吞吐量高？* 顺序写磁盘、利用操作系统的页缓存、零拷贝发送、批量处理和压缩。

**减分回答**：认为“零拷贝”就是完全不复制数据。

### Q11 进程、线程、协程（虚拟线程）有什么区别？

**考察点**：并发执行单元。

**参考回答**

- **进程**：资源分配的单位，有独立的地址空间；进程之间隔离性好，但切换和通信的开销大。
- **线程**：CPU 调度的单位，同一进程内的线程共享内存；Java 的平台线程与操作系统线程一一对应，创建和切换的开销较大，数量通常只能到几千个。
- **协程 / 虚拟线程**：由运行时在用户态调度，大量虚拟线程复用少量的操作系统线程（载体线程）；遇到阻塞 IO 时让出载体线程，
  创建和切换的开销很小，可以支持数十万甚至上百万个。
- **与 Agent 服务的关系**：Agent 服务大部分时间在等待 IO，虚拟线程或响应式模型都能以少量的操作系统线程支撑大量并发；
  CPU 密集的任务（例如大量向量计算）使用虚拟线程没有收益。

**追问**：*代码执行沙箱为什么通常用进程或容器隔离，而不用线程？* 线程共享内存，无法隔离不可信的代码；进程和容器提供了独立的地址空间和资源限制。

**减分回答**：说不出线程和协程在调度方式上的区别。

### Q12 什么是上下文切换？线程数过多为什么会导致性能下降？

**考察点**：操作系统调度。

**参考回答**

- **上下文切换**：CPU 从执行一个线程切换到另一个线程时，要保存当前线程的寄存器、程序计数器等状态，并加载另一个线程的状态；
  如果涉及内核态与用户态的切换、CPU 缓存失效，开销会更大。
- **线程过多的影响**：
  1. 频繁的上下文切换消耗 CPU；
  2. 每个线程都有栈内存（通常为几百 KB 到 1MB）；
  3. 锁的竞争加剧；
  4. CPU 缓存的命中率下降。
- **排查**：使用 `vmstat`、`pidstat` 查看上下文切换的次数；使用线程转储查看线程的数量和状态。
- **Agent 场景**：为每个请求创建一个平台线程去同步等待模型响应，线程数会随着并发量暴增；使用线程池并设置上限，或者使用虚拟线程、响应式模型。

**追问**：*线程池的线程数是不是越多越好？* 不是。IO 密集型任务可以多一些，但受上下文切换、内存和下游资源限制，需要通过压测确定。

**减分回答**：认为线程越多并发能力越强。

### Q13 文件描述符有什么限制？大量长连接的服务需要注意什么？

**考察点**：系统资源限制。

**参考回答**

- **文件描述符**：在 Linux 中，每个打开的文件、socket 都占用一个文件描述符。每个进程可以打开的数量有上限（`ulimit -n`，默认值常为 1024），
  系统层面也有总数的上限。
- **超出上限时**：会出现 “Too many open files” 错误，无法建立新的连接。
- **大量长连接的服务需要注意**：
  1. 调高进程和系统的文件描述符上限（容器中也要配置）；
  2. 关注每个连接占用的内存（缓冲区）；
  3. 确保连接关闭时释放资源，避免描述符泄漏；
  4. 监控当前打开的描述符数量。
- **Agent 场景**：WebSocket 客服服务，每个在线用户保持一个长连接；此外调用模型、数据库、Redis 的连接也占用描述符。

**追问**：*描述符数量一直在增长，可能是什么原因？* 连接或文件没有正确关闭（例如 HTTP 响应体没有读完或关闭，导致连接无法复用也无法释放）。

**减分回答**：不知道有文件描述符的限制。

### Q14 DNS 解析的过程是怎样的？和 SSRF 防护有什么关系？

**考察点**：DNS 与安全。

**参考回答**

- **解析过程**：浏览器缓存 → 操作系统缓存和 hosts 文件 → 本地 DNS 服务器 → 由本地 DNS 服务器递归查询根域名服务器、顶级域名服务器、权威域名服务器，
  得到 IP 地址后逐级缓存（受 TTL 控制）。
- **Java 中的 DNS 缓存**：JVM 会缓存解析结果，缓存时间受安全策略和相关配置控制；服务的 IP 变化后，JVM 可能仍然使用旧的地址。
- **与 SSRF 防护的关系**：
  1. 只校验 URL 中的域名是不够的，攻击者可以注册一个解析到内网 IP 的域名，所以要**校验解析后的 IP**，拒绝内网地址、云元数据地址等；
  2. **DNS 重绑定**：校验时解析到公网 IP，真正发起请求时再次解析得到内网 IP；需要在建立连接时再次校验，或者直接使用校验过的 IP 发起连接；
  3. 重定向也可能跳转到内网地址，需要对重定向的目标再次校验。
- **项目对照**：MCP 的远程地址校验，见 [项目第 05 期 Q6](../05-安全护栏与治理中间件.md)。

**追问**：*为什么要在保存配置和每次建立连接时都做校验？* 域名的解析结果可能随时变化，只在保存时校验一次无法防御 DNS 重绑定。

**减分回答**：只用正则表达式检查 URL 中是否包含 “localhost” 或 “127.0.0.1”。

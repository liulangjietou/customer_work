### Q1 RAGAS 是什么？常用的指标有哪些？

**考察点**：RAG 评测工具的核心概念。

**参考回答**

- **定位**：一个开源的 RAG 与 LLM 应用评测框架，大部分指标借助 LLM 作为裁判来计算。
- **常用指标**：
  - **Faithfulness（忠实度）**：答案中的陈述有多少能在检索到的上下文中找到依据，用来衡量幻觉；
  - **Answer Relevancy（答案相关性）**：答案是否切题；
  - **Context Precision（上下文精确率）**：检索到的内容中，相关的内容是否排在前面；
  - **Context Recall（上下文召回率）**：回答问题所需的信息是否都被检索到了（需要参考答案）；
  - **Answer Correctness / Factual Correctness**：答案与参考答案相比是否正确。
  还有不依赖 LLM、基于文档 ID 计算的上下文精确率和召回率。
- **输入数据**：问题、模型的回答、检索到的上下文，部分指标还需要参考答案。
- **用法**：离线批量评测，比较不同检索参数、分块策略、提示词的效果；也可以接入 CI。

**追问**：*RAGAS 的分数可以直接作为线上质量指标吗？* 不能直接使用。这些分数依赖裁判模型，有偏差和波动；
适合用来比较不同版本的相对优劣，并且需要用人工标注做校准（见[进阶第 06 期 Q6](../advanced/06-评测体系与数据飞轮进阶.md)）。

**减分回答**：只知道 RAGAS 这个名字，说不出任何一个指标的含义。

### Q2 用 RAGAS 这类工具评测时，有哪些常见的坑？

**考察点**：评测工具的实际使用经验。

**参考回答**

- **裁判模型的影响**：换一个裁判模型，分数可能整体变化，跨裁判模型的分数不能直接比较；需要固定并记录裁判模型的版本。
- **成本**：每个样本的每个指标都需要若干次模型调用，评测集大时成本可观；可以先用小样本调试，再全量运行。
- **中文效果**：部分指标内部的提示词是英文的，对中文场景的效果需要验证，必要时自定义提示词。
- **数据质量**：参考答案不准确，会导致召回率、正确性这类指标失真。
- **分数的解读**：分数低时，要结合具体的样本分析原因，而不是只看平均分。
- **版本变化**：工具的 API 和指标的实现随版本变化，需要锁定版本。

**追问**：*怎么确认 RAGAS 的忠实度分数是可信的？* 抽取一部分样本人工标注，计算与 RAGAS 分数的一致性。

**减分回答**：直接相信工具给出的分数。

### Q3 如何构建 RAG 评测数据集？能用工具自动生成吗？

**考察点**：评测数据的来源。

**参考回答**

- **来源**：
  1. 真实用户的问题（脱敏后），配上人工整理的参考答案和相关文档；
  2. 业务专家编写的典型问题和边界问题；
  3. 用工具基于知识库自动生成问题和答案（RAGAS 等工具提供了测试集生成的能力）。
- **自动生成的优缺点**：
  - 优点：速度快，能覆盖大量文档；
  - 缺点：生成的问题往往比真实问题更“规范”，与真实的用户表达有差距；可能有错误，需要人工抽检。
- **建议**：真实问题和生成的问题混合使用；按问题类型分组（事实查询、多跳推理、无答案的问题）；
  包含“知识库中没有答案”的问题，用来检验模型是否会承认不知道。

**追问**：*为什么要包含知识库中没有答案的问题？* 用来检验系统在检索不到时是否会编造答案，这是线上最常见的风险之一。

**减分回答**：只用自动生成的问题做评测。

### Q4 Langfuse 是什么？核心概念有哪些？

**考察点**：LLM 可观测平台的认知。

**参考回答**

- **定位**：开源的 LLM 应用工程平台，支持自行部署，覆盖链路追踪、提示词管理、评测与数据集等功能。新版本的 SDK 基于 OpenTelemetry 实现。
- **核心概念**：
  - **Trace**：一次完整的请求或对话轮次；
  - **Observation**：Trace 中的各个步骤，按类型区分，例如普通的 Span、模型调用（Generation，会记录模型、token 用量和成本）、
    工具调用、检索、Agent、评估器、安全护栏等；
  - **Session**：把同一个会话的多个 Trace 关联起来；
  - **Score**：对 Trace 或 Observation 的评分，可以来自用户反馈、人工标注或自动评估；
  - **Prompt 管理**：提示词的版本管理，并且能把 Trace 关联到具体的提示词版本；
  - **Dataset 与实验**：管理评测数据集，运行实验并比较结果。
- **优势**：可以自行部署，满足数据不出企业内网的要求；与多种框架有现成的集成。

**追问**：*自行部署 Langfuse 需要注意什么？* 它依赖数据库等多个组件，需要评估运维成本；追踪数据量大时要规划存储和保留策略；
提示词和回答中的敏感信息要脱敏。

**减分回答**：只知道它能“看日志”。

### Q5 LangSmith 和 Langfuse 有什么区别？怎么选？

**考察点**：工具选型。

**参考回答**

- **LangSmith**：LangChain 官方的平台，与 LangChain、LangGraph 的集成最紧密，提供追踪、评测、数据集、提示词管理等功能；
  以云服务为主，企业版支持自行部署。
- **Langfuse**：开源，可以自行部署，与框架无关，通过 SDK 或 OpenTelemetry 接入。
- **其他选择**：Arize Phoenix 等开源工具；基于 OpenTelemetry 的通用可观测平台（配合生成式 AI 的语义约定）；也可以自建。
- **选型依据**：
  1. 数据合规：是否允许把提示词和回答发送到外部的云服务；
  2. 技术栈：主要使用 LangChain 生态，还是 Java 等其他技术栈；
  3. 功能需求：只需要追踪，还是还需要提示词管理和评测；
  4. 成本与运维能力。
- **Java 项目**：更适合选择支持 OpenTelemetry 或者提供通用 HTTP API 的工具，便于从 Java 服务接入。

**追问**：*已经有了 Prometheus 和 Grafana，还需要专门的 LLM 可观测工具吗？* 指标系统适合看整体的趋势和告警，
但难以查看单次对话的完整过程（每一步的输入输出）；两者互补。

**减分回答**：“哪个有名用哪个”。

### Q6 Java 服务如何接入 LLM 可观测平台？

**考察点**：跨语言的工程实践。

**参考回答**

- **基于 OpenTelemetry**：Java 服务使用 OpenTelemetry SDK 生成 Span，按生成式 AI 的语义约定记录模型名称、token 用量等属性，
  再通过 OTLP 导出到支持 OpenTelemetry 的平台（Langfuse 的新版本、Phoenix，以及通用的追踪系统）。
- **使用平台提供的 HTTP API**：没有 Java SDK 时，按平台的接口直接上报 Trace 数据，需要注意异步和批量上报。
- **框架的集成**：部分 Java 框架提供了可观测的集成（例如 Spring AI 与 Micrometer 的集成，AgentScope 提供了 OpenTelemetry 支持）。
- **需要注意**：
  1. 上报必须是异步的旁路操作，失败不能影响主链路；
  2. 敏感信息在上报前脱敏；
  3. 控制采样率和数据量；
  4. 追踪 ID 要与业务日志、消息 ID 关联起来。
- **项目对照**：项目支持显式开启 OpenTelemetry，导出 Agent、模型、工具和 HTTP 的 Span（见 README 中的可观测说明）。

**追问**：*上报到外部平台的数据中包含用户的对话内容，有什么风险？* 隐私泄露和合规风险；需要脱敏、选择自行部署，或者只上报元数据。

**减分回答**：在主链路中同步调用平台的接口上报数据。

### Q7 如何把评测集成到 CI/CD 流程中？

**考察点**：评测的工程化。

**参考回答**

- **分层运行**：
  1. 每次提交：运行确定性的单元测试，以及少量的核心评测用例（冒烟测试），控制时间和成本；
  2. 合并到主分支或发布前：运行完整的评测集；
  3. 定期运行（例如每天）：检测模型厂商的变化和数据的漂移。
- **门禁**：核心指标不能低于基线；关键用例不能出现回归；评测不完整时阻止发布。
- **结果管理**：保存每次评测的结果和版本信息，生成与基线的对比报告，附在 PR 或发布记录中。
- **隔离**：评测使用独立的模型凭据和配额，调用费用单独统计；使用模拟的后端，避免对真实业务系统产生副作用。
- **稳定性**：模型输出有随机性，关键用例可以多次运行取通过率，避免偶然的失败阻塞流程。

**追问**：*评测在 CI 中偶尔失败，怎么处理？* 分析失败的原因：如果是模型的随机性，就增加运行次数或调整阈值；
如果是真实的回归，就要修复。不能简单地重试到通过为止。

**减分回答**：评测只在上线前手动运行一次。

### Q8 如何把用户反馈和线上追踪数据关联起来，用于改进 Agent？

**考察点**：数据闭环的实现。

**参考回答**

- **关联**：回答中返回消息 ID 或追踪 ID；用户的点赞、点踩、评分、转人工等行为带上这个 ID 上报，作为评分写入对应的 Trace。
- **筛选**：在平台中筛选出负面反馈的对话，查看完整的执行过程（检索到了什么、调用了哪些工具、模型的输出）。
- **沉淀**：把有问题的对话加入评测数据集（脱敏后），并标注期望的结果。
- **自动评估**：对线上抽样的对话运行自动评估（例如忠实度），发现没有用户反馈的问题。
- **跟踪改进效果**：修复后在评测集上验证，并观察线上同类问题的反馈是否减少。

**追问**：*用户很少主动反馈，怎么办？* 结合隐式信号（转人工、重复提问、会话中途放弃），并对线上对话抽样做自动评估和人工抽检。

**减分回答**：只统计点赞和点踩的总数。

### Q9 在可观测平台中如何追踪和分析成本？

**考察点**：成本的可观测。

**参考回答**

- **记录**：每次模型调用记录模型名称、输入和输出的 token 数；平台根据配置的单价计算成本（Langfuse 这类平台支持按模型配置价格）。
- **分析维度**：按用户、租户、功能、提示词版本、模型等维度统计；找出单次成本最高的对话和功能。
- **注意**：
  1. 平台计算的成本是估算值，最终要与厂商的账单对账；
  2. 提示词缓存、批量接口的折扣要正确反映在单价中；
  3. 思考类 token、Embedding 调用、评测调用也要计入；
  4. 绕开主链路的调用（例如 OCR）同样需要上报。
- **与内部计量的关系**：可观测平台适合分析和排查；计费和配额以系统内部唯一的计量点为准。

**追问**：*可观测平台显示的成本与厂商账单对不上，可能是什么原因？* 单价配置过时；缓存折扣没有计入；部分调用没有上报；
评测、巡检等调用没有纳入统计。

**减分回答**：只看厂商的月度账单。

### Q10 LLM 应用的追踪数据中包含敏感信息，怎么处理？

**考察点**：可观测与隐私的平衡。

**参考回答**

- **脱敏**：在数据上报之前，对手机号、身份证号、银行卡号等个人信息进行识别和替换；工具平台通常也提供了在 SDK 端做掩码处理的扩展点。
- **最小化**：根据需要选择记录的内容，例如只记录元数据（token 数、耗时、状态），或者只记录部分字段。
- **访问控制**：可观测平台的访问权限要严格控制，并记录访问日志。
- **保留期**：设置数据保留期限，到期自动删除。
- **部署方式**：敏感业务选择自行部署的平台，数据不出企业内网。
- **用户删除数据的请求**：追踪数据中的相关内容也需要按照策略删除。

**追问**：*脱敏之后，排查问题时看不到原文怎么办？* 在权限更严格的系统中保留原文（有审批和审计），或者在测试环境中复现问题。

**减分回答**：把完整的对话原文上报到第三方的云服务，不做任何处理。

# 通用第 01 期 · LLM 基础

> **本期结论**：做 Agent 应用开发不要求会训练模型，但必须清楚模型的输入输出边界：token、上下文窗口、采样参数、
> 结构化输出和缓存。很多线上问题（输出被截断、结果不稳定、成本失控、JSON 解析失败）的根因都在这一层。
>
> 题量 14。

### Q1 什么是 token？为什么应用开发者必须关心它？

**考察点**：token 与计费、上下文长度、延迟之间的关系。

**参考回答**

- **定义**：token 是模型处理文本的最小单位，由分词器（常见的是 BPE 类算法）把文本切成子词片段。
  一个英文单词可能对应 1 个或多个 token；中文通常是 1 个汉字对应 1～2 个 token，不同模型的分词器差异很大。
- **开发者需要关心的原因**：
  1. **计费**：按输入和输出的 token 数分别计费，输出单价通常更高。
  2. **容量**：上下文窗口按 token 计算，系统提示词、工具定义、历史消息、检索内容和输出都要算在里面。
  3. **延迟**：生成是逐个 token 进行的，输出越长，总耗时越长。
- **实践**：估算成本和裁剪上下文时，要用目标模型自己的分词器或接口返回的 `usage` 字段，不能按字数估计。

**追问**：*工具定义也占 token 吗？* 占。工具的名称、描述和参数 schema 每轮都会发给模型，
工具多的时候可能占掉上下文的很大一部分（项目实测见 [项目第 02 期 Q3](../02-Agent核心机制-ReAct工具调用与多Agent.md)）。

**减分回答**：“一个汉字就是一个 token”。

### Q2 简述 Transformer 的自注意力机制，以及它对应用开发有什么影响。

**考察点**：不要求推导公式，但要知道计算复杂度、KV Cache 和长上下文的代价。

**参考回答**

- **自注意力**：每个 token 通过 Query、Key、Value 三个向量，与序列中其他 token 计算相关性，再加权汇总信息。
  多头注意力让模型能同时关注不同类型的关系。
- **生成方式**：解码器是自回归的，一次生成一个 token，并把它接到输入后面继续生成。
- **对应用的影响**：
  1. **计算量随长度增长**：标准注意力的计算量与序列长度的平方相关，上下文越长，首 token 延迟和成本越高。
  2. **KV Cache**：生成时缓存之前 token 的 Key 和 Value，避免重复计算。它是“提示词缓存”和前缀复用的基础，
     也解释了为什么固定的前缀（系统提示词、工具定义）放在最前面更容易命中缓存。
  3. **位置效应**：模型对长上下文中间部分的信息利用得往往更差（常被称为 “Lost in the Middle”），
     关键信息应该放在开头或结尾。

**追问**：*为什么首 token 延迟和总耗时要分开看？* 首 token 延迟主要由输入长度（预填充阶段）决定，
总耗时主要由输出长度（解码阶段）决定，两者的优化手段不同。

**减分回答**：只会背 “Attention is all you need”，说不出它对成本和延迟的影响。

### Q3 temperature、top_p、top_k 分别控制什么？客服类 Agent 应该怎么设置？

**考察点**：采样参数的含义与按场景取值。

**参考回答**

- **temperature**：调整概率分布的“平滑程度”。越低越倾向选择最高概率的 token，输出越稳定；越高越发散。
- **top_p（核采样）**：只在累计概率达到 p 的最小候选集合中采样。
- **top_k**：只在概率最高的 k 个候选中采样。
- **一般不要同时大幅调整 temperature 和 top_p**，两者作用相似，同时调整会让效果难以预测。
- **场景取值**：
  - 客服、工具调用、信息抽取、结构化输出：低 temperature（例如 0～0.3），追求稳定和可复现；
  - 文案创作、头脑风暴：可以适当调高。
- **temperature=0 也不保证完全确定**：服务端的批处理和浮点计算差异可能导致同一输入得到不同输出，
  所以测试断言不能依赖逐字相同。

**追问**：*评测时应该怎么设置采样参数？* 固定参数并记录下来；对随机性较强的任务，每个用例跑多次，看通过率而不是单次结果。

**减分回答**：“temperature 越高模型越聪明”。

### Q4 大模型为什么会产生幻觉？应用层有哪些缓解手段？

**考察点**：幻觉的成因；在应用层能做什么，而不是寄希望于换模型。

**参考回答**

- **成因**：模型的本质是按概率续写文本，并不“知道”自己不知道；训练数据有时效性，也可能有错误；
  提示词要求模型必须给出答案时，它更容易编造。
- **应用层的缓解手段**：
  1. **提供依据**：用 RAG 或工具查询真实数据，并要求模型只依据给定资料回答，资料里没有就明确说不知道。
  2. **限制能力边界**：工具描述写清楚“能做什么、不能做什么”，例如“只登记申请，不执行打款”。
  3. **注入运行期事实**：比如当前日期，避免模型用训练数据里的时间做判断。
  4. **输出校验**：对关键结论做规则或模型二次校验，例如检测“已退款”这类没有依据的承诺。
  5. **展示引用**：让用户看到答案出处，也便于运营追查。
  6. **兜底路径**：拿不准时转人工。
- **项目对照**：越权承诺检测见 [项目第 05 期 Q4](../05-安全护栏与治理中间件.md)。

**追问**：*RAG 能彻底解决幻觉吗？* 不能。检索到的内容可能不相关或者过期，模型也可能不按资料回答，
所以还需要评测“回答是否忠于资料”（faithfulness）。

**减分回答**：“换更大的模型就没有幻觉了”。

### Q5 上下文窗口、最大输出长度、提示词长度三者是什么关系？输出被截断怎么排查？

**考察点**：容量规划；识别截断。

**参考回答**

- **关系**：输入 token 数 + 输出 token 数不能超过上下文窗口；最大输出长度（`max_tokens` 之类的参数）是单独的上限。
- **截断的表现**：回答说到一半停止，或者 JSON 缺少结尾。接口返回的结束原因（finish reason / stop reason）
  会标明是正常结束还是因为长度上限而停止。
- **排查思路**：
  1. 先看结束原因，确认是否是长度截断；
  2. 检查 `max_tokens` 设得是否太小；
  3. 检查输入是否过长，挤占了输出空间；
  4. 对结构化输出，截断会导致解析失败，需要对这种情况单独处理，而不是笼统地当作“模型不按格式输出”。
- **实践**：记录每次调用的结束原因和 token 用量，作为可观测数据。

**追问**：*为什么不直接把 `max_tokens` 设成最大？* 输出越长延迟和成本越高；而且有些厂商会按 `max_tokens` 预留配额，
设得过大可能影响并发额度。

**减分回答**：看到回答不完整就归结为“模型不稳定”。

### Q6 如何让模型稳定地输出 JSON？几种方式各有什么优缺点？

**考察点**：结构化输出的可靠性。

**参考回答**

| 方式 | 做法 | 可靠性 | 注意点 |
|---|---|---|---|
| 提示词约束 | 在提示词里要求输出 JSON 并给示例 | 最低 | 需要自己解析和容错 |
| JSON 模式 | 接口参数要求输出合法 JSON | 中 | 只保证是合法 JSON，不保证字段符合 schema |
| Schema 约束 | 提供 JSON Schema，服务端约束解码 | 高 | 依赖厂商支持，schema 能力有限制 |
| 借用工具调用 | 把输出定义成一个工具的参数 | 较高 | 模型可能不调用这个工具 |

- **无论哪种方式都要做校验和兜底**：解析失败、字段缺失、值超出枚举范围时，要么重试（带上错误信息），
  要么返回一个安全的默认结果，不能让异常直接传到用户那里。
- **项目对照**：项目的意图分类借用工具调用实现结构化输出，模型不调用时返回 `other` 兜底，
  见 [项目第 02 期 Q8](../02-Agent核心机制-ReAct工具调用与多Agent.md)。

**追问**：*字段较多时怎么提高成功率？* 减少嵌套层级；用枚举限制取值；给每个字段写清描述；
把复杂任务拆成多个步骤，每步输出少量字段。

**减分回答**：“用正则从回答里抠出 JSON 就行”。

### Q7 提示词缓存（Prompt Caching）的原理是什么？怎样设计提示词才能提高命中率？

**考察点**：理解基于前缀的缓存；据此组织提示词结构。

**参考回答**

- **原理**：服务端把已经计算过的前缀（KV Cache）缓存起来，后续请求的前缀完全相同时直接复用，
  降低首 token 延迟，缓存命中部分的计费通常也显著更便宜。具体的规则（最小长度、有效期、是否需要显式标记）因厂商而异。
- **提高命中率的做法**：
  1. **不变的内容放前面**：系统提示词、工具定义、固定的示例放在最前面，每轮变化的内容放在最后。
  2. **前缀保持逐字不变**：不要在系统提示词开头插入时间戳、请求 ID 这类每次都变的内容。
     需要注入当前日期时，放在靠后的位置，或者控制粒度（例如只精确到天）。
  3. **工具列表顺序固定**：每轮动态增减工具，会导致前缀变化。
- **和语义缓存的区别**：提示词缓存复用的是计算过程，结果仍然由模型实时生成；语义缓存直接复用上一次的答案，
  风险更大（见 [项目第 08 期 Q3](../08-模型路由成本评测与系统设计.md)）。

**追问**：*按轮收窄工具面和提示词缓存有冲突吗？* 有。收窄工具面能减少 token，但会让前缀变化、降低缓存命中率，
需要用数据衡量两者的得失。

**减分回答**：把提示词缓存和语义缓存混为一谈。

### Q8 System、User、Assistant、Tool 几种消息角色各有什么作用？多轮对话的消息怎么组织？

**考察点**：消息协议的基础；工具消息的配对规则。

**参考回答**

- **System**：设定角色、规则和约束，优先级通常最高。
- **User**：用户输入。
- **Assistant**：模型的回复，可以包含文本，也可以包含工具调用请求。
- **Tool**：工具执行结果，必须通过调用 ID 与发起调用的那条 Assistant 消息对应。
- **组织规则**：
  1. 消息按时间顺序排列；
  2. **工具调用和工具结果必须成对出现**，只有结果没有调用，多数厂商会直接报错；
  3. 不同厂商对消息顺序有不同限制（例如是否允许连续两条同角色消息），适配多厂商时要做格式转换。
- **项目对照**：裁剪上下文时保证调用与结果成对，见 [项目第 04 期 Q3](../04-上下文工程与记忆.md)。

**追问**：*用户能否通过输入冒充 System 消息？* 如果把用户输入直接拼进系统提示词，就存在这个风险。
用户内容应该始终放在 User 消息里，并对外部内容做隔离标记。

**减分回答**：把所有内容都拼成一个大字符串发给模型。

### Q9 大模型的推理（reasoning / thinking）模型和普通模型在使用上有什么区别？

**考察点**：推理模型的成本、延迟和使用限制。

**参考回答**

- **区别**：推理模型在输出最终答案之前，会先生成一段思考过程。复杂推理、规划、代码类任务效果更好，
  但延迟更高，思考过程产生的 token 通常也要计费。
- **使用上的注意点**：
  1. **成本和配额**：思考 token 会计入用量，配额和账单要算上这部分；
  2. **延迟**：用户侧最好展示“正在思考”的状态，或者只把推理模型用在后台任务上；
  3. **输出处理**：思考内容一般不直接展示给终端用户，流式处理时要区分思考增量和正文增量；
  4. **参数限制**：部分推理模型不支持或忽略采样参数。
- **选型**：简单的问答和分类用普通模型；复杂规划、多步推理再用推理模型。可以结合模型路由按任务选择。

**追问**：*流式输出时如何避免把思考过程发给用户？* 按事件类型过滤，只下发正文增量；
项目中流式出口只处理正文增量事件，思考增量不下发（见 `CustomerServiceService.streamFromAgent`）。

**减分回答**：“推理模型更强，所以全部换成推理模型”。

### Q10 什么是 Embedding？余弦相似度、点积、欧氏距离怎么选？

**考察点**：向量表示与相似度度量的基础。

**参考回答**

- **Embedding**：把文本映射成一个固定维度的向量，语义相近的文本在向量空间里距离更近。
- **度量方式**：
  - **余弦相似度**：只看方向，不看长度，最常用；
  - **点积**：同时受方向和长度影响；向量已经归一化时，点积与余弦相似度的排序结果一致；
  - **欧氏距离**：看绝对距离；向量归一化后，它与余弦相似度也是单调对应的。
- **选择原则**：使用 Embedding 模型文档推荐的度量方式；向量库建索引时选择的度量要与之一致。
- **注意**：不同 Embedding 模型的向量**不能混用**，维度不同时根本无法比较；即使维度相同，不同模型之间的分数也没有意义。
  更换 Embedding 模型需要重建索引。

**追问**：*相似度阈值该怎么定？* 不同模型的分数分布不同，阈值不能照搬经验值，要用标注数据来定，
并观察未命中请求的最高分分布。

**减分回答**：“相似度 0.8 以上就算相关”，且说不出这个数从哪来。

### Q11 微调（Fine-tuning）、RAG 和提示词工程分别适合解决什么问题？

**考察点**：技术选型能力。

**参考回答**

- **提示词工程**：成本最低、迭代最快。适合调整输出风格、格式和规则，应该最先尝试。
- **RAG**：适合需要**最新、私有、可追溯**知识的场景，比如企业知识库、政策问答。知识更新只需要更新文档，
  而且能给出引用来源。
- **微调**：适合需要改变模型**行为模式**的场景，比如固定的输出格式、领域术语风格、特定分类任务，
  或者想用小模型替代大模型来降低成本。它不适合用来“灌知识”：知识更新要重新训练，也无法给出引用。
- **组合使用**：常见做法是提示词工程 + RAG 先做到可用；等积累了足够多的高质量数据，再考虑用微调降低成本或稳定格式。

**追问**：*微调前需要准备什么？* 高质量标注数据、评测集和对照基线；没有评测集，就无法判断微调是否有效。

**减分回答**：“知识问答效果不好就微调”。

### Q12 调用大模型 API 时，常见的错误类型有哪些？分别怎么处理？

**考察点**：错误分类与重试策略。

**参考回答**

| 错误 | 典型原因 | 处理方式 |
|---|---|---|
| 429 限流 | 超过每分钟请求数或 token 数 | 按 `Retry-After` 或指数退避加抖动后重试；本地做好限流和排队 |
| 5xx / 超时 | 服务端故障或过载 | 有限次数重试；连续失败时熔断并切换备用模型 |
| 400 参数错误 | 消息格式错误、超过上下文长度、schema 不合法 | 不要重试，修正请求；超长时先裁剪上下文 |
| 401 / 403 | 密钥错误或无权限 | 不要重试，告警 |
| 内容审核拦截 | 触发厂商的安全策略 | 返回安全话术，记录审计 |

- **流式调用的额外问题**：连接可能中途断开，已经发出的内容无法撤回。
  重试时要考虑是否会让用户看到重复内容（见 [项目第 08 期 Q1](../08-模型路由成本评测与系统设计.md)）。

**追问**：*为什么退避要加随机抖动？* 避免大量客户端在同一时刻集中重试，引发“重试风暴”。

**减分回答**：所有错误都统一重试 3 次。

### Q13 多模态模型（视觉、语音）接入应用时要注意什么？

**考察点**：多模态的成本、安全与链路。

**参考回答**

- **成本**：图片按分辨率折算成 token，高清大图的成本很高，上传前应压缩或裁剪到合适尺寸；
  语音按时长计费。
- **链路**：可以直接把图片交给多模态模型理解，也可以先 OCR 或语音转文字，再交给文本模型。
  后者更便宜、更容易调试，但会丢失版面和图像信息。
- **安全**：图片和文档里的文字同样可能包含恶意指令（间接注入），要当作不可信内容隔离处理。
- **计量**：绕开主链路的多模态调用也要计入用量和配额，否则成本不可见
  （项目对照：`VisionOcrUsageRecorder`，见 [项目第 08 期 Q5](../08-模型路由成本评测与系统设计.md)）。
- **隐私**：图片中可能含有身份证、手机号等个人信息，需要脱敏或获得授权。

**追问**：*用户上传的截图里写着“忽略以上指令”，会发生什么？* 如果 OCR 结果被当作用户本人的输入直接拼进上下文，
这就是一次提示词注入，所以要按附件格式识别并包进隔离块。

**减分回答**：只关心能否识别图片，不考虑成本、安全和计量。

### Q14 如何选择模型？需要考虑哪些维度？

**考察点**：选型方法论。

**参考回答**

- **效果**：在自己的业务评测集上比较，而不是只看公开榜单。
- **能力支持**：是否支持工具调用、结构化输出、流式输出、多模态，上下文窗口多大。
- **延迟**：首 token 延迟和每秒输出 token 数。
- **成本**：输入和输出单价、是否支持提示词缓存。
- **稳定性与合规**：服务可用性、限流额度、数据是否出境、是否支持私有化部署。
- **可替换性**：代码里通过统一的模型抽象接入，保留切换和主备的能力，避免被单一厂商绑定。
- **实践**：按任务分级选型，比如意图分类用小模型，复杂问题用大模型，并配置备用模型。

**追问**：*国产模型通过 OpenAI 兼容接口接入时，有什么坑？* 兼容程度参差不齐：消息格式、工具调用、
上下文窗口等元数据可能与官方接口不一致。项目中就遇到过按兼容协议接入后，框架查不到模型的上下文窗口、返回 0 的问题，
需要按真实厂商补充推断。

**减分回答**：“用最贵的模型最稳妥”。

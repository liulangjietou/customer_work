# 通用第 02 期 · Agent 范式与工具调用

> **本期结论**：Agent 的本质是“模型决定下一步做什么”。面试官通过这组题判断候选人能不能讲清三件事：
> 什么时候应该用 Agent、什么时候用固定工作流更好；工具调用的完整流程和失败处理；多 Agent 的代价。
>
> 题量 15。

---

### Q1 什么是 AI Agent？它和普通的大模型调用、固定工作流有什么区别？

**考察点**：概念边界。

**参考回答**

- **普通调用**：一次输入、一次输出，没有自主决策。
- **工作流（Workflow）**：步骤和分支由代码预先定义，模型只负责其中某些节点。流程可预测、容易测试。
- **Agent**：模型根据目标和当前观察，自主决定下一步调用什么工具、何时结束，形成“思考 → 行动 → 观察”的循环。
  灵活，但结果更难预测，成本和延迟也更高。
- **常见的组成部分**：模型、工具、记忆、规划，以及一层负责上下文管理、执行环境和治理的工程外壳（Harness）。
- **选择原则**：能用固定流程解决的，优先用工作流；路径不确定、需要根据中间结果决定下一步时，才用 Agent。

**追问**：*能否把二者结合？* 可以，而且很常见：外层用工作流保证关键步骤（例如审批）必须发生，
内层用 Agent 处理开放式的对话和查询。

**减分回答**：“调用了工具就是 Agent”。

### Q2 ReAct 是什么？和 CoT 有什么区别？

**考察点**：经典推理范式。

**参考回答**

- **CoT（思维链）**：让模型先写出推理步骤再给答案，提升多步推理的准确率，但整个过程只依赖模型内部知识。
- **ReAct**：把推理（Reason）和行动（Act）交替进行：模型思考后调用工具，拿到观察结果再继续思考。
  它把外部信息引入推理过程，能减少凭空编造。
- **ReAct 的问题**：步骤多时容易绕圈、重复调用；每一步都是一次模型调用，延迟和成本随步数增长；
  需要设置最大迭代次数，并处理次数用完的情况。

**追问**：*最大迭代次数用完了该怎么办？* 不能只让模型写一句道歉就结束，要给出明确的后续路径，比如转人工，
并记录指标（项目对照：`LoopGuardMiddleware`，见 [项目第 02 期 Q1](../02-Agent核心机制-ReAct工具调用与多Agent.md)）。

**减分回答**：把 ReAct 和 CoT 当成同一件事。

### Q3 除了 ReAct，还有哪些常见的 Agent 规划范式？

**考察点**：知识广度与适用场景。

**参考回答**

- **Plan-and-Execute**：先生成完整计划，再逐步执行，必要时重新规划。适合步骤较多、目标明确的任务，
  可以减少每一步的模型调用开销。
- **Reflexion（反思）**：执行后让模型评估结果，把教训写进记忆再重试。适合有明确对错反馈的任务，比如写代码跑测试。
- **Tree of Thoughts**：同时探索多条推理路径并评估择优，效果好但成本很高。
- **任务清单（Todo）**：让模型把多步任务写成待办清单，逐项更新状态，防止长任务中途遗漏。
- **选择原则**：按任务复杂度和预算选择。客服这类场景通常 ReAct 加任务清单就够用了。

**追问**：*计划写好后，外部条件变化了怎么办？* 需要支持重新规划：执行过程中发现前提不成立时，回到规划步骤，而不是硬按原计划执行。

**减分回答**：只知道 ReAct。

### Q4 描述 Function Calling 的完整流程。

**考察点**：工具调用的消息流转。

**参考回答**

1. 应用把工具的名称、描述和参数 JSON Schema 随请求一起发给模型。
2. 模型判断需要调用工具时，返回一条包含工具名和参数 JSON 的消息（带调用 ID），而不是直接回答。
3. **应用自己执行工具**（模型不会真正执行任何代码），得到结果。
4. 应用把结果作为工具消息发回给模型，并带上对应的调用 ID。
5. 模型根据结果继续推理：要么再次调用工具，要么给出最终回答。

- **要点**：一轮可能返回多个工具调用；参数是模型生成的，**必须校验**；工具执行的权限由应用控制，而不是由模型决定。

**追问**：*模型生成的参数格式不对怎么办？* 返回一条模型能看懂的错误信息，让它修正后重新调用；
同时限制重试次数，避免无限循环。

**减分回答**：“模型会自己去调用接口”。

### Q5 如何设计一个好的工具（Tool）？

**考察点**：工具设计的最佳实践。

**参考回答**

- **职责单一、粒度合适**：一个工具做一件事，名称直接表达用途，比如 `queryOrderStatus`。
  粒度太细，模型要调用很多次；太粗，参数复杂，容易出错。
- **描述写清三件事**：能做什么、不能做什么、调用前需要满足什么条件。例如“只登记退款申请，不执行支付”。
- **参数简单明确**：尽量用枚举和明确的格式约束，每个参数都写说明；避免深层嵌套。
- **返回结果面向模型**：返回精简、结构清楚的文本；出错时返回可读的原因，并告诉模型下一步该怎么做。
- **区分只读和写操作**：写操作要考虑幂等、审批和权限。
- **控制数量**：工具定义每轮都会占用上下文，工具越多，模型选错的概率也越大。

**追问**：*工具返回了几万字的结果怎么办？* 在工具内部先截断或摘要；或者把完整结果存到外部，只返回摘要和引用，
需要时再让模型去读取。

**减分回答**：把后端接口原样暴露成工具，参数和返回值都不做整理。

### Q6 工具很多（几十上百个）时，怎么避免模型选错、上下文被撑满？

**考察点**：工具面管理。

**参考回答**

- **分组与静态裁剪**：按业务域分组，部署时关掉用不上的组，零误判风险。
- **按意图动态筛选**：先识别意图，只暴露相关工具。风险是意图判错就拿不到需要的工具，
  所以需要置信度门槛，判不准时保留完整工具面。
- **工具检索（meta-tool）**：让模型先搜索工具再使用，适合工具极多的场景，代价是多一次往返、首字延迟增加。
- **分层 Agent**：由上层 Agent 选择领域，再交给只持有该领域工具的子 Agent。
- **项目对照**：项目实测工具定义约占上下文预算的一半，并比较了三种收敛方式的代价，
  见 [项目第 02 期 Q3](../02-Agent核心机制-ReAct工具调用与多Agent.md)。

**追问**：*有没有不能被关掉的工具？* 有，比如转人工。关掉它，用户就可能被困在智能体里出不来。

**减分回答**：“把所有工具都给模型，让它自己选”。

### Q7 工具调用应该并行还是串行执行？

**考察点**：并发与业务语义的取舍。

**参考回答**

- **并行的好处**：多个互不相关的查询同时执行，降低总延迟。
- **并行的风险**：
  1. 写操作与审批交错：审批拦住了一个操作，另一个已经执行，无法回滚；
  2. 线程切换后上下文（租户、用户身份）可能丢失；
  3. 调用顺序不确定，日志和计量更难对齐。
- **实践**：只读工具可以并行；写操作串行执行并把审批放在前面。
  框架升级可能改变默认执行模式，要显式配置，不要依赖默认值
  （项目对照：[项目第 02 期 Q4](../02-Agent核心机制-ReAct工具调用与多Agent.md)）。

**追问**：*“模型一轮返回多个工具调用”就等于并行执行吗？* 不等于。一轮返回多个调用是模型的行为；
是否并行执行由应用或框架决定。

**减分回答**：“并行更快，所以都应该并行”。

### Q8 工具调用失败时的重试策略怎么设计？

**考察点**：幂等性与分层容错。

**参考回答**

- **先区分错误类型**：参数错误不要重试，把错误信息返回给模型修正；临时性故障（超时、5xx）可以有限重试。
- **只对幂等操作自动重试**：查询可以重试；创建订单、发起退款这类写操作，超时时请求可能已经到达下游，
  盲目重试会重复执行。写操作要依靠幂等键，由下游去重。
- **设置合理的超时**：框架默认超时可能很长，客服场景需要秒级超时，否则用户会长时间等待。
- **退避**：指数退避加随机抖动。
- **兜底**：多次失败后返回友好提示或转人工，并记录指标和告警。

**追问**：*超时后怎么确认写操作是否成功？* 按幂等键查询下游结果或回执，而不是再执行一次。

**减分回答**：“失败了就重试三次”。

### Q9 什么是 Human-in-the-Loop（HITL）？哪些操作需要人工确认？

**考察点**：人机协作与风险控制。

**参考回答**

- **定义**：在 Agent 执行关键步骤前后引入人工确认、审批或接管。
- **需要人工确认的操作**：涉及资金（退款、支付）、不可逆操作（删除数据）、对外发送信息、高风险或大额业务，
  以及模型置信度低的情况。
- **实现方式**：
  1. 工具本身只“登记申请”，由人审批后再真正执行；
  2. 框架层的权限规则（允许 / 拒绝 / 询问）；
  3. 转人工坐席接管对话。
- **工程要点**：审批决策要幂等；决策状态和执行状态分开记录；审批超时要有处理策略；
  整个过程要留审计记录（项目对照：[项目第 05 期 Q5](../05-安全护栏与治理中间件.md)）。

**追问**：*人工审批通过后执行失败了怎么办？* 不回滚审批决策，记录执行失败状态，由巡检重试或告警。

**减分回答**：“在提示词里告诉模型大额退款要谨慎”。

### Q10 多 Agent 系统有哪些常见的协作模式？

**考察点**：多智能体架构的知识广度。

**参考回答**

- **路由（Router）**：先判断意图，再分派给对应的专家 Agent。
- **主管（Supervisor / Orchestrator-Workers）**：主 Agent 拆解任务、分派给子 Agent，再汇总结果。
- **并行会诊 + 归纳**：多个专家同时处理同一个问题，再由归纳 Agent 去重、消解冲突。
- **流水线（Sequential）**：前一个 Agent 的输出作为下一个的输入，逐步细化。
- **交接（Handoff）**：当前 Agent 把对话控制权交给另一个更合适的 Agent。
- **辩论 / 评审**：一个生成、一个评审，反复改进。
- **项目对照**：`MultiAgentOrchestrator` 实现了路由、并行会诊、归纳和串行模式，
  见 [项目第 02 期 Q7](../02-Agent核心机制-ReAct工具调用与多Agent.md)。

**追问**：*子 Agent 之间怎么共享信息？* 通过主 Agent 传递、共享的外部状态（数据库、文件）或消息总线；
尽量只传必要信息，避免把完整上下文复制给每个子 Agent。

**减分回答**：只会说“多个 Agent 互相聊天”。

### Q11 什么时候应该用多 Agent？什么时候不应该？

**考察点**：判断成本与收益。

**参考回答**

- **适合的场景**：
  1. 任务可以拆成相互独立的子任务，能并行处理；
  2. 不同子任务需要不同的工具、提示词或权限，隔离后更清晰；
  3. 单个 Agent 的上下文装不下全部信息，需要用子 Agent 分担。
- **不适合的场景**：实时对话、对延迟敏感、任务本身不复杂。多 Agent 的模型调用次数和成本成倍增加，
  出错的环节也更多，调试更困难。
- **原则**：先用单 Agent 做到可用；只有在出现明确瓶颈时才拆分，并用评测数据证明拆分确实有收益。

**追问**：*项目为什么让 H5 的每条消息都走单 Agent？* 多 Agent 一次会诊至少需要“路由 + 多个专家 + 归纳”，
延迟和成本都成倍增加，所以多 Agent 只作为独立入口提供。

**减分回答**：“多 Agent 更高级，所以都用多 Agent”。

### Q12 如何防止 Agent 陷入死循环或无效重复？

**考察点**：Agent 运行的边界控制。

**参考回答**

- **硬性上限**：最大迭代次数、最大工具调用次数、单轮总超时、token 预算。
- **重复检测**：同一个工具使用完全相同的参数连续调用多次，通常说明模型没能从结果中学到东西，应告警或干预。
  注意要把参数计入判断，同一个工具用不同参数查多个订单是正常行为。
- **干预方式**：注入提示，告诉模型换一种方法；或者直接结束并转人工。
- **可观测**：统计迭代次数耗尽和重复调用的次数，否则这些问题完全不可见。

**追问**：*为什么检测到重复调用后不直接拦截？* 直接拦截需要让模型知道“别再这样调用”，
而修改事件流并不会改变模型下一轮看到的内容；只能通过注入提示来引导，但效果取决于模型是否采纳。

**减分回答**：只设置最大迭代次数，用完后什么也不做。

### Q13 Agent 的状态应该放在哪里？为什么推荐“Agent 无状态、状态外置”？

**考察点**：可扩展架构。

**参考回答**

- **状态包括**：对话历史、工具调用记录、任务进度、中间变量。
- **状态外置**：Agent 实例本身不保存状态，每次调用按“用户 + 会话”从外部存储加载，结束后写回。
- **好处**：
  1. 多实例部署时，请求落到任何实例都能继续对话；
  2. 实例重启或扩缩容不会丢失对话；
  3. 可以缓存 Agent 实例来节省构建开销，但缓存只是加速，不是状态来源。
- **需要注意**：同一会话的并发请求会同时读写状态，需要会话锁或乐观并发（版本号）来防止相互覆盖。

**追问**：*状态的键为什么必须包含用户身份？* 如果只用客户端传来的会话 ID，攻击者可以猜测或伪造会话 ID，读到别人的对话。

**减分回答**：“把对话历史存在 Agent 对象的成员变量里”。

### Q14 Agent Skills 是什么？和工具、MCP 有什么区别？

**考察点**：新概念的理解。

**参考回答**

- **Skills**：把完成某类任务所需的说明文档、脚本和资源打包在一起，模型需要时按需加载，
  不需要时只占用很少的上下文（通常只有名称和简介）。
- **与工具的区别**：工具是一个可调用的函数；Skill 是一套“怎么做”的知识和配套资源，可以包含多个步骤和脚本。
- **与 MCP 的区别**：MCP 是连接外部系统的协议，解决“怎么接入”；Skill 解决“怎么完成某类任务”。二者可以组合使用。
- **风险**：Skill 中可能包含可执行代码，需要沙箱隔离和权限控制，对外部署时要谨慎开放。

**追问**：*Skill 的内容由谁维护、怎么版本化？* 应该和代码一样进行版本管理和审核；项目中技能以 MySQL 为权威存储，
磁盘目录只是启动时重建的缓存。

**减分回答**：把 Skill 当成工具的另一种叫法。

### Q15 设计一个 Agent 时，你会按什么步骤推进？

**考察点**：工程方法论。

**参考回答**

1. **明确目标和边界**：Agent 负责哪些事、不负责哪些事、什么情况下必须交给人。
2. **先做评测集**：收集真实问题和期望结果，作为后续每次改动的衡量标准。
3. **从简单方案开始**：先用单 Agent 加少量核心工具，做到可用。
4. **设计工具和权限**：只读与写操作分开，高风险操作加审批。
5. **加上治理能力**：安全护栏、可观测、成本控制、降级兜底。
6. **灰度上线并收集反馈**：badcase、用户满意度、知识盲区。
7. **根据数据迭代**：每次改动都跑评测，确认没有引入回归。

**追问**：*没有评测集能上线吗？* 能上线，但无法判断后续的改动是变好还是变坏，也就无法持续优化。

**减分回答**：一上来就设计复杂的多 Agent 架构，却说不清要解决的具体问题。

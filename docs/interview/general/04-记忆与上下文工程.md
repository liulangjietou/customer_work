# 通用第 04 期 · 记忆与上下文工程

> **本期结论**：上下文是 Agent 最稀缺的资源。记忆和上下文工程要回答的都是同一个问题：
> 在有限的窗口里，给模型放最有用的信息。能讲清“放什么、放哪里、什么时候丢、丢了怎么找回”的候选人，
> 基本具备了做长会话 Agent 的能力。
>
> 题量 13。

---

### Q1 什么是上下文工程？它和提示词工程有什么区别？

**考察点**：概念理解。

**参考回答**

- **提示词工程**：关注如何写好一段指令。
- **上下文工程**：关注每次模型调用时，**动态组装哪些信息**，包括系统指令、工具定义、对话历史、记忆、检索结果、
  任务状态，以及这些信息的数量、顺序、格式和淘汰策略。
- **为什么重要**：Agent 需要多轮调用模型，上下文会不断变长。信息太少，模型做不对；信息太多，成本上升、
  注意力被稀释，甚至超出窗口。
- **常用手段**：写入外部（把信息存到文件或数据库）、选择（按需检索）、压缩（摘要、裁剪）、隔离（交给子 Agent）。

**追问**：*上下文越长越好吗？* 不是。无关信息会干扰模型，长上下文中间位置的信息也更容易被忽略。

**减分回答**：“上下文工程就是写更长的提示词”。

### Q2 Agent 的记忆通常分为哪几类？

**考察点**：记忆分层。

**参考回答**

- **短期记忆**：当前会话的对话历史，放在上下文里。
- **长期记忆**：跨会话保存的信息，按需检索后放入上下文。常见的三类：
  - **事实性记忆**：用户偏好、个人信息，例如“对花生过敏”；
  - **经历性记忆**：过去发生过的事件和对话摘要；
  - **程序性记忆**：做事的方法和规则，例如成功的操作流程。
- **工作记忆**：当前任务的中间状态，例如待办清单、已收集的表单字段。
- **设计要点**：不同类型的记忆存储方式、写入时机和过期策略都不同，不要把它们混在一起。

**追问**：*工作记忆为什么不能只依赖对话历史？* 对话历史可能被裁剪或压缩，裁掉之后模型就忘了任务进度。
关键进度应该写到结构化存储里（项目对照：槽位填充进度保存在数据库，见 [项目第 02 期 Q6](../02-Agent核心机制-ReAct工具调用与多Agent.md)）。

**减分回答**：“记忆就是保存聊天记录”。

### Q3 短期记忆（对话历史）超出上下文窗口时，有哪些处理办法？

**考察点**：常见策略与取舍。

**参考回答**

| 方法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 滑动窗口 | 只保留最近 N 条或 N 个 token | 简单、零成本 | 早期的关键背景会丢失 |
| 保留两头 | 保留最早几条和最近几条，丢掉中间 | 保住了开头的背景 | 中间信息丢失 |
| 摘要压缩 | 用模型把旧历史总结成摘要 | 保留要点 | 要额外调用模型，可能丢细节 |
| 外部检索 | 历史存到外部，按需检索回来 | 信息不丢 | 实现复杂，依赖检索质量 |

- **注意**：裁剪时工具调用和工具结果必须成对保留或成对丢弃，否则会触发接口报错。
- **项目对照**：项目主链路用“保留两头”的确定性裁剪兜底，长会话链路用模型压缩，
  见 [项目第 04 期 Q2、Q3](../04-上下文工程与记忆.md)。

**追问**：*什么时候触发压缩？* 常见做法是按 token 数或消息数设阈值，接近上限时触发，并保留最近若干条原文。

**减分回答**：“超出了就把最早的消息删掉”，不考虑工具消息的配对问题。

### Q4 长期记忆怎么写入？什么信息值得记住？

**考察点**：记忆写入的策略。

**参考回答**

- **写入方式**：
  1. 模型在对话中调用“记住”工具主动写入；
  2. 会话结束后，后台异步提取值得记住的信息；
  3. 用户明确要求记住。
- **值得记住的信息**：长期稳定的偏好、关键个人信息、重要的历史结论。临时性的信息（例如“今天有点忙”）不要记。
- **处理冲突**：新信息与旧信息矛盾时（例如更换了收货地址），要更新或标记旧信息失效，而不是两条都保留。
- **合规**：需要用户授权；支持查看、导出、删除；设置保留期限。

**追问**：*记忆写错了怎么办？* 提供修正和删除的入口；重要记忆可以附上来源和时间，便于判断是否仍然有效。

**减分回答**：把每轮对话都原样存进长期记忆。

### Q5 长期记忆怎么检索？有哪些打分方法？

**考察点**：记忆召回的质量。

**参考回答**

- **检索方式**：关键词匹配、向量相似度，或者两者结合。
- **打分因素**：相关性、时间新近程度、重要程度，常按加权组合计算。
- **中文关键词匹配的坑**：按单个字统计时，“的、是、我”这类虚词几乎出现在所有记录中，会让无关记录得到高分。
  改为按相邻两个字（bigram）匹配、过滤掉虚词组合，并按查询长度归一化，效果会明显改善。
- **召回控制**：设定最低分数，没有相关记忆时返回空结果，不要硬凑几条无关记忆塞进上下文。
- **项目对照**：见 [项目第 04 期 Q6](../04-上下文工程与记忆.md)。

**追问**：*同义表达（“忌口”和“过敏”）怎么召回？* 关键词匹配无法处理，需要向量召回；
但向量召回需要为每条记忆生成向量，要评估成本和收益。

**减分回答**：“把所有记忆都放进上下文”。

### Q6 记忆怎么做隔离？

**考察点**：多用户、多租户场景的数据安全。

**参考回答**

- **隔离维度**：至少包含租户和用户；同一个用户的不同 Agent 是否共享记忆，要按业务需求明确。
- **身份来源必须可信**：记忆的归属应该来自服务端验证过的身份（JWT、API Key），不能来自客户端传入的会话 ID。
- **缓存也要隔离**：如果缓存了绑定记忆的 Agent 实例，缓存的键必须包含同样的隔离维度，
  否则不同用户会复用同一个实例的记忆。
- **存储层兜底**：在数据库层做租户过滤，缺少身份时直接拒绝执行。

**追问**：*匿名用户的记忆怎么处理？* 一般不写长期记忆，或者只在会话范围内保存；用户登录后再按需关联。

**减分回答**：只按会话 ID 保存记忆。

### Q7 上下文里各部分内容应该怎么排序？

**考察点**：上下文组装的细节。

**参考回答**

- **不变的内容放在前面**：系统指令、工具定义、固定示例。这样有利于提示词缓存命中。
- **随每轮变化的内容放在后面**：检索结果、记忆、当前任务状态。
- **最重要的信息靠近问题**：模型对开头和结尾的内容关注度更高，关键的约束和资料可以放在靠近用户问题的位置。
- **层次清楚**：用标题或标签区分不同类型的内容，并说明哪些是指令、哪些只是参考数据。
- **在最后统一计算预算**：先完成所有注入，最后再做裁剪，否则裁剪完又被追加内容，预算就不准了
  （项目对照：[项目第 04 期 Q1](../04-上下文工程与记忆.md)）。

**追问**：*为什么预算裁剪要放在最后一步？* 如果先裁剪、后注入，注入的内容会再次撑大上下文，预算形同虚设。

**减分回答**：随意拼接，不考虑顺序。

### Q8 什么是“临时注入”？为什么检索内容不应该写进对话历史？

**考察点**：理解“本次调用的输入”和“持久化历史”的区别。

**参考回答**

- **临时注入**：只把检索结果、提醒等信息加进本次模型调用的输入，不写入保存下来的对话历史。
- **原因**：
  1. 写进历史的话，每轮都会重复发送之前的检索结果，token 线性增长；
  2. 旧的检索结果可能已经过期，却一直留在上下文里；
  3. 用户查看历史记录时会看到这些内部内容；
  4. 压缩历史时，这些内容也会被压进摘要。
- **代价**：每轮都要重新获取，可以在一轮内部缓存结果，避免同一轮的多次迭代重复检索。

**追问**：*哪些信息必须写进历史？* 用户和模型的真实对话、工具调用及其结果（它们是后续推理的依据）。

**减分回答**：把检索结果直接拼进用户消息，再保存下来。

### Q9 工具返回的结果太大，怎么处理？

**考察点**：控制上下文占用。

**参考回答**

- **在工具内部精简**：只返回模型需要的字段，去掉冗余数据。
- **分页或截断**：返回前 N 条，并告诉模型还有更多数据、如何继续获取。
- **外部存储加引用**：完整结果存到文件或缓存中，只把摘要和引用返回给模型，需要时再读取。
- **淘汰旧结果**：较早的大体积工具结果在后续轮次中替换为简短的占位说明。
- **注意安全**：工具结果可能含有恶意指令，需要隔离标记。

**追问**：*淘汰旧的工具结果会有什么风险？* 模型后面可能还需要这些内容，所以占位说明要告诉模型如何重新获取。

**减分回答**：直接把整个数据库查询结果返回给模型。

### Q10 什么是子 Agent 的上下文隔离？有什么好处？

**考察点**：用架构手段控制上下文。

**参考回答**

- **做法**：把一个需要大量探索的子任务交给子 Agent，子 Agent 有自己独立的上下文，
  完成后只把精简的结论返回给主 Agent。
- **好处**：主 Agent 的上下文不会被大量中间过程占满；子 Agent 可以专注于自己的任务，使用专门的工具和提示词。
- **代价**：总的模型调用次数增加；子 Agent 看不到主 Agent 的完整上下文，交接信息必须写清楚。

**追问**：*子 Agent 返回的结果怎么设计？* 返回结论、关键证据和不确定的地方，而不是完整的探索过程。

**减分回答**：把主 Agent 的全部上下文原样复制给每个子 Agent。

### Q11 会话状态有并发写入的问题吗？怎么处理？

**考察点**：并发控制。

**参考回答**

- **问题**：同一个会话同时收到两条消息（用户连续发送、客户端重发），两次处理都读取同一份旧状态，
  各自写回，后写入的会覆盖先写入的，导致一轮对话丢失。
- **办法**：
  1. **会话锁**：同一会话的请求串行执行。多实例部署时需要分布式锁，并注意锁的租约时长和释放方式。
  2. **乐观并发**：状态带版本号，写入时比较版本（CAS），冲突时重试或合并。
  3. **消息去重**：用客户端生成的消息 ID 做幂等，避免重发的消息被处理两次。
- **纵深防御**：锁可能因为故障降级或过期而失效，乐观并发作为最后一道防线，并记录冲突指标
  （项目对照：[项目第 04 期 Q7](../04-上下文工程与记忆.md)）。

**追问**：*乐观并发的冲突策略默认是覆盖时，有什么风险？* 冲突被静默吸收，不报错也不打日志，问题完全不可见，必须加指标。

**减分回答**：“用户不会同时发两条消息”。

### Q12 如何在多轮对话中保持任务目标不偏移？

**考察点**：长任务的稳定性。

**参考回答**

- **显式记录目标和计划**：用任务清单记录目标和每一步的完成状态，每轮都提供给模型。
- **阶段化提示词**：按对话所处阶段（识别意图、收集信息、办理、确认）动态调整指令，让模型聚焦当前步骤。
- **定期对齐**：在关键节点复述目标和进度，让用户确认。
- **结构化保存关键信息**：已确认的订单号、诉求等写入结构化状态，而不是只依赖对话历史。

**追问**：*阶段化提示词有什么坑？* 阶段推进的判断条件和提示词内容必须一致。项目中出现过第一个阶段的提示词禁止调用工具，
而阶段推进恰恰依赖工具调用，结果会话永远停在第一阶段。

**减分回答**：“把目标写在系统提示词里就行”。

### Q13 用户说“忘记我之前说的”，系统应该怎么处理？

**考察点**：隐私合规和记忆治理。

**参考回答**

- **区分范围**：是撤回当前会话中的某句话，还是删除长期记忆中的信息？必要时向用户确认。
- **长期记忆**：执行删除，并确认所有副本（缓存、向量索引、备份）都按策略处理；给用户一个明确的结果反馈。
- **合规要求**：提供查看、导出、删除的能力，记录用户授权状态；没有授权时不写入长期记忆。
- **审计**：记录删除操作的时间和范围，便于合规检查。

**追问**：*删除记忆后，模型为什么还可能提到那些信息？* 当前会话的上下文里可能还保留着这些内容，或者缓存还没失效；
需要同时清理当前上下文和缓存。

**减分回答**：只是让模型在回答里说“好的，我已经忘记了”，实际什么都没删。

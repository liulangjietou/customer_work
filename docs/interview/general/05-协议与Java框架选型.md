# 通用第 05 期 · 协议（MCP / A2A / AG-UI）与 Java 框架选型

> **本期结论**：MCP 已经是 JD 里的高频词。面试官不满足于“MCP 是工具协议”这种回答，而是要听到它的架构角色、
> 传输方式和安全风险。Java 方向还一定会问框架选型：Spring AI、Spring AI Alibaba、LangChain4j、AgentScope Java
> 各适合什么场景，以及 Java 在 Agent 开发中的优势和短板。
>
> 说明：框架迭代很快，本期只讲稳定的核心概念。具体 API 和版本以官方文档为准。
>
> 题量 15。

---

### Q1 MCP 是什么？解决了什么问题？

**考察点**：协议的定位。

**参考回答**

- **定义**：Model Context Protocol（模型上下文协议），由 Anthropic 在 2024 年底提出的开放协议，
  用统一的方式把外部工具、数据和提示词模板提供给 AI 应用。
- **解决的问题**：以前每个 AI 应用接入每个外部系统都要单独适配，形成 M×N 的集成工作量。
  有了 MCP，外部系统只需实现一次 MCP 服务端，所有支持 MCP 的应用都能使用，工作量降为 M+N。
- **与 Function Calling 的关系**：Function Calling 是模型层面“决定调用哪个工具”的能力；
  MCP 是应用和外部系统之间“如何发现和调用工具”的协议。两者是配合关系，不是替代关系。

**追问**：*有了 MCP，还需要自己写工具吗？* 需要。业务核心逻辑、强权限控制的操作，往往更适合直接实现为应用内部的工具。

**减分回答**：“MCP 就是 Function Calling 的新名字”。

### Q2 MCP 的架构中有哪些角色？提供了哪些能力？

**考察点**：协议结构。

**参考回答**

- **角色**：
  - **Host**：AI 应用本身，例如 IDE 或客服系统；
  - **Client**：Host 内部负责和某一个 MCP 服务端保持连接的组件，一般一对一；
  - **Server**：对外提供能力的服务。
- **服务端提供的能力**：
  - **Tools**：可被模型调用的函数；
  - **Resources**：可读取的数据，例如文件、数据库记录；
  - **Prompts**：可复用的提示词模板。
- **客户端可以提供的能力**：例如 Sampling（服务端请求客户端调用模型）、Roots（告诉服务端可访问的范围），
  以及向用户收集补充信息的能力。
- **通信格式**：基于 JSON-RPC 2.0；连接建立时先做初始化和能力协商。

**追问**：*工具列表变化时客户端怎么知道？* 服务端可以发送列表变更通知，客户端重新拉取；
应用侧最好对工具契约做快照和比对，发现不兼容的变化时告警。

**减分回答**：只知道 MCP 能“调用工具”。

### Q3 MCP 支持哪些传输方式？怎么选择？

**考察点**：部署形态。

**参考回答**

- **stdio**：客户端以子进程方式启动服务端，通过标准输入输出通信。适合本地工具，部署简单，
  但要在本机执行程序，安全风险较高。
- **Streamable HTTP**：通过 HTTP 通信，可以用 SSE 推送流式消息，适合远程服务、多客户端共享。
  它取代了早期单独的 HTTP + SSE 传输方式。
- **选择**：本地开发工具选 stdio；企业服务化部署选 HTTP，并配合鉴权（HTTP 传输推荐基于 OAuth 的授权方案）。

**追问**：*服务端要求把 stdio 命令配置在后台，风险是什么？* 相当于允许在服务器上执行任意程序。
必须对可执行文件、工作目录和环境变量做白名单限制，并清空继承的环境变量
（项目对照：[项目第 05 期 Q6](../05-安全护栏与治理中间件.md)）。

**减分回答**：不知道有不同的传输方式。

### Q4 接入第三方 MCP 服务有哪些安全风险？

**考察点**：供应链与运行时安全。

**参考回答**

- **SSRF**：远程 MCP 地址可能指向内网或云元数据地址。需要校验域名解析出的 IP，禁止内网、链路本地、云元数据地址，
  并且在保存配置和每次建立连接前都要校验。
- **工具投毒**：工具描述里可能藏有恶意指令，诱导模型执行危险操作；工具返回结果也可能包含注入内容。
- **权限过大**：一个 MCP 服务可能暴露很多工具，要按工具、Agent、用户分别授权，并对写操作加审批。
- **凭据泄露**：访问第三方所需的密钥要加密存储，不能出现在日志和配置明文里。
- **上游变更**：第三方可能修改工具的参数或行为，需要做契约快照比对和告警。

**追问**：*发现上游契约发生了不兼容的变化，应该自动停用吗？* 通常只告警、由人决定。上游演进是常态，
自动停用可能导致业务中断，而且判断依据（基线）本身也可能已经过期。

**减分回答**：“MCP 是标准协议，所以是安全的”。

### Q5 A2A 协议是什么？和 MCP 有什么区别？

**考察点**：Agent 之间的互操作。

**参考回答**

- **A2A（Agent2Agent）**：由 Google 在 2025 年提出，后来交给 Linux 基金会维护，用于**不同 Agent 之间**的发现和协作。
- **核心概念**：
  - **Agent Card**：描述一个 Agent 的能力、接口地址和鉴权方式，供其他 Agent 发现；
  - **Task**：一次协作的任务，有明确的生命周期状态；
  - 支持流式更新和异步通知，适合长时间运行的任务。
- **与 MCP 的区别**：MCP 解决“Agent 如何使用工具和数据”，调用方完全掌控流程；
  A2A 解决“Agent 如何把任务委托给另一个有自主能力的 Agent”，对方内部如何完成是不透明的。
- **两者互补**：一个 Agent 可以用 MCP 调用工具，同时通过 A2A 与其他 Agent 协作。

**追问**：*对外开放 A2A 接口要注意什么？* 鉴权、限流、租户隔离、审计，以及对方 Agent 的输出同样是不可信内容。

**减分回答**：把 A2A 和 MCP 当成竞争关系。

### Q6 AG-UI 协议解决什么问题？

**考察点**：Agent 与前端的交互。

**参考回答**

- **定位**：定义 Agent 后端与用户界面之间的事件流协议，让前端能实时展示 Agent 的执行过程。
- **事件类型**：运行的开始和结束、文本消息的增量、工具调用的开始 / 参数 / 结束、状态快照和增量更新等。
- **价值**：前端不用为每个 Agent 框架单独适配；可以展示“正在查询订单”这类中间过程，
  也可以支持人工确认等交互。
- **与 MCP、A2A 的关系**：三者分别面向“Agent 与工具”“Agent 与 Agent”“Agent 与用户界面”。

**追问**：*不用 AG-UI，自己用 SSE 推送文本不行吗？* 可以，但工具调用状态、中断、人工确认这些交互都要自定义协议，
渠道和前端一多，维护成本就很高。

**减分回答**：不知道这个协议，或者把它当成模型 API。

### Q7 Spring AI 的核心抽象有哪些？

**考察点**：Java 主流框架的认知。

**参考回答**

- **ChatClient**：流式风格的模型调用 API，支持同步和流式（基于 Reactor 的 `Flux`）调用。
- **Advisor**：环绕模型调用的拦截链，用来实现对话记忆、RAG、日志、安全检查等横切逻辑。
- **工具调用**：用 `@Tool` 注解声明方法，由框架生成 schema 并处理调用流程。
- **结构化输出**：把模型输出转换成 Java 对象。
- **VectorStore / Embedding**：统一的向量存储和 Embedding 抽象，适配多种向量库。
- **MCP 支持**：提供 MCP 客户端和服务端的集成。
- **优势**：与 Spring Boot 生态天然结合（自动装配、配置、可观测），厂商适配多，社区活跃。

**追问**：*Advisor 和本项目的治理中间件有什么相似之处？* 都是拦截链模式，都需要关注执行顺序：
比如审计应该记录脱敏后的内容，这决定了两者的相对顺序。

**减分回答**：只知道 Spring AI 能调用 OpenAI。

### Q8 Spring AI Alibaba 和 Spring AI 是什么关系？

**考察点**：国内生态。

**参考回答**

- **关系**：Spring AI Alibaba 基于 Spring AI 构建，补充了阿里云生态（通义千问 / 百炼等）的适配，
  并在其上提供更多面向 Agent 的能力，例如图（Graph）编排的工作流和多 Agent、与 Nacos 等组件的集成。
- **适用场景**：主要使用阿里云模型和中间件、需要工作流编排能力的团队。
- **选型注意**：关注它与 Spring AI 版本的对应关系；使用编排能力前，评估是否真的需要 Agent，还是固定工作流就够了。

**追问**：*图编排和 ReAct Agent 怎么选？* 流程确定、需要严格控制步骤时用图编排；
路径不确定、需要模型动态决策时用 ReAct。两者也可以嵌套使用。

**减分回答**：把两者当成完全独立、不相关的框架。

### Q9 LangChain4j 的核心概念有哪些？和 Spring AI 怎么选？

**考察点**：框架对比。

**参考回答**

- **核心概念**：
  - **AI Services**：用 Java 接口声明式地定义 AI 能力，框架生成实现；
  - `@Tool` 注解声明工具；
  - **ChatMemory**：对话记忆（按消息条数或 token 数保留窗口）；
  - **EmbeddingStore** 和检索增强组件。
- **对比**：
  - LangChain4j 不依赖 Spring，可以用在任何 Java 项目中，功能丰富，AI Services 的写法简洁；
  - Spring AI 与 Spring 生态结合更紧密，适合以 Spring Boot 为主的团队。
- **选型原则**：看团队现有技术栈、需要的厂商和向量库是否有适配、对框架稳定性的要求；
  核心业务逻辑尽量不要和框架 API 深度耦合，保留替换空间。

**追问**：*怎样降低被框架绑定的风险？* 在框架之上定义自己的接口（模型、工具后端、存储），业务代码只依赖这些接口。

**减分回答**：“哪个 star 多用哪个”。

### Q10 AgentScope Java 有什么特点？

**考察点**：对项目所用框架的理解。

**参考回答**

- **定位**：阿里开源的 Agent 框架 AgentScope 的 Java 版本，以 ReAct Agent 为核心，面向企业级 Agent 应用。
- **核心能力**（以本项目使用的 2.0 版本为例）：
  - `ReActAgent`，以及工具集 `Toolkit`（支持工具分组）；
  - **中间件**：可以在 Agent 调用、推理、工具执行等阶段插入治理逻辑；
  - **状态外置**：按用户和会话自动持久化状态；
  - RAG、长期记忆、Skill、权限系统、MCP 接入；
  - Harness：长会话压缩、计划模式、工作区、子 Agent。
- **使用体会**（结合本项目）：升级时要关注默认行为变化（例如工具默认改为并行执行），
  以及新增的接口默认方法对自定义装饰器的影响。
- **项目对照**：见 [项目第 01 期](../01-项目全景与架构设计.md) 和 [项目第 06 期 Q7](../06-Java并发与响应式流式链路.md)。

**追问**：*为什么要统一装配入口？* 框架提供了很多可插拔能力，但每个构建 Agent 的入口都要装配一遍，
容易漏掉；统一入口再加结构化测试，可以防止“某条链路没接上治理能力”。

**减分回答**：只会说“阿里出的，用的人多”。

### Q11 用 Java 做 Agent 开发，相比 Python 有什么优势和短板？

**考察点**：技术视野。

**参考回答**

- **优势**：
  1. 企业现有系统大多是 Java，Agent 能直接复用业务服务、权限体系和中间件；
  2. 类型系统和工程化工具成熟，更适合长期维护的大型系统；
  3. 并发和高可用方面经验丰富（线程池、响应式编程、虚拟线程）；
  4. 可观测、配置中心、灰度发布等生产能力完善。
- **短板**：
  1. 模型训练、新算法和论文复现的生态主要在 Python；
  2. 新框架和新能力通常先出 Python 版本；
  3. 数据处理和科学计算工具不如 Python 丰富。
- **常见做法**：业务 Agent 和平台层用 Java；模型训练和部分数据处理用 Python，通过接口协作。

**追问**：*招聘要求里写了 LangChain / LangGraph，Java 开发者怎么准备？* 理解背后的概念（链、图编排、状态、检查点），
能说清楚 Java 生态中对应的实现方式即可。

**减分回答**：“Java 做不了 AI”。

### Q12 调用大模型时，用 WebFlux 响应式编程还是 JDK 21 的虚拟线程？

**考察点**：Java 并发模型的选择。

**参考回答**

- **特点**：大模型调用是典型的高延迟 IO（秒级甚至更长），而且需要流式输出。
- **WebFlux / Reactor**：非阻塞，天然支持流式（`Flux`）和背压，适合 SSE 和 WebSocket 推送。
  缺点是代码和调试更复杂，ThreadLocal 上下文需要额外传递，遇到阻塞调用要切换到弹性线程池。
- **虚拟线程**：用同步阻塞的写法就能获得高并发，代码简单、容易调试。流式输出仍然需要 SSE 等机制，
  ThreadLocal 的使用也要谨慎（虚拟线程数量可能极大）。
- **选择**：已经基于 WebFlux 构建、对流式要求高的系统继续用响应式；新系统、团队更熟悉同步编程时可以考虑虚拟线程。
  不管用哪种，都要设置超时、限流和并发上限，因为瓶颈往往是模型厂商的调用额度，而不是本地线程。

**追问**：*在 WebFlux 里调用阻塞的 SDK 会怎样？* 会阻塞事件循环线程，拖慢所有请求；
Reactor 在检测到非阻塞线程上的阻塞操作时会直接抛出异常。

**减分回答**：“虚拟线程出来后响应式就没用了”。

### Q13 如何统一接入多家模型厂商？

**考察点**：抽象设计。

**参考回答**

- **统一接口**：业务代码只依赖统一的模型接口（输入消息和工具，输出流式响应），厂商差异由适配层处理。
- **需要适配的差异**：消息格式、工具调用格式、结构化输出方式、上下文窗口和能力元数据、错误码和限流方式。
- **能力声明**：每个模型声明自己支持的能力（工具调用、结构化输出、多模态、窗口大小），调用前检查。
- **支持的模型厂商清单只维护一份**：否则会出现一处支持、另一处不支持的不一致
  （项目中就遇到过后台登记页和运行时的厂商清单不同步）。
- **在统一接口之上再加主备切换、分级路由、熔断和计量**，作为装饰器叠加。

**追问**：*用 OpenAI 兼容接口接入所有厂商可以吗？* 能跑通，但可能丢失厂商特有的能力，
也可能出现消息格式不兼容（例如某些厂商丢失 system 角色），需要逐个验证。

**减分回答**：业务代码里直接写 `if (provider == "xxx")`。

### Q14 提示词应该怎么管理？

**考察点**：提示词的工程化。

**参考回答**

- **版本化**：提示词像代码一样管理版本，每次修改可追溯、可回滚。
- **与代码解耦**：放在配置中心，支持不重启更新；但发布要经过评测门禁和审批，不能随意在线修改。
- **记录实际生效的版本**：用内容指纹标识运行时实际使用的提示词，并与评测结果、线上指标关联，方便归因。
- **灰度发布**：先对部分租户或流量生效，观察指标后再全量发布。
- **提示词与装配保持一致**：提示词中提到的工具和能力，必须真实存在并已装配。

**追问**：*为什么要记录“实际生效的版本”，而不是“发布的版本”？* 灰度范围、推送失败或者有人绕过流程直接修改，
都会让两者不一致；只有实际生效的版本才能与指标对应上。

**减分回答**：把提示词写死在代码的字符串常量里，改一个字就要重新发版。

### Q15 Agent 平台一般由哪些模块组成？

**考察点**：平台化视角。

**参考回答**

- **模型管理**：模型资产、凭据、主备与路由策略、价格。
- **Agent 管理**：提示词、工具、知识库、Skill 的组合与版本。
- **工具与 MCP 管理**：注册、授权、契约监控。
- **知识库管理**：文档接入、分块、版本、权限、质量检查。
- **评测中心**：评测集、自动评测、回归对比、发布门禁。
- **发布与配置**：灰度、回滚、生效确认。
- **运行时**：对话接入、会话管理、治理中间件、流式输出。
- **运营与监控**：调用日志、成本账单、满意度、badcase、告警。
- **租户与权限**：多租户隔离、角色与数据范围、审计。

**追问**：*控制面和运行面为什么要分开？* 两者的可用性要求、权限和变更频率不同；控制面故障不应该影响线上对话。

**减分回答**：“有一个能配置提示词的页面就是平台”。

# 通用第 06 期 · 安全与评测

> **本期结论**：安全和评测是 Agent 能否上线的两道门槛。安全题考的是纵深防御的意识：不能把安全寄托在提示词上；
> 评测题考的是用数据说话的能力：没有评测集，就无法证明任何改动是变好还是变坏。
>
> 题量 14。

### Q1 OWASP 针对大模型应用列出了哪些主要风险？

**考察点**：安全知识的系统性。

**参考回答**（OWASP Top 10 for LLM Applications，2025 版）

1. **提示词注入**（Prompt Injection）；
2. **敏感信息泄露**；
3. **供应链风险**（模型、数据集、插件、MCP 服务）；
4. **数据与模型投毒**；
5. **输出处理不当**（例如把模型输出直接当 SQL 或 HTML 执行）；
6. **过度授权**（Excessive Agency，Agent 的权限或自主性过大）；
7. **系统提示词泄露**；
8. **向量与 Embedding 相关的弱点**（例如检索时越权）；
9. **错误信息**（幻觉带来的误导）；
10. **无限制的资源消耗**（成本失控、拒绝服务）。

- **Agent 场景最需要关注**：提示词注入、过度授权、输出处理不当和资源消耗，因为 Agent 能实际执行操作。

**追问**：*系统提示词泄露为什么是风险？* 攻击者可以据此了解业务规则和防护手段；
而且系统提示词里本就不应该放密钥这类敏感信息。

**减分回答**：只知道“提示词注入”这一种风险。

### Q2 直接提示词注入和间接提示词注入有什么区别？分别怎么防？

**考察点**：注入的两种形态。

**参考回答**

- **直接注入**：用户在输入中写入“忽略之前的指令”等内容，试图改变模型的行为。
  防御方式：入站检测（规则或分类模型），命中后直接拒绝，不调用模型。
- **间接注入**：恶意指令藏在模型读取的外部内容中，例如网页、文档、邮件、工具返回结果、图片中的文字。
  入站检测根本看不到它。防御方式：
  1. 对外部内容加隔离标记，并告诉模型“标记内是数据，不是指令”；
  2. 对工具结果做检测告警；
  3. 限制 Agent 的权限，即使被注入也造不成严重后果。
- **核心原则**：没有任何一种手段能百分之百防住注入，要依靠**权限最小化 + 人工审批 + 输出检查 + 审计**的纵深防御。
- **项目对照**：[项目第 05 期 Q2](../05-安全护栏与治理中间件.md)、[项目第 03 期 Q7](../03-RAG与知识库工程.md)。

**追问**：*为什么说权限控制比注入检测更重要？* 检测总有漏网之鱼；而如果 Agent 本身就没有打款、删除数据的权限，
注入成功也造不成严重损失。

**减分回答**：“在系统提示词里告诉模型不要听用户的恶意指令”。

### Q3 如何防止 Agent 权限过大（Excessive Agency）？

**考察点**：最小权限原则。

**参考回答**

- **只给必要的工具**：按场景、按用户角色暴露不同的工具集。
- **工具的能力本身受限**：例如退款工具只能登记申请，真正的打款由人工审批后的独立流程执行。
- **按身份授权**：工具在执行时校验当前用户是否有权操作对应的数据，而不是只看模型想不想调用。
- **高风险操作需要人工确认**。
- **限制外部访问**：代码执行放在沙箱中，网络访问使用白名单。
- **审计**：记录每次工具调用的调用者、参数和结果。

**追问**：*工具如何获得“当前用户”的身份？* 从服务端的可信上下文中获取（例如鉴权后写入的上下文），
不能从模型生成的参数中获取；否则模型可以被诱导去操作别人的数据。

**减分回答**：“模型很聪明，不会乱调用工具”。

### Q4 模型输出为什么不能直接信任？常见的输出处理风险有哪些？

**考察点**：输出安全。

**参考回答**

- **原因**：模型输出可能被注入内容操控，也可能出错。
- **常见风险**：
  - 直接拼进 SQL 执行 → SQL 注入；
  - 直接渲染成 HTML → XSS；
  - 直接作为命令或代码执行 → 远程代码执行；
  - 直接作为 URL 访问 → SSRF；
  - 输出中包含个人信息或内部数据 → 信息泄露。
- **处理方式**：
  1. 把模型输出当作不可信的用户输入对待：参数化查询、输出编码、白名单校验；
  2. 对个人信息做脱敏；
  3. 对违规内容做过滤；
  4. 对关键结论（例如“已退款”）核对工具调用的证据。

**追问**：*流式输出时怎么做内容过滤？* 敏感词可能被拆到两个分片里，需要滑动缓冲：
只放行确定不会构成敏感词的部分，流结束时再输出剩余内容（见 [项目第 05 期 Q3](../05-安全护栏与治理中间件.md)）。

**减分回答**：把模型输出直接交给下游系统执行。

### Q5 Agent 系统中如何保护用户隐私和敏感数据？

**考察点**：数据合规。

**参考回答**

- **数据最小化**：只把完成任务必需的信息发给模型。
- **脱敏**：手机号、身份证号、银行卡号等在日志、审计和发给第三方模型前进行脱敏。
- **隔离**：会话、记忆、缓存都按租户和用户隔离。
- **授权与删除**：长期记忆需要用户授权，支持查看、导出、删除和保留期限。
- **日志与审计**：日志中不记录明文凭据和敏感数据；API Key 这类凭据只保存哈希指纹。
- **模型厂商合规**：确认数据是否出境、是否会被用于训练；敏感场景使用私有化部署。

**追问**：*审计日志应该记录脱敏前还是脱敏后的内容？* 通常记录脱敏后的内容，
避免审计系统本身成为泄露源。这也决定了“脱敏”要在“审计”之前执行。

**减分回答**：“内部系统，不用考虑隐私”。

### Q6 为什么说 Agent 必须有评测集？评测集怎么构建？

**考察点**：评测的必要性。

**参考回答**

- **必要性**：模型输出不确定，改一次提示词、换一次模型、调整一次检索参数，都可能在修好一些问题的同时弄坏另一些问题。
  没有评测集，就无法判断改动的实际效果。
- **构建方式**：
  1. 从真实用户问题中抽样，覆盖主要意图和高频问题；
  2. 加入历史 badcase 和边界情况（例如信息不全、情绪激动、越权请求、注入攻击）；
  3. 为每个用例标注期望结果：期望的答案要点、应该调用的工具、不应该出现的内容；
  4. 定期更新，把新发现的问题补充进去。
- **管理**：评测集要有版本；增删用例后，前后两次的分数不能直接比较。

**追问**：*评测集应该有多大？* 从几十条高质量用例开始，逐步扩充到覆盖主要场景；质量比数量重要。

**减分回答**：“上线后看用户反馈就行”。

### Q7 LLM-as-Judge 是什么？有哪些偏差？怎么控制？

**考察点**：自动评测方法。

**参考回答**

- **做法**：用一个模型按照评分标准，对另一个模型的输出打分或做比较。适合评估相关性、准确性、完整性这类难以用规则判断的维度。
- **两种方式**：单独打分（例如 1～5 分）和两两比较（判断 A 和 B 哪个更好，通常更稳定）。
- **常见偏差**：
  - **位置偏差**：两两比较时倾向于某个位置的答案；
  - **长度偏差**：倾向于更长的答案；
  - **自我偏好**：倾向于和自己同一家族的模型的输出；
  - **打分不稳定**：同一输入多次打分结果不一致。
- **控制方法**：写清评分标准并给出示例；两两比较时交换位置各评一次；固定并记录裁判模型的版本；
  用人工标注数据校准；必要时选用与被测模型不同家族的模型做裁判。
- **结果处理**：裁判不可用或输出无法解析时，本次评测应该标记为“不完整”，不能当作通过。

**追问**：*裁判的输出格式怎么保证能解析？* 要求固定格式（例如 `SCORE: 4`），用严格的正则解析；
解析失败要单独计数，而不是当成 0 分或者满分。

**减分回答**：“用 GPT 打分就行”，不知道有偏差。

### Q8 Agent 的评测和普通问答的评测有什么不同？

**考察点**：轨迹评测。

**参考回答**

- **不只看最终答案，还要看过程（轨迹）**：
  - 是否调用了正确的工具；参数是否正确；调用顺序是否合理；
  - 是否调用了不应该调用的工具（例如没有做资格校验就发起退款）；
  - 用了多少步、多少 token、多长时间。
- **不只看单次结果，还要看稳定性**：同一个用例运行多次，统计通过率。
  一次通过（pass@k）和每次都通过（常写作 pass^k）是两个不同的指标，面向用户的 Agent 更看重后者。
- **需要模拟环境**：工具要用模拟后端或回放数据，避免评测时对真实系统产生副作用。

**追问**：*评测时调用真实业务系统可以吗？* 只读查询可以谨慎使用，写操作绝对不可以。
评测应该使用模拟后端或只读回放。

**减分回答**：只比较最终回答的文本是否一致。

### Q9 如何做回归评测？怎样判断一次改动是变好还是变坏？

**考察点**：评测结果的解读。

**参考回答**

- **与基线对比**：每次改动后，在同一个评测集上运行，与上一个版本的结果比较。
- **不只看总分**：总准确率从 90% 提高到 92%，可能是修好了 3 个、又弄坏了 1 个。
  要逐个用例列出**回归**（上次通过、这次失败）和**修复**（上次失败、这次通过），被弄坏的用例要优先查看。
- **注意可比性**：评测集有变化时，两次结果不能直接比较；取“上一次”基线时按写入顺序，而不是按时间戳（可能在同一毫秒内）。
- **设置容差**：浮点数的微小差异不应该被报告为变化。
- **归因**：记录每次评测时的提示词版本、模型版本和数据版本，指标变化时先看哪个版本变了。

**追问**：*评测结果能否作为发布门禁？* 可以，而且应该。但门禁要考虑评测不完整的情况（例如裁判不可用），
这时应该阻止发布，而不是默认放行。

**减分回答**：只看平均分有没有上升。

### Q10 线上怎么评估 Agent 的效果？

**考察点**：线上指标体系。

**参考回答**

- **业务指标**：问题解决率、转人工率、用户满意度（CSAT）、重复咨询率、平均处理时长。
- **质量指标**：负反馈率、知识未命中率、兜底回复比例、越权承诺拦截次数。
- **性能指标**：首 token 延迟、总耗时、错误率、超时率。
- **成本指标**：每次对话的 token 数和费用、缓存命中率。
- **A/B 测试**：新旧版本分流对比；流量不足时不要下结论。
- **注意满意度的统计口径**：同时记录发出的邀请数和收到的评价数，否则算不出回收率；
  回收率很低时，满意度只代表愿意评价的少数人。

**追问**：*评测和合成监控的会话要不要计入满意度？* 不要。这些会话背后没有真实用户，计入会稀释指标。

**减分回答**：只看调用量。

### Q11 如何构建 badcase 闭环？

**考察点**：持续改进的机制。

**参考回答**

1. **收集**：用户负反馈、转人工的对话、知识未命中、评测失败、人工抽检。
2. **归类**：按原因分类，例如知识缺失、检索错误、工具错误、提示词问题、模型能力不足。
3. **分派与跟踪**：每类问题有明确的负责人和处理时限。
4. **修复**：补充知识、调整提示词、修改工具等。
5. **验证**：把 badcase 加入评测集，确认修复有效且没有引入回归。
6. **观察线上效果**：修复上线后，确认同类问题是否减少。

**追问**：*知识缺失类问题怎么处理最高效？* 聚合相似的未命中问题，生成候选知识，经审核并在隔离环境复评后再发布。

**减分回答**：“发现问题就改提示词”。

### Q12 如何控制 Agent 的资源消耗，防止被滥用？

**考察点**：无限制资源消耗的防护。

**参考回答**

- **多层限流**：按 IP、用户、API Key、租户分别限流；既限制请求次数，也限制 token 用量。
- **单次调用的边界**：最大迭代次数、最大工具调用次数、最大输出长度、总超时。
- **配额与预算**：按租户设置日或月的 token 配额和费用预算，超出时降级到便宜模型或拒绝服务。
- **异常检测**：监控突然升高的调用量和成本并告警。
- **防止放大攻击**：一次输入触发大量模型调用或工具调用（例如诱导 Agent 反复循环）。

**追问**：*配额超出后降级到便宜模型，如果没有配置备用模型怎么办？* 应该直接拒绝，而不是继续使用主模型，
否则就突破了管理员设定的预算。

**减分回答**：只在网关上限制每秒请求数。

### Q13 安全护栏自身出故障时，应该放行还是拦截？

**考察点**：故障时的取舍。

**参考回答**

- **判断依据**：比较“护栏故障导致服务不可用”和“漏放一次”哪个代价更大。
- **倾向放行（fail-open）**：检测类、辅助类的护栏，例如注入检测、循环检测、缓存查询。
  它们故障时不应该让整个服务不可用。
- **倾向拦截（fail-closed）**：隔离类、合规类的防线，例如缺少租户身份、内容风控不可用、超出预算。
  这时宁可拒绝服务，也不能泄露数据或突破边界。
- **降级而不是放行**：限流依赖的 Redis 故障时，降级为本地限流，而不是直接取消限流。
- **关键是显式决策并写明理由**，而不是随手写一个 `catch` 返回默认值。

**追问**：*放行了就不管了吗？* 不是。故障本身要告警，并记录漏检的风险。

**减分回答**：所有地方都 `catch` 住异常然后继续执行。

### Q14 如何进行 Agent 的红队测试？

**考察点**：主动安全测试。

**参考回答**

- **测试内容**：
  - 提示词注入（直接和间接）、越狱；
  - 诱导泄露系统提示词或其他用户的数据；
  - 诱导越权操作（给别人退款、查询别人的订单）；
  - 诱导做出虚假承诺；
  - 资源消耗攻击（诱导无限循环）；
  - 利用工具参数（SQL 注入、路径穿越、SSRF）。
- **方法**：人工构造攻击用例，加上自动化生成的变体；把发现的问题加入评测集，作为长期的回归用例。
- **频率**：上线前必做；模型、提示词、工具有较大变更时重做。

**追问**：*红队测试发现问题后怎么修？* 优先修权限和能力边界这类根因，而不是只在提示词里补一句禁止语。

**减分回答**：“我们用的是大厂模型，安全不用自己管”。

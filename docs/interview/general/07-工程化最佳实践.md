# 通用第 07 期 · 工程化最佳实践

> **本期结论**：Demo 和生产系统的差距，几乎都在工程化上：流式输出怎么稳定、失败怎么兜底、成本怎么控制、
> 出了问题怎么排查、上线前要检查什么。本期题目偏实践，适合考察候选人是否真正把 Agent 放到过线上。

### Q1 流式输出用 SSE 还是 WebSocket？

**考察点**：协议选型。

**参考回答**

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端到客户端单向 | 双向 |
| 协议 | 基于普通 HTTP，易穿透代理 | 需要协议升级，部分代理和网关要额外配置 |
| 断线重连 | 浏览器原生支持自动重连 | 需要自己实现 |
| 适合场景 | 一问一答式的流式回复 | 实时双向交互：用户可随时打断、坐席消息推送、多种事件混合 |

- **选择**：简单的对话接口用 SSE；需要双向实时交互（例如客服系统中用户、AI、坐席三方消息都要推送）时用 WebSocket。
- **项目对照**：项目同时提供 HTTP、SSE 和 WebSocket，H5 使用 WebSocket。

**追问**：*SSE 经过 Nginx 后变成一次性返回，为什么？* 代理缓冲了响应。需要关闭代理缓冲（例如设置响应头
`X-Accel-Buffering: no` 或修改代理配置），并确保没有启用会缓冲内容的压缩。

**减分回答**：“WebSocket 更先进，所以都用 WebSocket”。

### Q2 流式输出有哪些工程问题需要处理？

**考察点**：流式链路的完整性。

**参考回答**

- **空闲超时**：模型长时间没有输出时，要按“相邻两次输出的间隔”超时，结束连接并返回提示，避免连接泄漏。
- **心跳**：长时间没有数据时定期发送心跳，防止被网关断开。
- **客户端断开**：用户关闭页面后要取消上游的模型调用，避免继续消耗 token。
- **错误处理**：已经输出的内容无法撤回，中途出错时要追加说明，而不是简单地断开。
- **只处理用户能看到的内容**：安全检查和过滤要作用在实际发给用户的增量上，而不是只处理最终汇总的结果。
- **结束信号**：明确告诉前端这一轮结束了，并附带消息 ID、引用等信息。
- **切换线程**：不要在模型的 IO 线程上执行耗时的下游处理。

**追问**：*流式输出的内容要写入缓存或数据库，什么时候写？* 在流正常结束后再写；出错或走兜底的流不要写入缓存，
否则会把半截回答缓存下来。

**减分回答**：只会把模型的流直接转发给前端。

### Q3 如何保证同一条消息不会被处理两次？

**考察点**：幂等设计。

**参考回答**

- **原因**：网络不稳定时客户端会重发；如果不去重，同一个问题会被回答两次，写操作也可能执行两次。
- **做法**：
  1. 客户端为每条消息生成唯一 ID，重发时沿用；
  2. 服务端根据租户、会话、发送方和客户端消息 ID 生成确定性的消息号；
  3. 先查询是否已经处理过，处理过就直接返回之前的结果；
  4. 用锁减少并发冲突，用数据库唯一约束作为最终裁决。
- **写操作要额外保证幂等**：调用下游时传递幂等键，由下游去重。
- **项目对照**：[项目第 07 期 Q3](../07-生产化-多租户限流幂等与一致性.md)。

**追问**：*同一个消息 ID 对应的内容不一样怎么办？* 返回冲突错误，而不是按旧内容或新内容处理。

**减分回答**：“前端按钮防重复点击就够了”。

### Q4 模型服务的高可用怎么设计？

**考察点**：容错体系。

**参考回答**

- **主备切换**：配置多个候选模型，主模型失败时切换到备用模型。
- **熔断**：连续失败达到阈值后暂时跳过该模型，一段时间后放行少量请求试探恢复。
- **超时和重试**：设置合理的超时；只对临时性错误做有限次数的重试，并加退避和抖动。
- **流式中途失败**：已经输出部分内容后，是否切换模型要按场景决定。面向用户的对话中，切换后可能出现内容重复错乱，
  通常选择停止并返回兜底提示。
- **降级**：模型全部不可用时，返回友好提示、引导转人工或留言。
- **限流与排队**：模型厂商有并发和 token 额度限制，本地要做限流和排队，避免把额度打满后全面失败。

**追问**：*备用模型和主模型的能力不一样怎么办？* 调用方拿到的能力声明应该取各候选中较弱的那个，
否则切换到备用模型时可能直接失败。

**减分回答**：只配置一个模型，失败就报错。

### Q5 如何降低 Agent 的调用成本？

**考察点**：成本优化手段。

**参考回答**

- **减少输入 token**：精简系统提示词和工具定义；控制历史长度；只注入最相关的检索结果。
- **利用提示词缓存**：固定内容放在前面，保持前缀不变。
- **模型分级**：简单问题用便宜的模型，复杂问题用大模型；判断要保守，判错的代价应该是“少省了钱”而不是“答错了”。
- **语义缓存**：对通用问题复用答案，但必须严格限制范围，避免把个人数据返回给其他用户。
- **控制输出长度**：限制最大输出，要求简洁回答。
- **减少不必要的调用**：用规则处理能确定的情况（例如关键词直接转人工）；避免多 Agent 滥用。
- **先度量再优化**：统计每个环节的 token 占比，找出真正的大头。

**追问**：*怎么证明成本优化没有降低效果？* 优化前后在同一个评测集上对比质量，同时对比单次对话的成本。

**减分回答**：“换便宜的模型”，不考虑质量影响。

### Q6 Agent 系统的可观测性应该包括哪些内容？

**考察点**：监控与排查体系。

**参考回答**

- **链路追踪**：一次对话中每次模型调用、工具调用、检索的耗时和结果，能串成完整的调用链。
  可以参考 OpenTelemetry 为生成式 AI 定义的语义约定。
- **指标**：请求量、错误率、首 token 延迟、总耗时、token 用量、成本、缓存命中率、工具失败率、转人工率。
- **日志**：带请求 ID、会话 ID、错误码；敏感信息脱敏。
- **回放**：保存模型调用的输入输出快照（注意脱敏和权限），便于复现问题。
- **业务审计**：谁在什么时候调用了哪个工具、参数和结果是什么。
- **注意指标口径的一致性**：同名指标的标签要一致；计量点要唯一，避免重复统计或漏统计。

**追问**：*用户反馈“回答不对”，你怎么排查？* 根据会话找到调用链，依次查看：检索到了什么、调用了哪些工具、
工具返回了什么、提示词版本和模型版本是什么，然后判断问题出在哪个环节。

**减分回答**：“有日志就够了”。

### Q7 如何实现 Agent 配置的灰度发布和回滚？

**考察点**：变更管理。

**参考回答**

- **版本化**：模型、提示词、工具、知识库等配置每次发布都形成不可变的版本。
- **发布门禁**：发布前运行评测，不通过就阻止发布。
- **灰度**：先对部分租户或部分流量生效，观察指标。
- **生效确认**：配置下发后，每个实例回报是否成功应用；配置中心收到了配置不等于实例已经生效。
- **回滚**：把旧版本作为新版本重新发布；历史只增不删，任何时候都能说清线上运行的是哪个版本。
- **配置安全**：配置中的密钥加密传输；接收方校验签名和内容指纹，校验失败时保留最后一份可用的配置。

**追问**：*配置切换期间，缓存里旧模型产生的答案怎么办？* 用“配置代际”区分，切换后旧代际的缓存不再命中，
切换前发起的请求也不能把结果写入新代际。

**减分回答**：“直接修改配置中心，实例自动刷新”。

### Q8 多租户的 Agent 平台需要在哪些地方做隔离？

**考察点**：SaaS 隔离的完整性。

**参考回答**

- **数据**：会话、记忆、知识库、工单、日志、缓存，全部按租户隔离；在数据库访问层统一过滤，缺少租户身份时直接拒绝。
- **配置**：每个租户的提示词、模型、工具、知识库配置相互独立，某个租户的配置缺失时不能回退到其他租户的配置。
- **资源**：按租户设置配额和限流，避免一个租户耗尽共享的模型额度。
- **权限**：租户管理员的权限不能超出自己的租户范围；跨租户操作只能由平台管理员执行，并留审计。
- **向量检索与缓存**：检索时必须带上租户过滤条件；语义缓存按租户（甚至更细的范围）隔离。

**追问**：*有意的跨租户查询（例如平台运维统计）怎么实现才安全？* 通过显式的、可搜索的白名单方法实现，
而不是给上下文设置一个表示“全部租户”的特殊值；否则“忘记设置租户”和“有意查询全部”在代码里无法区分。

**减分回答**：“每张表加一个 tenant_id 字段就行”。

### Q9 如何做好 Agent 应用的测试？

**考察点**：测试策略。

**参考回答**

- **单元测试**：工具、解析、路由规则、过滤器这类确定性逻辑，用模拟的模型响应来测试。
- **集成测试**：用真实的框架链路（真实 Agent + 模拟的模型和后端）验证装配和调用流程，
  而不是只测试单个方法，避免“逻辑正确但没有接到链路上”。
- **评测**：用评测集测试模型相关的效果（见 [通用第 06 期](06-安全与评测.md)）。
- **结构性检查**：用扫描源码或反射的测试，确保新增的链路都接入了统一的治理能力。
- **变异测试**：故意改错被测代码，确认测试会失败，避免写出永远通过的断言。
- **稳定性**：涉及线程、时间、异步回调的测试容易出现偶发失败，要找到根因，而不是简单地重试。

**追问**：*单元测试全部通过，线上功能却不生效，常见原因是什么？* 测试注入了模拟对象，
而真实环境中依赖的 Bean 根本不存在；或者测试手工构造的上下文在真实链路中并不存在。

**减分回答**：“模型输出不确定，所以没法写测试”。

### Q10 Agent 系统应该如何处理长时间运行的任务？

**考察点**：异步任务设计。

**参考回答**

- **异步化**：把长任务放到后台执行，立即返回任务 ID，客户端通过轮询、推送或回调获取进度和结果。
- **持久化任务状态**：任务状态和中间结果存入数据库，服务重启后能继续执行或恢复。
- **进度可见**：通过任务清单或事件流展示当前步骤。
- **支持中断和恢复**：用户可以取消任务；被中断的工具调用在恢复时能继续执行。
- **超时与资源限制**：设置总时长上限、最大步骤数和预算。
- **优雅停机**：发布或缩容时，等待正在执行的任务完成或保存状态，再停止服务。

**追问**：*后台任务中如何保留用户和租户的上下文？* 在提交任务时捕获身份信息，并在任务执行线程中显式恢复；
不能依赖原来的请求线程。

**减分回答**：让 HTTP 请求一直等待到任务完成。

### Q11 如何设计转人工机制？

**考察点**：人机协同的业务设计。

**参考回答**

- **触发条件**：
  - 用户明确要求人工（可以用关键词直接判断，不必调用模型）；
  - 情绪激动、投诉升级；
  - 高风险或大额业务；
  - Agent 多次尝试仍无法解决（例如迭代次数用完）；
  - 知识库没有答案。
- **流程**：工单状态流转（AI 服务中 → 等待人工 → 处理中 → 待确认 → 已解决）；把对话历史和 AI 的摘要交给坐席，避免用户重复描述问题。
- **保障**：转人工通道不能被配置关闭；排队时给用户明确的等待提示。
- **回流**：人工处理的结果和原因用于改进知识库和 Agent。

**追问**：*转人工后用户继续发消息怎么办？* 根据工单状态路由：已被坐席接手的消息转发给坐席，排队中的给出等待提示，
不再交给 AI 回答。

**减分回答**：“在提示词里写一句‘必要时建议用户联系人工客服’”。

### Q12 Agent 服务如何实现水平扩展？

**考察点**：分布式架构。

**参考回答**

- **应用无状态化**：会话状态外置到数据库或缓存；实例内只保留可以重建的缓存。
- **把进程内的组件替换为分布式实现**：限流计数器、会话锁、消息广播（例如 WebSocket 推送到其他实例上的连接）、定时任务的互斥。
- **会话粘性**：如果仍使用进程内锁，需要网关按会话把请求路由到同一个实例。
- **依赖故障时的降级**：分布式组件故障时降级为本地实现，而不是直接取消保护。
- **优雅停机和健康检查**：滚动发布时不中断正在进行的对话。
- **瓶颈往往在模型厂商**：扩容应用实例并不能突破模型的调用额度，要同时规划额度和排队。

**追问**：*WebSocket 连接在 A 实例，消息在 B 实例产生，怎么推送？* 通过消息广播（例如 Redis 发布订阅）
把消息发给所有实例，由持有连接的实例推送，并防止实例收到自己发出的广播后重复处理。

**减分回答**：“加机器就行”。

### Q13 一个 Agent 应用上线前，需要检查哪些事项？

**考察点**：上线清单。

**参考回答**

- **效果**：评测集通过；高频问题人工抽检；已知 badcase 已修复或有兜底。
- **安全**：注入防护、权限最小化、高风险操作有审批、敏感信息脱敏、红队测试完成。
- **稳定性**：超时、重试、熔断、备用模型、降级话术都已配置并验证过；压测覆盖了预期峰值。
- **成本**：配额、限流、预算告警已配置；单次对话的成本在预期范围内。
- **可观测**：指标、链路追踪、告警、日志脱敏都已就绪。
- **运营**：转人工流程、坐席排班、反馈收集和 badcase 处理流程已经就绪。
- **合规**：数据出境、隐私授权、内容安全审核符合要求。
- **回滚**：配置和版本可以快速回滚。
- **演示数据已清理**：知识库、业务数据中不能残留测试或演示数据，否则 Agent 会把它们当作真实信息回答用户。

**追问**：*为什么要强调清理演示数据？* 智能体会把知识库和业务表里的内容当作事实回答用户，
演示数据留在生产环境中就会变成错误答案。

**减分回答**：“功能测试通过就可以上线”。

### Q14 做 Agent 项目，你总结的最重要的几条工程经验是什么？

**考察点**：经验沉淀和工程判断力（开放题）。

**参考回答**（可结合本项目的经验）

1. **先度量，再优化**：成本、延迟、效果都要先有数据，再决定改什么。
2. **单一入口**：治理能力只在一个地方装配，避免“某条链路漏接”。
3. **关注用户实际看到的内容**：流式场景下，安全和质量检查必须作用在真正发给用户的内容上。
4. **显式决定故障时的行为**：每个护栏失败时放行还是拦截，都要有理由。
5. **把行为变更和版本升级分开**：框架升级时显式固定关键行为，并检查默认值和接口的变化。
6. **注释和文档描述的是意图，不是事实**：声称的能力要去代码里核实，提示词里提到的工具必须真实装配。
7. **用自动化测试守住结构**：反复出现的问题，用结构性测试防止复发。

**追问**：*能否讲一个具体的例子？* 应结合亲身经历，按“现象 → 根因 → 修复 → 防复发”讲清楚
（可参考 [项目第 08 期 Q7](../08-模型路由成本评测与系统设计.md)）。

**减分回答**：只列出一堆技术名词，没有具体的例子和取舍。

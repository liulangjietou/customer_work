# 多租户架构设计（B1 租户地基）

本文是 B1 批次的设计定案，回答三个问题：**租户是什么、数据怎么不串、身份从哪来**。
配额计费（B3）、按租户灰度（B4）建立在本文的 `tenant_id` 之上，不在本文范围。

## 1. 租户模型

隔离级别：**共享库 + `tenant_id` 行级过滤**（不做 schema-per-tenant）。

`tenant_id` 为 `VARCHAR(64)`，只表示数据归属。系统只保留一个内置租户：

| 值 | 含义 |
|---|---|
| `default` | 升级前的存量数据与共享基线配置归属，等价于"原来那个单租户系统" |
| 其它 | 真实业务租户，由 `sys_tenant.tenant_code` 定义 |

跨租户能力不再由特殊租户编码隐式表达，而由 `sys_role.control_plane` 显式表达；仅内置
`super_admin`、`operator` 角色启用。真正执行跨租户操作时，还必须同时通过接口原有的权限点校验。
普通角色编辑接口不能修改该字段；给用户分配、移除、恢复、编辑或删除控制面角色，也必须由已有控制面用户执行。

选 `VARCHAR` 而非 `BIGINT`：`tenant_id` 要出现在 API Key 映射、日志 MDC、指标标签、Nacos dataId 里，
可读的编码（如 `acme`）比自增数字好排查，且与既有 `TenantResolver.DEFAULT_TENANT = "default"` 的口径衔接。

### 生命周期

`sys_tenant.status`：`ACTIVE`（正常）→ `SUSPENDED`（冻结，登录与 API 拒绝，数据保留）→ `TERMINATED`（退租，数据保留待导出/清理）。
冻结与退租不只改状态：还会递增 `accessEpoch`、撤销后台会话并可靠发布访问快照；退租额外停用渠道，
运行时应用冻结/退租快照后主动断开该租户已有 WebSocket。当前刻意保留业务数据，不做级联物理删除，
也尚未生成租户级全量归档包。

## 2. 数据隔离

### 2.1 强制机制

MyBatis-Plus `TenantLineInnerInterceptor`（3.5.7）全局改写，两侧各挂一次：
starter 的 `CustomerWorkPersistenceConfig`（独立 `customerWorkSqlSessionFactory`）与 admin 的 `MybatisPlusConfig`。

选它而非在 Store SPI 逐个手工过滤的理由：

- 一处配置覆盖 `SELECT/UPDATE/DELETE` 与 XML 手写 SQL，符合项目"防御式编程只保留一处"的规范；
- **`INSERT` 由拦截器自动补 `tenant_id` 列与值**，因此已有的写入代码零改动——这是"加列"比"加忽略表"更省事的根本原因；
- 全仓复杂 SQL 只有 3 个 XML（`OrderMapper` 的 `LEFT JOIN cw_user`、`AgentCallLogMapper` 的 `GROUP BY`、
  admin 的 `ChatSessionStateQueryMapper`），改写面小、可逐个回归。

### 2.2 逐表归属

**原则：能加列的全加。** 忽略表清单越短越安全——漏加一张表就是一个串数据的口子，而多加一列 `tenant_id` 没有代价。
关联表（`ai_agent_skill`、`sys_user_role` 等）同样加列，不靠"JOIN 主表天然隔离"这种需要每次推理的间接保证。

| 类别 | 表 | 处理 |
|---|---|---|
| 客服端业务数据 | `cw_*` 全部 43 张（B7 新增 `cw_subject_quota_level` / `cw_subject_quota_hit`） | 加 `tenant_id`，自动过滤 |
| admin 配置与业务数据 | `ai_*` 除下方例外的全部、`sys_user`、`sys_role`、`sys_operation_log`、关联表 | 加 `tenant_id`，自动过滤 |
| 全局级（忽略过滤） | `sys_permission`、`sys_menu_change_log`、`ai_system_tool`、`sys_tenant`、`ai_model_price`、`login_carousel_image`、`flyway_schema_history` | 不加列，进忽略清单 |
| 框架自建（忽略过滤） | `ai_chat_session_state` | 见 §4.1 |
| 两级可见（忽略过滤） | `ai_model_config` | 见 §2.4 |
| **带 `tenant_id` 但不自动过滤** | `sys_tenant_quota` | 见 §2.5 |

全局级表的判定依据是"内容由系统定义、租户只读"：`sys_permission` 是权限点/菜单树的代码级定义，
`ai_system_tool` 是代码里 `@Tool` 注册的工具目录（租户是否启用某工具走租户级的 `ai_agent_system_tool` 关联表），
`ai_model_price` 的单价由平台统一定义（租户不该也不能自己定价，故无 `tenant_id` 列），
`login_carousel_image` 服务于登录页——登录前匿名访问，此刻没有任何租户上下文，加列参与过滤只会让登录页 fail-closed 打不开。

> 这份表格与代码里的 `TenantInterceptors.TENANT_IGNORED_TABLES` 必须逐条对齐。
> 两边曾漂移过三张表（`login_carousel_image`、`ai_model_price`、`sys_tenant_quota`），
> 后果是按本文档做安全评审的人会漏掉它们。

### 2.3 唯一约束改造

行级隔离后，原先的全局唯一键会阻止两个租户使用相同的业务标识，必须前置 `tenant_id`：

| 表 | 原约束 | 改为 |
|---|---|---|
| `cw_user` | `(username)` | `(tenant_id, username)` |
| `cw_knowledge` | `(title)` | `(tenant_id, title)` |
| `cw_sensitive_word` | `(word)` | `(tenant_id, word)` |
| `cw_rate_limit_rule` | `(rule_name)` | `(tenant_id, rule_name)` |
| `cw_subject_quota_level`（B7 新建） | — | `(tenant_id, level_code)`，建表即带 |
| `cw_dict_type` | `(dict_type)` | `(tenant_id, dict_type)` |
| `cw_dict_item` | `(dict_type, item_key)` | `(tenant_id, dict_type, item_key)` |

不改的两个：`cw_chat_message.(message_id)` 是框架 `Msg.id` 的 UUID，全局唯一；
`sys_user.(username)` **刻意保持全局唯一**——admin 只有一个登录入口，若允许跨租户重名，登录时无法判定归属租户，
用户得先填租户编码才能登录。全局唯一换取登录体验，代价是租户不能自选已被占用的账号名，可接受。

各表主键均为 `VARCHAR(64)` 业务号或自增 ID，天然全局唯一，不受影响。

### 2.4 `ai_model_config` 为何破例

该表存模型接入凭据（`api_key`）。若按普通租户级表处理，控制面要为每个租户复制一份 key，
则 key 轮换需批量更新 N 份，且租户管理员在自己的数据域里能读到共享凭据——这是真实的凭据泄露面。

处理：加 `tenant_id` 但进忽略清单，由两个统一入口显式做两级可见性：管理 CRUD 走
**`ModelConfigService`**（`applyReadScope` / `requireModel` / `requireWritableModel` / `clearOtherDefaults`），
智能体、知识库、Embedding 与发布运行时读取走 **`ModelConfigAccess`**。业务代码禁止直接注入
`AiModelConfigMapper`。

| 操作 | 控制 |
|---|---|
| 列表 / 详情 | `tenant_id IN (当前租户, 'default')`；不可见与不存在统一报 404，不泄漏"这个 id 属于别人" |
| default 共享记录的凭据回显 | 对非控制面用户置为固定占位串（脱敏串仍会漏出前后若干位，而这把 key 不属于他们） |
| 更新 / 删除 | 强制归属当前视角租户；非控制面用户不能改 default 共享记录 |
| 新建 | 显式落 `tenant_id`（拦截器不会自动补这一列） |
| 设为默认 | `clearOtherDefaults` 带租户条件，否则一个租户设默认会把所有租户的 `is_default` 清零 |
| 运行时按 ID / 自动选择 | `ModelConfigAccess` 只返回当前租户与 default；自动选择先本租户、后 default fallback |
| 缺租户上下文 | fail-closed 抛错，与租户维度整体取舍一致 |

> **`ModelConfigService` 与 `ModelConfigAccess` 是这张忽略表的补偿防线**——它刻意不在
> `DataScopeTables` 白名单里（见 `docs/数据权限设计.md`），没有拦截器兜底。绕过这两个入口直接调用
> Mapper，忽略清单不会报错；异步运行时若不传播 `TenantContext`，访问器会 fail-closed。
>
> 曾经发生过的事：忽略清单与本文档都写着"由 Service 层做两级可见性"，而 `ModelConfigService` 全文
> `tenant` 零命中——文档为一个不存在的控制盖了章，按本文档做安全评审的人会直接放行。
> 因此这条约定现在由回归测试锁住，不再只靠文字约定。

**为什么不把两级做成拦截器的通用能力**：`TenantLineInnerInterceptor` 对 SELECT/UPDATE/DELETE 共用同一个
`buildTableExpression`，一旦改成 `IN (租户, default)`，`UPDATE`/`DELETE` 也会放行到共享记录上，等于给租户开了越权写的口子。
一张表的手工过滤，好过全局的越权风险。

### 2.5 `sys_tenant_quota` 为何带列却不过滤

配额表带 `tenant_id`，但**刻意不参与自动过滤**：控制面用户要跨租户配额度，而租户管理员本就不该看到自己的额度设置
（能看到就离能改不远）。这与 §2.4 的方向相反——那张表是"放宽读、收紧写"，这张表是"整体不给租户看"。

访问控制因此落在 **Controller 的控制面角色 + 权限点校验**上。**给这张表新写任何查询接口，都必须复用该双重校验**：
拦截器不管、数据权限白名单也不含它，漏一处就是租户能自己调大付费额度。

### 2.6 控制面的跨租户视角

控制面用户需要跨租户看数据（租户列表、全局统计），而拦截器会强制把查询钉在某一个 `tenant_id` 上。
解决办法是 MyBatis-Plus 的 `@InterceptorIgnore(tenantLine = "1")` / `InterceptorIgnoreHelper`：
**跨租户查询走显式标注的专用 Mapper 方法**，且调用入口必须同时校验 `control_plane` 与对应权限点。

不采用"TenantContext 塞特殊值代表全局"的做法——那会让"忘记设置上下文"与"故意查全局"在代码上无法区分，
一处疏漏就是全量泄露。显式标注则是可 grep、可 review 的白名单。

控制面专属权限由 `ControlPlanePermissions` 集中定义，并同时用于三处：新租户开通时不授予、
普通用户读取角色权限树时不展示、`RoleService` 保存普通角色时拒绝重新授予。V63 还会清理存量普通角色的
对应关联；Controller 的 `CrossTenantAuthority` 复验仍是最终安全边界，不能因为权限关系已清理就删除。
`billing:view` 是刻意保留的租户自助权限：普通租户只能调用自己的账单接口，配额、定价、跨租户总览与归集仍为控制面能力。

当前敏感词运行时使用进程级单例过滤器，会合并各租户启用词。完成按租户分片前，新增、编辑、启停、删除与导入
统一要求控制面角色，避免普通租户写入高频单字影响其它租户；分页、详情和导出仍按当前租户读取。

## 3. 租户身份从哪来

现有 `TenantResolver` 从 `sessionId` 前缀猜租户，且**无分隔符时整个 sessionId 即租户**——
现网每个会话都是一个独立"租户"，这个类只服务于记忆分文件落盘，不能作为安全边界，本批次不再让它参与鉴权链路。

三个入口各自的权威来源：

| 入口 | 来源 | 说明 |
|---|---|---|
| 服务端接入方 | API Key → tenant 映射 | `ApiKeyAuthWebFilter` 鉴权成功后把 key 绑定的 `tenant_id` 写入上下文 |
| H5 用户端 | 登录态（token 内绑定） | 见下方说明 |
| admin 后台 | 登录用户的 `sys_user.tenant_id` + 角色 | `control_plane=1` 且具备对应权限点时可显式切换目标租户 |

**H5 的登录请求本身必须携带租户标识**（URL 参数或前端构建配置注入的 `tenantCode`），
否则服务端无从判断该拿哪个租户的用户表校验密码。这不是设计妥协——任何 SaaS 的登录入口都需要租户线索。
"不信任前端传参"约束的是**登录之后**：登录成功即把 `tenant_id` 焊进 token，后续请求一律从 token 取，
忽略前端再传的任何租户参数。

上下文载体 `TenantContext` 需双通道：客服端是 WebFlux（Reactor Context），admin 是 Spring MVC（ThreadLocal）。

## 4. 已知约束

### 4.1 框架自建表不受拦截器管辖

`ai_chat_session_state` 由框架 `MysqlAgentStateStore` 直接持有 `DataSource` 读写，**绕过 MyBatis**，
既加不了列也拦不住 SQL。因此不能再把 UUID“难猜”当授权：admin 工作区以 `ai_workspace_session` 固化
`tenant/agent/session/owner` 根归属，聊天、历史、附件、项目与 VibeCoding 入口统一先过 owner guard；进程内
Agent、历史缓存、执行模式、Plan 确认与工作目录也使用租户作用域 key。H5 会话则由 JWT 用户身份和
`UserSessionGuard` 校验 session 前缀归属。

本项目自己的只读分页查询（`ChatSessionStateQueryMapper`）走 MyBatis，因此该表必须进忽略清单，
否则拦截器会给它拼一个不存在的 `tenant_id` 列导致 SQL 报错；忽略仅解决表结构兼容，访问授权仍由上述
根资源 guard 承担。

### 4.2 IM 渠道的用户身份串扰

框架 issue #1966/#1764 的限制：多用户共享群场景下渠道侧用户身份可能串扰。
本批次按"每租户独立机器人/群"部署来规避（`ai_channel_robot` 已加 `tenant_id`），共享群场景的风险在部署文档中声明。

### 4.3 跨库同名表

`cw_agent_call_log` / `cw_agent_call_segment` 在客服端库与 admin 库各有一份（admin 复用 starter 的 Mapper）。
两边都要加列，且两侧拦截器都要生效，否则调用统计会串租户。

## 5. 存量数据

- `cw_*` 加列用 `NOT NULL DEFAULT 'default'`，存量行自动归入 `default` 租户，无需数据迁移脚本；
- `sys_tenant` 只保留 `default` 内置记录；
- V63 / V7 将遗留特殊租户的数据、共享配置与后台用户统一归入 `default`，V8 补齐客服端长期记忆、
  事实日志与语义缓存的遗留租户分区键；
- V63 给 `sys_role` 增加 `control_plane`，仅把已有 `super_admin`、`operator` 角色标记为控制面角色，
  并从其余角色移除控制面专属权限关系。

客服端库已由 starter 的 Flyway 管理。V2 会为全部 `cw_*` 表幂等补齐 `tenant_id`、租户首列索引并重建
六个租户内唯一键；存量库以版本 `0` 接管后自动执行。admin 库继续使用自身 Flyway，并按规范同步镜像到
`mysql/02-customer-admin/`。

V7 / V8 与 V63 涉及两库且 MySQL 多条 DML 不具备整份迁移级原子性。部署必须进入维护窗并先备份、停止旧版本写入，
按 **customer-work V7、V8 → admin V63 → 启动新代码** 的顺序执行；归并后无法可靠区分旧数据，回滚依赖备份。

三条迁移只处理精确旧值，不会把真实业务租户合并到 `default`：SQL 条件限定为
`tenant_id = '__platform__'`，V8 也只处理已经归入 `default` 且 `scope_id = '__platform__'` 的历史分区键。
上线前后的完整切换清单如下：

1. 停止旧 admin、customer-work 与发布 worker 写入，分别备份两库；先执行迁移冲突预检，任何唯一键冲突都先人工合并，
   不得用 `UPDATE IGNORE` / `REPLACE` 跳过数据。
2. 将 customer-work 实例的 `NACOS_TENANT_CODE` 改为 `default`，把
   `<baseDataId>-tenant-__platform__` 重新发布到 `<baseDataId>-tenant-default` 并核对 revision / content hash。
   新代码仅在 canonical dataId 缺失时兼容读取旧 dataId，不会自动覆盖或复制 Nacos 配置；确认全部实例已监听新 dataId 后再删除旧项。
3. 失效或轮换所有携带旧租户值的 Sa-Token 登录态、H5 JWT、Agent Token、Workbench Token 与 OpenAPI token 映射，
   让客户端重新取得 `default` 凭据。新代码会拒绝旧租户值，避免迁移后重新写回历史数据，但不会替客户端续签。
4. Redis 配额在最长一个保留周期内同时读取 `default` 与历史计数并求和，新增用量只写 `default`；当前最长月度窗口为
   40 天，旧键全部过期且账单核对一致后才能移除兼容逻辑。
5. VibeCoding 的 MinIO 工作区始终优先读取 `default` 对象；仅在新对象确实不存在时回读历史对象，验证归档后通过
   conditional put 安全复制。旧对象要保留到对象清单、数量与抽样 hash 核对完成，不能在发布当天直接批量删除。
6. V8 已迁移 MySQL 长期记忆、事实日志与语义缓存。当前 prod 门禁在长期记忆开启时强制 `provider=memory`；
   若升级前的历史环境或非生产环境曾使用 Mem0、ReMe、百炼，仍需按提供方能力将远端 userId 从旧租户值迁到
   `default`。外部 Provider 在补齐导出/擦除回执 SPI 前不能重新进入生产；短期 AgentState 保留旧 session scope，
   避免同一历史会话上下文中断。
7. 确认两库、Redis、MinIO、Nacos 与运行日志不再产生旧租户值后，再恢复流量；发现残留必须停写排查，不能执行
   `tenant_id <> 'default'` 一类会吞掉真实业务租户的清库 SQL。

旧版本曾允许 LDAP 首登默认绑定 `super_admin`。V63 不会静默删除既有合法管理员的角色关联；发布前必须审计
LDAP 用户已有的 `super_admin` / `operator`，按明确 allowlist 人工确认：

```sql
SELECT u.id, u.username, r.role_code
FROM sys_user u
JOIN sys_user_role ur ON ur.user_id = u.id
JOIN sys_role r ON r.id = ur.role_id
WHERE u.login_type = 'LDAP'
  AND u.deleted = 0
  AND r.role_code IN ('super_admin', 'operator');
```

Outbox/死信定时调度属于明确的跨租户运维扫描：领取与完成租约走 `CrossTenantOperations`，消息本身保存
`tenant_id`，执行 Handler 前用 `TenantContext` 恢复原租户并在结束后还原。不得把 Outbox 表加入忽略清单。

## 6. 租户开通时复制的种子

当前开通流程只创建 `sys_role.tenant_admin` 并授予租户安全权限。`cw_dict_type` / `cw_dict_item`、
`cw_sensitive_word`、`cw_rate_limit_rule` 位于另一物理库，尚未由 admin 开通事务自动复制；需要按租户单独维护。

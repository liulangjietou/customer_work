# 数据权限设计（租户 + 用户双维度隔离）

本文回答一个问题：**后台页面上，谁能看到哪些行**。

租户维度（"哪个租户的数据"）由 B1 的 `tenant_id` 行级过滤承担，见 `docs/多租户架构设计.md`；
本文只讲叠加在其上的用户维度（"这个租户里，谁的数据"）。两者正交，最终效果是"当前租户 + 本人"。

## 1. 三档数据范围

范围挂在角色上（`sys_role.data_scope`），不是写死在代码里：谁能看全量属于运营策略，会随组织变化，
焊进版本里意味着每加一个角色就要改代码发版。

| 取值 | 含义 | 默认落在谁身上 |
|---|---|---|
| `ALL` | 不受用户维度限制，且具备切换租户视角的资格 | `super_admin`、`operator` |
| `TENANT` | 本租户内所有成员的数据都可见 | `tenant_admin`（租户开通时自动创建） |
| `SELF` | 只看自己创建的个人产出物 | 其余一切角色，含新建角色的默认值 |

三条判定规则：

- **多角色取最宽**（`DataScope.widest`），与权限点的并集语义一致；
- **脏值回落 `SELF`**（`DataScope.parse`）。看得少是可修复的，看到全部租户是不可挽回的；
- **`ALL` 额外要求用户归属平台租户**（`DataScopeResolver`）。租户管理员能在自己租户里建角色，
  若只认字段值，任意租户建一个 `ALL` 角色就能越出本租户——这与 `AdminStpInterfaceImpl`
  对超管角色额外校验平台归属是同一个道理：凡是"能越出本租户"的判定，都不能只看租户自己能改的字段。
  服务端在 `RoleService#resolveDataScope` 保存时也拦一次，前端隐藏选项只是体验。

`ALL` 与 `TENANT` 在 SQL 层的效果相同（都不追加归属条件），差别在于**能否切换租户视角**——
后者由租户归属决定（`TenantSession.isPlatformOperator`）。跨租户的聚合查询仍走既有的
`CrossTenantOperations` 白名单，本功能不新开全局口子。

## 2. 强制点：`DataScopeInnerInterceptor`

复用 MyBatis-Plus 的 `BaseMultiTableInnerInterceptor`——它已经把 JOIN、子查询、UNION、WITH
里每一处表引用都遍历到位，自己解析 SQL 只会漏掉这些角落。改写结果形如：

```sql
SELECT * FROM ai_project WHERE status = 1 AND (create_by = 7 OR create_by IS NULL)
```

三个刻意的取舍：

- **不处理 INSERT**。归属列由 `MyMetaObjectHandler` 在字段填充阶段写入，那里能拿到完整登录态；
  拦截器在 SQL 层再补一次，两处都写迟早对不上。
- **处理 UPDATE / DELETE，不只是 SELECT**。只过滤列表页而不管写操作的话，用户虽然看不到别人的行，
  却能凭 ID 直接改删——`updateById` 只按主键定位，这是实打实的越权。加上条件后越权写影响 0 行。
- **`IS NULL` 视为租户内共享**。存量数据没有归属人，若一并挡掉，升级当天所有历史记录会从页面消失；
  而新产生的数据一律带归属人，随时间自然收敛。

### 没有上下文时不过滤，这与租户维度相反

租户缺失意味着"不知道该看哪个租户的数据"，放行等于泄露，所以 `TenantContext.require()` 是 fail-closed。
数据范围缺失则只出现在压根没有"人"的链路上——内置调度器、异步回调、脚本令牌回调、开放 API。
这些链路本就不是"页面数据"，对它们 fail-closed 只会把后台任务整体打挂，而跨租户那道防线仍由租户拦截器守着。

例外是**凭令牌进入的链路**：令牌背后是一个确切的人。`WorkbenchAgentController` 用
`DataScopeContext.callAs(userId, ...)` 显式还原身份，否则 A 的 ScriptCat 脚本能读到 B 录的站点密码
（`workbench_site` 行里存着目标系统的账号密码）。

## 3. 白名单：哪些表参与"仅本人"

**这里是白名单，与租户维度的黑名单方向相反，这是刻意的。**

租户维度"能加列的全加"，漏一张就是串数据；用户维度恰恰相反——绝大多数表是租户内共享的配置资产，
误加一张的后果是同租户成员之间协作断掉（A 建的智能体 B 用不了），而这种故障不会报错，
只表现为"数据莫名其妙少了"，比串数据更难排查。清单见 `DataScopeTables`，`DataScopeTablesTest` 把
"哪些表绝不能进白名单"钉成了断言。

| 表 | 归属列 | 页面 |
|---|---|---|
| `ai_project` / `ai_project_session` | `create_by` | 工作区 - 项目与会话 |
| `ai_chat_attachment` | `create_by` | 工作区 - 对话附件（正文会解析成文本落库，泄露面等同于对话内容） |
| `ai_code_knowledge_index` | `create_by` | 工作区 - 代码知识库 |
| `ai_code_review_task` / `ai_coding_audit_log` | `user_id` | 工作区 - 代码评审 / AI 编码审计 |
| `workbench_site` | `create_by` | 我的工作台 - 站点账号本 |
| `ai_scheduled_task` | `create_by` | 定时任务 |
| `sys_operation_log` | `user_id` | 系统管理 - 操作日志 |

刻意**不在**清单里的四类：

- **租户内共享的配置资产**：`ai_agent`、`ai_knowledge_base`、`ai_skill`、`ai_mcp`、`ai_model_config`、
  `ai_channel_robot`、`sql_*`、字典/敏感词/限流规则。它们虽有 `create_by`，但语义是"谁录的"而非"谁的"。
- **子表**：`ai_code_knowledge_chunk`、`ai_scheduled_task_run`、`ai_agent_*` 关联表。可见性跟随主表，
  查询一律带主表 ID，在子表上再挂一份归属列等于维护两套事实。
- **运行时产物**：`ai_agent_task`（框架子智能体后台任务）、`ai_channel_session`、`cw_agent_call_log`。
  产生于智能体运行线程而非 Web 请求，压根填不出归属人。
- **已在 Service 层按人过滤的**：`ai_site_message`（收件人）、`workbench_token`（持有人）。
  再加一层是重复防御，且这两张表的 `user_id` 语义不是"创建人"，混在一处只会误导。

## 4. 对话会话：框架表的变通

`ai_chat_session_state` 由框架 `MysqlAgentStateStore` 直接持 `DataSource` 读写、绕过 MyBatis，
既加不了归属列（框架不会填）也拦不住 SQL。而"别人的对话内容"恰恰是最敏感的页面数据。

变通是在 admin 侧单独记一份归属 `ai_chat_session_owner`（只记谁发起的，不记内容，框架换实现也不受影响）：

- **登记**在 `ChatService#chatStream` 的同步段完成——返回 `Flux` 后订阅发生在别的线程，那里拿不到登录态；
- **列表**用 `NOT EXISTS` 反向排除"明确属于别人的"会话，而不是正向匹配"属于我的"。
  正向匹配会让功能上线前、归属表里没有记录的存量会话整个消失，反向排除则把它们留在共享档，
  与 `create_by IS NULL` 的口径一致；
- **详情**在 `ChatHistoryService#getMessages` 里校验归属，且**必须在读缓存之前**——
  `ChatHistoryCache` 按 `(agentCode, sessionId)` 存，不含用户维度，先读缓存等于绕过校验；
- 该表**不进** `DataScopeTables` 白名单：那条 SQL 用的是反向条件，若拦截器再自动加一遍正向条件，
  两者 AND 起来恒假，排除条件会整个失效——比不过滤更糟，因为它看起来是生效的。

## 5. 打开租户开关的连带修复

`admin.tenant.enabled` 此前默认 `false`（跨租户数据完全打通），本批次改为默认 `true`。开关一开，
几条**没有登录态**的链路会因缺租户上下文 fail-closed，必须一并处理：

| 链路 | 处理 |
|---|---|
| 开放 API `/api/open/**` | 令牌是全局单值、不带租户，按 `admin.open-api.tenant-code`（默认 `default`）设上下文。**过渡方案**，要多租户接入应把令牌做成 `令牌 → 租户` 映射表 |
| 工作台脚本回调 `/api/workbench/agent/**` | 跨租户按 token 定位到令牌行，从行里读出租户与用户，再还原两个上下文 |
| 内置调度器 / XXL-JOB | 扫描任务走 `CrossTenantOperations`，执行前按任务所属租户还原上下文（`ScheduledTaskService#executeFromScheduler`）。手动触发不走这里——那是 Web 请求，上下文已由拦截器设好，直接调 `execute` 才能保证"只能触发自己租户的任务" |
| 登录页轮播图 `/api/login-images/**` | `login_carousel_image` 归入平台级忽略清单。登录页是平台统一入口，登录前没有任何租户上下文可用 |

同时补齐了 V49 遗漏的 7 张表的 `tenant_id`：`sql_datasource` / `sql_define` / `sql_define_param` /
`sql_field_transform` / `workbench_site` / `workbench_token` / `ai_config_version`。这些表既无列、
又不在忽略清单里，开关一开相关页面会当场 `Unknown column 'tenant_id'` 报 500。

## 6. 已知边界

- **生效时机**：范围在每次请求实时解析（`DataScopeInterceptor` → `DataScopeResolver`），
  改完角色立即生效，不需要重新登录；代价是每请求多两次索引查询，与既有的 Sa-Token 权限查询同量级。
- **`ai_chat_session_state` 本身不参与租户过滤**（框架表，B1 起即在忽略清单）。跨租户的会话隔离
  仍依赖 `session_id` 的 `{agentCode}:{uuid}` 命名不可猜，本批次只解决了同库内的用户维度可见性。
- **`ai_scheduled_task_run` 等子表**未挂归属列，知道主表 ID 即可读到执行记录。风险面小于列表泄露，
  但如需收紧，正确做法是在 Service 层带上主表归属校验，而不是给子表加列。
- **`ai_scheduled_task.task_code` 仍是全局唯一**。多租户下两个租户不能用同名任务编码，
  这既是约束也是 `executeFromScheduler` 能按 code 无歧义定位租户的前提；要放开必须同时给
  XXL-JOB 的任务参数补上租户维度。

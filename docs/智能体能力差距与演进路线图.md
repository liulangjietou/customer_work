# customer-work 智能体能力差距与演进路线图

> 审计日期：2026-09-04 ~ 09-05
> 审计对象：`main` 分支（AgentScope Java 2.0.0 GA）
> 审计方法：15 个能力维度并行测绘（代码为准）+ 独立业界基线对标 + 对抗性验证（默认立场「这条空白不成立」）
> 验证口径：本文把结论分成两档 —— **【实测】**表示审计者本人用 grep/读源码逐条核实过；
> **【待复核】**表示由审计智能体提出并给出了 `file:line` 证据，但未经二次人工核实，实施前应先复验。
> 这个区分是必要的：本次审计过程中已有两条智能体结论被核实后修正（见附录 B）。

## 摘要

三句话结论：

1. **这个项目的控制面已经做到了一流水准，运行面却有几处静默失效。** ModelOps 上线认证、EvalOps 发布门禁、在线实验护栏、SLO error budget、FinOps 账单对账、多租户与数据权限双维隔离、Trace Replay —— 这些能力都真实落在代码里而非文档承诺，放在同类产品里属于第一梯队。问题出在另一侧：**真实用户走的那条链路上，有六处能力是「装了但不生效」或「接在没人走的路上」**，而且全都不报错。

2. **最本质的结构性差距是「装配正确性没有运行时验证」。** `AgentAssemblyAlignmentTest` 是项目为「能力接错链路」这个已复发六次的缺陷形状设的唯一机器防线，但它是**文本扫描**——断言源码里出现过 `governanceAssembler.applyTo` 这个字符串。于是 `customer-channel` 调用了装配器、门禁通过、而装进去的中间件是**空集**。同类盲区还有：开关默认值与生产 yml 的实际取值没有门禁、SPI 有实现但零调用方没有门禁、提示词片段的实际内容没有门禁。本次审计发现的 P0 几乎全部落在这个盲区里。

3. **框架版本落后两个维护版，而这两个版本恰好修的都是本项目的痛点。** 项目锁 `2.0.0`，上游已到 `2.0.2`。v2.0.1 把 GLM/DeepSeek/Kimi/MiniMax 做成一等公民 provider（本项目至今走 OpenAI 兼容协议，而该路径会丢 system role）、新增 `MiddlewareBase.order()`（本项目 18 个中间件里只有 1 个带 `@Order`）、修了长生命周期 Agent 的内存泄漏；v2.0.2 允许 Channel 传入 `RuntimeContext`（本项目的「单租户群」部署限制正是因为这个缺口）。升级的收益远大于成本，但有一处藏在 "Refactored" 段落里的行为变更需要显式规避。

## 优先级判定原则

本文的优先级**不按技术先进性排，按对智能客服 SaaS 真实使用场景的影响排**：

| 档位 | 判定标准 |
|---|---|
| **P0** | 已在损害线上用户体验、或引爆条件只是一次配置变更、或它是多条其他改进的地基 |
| **P1** | 明显制约产品竞争力或运营效率，季度内应完成 |
| **P2** | 有价值但可等，或收益要到一定规模才显现 |
| **P3** | 锦上添花 |

两条排序细则：
- **已在线上跑、有真实用户的链路 > 尚未有人使用的扩展点**。所以「H5 用户走的 WS 流式链路」上的问题一律优先于后台工作台上的问题。
- **静默失效 > 显式报错**。会报错的问题运维能发现，静默失效的问题会以「智能体不太聪明」的形式存在很久。

## 第一部分 · 已验证的线上缺陷（P0，建议立即修）

这一部分的六条**全部经过实测核实**。它们不是「对标业界还差什么」，而是当前代码里已经存在、且不会报错的缺陷。

### P0-1【实测】生产环境的 RAG 会静默落到 4 条硬编码 demo 文本

**现状**：`customer-work-app-server/src/main/resources/application-prod.yml:73` 写的是

```yaml
rag:
  provider: ${RAG_PROVIDER:memory}
```

`memory` 对应 `InMemoryKeywordKnowledge`，它的语料是 `KnowledgeProvider.java:40` 里硬编码的 4 条字符串——七天无理由退货、发票开具、满 99 包邮、大额退款复核。打分函数是「查询里去重后的字符有几个出现在文档中」。

而 C 端建 Agent 的唯一入口 `CustomerServiceAgentFactory.java:238-240` 挂的正是这个 provider：

```java
if (properties.getRag().isEnabled()) {
    builder.knowledge(knowledgeProvider.get()).ragMode(RAGMode.AGENTIC);
}
```

**后果**：生产上线时若运维漏配 `RAG_PROVIDER` 环境变量，客服智能体的全部知识就是这 4 句话。后台那整套企业知识库（版本管理、ACL、新鲜度门禁、KnowledgeOps 同步、lineage）对线上对话**零影响**。而看板与后台会让运营以为知识库在工作。

这与 CLAUDE.md 里「完整镜像自带演示数据，上生产前必须清」是同一类问题的另一面——那条说的是数据库里的 demo 数据，有 `scripts/clear-demo-data.sh` 可清；这条是**代码里硬编码的 demo 知识**，没有任何脚本能处理，只能靠配对一个环境变量。

**为什么方向是错的**：生产默认值应当 fail-closed（配错就启动失败），而不是静默降级到 demo 语料。项目的 `AdminProductionReadinessValidator` 已经为邮件、Redis、记忆 provider 做了这类生产门禁，RAG 是同等重要的能力却没有进这道门。

**修法**（S，半天）：
1. `AdminProductionReadinessValidator` / `ProductionReadinessValidator` 增加一条：prod profile 下 `rag.enabled=true` 且 `rag.provider=memory` 直接拒绝启动，错误信息点名要配哪个环境变量。
2. `KnowledgeProvider` 里那 4 条 demo 文本移到 `src/test` 或加 `@Profile("!prod")` 守卫。
3. prod yml 里那行加注释说明它是必配项——按项目「yml 只写三类东西」的规范，这属于第②类（与 Java 默认值刻意不同的覆盖），必须写清理由。

### P0-2【实测】每一轮对话的系统提示词都在指示模型「暂不调用业务工具」

**现状**：`DialogStageMiddleware` 是 `@Component` 且**没有任何条件开关**，每轮把当前对话阶段的指令片段追加到系统提示词**末尾**：

```java
DialogStage stage = stageService.current(sessionId);
String note = String.format("%n%n[对话阶段] 当前处于%s", stage.promptFragment());
return Mono.just((currentPrompt == null ? "" : currentPrompt) + note);
```
（`core/middleware/DialogStageMiddleware.java:31-33`）

而 `DialogStageService` 的 `set()` 与 `advance()` 在**整个仓库的生产代码里零调用方**（只有 `DiagnosticService:92` 调只读的 `current()`）。状态机有完整的 SPI（接口 + InMemory + MyBatis 三件套）、有阶段流转定义（`GREETING→COLLECTING→PROCESSING→CONFIRMING`），但没有任何一处推进它。

于是每个会话永远停在初始态 `GREETING`，而 `GREETING` 的 `promptFragment()` 原文是（`capability/dialog/DialogStage.java:13`）：

> 「【接待识别】阶段：先理解用户意图，意图不清时主动澄清，**暂不调用业务工具**。」

**后果**：客服端每一轮对话，系统提示词末尾都写着「暂不调用业务工具」，而且位置在最后——越靠后的指令对模型行为影响越大。用户问「我的订单到哪了」，模型收到的最后一句指令是让它别调工具。

这条不会报任何错，只会表现为**工具调用率被无声压低、智能体倾向于反问澄清而不是直接查**。如果线上有「智能体总是先问一堆问题才干活」的反馈，病根很可能在这里。

**修法**（M，1 周）：两条路二选一，不要都做。
- **快路**：既然状态机没有写侧，先把 `DialogStageMiddleware` 从装配里摘掉（或给它加 `@ConditionalOnProperty` 默认关），消除这段负面提示。
- **正路**：把状态机接起来——在 `CustomerServiceService` 的对话回合里按「是否已识别意图/是否已收齐槽位/是否已确认」推进阶段。这条与 P1-4（槽位填充不在主链路上）是同一件事的两半，建议合并做。

无论走哪条，都应补一条门禁：**注入提示词的中间件，其注入内容必须有测试断言**。当前 `AgentAssemblyAlignmentTest` 只管「有没有装」，不管「装进去说了什么」。

### P0-3【实测】IM 渠道的治理中间件全部失效

**现状**：`AgentGovernanceAssembler#applyTo` 里只有两个中间件是直接 `new` 的（生命周期、可观测），其余全部走容器：

```java
if (pluggableMiddlewares != null) {
    pluggableMiddlewares.orderedStream().forEach(builder::middleware);
}
```
（`core/agent/AgentGovernanceAssembler.java`）

而 `customer-channel` 用 `@SpringBootApplication` 只扫自己的包，starter 里带 `@Component` 的中间件全部不会被注册。该模块里**一个 `MiddlewareBase` Bean 都没有**——代码注释自己写明了这一点：

> 「装到的可插拔中间件取决于本容器里实际存在多少 `MiddlewareBase` Bean」
> （`customer-channel/.../CustomerWebAgentConfig.java:69`）

**后果**：钉钉、企微、微信、飞书四条对外渠道的对话上，以下能力全部缺失：

| 缺失能力 | 中间件 | 后果 |
|---|---|---|
| 出站敏感词过滤 | `SensitiveWordMiddleware` | 违规内容直接发给客户 |
| PII 脱敏 | `MaskingMiddleware` | 手机号/订单号原样外发 |
| 提示词注入防护 | `PromptInjectionGuardMiddleware`、`IndirectInjectionGuardMiddleware` | 渠道是对外入口，恰恰最需要 |
| 租户上下文 | `TenantContextMiddleware` | 持久层隔离依赖它 |
| token 计量与分段耗时 | `AgentCallTimingMiddleware` | **该链路用量既不进配额也不进账单** |
| 审计留痕 | `AuditMiddleware` | 对外渠道无审计 |
| 工具授权 | `SubjectToolAuthorizationMiddleware`、`ToolGuardMiddleware` | 工具越权无闸门 |

IM 渠道是面向真实客户的对外入口，却是全项目治理最薄弱的一条链路。

**门禁为什么没挡住**：`AgentAssemblyAlignmentTest` 是纯文本扫描——它检查源码里有没有 `"governanceAssembler.applyTo"` 这个字符串（第 53 行），以及装配器源码里有没有 `"pluggableMiddlewares"` 这个词（第 144 行）。channel 确实调了 applyTo，所以门禁通过。它回答不了「运行时解析出几个 Bean」。

**修法**（M，1 周）：
1. channel 模块显式声明所需的 `MiddlewareBase` Bean（这是该模块复用 starter 能力的既定方式，`chatModel`/`agentStateStore` 都是这么做的）。注意 CLAUDE.md 记着 admin 有自己的 `SensitiveDataMasker`，声明同名 Bean 会抛 `BeanDefinitionOverrideException`——channel 侧要先确认命名不冲突。
2. **门禁升级为运行时断言**：用 `ApplicationContextRunner`（channel 是 Servlet 栈，注意不要误用 `ReactiveWebApplicationContextRunner`）断言各模块容器里 `MiddlewareBase` Bean 的数量与种类下限。这条比第 1 条更重要——它是防止同类问题第八次复发的唯一办法。

### P0-4【实测】MCP 注册在客服端没有超时，而同一个坑 admin 已经修过

**现状**：客服端两个装配器里有四处**裸 `.block()`**：

- `tool/McpToolkitConfigurer.java:91`（buildClient）与 `:96`（registerMcpClient）
- `tool/HigressToolkitConfigurer.java:56` 与 `:58`

而 admin 侧同一段逻辑是带超时的，并且注释里完整记录了故障现场（`AdminAgentInstanceFactory.java:797-802`）：

> 「必须显式给 `.block(...)` 传超时——不传时 `Mono.block()` 会无限等待，一旦某个 MCP 服务握手卡住（比如服务端不支持可选的 SSE 长连接导致 SDK 内部状态卡死，见批次六联调排查），整个 `/chat/stream` 请求线程会跟着永久挂起、前端界面看起来『没有响应』，且不会抛出任何异常——下面的 try/catch 根本等不到超时异常被抛出」

也就是说**这个故障在本项目上真实发生过一次，admin 修了，而它参考的来源 starter 至今没修**。

**为什么是 P0 而不是 P2**：`customer-work.mcp.enabled` 与 `higress.enabled` 当前默认都是 `false`，所以还没在线上爆炸。但 MCP 服务列表是可以经 Nacos 运行时配置下发的（`RuntimeConfigApplier` 会应用 `mcpServers`）——**运营改一次配置就能在不动代码的情况下把这颗雷引到 H5 主链路上**。P0 的理由不是「现在坏了」，而是「引爆条件是一次配置变更，引爆后查不出来」。

叠加的问题：MCP 注册压在 `resolveAgent` 的每会话建 Agent 路径上（`CustomerServiceService:779-782` → `CustomerServiceAgentFactory:178-194`），即每开一个新会话就为每个 MCP 服务重新握手一次。

**修法**：
- 立即（S，半天）：四处 `.block()` 全部改带超时，超时值下沉成常量类与 admin 的 `MCP_REGISTER_TIMEOUT` 收敛成同一个定义处（正是项目「同一个字面量只允许一个定义处」规范的适用场景）。
- 结构性（M，2 周）：`McpClientPool` 进程级复用已连接客户端，Agent 装配路径上只剩「取一个已就绪客户端」。**框架边界**：`Toolkit.registerMcpClient` 只接受 `Mono<Void>`，没有「一个客户端 attach 到多个 Toolkit」的入口，`McpClientWrapper.close()` 又是终结性的，需要在 wrapper 外包一层引用计数壳，并保证 `ManagedToolkit.close()` 只做归还不做关闭。
- 门禁（S）：照 `SharedConstantAlignmentTest` 的模式加源码扫描——MCP/Higress 装配路径上出现无参 `.block()` 直接红。

### P0-5【实测】生产环境下长期记忆整条链路静默空转

**现状**：`application-prod.yml:64` 强制 `consent-required: true`，`MemoryConsentService.isGranted` 查不到同意记录时 `orElse(false)` 是 fail-closed。全仓唯一能授权的入口是 `UserPrivacyController` 的 `grant`，而 H5 用户端 `customer-work-app/src/` 里**没有任何代码调用它**（grep `privacy` 只命中 `CsatSurveyCard.vue` 里的 CSS 类名 `privacy-note` 和一句文案）。

**后果**：按当前代码上生产，每个真实用户的 `GovernedLongTermMemory.record` 都走 `Mono.empty()`、`retrieve` 都返回空串。`cw_long_term_memory` / `cw_fact_log` 表照建、保留期清理任务照跑、日志一行不报错。三层记忆里的 L2/L3 在生产等于不存在。

这是「能力只接在用户不走的那条路上」的一个变体——这次不是接错链路，而是**开关的另一半（用户授权入口）没有交付到用户手里**。后端接口齐备、合规设计完整（同意版本、导出、撤回并删除、保留期清理），唯独少了前端那个勾选框。

**修法**（S，2-3 天）：H5 用户端补记忆授权入口——首次进入或首次触发记忆写入时弹一次同意说明，调 `/api/customer/user/privacy/memory-consent`。同时补一条门禁：**声明了「生产必须开启」的开关，其开启路径必须有可达的调用方**。

### P0-6【实测】长会话上下文没有上界，而唯一的收敛手段开了会踩雷

**现状**分两半：

*膨胀侧默认全开*：`RagProperties.enabled=true`、`MemoryProperties.longTermEnabled=true` 且 `CustomerServiceAgentFactory` 用 `LongTermMemoryMode.BOTH` 每轮静态注入、`maxIters=10` 允许十轮工具结果堆叠。

*收敛侧全部关闭或无调用方*：
- `ContextProperties.budgetEnabled=false`（`infra/config/properties/ContextProperties.java:36`），生产 yml 里也没打开；
- 模型驱动的 `Compaction` 只能挂 `HarnessAgent`，而 `HarnessAgentFactory.createHarnessAgent` 在 `src/main` 下**零调用方**（只有 5 个测试方法在调），所以 prod yml 里那句 `compression-enabled: true` 不接任何链路；
- `ToolResultEviction` 对应框架 issue #1695，项目已明确不依赖它。

`ContextBudgetMiddleware` 的类注释自己把这个失衡描述为它要修的问题——但它本身也是默认关的，问题原封不动留着：默认配置下一条长会话没有任何上下文上界，一路涨到厂商报 `context length exceeded` 为止，而 `ResilientChatModel.java:73` 拿到这个错只决定「不重试」，没有 trim-and-retry、没有降级到更大窗口的模型、没有触发压缩。

**而开启它又有一个真实的 bug**：`ContextProperties:34` 的 javadoc 写着「生产部署建议显式开启」，但 `trim()` 的实现是——把消息按 `isPinned`（SYSTEM + SYNTHETIC）分成两组，非 pinned 的那组做纯位置切分：

```java
kept.addAll(budgeted.subList(0, keepEarliest));
kept.addAll(budgeted.subList(budgeted.size() - tailCount, budgeted.size()));
```

整个文件里 `ToolUseBlock` 与 `ToolResultBlock` 出现次数为 **0**。这个切法会把一条 assistant 的 `tool_use` 与它对应的 `tool_result` 切散，而多数厂商对孤立的 `tool_result` 直接返 400。文档在引导用户踩这个雷。

**修法**（M，1-2 周）：
1. `trim()` 增加工具配对保护：切分前先把 `tool_use` 与其 `tool_result` 绑成不可分割的单元。这是开启该中间件的前置条件。
2. 预算单位从「消息条数」改为「token 估算」，与模型实际窗口挂钩（`getContextWindowSize()` 当前有 6 个消费方，全都只在装饰器之间向上转报，没有一处拿它和本次消息体量做比较）。
3. `ResilientChatModel` 在识别到 context length exceeded 时补一次 trim-and-retry，而不是直接放弃。
4. 评估把默认值改为开启——但必须先做完第 1 步。

## 第二部分 · 能力空白（对标业界先进实践）

这一部分是「对标业界还缺什么」，与第一部分的「已经坏了」性质不同。除标注【实测】外均为【待复核】。

### P0 档

#### 空白 1【待复核】工具执行没有超时、重试与降级

框架唯一的工具环绕点 `Tracer.callTool` 被实现成了纯日志——`LoggingTracer.java:38-46` 只做 `action.get().doFirst(打日志).doFinally(打日志)`，连传进来的 `ToolCallParam` 都没用，日志内容是固定字符串 `span start tool-call`，工具名都没记。

全仓 `retryWhen`/`Retry.backoff` 只出现在两处：`ResilientChatModel:43`（模型调用）与 `DeadLetterService:183`（死信队列），**工具执行一次都没有**。本地 `@Tool`（23 个方法，背后是 `MybatisOrderBackend` 这类同步 JDBC）没有任何超时；MCP 工具靠 SDK 的 `requestTimeout`（30s）勉强兜住；admin 的 `HttpClientTools` 里 grep 不到任何 Timeout。

智能客服的工具背后是订单库、售后系统、会员系统这些真实业务后端，它们会慢会挂。项目在模型侧做了 failover、熔断、分级路由一整套弹性，**工具侧一样都没有**——而客服场景里工具失败对用户体验的伤害不比模型失败小。

**方案**：新增 `ToolExecutionPolicy`（per-tool 超时/重试/退避/降级文案），走 Store SPI 模式落客服端库；执行侧新增 `ResilientToolTracer implements Tracer`。**选 Tracer 而不是中间件是有理由的**：`Tracer` 由框架在每次工具调用处回调，天然覆盖全部 7 条链路（含 channel 那条中间件为空的），而 `MiddlewareBase.onActing` 是整批粒度、且在 channel 上根本没装配。

**框架边界**：`TracerRegistry` 是全局静态单例，`TracingConfig:41-48` 的注册既受 `observability.tracing-enabled` 开关控制，又在 OTel 开启时**主动跳过注册**（避免 span 出两份）。也就是说「工具执行环绕能力」被绑死在可观测开关上，**生产开 OTel 时这个环绕点根本不存在**。改造必须先把 Tracer 注册从可观测开关里独立出来。

#### 空白 2【实测局部】受管知识库检索是「全量拉进 JVM + Java 里暴力算余弦」

`ManagedKnowledgeSearchService.java:82-108` 的执行序列：查版本成员 → 过 ACL → **把该版本下全部已授权 chunk 一次性 `selectList` 捞进内存**（无 limit、无分页）→ 逐条 `objectMapper.readValue(chunk.getEmbedding(), float[].class)` → `VectorMath.cosine` 在 Java 里逐条算分 → 内存排序 → `limit(topN)`。

按 1024 维、1 万 chunk 估算，单次提问要从 MySQL 拉出并解析约 40MB 的 JSON 浮点文本、做 1000 万次浮点乘加，**而且是在请求线程上同步做的**。

今天它只打在 admin 工作台（低频、内部员工）所以没炸。**一旦空白 3（知识栈打通）修好，同一段代码就会挂到每个 H5 用户的每一轮对话上**——那时它既是首字延迟的主要来源，也是一次知识库扩容就能触发的 OOM 事故点。项目在流式卡顿那次已经踩过同源教训（每层都重算本可缓存的东西）。

**方案**：定义 `VectorStore` SPI（照已套用 8 次的 Store SPI 模式），向量列从 JSON 文本改为定长 `VARBINARY`（1024 维 float32 = 4KB，比 JSON 小约 3 倍且零解析开销），为后续接 Qdrant 留替换位。**无框架依赖**。

#### 空白 3【实测】客服端与后台是两套互不相通的知识栈

见 P0-1。补充一点：C 端那条工具路径 `KnowledgeBaseTools` 查的是 `cw_knowledge` 表，SQL 是 `KnowledgeMapper.xml:9-11` 的三列 `LIKE CONCAT('%', #{q}, '%')`。**中文整句 LIKE 的召回率接近 0**——只有用户恰好复述了知识条目里的连续子串才命中。

**方案**：运行时要读的表放客服端库（照内容风控三表、`cw_tenant_quota` 的先例），新建 `cw_knowledge_chunk` / `cw_knowledge_version`，admin 侧经 `CustomerWorkFacade` 写入，从根上取消「starter 反向读 admin 库」这个不成立的方向。

#### 空白 4【待复核】WebSocket 下行推送是进程内的，多副本下坐席回复静默丢失

`WsSessionRegistry` 是进程内 Sink 注册表。多副本部署时，坐席在 A 副本回复、用户 WS 连在 B 副本，消息发不出去且不报错。项目已经为水平扩展做了 `WindowCounter`/`SessionLock` 的 Redis 实现，但下行推送这条没做。

#### 空白 5【待复核】优雅停机是空转的

`GracefulShutdownService` 接了框架的 `GracefulShutdownManager`，但框架的在途请求登记中间件从未装配，导致 `awaitTermination` 恒立即返回并打印「完成=true」。滚动发布时会截断在途对话。

#### 空白 6【待复核】视觉 OCR 模型整条链路绕开 ModelOps 治理

凭据不轮换、无上线认证、无 failover、token 零计量、租户不隔离。项目为对话模型建了极完整的 ModelOps（认证/健康/路由/影响分析），OCR 模型完全在体系外。

#### 空白 7【待复核】自我纠错实为「检测 + 打一行日志」

`SelfCorrectionMiddleware` 检测到模型的越权资金承诺后只打日志，内容照原样发给用户，且默认整体关闭。

### 3.2 升级能直接解决的既有痛点（按价值排序）

#### A. GLM / DeepSeek / Kimi / MiniMax 成为一等公民 provider —— 解决"上下文窗口=0"的病根

**现状**：项目 `ModelProviders` 只定义 5 个 provider（`dashscope` / `openai` / `anthropic` / `gemini` / `ollama`），GLM、DeepSeek 等国产模型**一律走 OpenAI 兼容协议**接入。

这正是 PR #154 那个缺陷的病根。三处代码注释都记录了同一件事：

- `ChatModelFactory.java:51` —— 「第三方模型（glm / deepseek / 自建网关）走 OpenAI 兼容协议时一律推断为 0，而 0 会被下游…」
- `AdminModelFactory.java:130` —— 「框架的推断表只收录各厂商官方模型名」
- `AgentScopeModelCertificationProbe.java:115` —— 「第三方模型一律查不到返回 0」

**v2.0.1 提供**：
- `Add DeepSeek as first-class provider` (#2307, #2211)
- `Add GLM (Zhipu AI) provider with dedicated formatters` (#2316)
- `Add Kimi (Moonshot AI) provider with dedicated formatters` (#2320, #2213)
- `Add MiniMax OpenAI-compatible provider` (#2299)
- `Add OpenAI-compatible extension package for third-party vendors` (#2208)

**为什么"专用 formatter"比"OpenAI 兼容"重要**：同一份 release notes 里还有一条修复——`DeepSeek formatter: preserve system role` (#2189, #2168)。也就是说走通用兼容路径时，**system role 会丢**。系统提示词是客服智能体全部行为约束的载体，丢 system role 意味着人设、边界、话术规范在那一次调用里全部失效——而这不会报错。

**改造动作**：
1. `ModelProviders` 增加 `glm` / `deepseek` / `kimi` / `minimax` 四个常量（注意 CLAUDE.md 的"同一字面量只允许一个定义处"约定，该常量类当前在 4 处重复定义了同一组值，本次一并收敛）。
2. `ChatModelFactory` / `AdminModelFactory` 增加对应分支，改用原生 provider 构建。
3. **保留** `buildModelWithWindow` 的显式窗口注入——它仍是自建网关等未收录模型的唯一正确解，只是不再需要为 GLM/DeepSeek 兜底。
4. 复核 `AgentScopeModelCertificationProbe`：这些模型进入推断表后，"先声明后实测"的窗口判定应能走通声明路径。
5. 后台"模型资产"页面的 provider 下拉需要同步扩项，`ai_model_asset` 已有数据的 provider 字段要评估是否迁移。

**价值**：国产模型是本项目最可能的生产模型选择，让它们从"兼容模式凑合用"变成"一等公民"，直接影响 function calling 成功率、结构化输出可靠性与 system role 保真。

---

#### B. `MiddlewareBase.order()` —— 给 18 个自研中间件一个显式的顺序契约

**现状**：项目有 18 个自研中间件，全部由 `AgentGovernanceAssembler#applyTo` 按**代码书写顺序**装配，没有任何显式的顺序声明（grep `order()` 结果为空）。

这是一个已经踩过同类坑的形状。CLAUDE.md 里记着：`SubjectQuotaWebFilter` 的 Order 必须排在两个鉴权过滤器之后（`+30` > ApiKey `+10` > UserAuth `+20`），抢在前面会把登录用户全按匿名 IP 限流。中间件侧存在完全对称的风险——例如 `MaskingMiddleware` 与 `ObservabilityMiddleware` 的相对位置决定了**未脱敏内容会不会进 trace**，而顺序写反不会报任何错。

**v2.0.1 提供**：`Middleware execution ordering via MiddlewareBase.order()` (#2532, #2449)。

**改造动作**：给 18 个中间件各声明 `order()`，把"为什么这个中间件必须在那个之前"从隐式的代码行序变成可断言的显式契约，并在 `AgentAssemblyAlignmentTest` 里加一条断言（新增中间件不声明 order 就红）。这与项目"单一真相来源"的既有约定同源。

**价值**：中等偏高。它不解决当前的 bug，但把一类"改了不报错、只在特定场景炸"的风险变成编译期/测试期可见。

#### C. 长生命周期 Agent 的内存泄漏修复 —— 生产硬需求

**v2.0.1 修复**：
- `Unbind ShutdownStateSaver on close to fix memory leak` (#2384)
- `Unbind state-saver on ReActAgent.close()` (#2322, #2321)
- `Expose ReActAgent state-cache cleanup APIs for long-lived instances` (#2572)

**为什么对本项目要紧**：这是一个多租户 SaaS，Agent 实例按租户/会话复用且进程长期运行，正是 #2572 描述的 "long-lived instances" 场景。项目已有 `AgentResourceCloser`，说明资源回收这条线本来就在关注，但 2.0.0 上 `close()` 不解绑 state-saver 这个泄漏是**应用层修不掉的**。

**改造动作**：升级后复核 `AgentResourceCloser` 是否需要改为调用新暴露的 state-cache 清理 API。

#### D. HITL 审批链路的两个修复

**v2.0.1 修复**：
- `Prevent pending recovery from consuming HITL approvals` (#2109, #2534)
- `Emit UserConfirmResultEvent when resuming permission HITL` (#2511)

项目的 `HumanApprovalMiddleware` + `capability/approval` 是退款等高风险操作的闸门。"pending recovery 消耗掉 HITL 审批"意味着**一次审批可能被恢复流程吃掉**，用户看到的是审批没生效或重复弹出。升级前建议在测试环境重放一次"审批 → 进程重启 → 恢复"的场景确认现状。

#### E. Channel 传入 RuntimeContext —— 有条件地解除"单租户群"部署限制

**现状**：`docs/customer-channel操作文档.md:205` 有一段诚实声明——对照框架 #1966/#1764，Channel 无法把 IM 平台侧真实用户身份映射进 `RuntimeContext`，因此**生产建议按单租户群部署**（一个群只对应一个业务身份）。实测佐证：`customer-channel` 整个模块里 `RuntimeContext` 出现 **0 次**。

**上游变化**（需要精确区分，不能夸大）：
- v2.0.2 新增 `feat(channel): allow callers to pass RuntimeContext into Gateway` —— 给了**调用方主动传入**的口子。
- issue **#1966 仍 open** —— 框架**不会**自动把 InboundMessage 里的平台身份映射进 RuntimeContext。
- issue **#1764 已 CLOSED（2026-07-24）** —— AguiAgentAdapter 可以设置 RuntimeContext 了。

**结论**：升级到 2.0.2 后，"单租户群"限制**可以由项目自己解除**——因为钉钉/企微/微信的连接器本来就在自己解析消息（`DingTalkStreamConnector`、`WeChatCallbackController` 等），平台用户 ID 就在手里，缺的只是一个传进去的口子，而 v2.0.2 补上了这个口子。这不是"等框架修好"，是"框架给了接口，项目做映射"。

**改造动作**：在 `ChannelMessagePipeline` 里把平台用户标识解析为业务身份，构造 `RuntimeContext` 传入 Gateway；同步更新操作文档里的生产边界声明。

**价值**：高。企业客服群天然是多人的，"一个群一个身份"这个限制实际上挡住了 IM 渠道最主流的用法。

### 3.3 升级的破坏性风险：Toolkit 默认改为并行执行

**v2.0.1 refactor**：`Change Toolkit default execution mode to parallel` (#2558, #2529)

这是整次升级里**唯一会改变线上语义的变更**，且它藏在 "Refactored" 段落而不是 "Breaking Changes" 里。

项目当前注册 7 组业务工具（`OrderTools` / `MemberTools` / `ProductTools` / `AfterSalesTools` / `ComplaintTools` / `HumanHandoffTools` / `KnowledgeBaseTools`）。工具实现本身是 `Mono` 异步、无共享可变字段，单看代码并行是安全的。真正的风险在**工具之间的业务语义**与**中间件的判定语义**：

1. **审批语义**：模型一轮里同时发起"查订单"和"发起退款"两个工具调用时，`HumanApprovalMiddleware` 会拦住退款，而查询已经跑完。串行模式下这个交错不会出现。审批被拒时另一个工具的副作用是否需要回滚，当前链路没有这个概念。
2. **转人工的幂等**：`HumanHandoffTools#transferToHuman` 与工单创建并行触发时是否会产生两条记录。
3. **配额与计量**：`AgentCallTimingMiddleware` 是 token 的唯一落点，并行工具调用下的分段耗时统计口径会变。
4. **租户上下文传播**：并行执行意味着工具跑在不同线程上，而本项目已经在这个形状上栽过——CLAUDE.md 记着"异步回调要显式恢复租户上下文"这条约定**已复发一次**（知识库连通性测试）。工具并行化会新增一批需要显式传播 `TenantContext` / `QuotaSubjectContext` 的位置。

**升级动作**：升级时**先显式把执行模式设回串行**，把行为变更与版本升级解耦；并行化作为独立批次单独评估、单独回归。这符合项目"一个批次一个 PR + 全量回归"的既有节奏。

### 3.5 升级建议

**分两个批次，不要合并**：

**批次 A（纯升级 + 回归）**：`2.0.0 → 2.0.2`，显式固定 Toolkit 为串行执行，不改任何业务代码。验收标准是全量测试（约 3654 用例）全绿 + 7 条链路的手工冒烟。这一批拿到的是内存泄漏修复、HITL 加固、流式稳定性修复（`JdkHttpTransport` SSE 绝对超时 #1322、OpenAI `[DONE]` 哨兵 #2104、`Flux.defer` 重试 #2079）——全是白拿的生产收益。

**批次 B（能力接入）**：国产模型一等公民接入 + 中间件 order 契约 + Channel 身份映射。每项独立可回滚。

**不建议在这两批里做的**：Toolkit 并行化（独立评估）、子智能体路线重估（框架侧 #1953/#1954/#1700/#1911 仍 open，自研 orchestrator 的规避仍然是对的）。

## 第四部分 · 分批实施路线图

批次划分遵循项目既有节奏：**一个批次一个 PR + 全量回归（约 3654 个用例）**。P0 项集中在前两批。

### 批次一：止血（S~M，约 1 周）

目标是把「已经在损害线上、但改动量很小」的几条先关掉。这一批不引入任何新架构，全部是开关、超时、守卫。

| 项 | 动作 | 工作量 |
|---|---|---|
| P0-1 | 生产门禁拒绝 `rag.provider=memory`；demo 语料加 `@Profile("!prod")` | S |
| P0-2 | `DialogStageMiddleware` 加条件开关默认关（正路留到批次三） | S |
| P0-4 | 四处 `.block()` 补超时 + 常量收敛 + 源码扫描门禁 | S |
| P0-5 | H5 补记忆授权入口 | S |
| P0-6a | `trim()` 补 `tool_use`/`tool_result` 配对保护 | M |

**验收**：全量测试绿 + 7 条链路手工冒烟 + 一次 prod profile 启动验证（应在缺 `RAG_PROVIDER` 时明确失败）。

### 批次二：装配正确性与框架升级（M，约 2 周）

这一批解决摘要里说的「最本质的结构性差距」，并把框架升上去。两件事放一批是因为它们都要动装配层，合并可以少一次全量回归。

| 项 | 动作 | 工作量 |
|---|---|---|
| P0-3 | channel 显式声明 `MiddlewareBase` Bean | M |

| 兼容-A | `2.0.0 → 2.0.2` 纯升级，**显式固定 Toolkit 为串行执行** | M |
| 兼容-B | 18 个中间件声明 `MiddlewareBase.order()` + 顺序契约断言 | M |

**验收**：全量测试绿 + 中间件顺序断言覆盖全部 18 个 + channel 链路实测确认脱敏与敏感词生效。
**回滚点**：框架升级与中间件改造应是两个独立 commit，便于二分。

### 批次三：知识链路重做（L，约 4-6 周）

这是投入最大的一批，但它决定了这个系统「聪不聪明」。**顺序不能反**——先建向量存储再打通链路，否则 P0-1 修好的当天就会撞上空白 2 的性能墙。

1. `VectorStore` SPI + `VARBINARY` 向量列 + Flyway 迁移 + schema 快照刷新（空白 2）
2. `cw_knowledge_chunk` / `cw_knowledge_version` 落客服端库，admin 经 `CustomerWorkFacade` 写入（空白 3）
3. C 端知识检索切到受管知识库，`KnowledgeRetrievalProvider` 接入主链路
4. 结构化引用回传（P1-6）
5. 对话阶段状态机接上写侧 + 槽位填充接入主链路（P0-2 正路 + P1-4）

**验收**：需要先建立检索质量基线——这批的验收标准不能只是「测试绿」，要有一组固定 query 的召回率对比。

### 明确不建议现在做的

## 附录 A · 审计方法与覆盖度

**方法**：15 个能力维度（规划推理/多智能体/上下文工程/记忆/工具与MCP/RAG/评测/可观测/安全治理/模型层/运行时/渠道交互/业务闭环/平台多租户/工程交付），每个维度并行做两件独立的事——一个 agent 读源码测绘现状，另一个 agent 在**不看本项目代码**的前提下梳理业界基线（避免锚定）；交叉出候选空白后，每条派一个「默认立场是这条不成立」的怀疑者做实现性反驳 + 价值反驳。

**实际执行**：因两次触及会话用量上限，完整的 15 维流程只跑完了多智能体、记忆、上下文三个维度的深度测绘；工具/RAG/模型多模态/运行时/规划推理五个维度改用收敛后的单阶段扫描完成；其余七个维度（评测、可观测、安全治理、渠道交互、业务闭环、平台多租户、工程交付）**未做独立测绘**——这些恰好是审计者已通过 grep 独立确认为强项的维度（ModelOps/EvalOps/SLO/FinOps/多租户/数据权限/Trace Replay 均已真实落地），但**不排除其中仍有未发现的空白**。这是本次审计的覆盖度边界，如实声明。

**验证深度**：标【实测】的 10 条由审计者本人核实。其余条目有 `file:line` 证据但未二次核实。

## 附录 B · 审计过程中被修正的结论

保留这一节是因为它说明了为什么「智能体给出的结论必须复核」：

## 附录 C · 本次审计确认的强项

写下来是为了让上面的差距清单有个参照系。以下能力均经 grep 核实真实落地在代码里，不是文档承诺：

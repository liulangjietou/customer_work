## 二、已实测排除的风险（P0 探针，commit `3128108`）

以下 issue 描述的现象，在本项目实际调用路径下**编写探针测试并实测未复现**：

| Issue | 描述的风险 | 实测结论 |
|---|---|---|
| #1941 / #1675 | 同步 `call()` 不触发 `onAgent` 中间件钩子 | **未复现**。实测 `call()` 与 `streamEvents()` 均触发 `onAgent`（各 1 次），主链路挂载在 `onAgent` 上的脱敏（Masking）、可观测（Observability）等中间件正常生效。 |
| #1681 / #1619 / #1623 | 多租户状态被错误归入 `_default`/`default` 命名空间，导致跨租户状态泄漏 | **未复现**。状态按 `(userId, sessionId)` 正确隔离，落盘路径为 `<root>/<userId>/<sessionId>/agent_state.json`，跨租户不可见，未观察到 `_default`/`default` 命名空间污染。 |

对应测试：
- `MiddlewareInvocationVerificationTest`
- `TenantIsolationVerificationTest`

这两个探针已经**固化为回归测试**，随每次 `mvn test` 常态化运行。其价值不止是"证明当前版本没问题"，更重要的是：**升级到 RC5 / GA 时，如果上游改动导致这两个行为发生漂移（钩子不触发了，或者隔离失效了），测试会立刻红，起到显式的行为漂移告警作用**，不需要靠线上事故才能发现。

## 四、靠架构决策天然规避的风险

以下几类风险不是靠"打补丁"规避的，而是本项目在架构设计阶段就选择了不依赖框架对应能力，因此这些 issue 描述的缺陷天然不在本项目主链路上：

| Issue | 框架侧的问题 | 本项目的架构决策 |
|---|---|---|
| #1726 | AG-UI 协议下框架无法完成"权限确认"闭环（前端拿不到标准的确认交互） | 人工审批闭环（HITL）不绑定框架的 `CONFIRM_SINK_KEY`，而是落在**应用层**：新增 `approval` 包（`PendingApprovalService` + `ApprovalRequest` 状态机）与 `ApprovalController`（`GET /approvals`、`POST /approvals/{id}/approve\|deny`），退款等高风险工具登记待审单、人工放行后回调执行，形成"挂起 → 人工决策 → 生效"的完整闭环，不依赖框架尚未打通的 Web 友好确认 API。**GA 后新证据**：[#2024](https://github.com/agentscope-ai/agentscope-java/issues/2024)（2026-07-09 提交，仍 open）报告 `AguiAgentAdapter` 对外部工具挂起（`SchemaOnlyTool`/`TOOL_SUSPENDED`）的 AG-UI 语义映射有 bug，导致 CopilotKit 前端 HITL 弹不出确认 UI——反向印证了当初"不绑定框架 AG-UI 确认机制"是正确判断，而非过度设计 |
| #1850 | 框架内置 `ReActAgent.Builder.fallbackModel(...)` 存在已知缺陷，实际不工作 | 使用**自研 `FallbackChatModel`**（模型调用装饰器：主模型失败时切换到兜底模型），行为由 `FallbackChatModelTest` 覆盖，不依赖框架内置实现。**GA 已修复**（[#1851](https://github.com/agentscope-ai/agentscope-java/pull/1851)，2026-07-06 合入），但本项目仍保留自研版——理由不再是"规避缺陷"，而是需要与 `ResilientChatModel`（退避重试）叠加组合，框架内置版目前无此组合能力 |
| #1954 / #1953 / #1700 / #1911 | Harness 子智能体（subagent）存在跳过执行、父子上下文不传递、资源不回收等问题 | 生产环境下需要的"可控并行多专家协作"，改走本项目自研的 **`MultiAgentOrchestrator`**（真并发 fanout + 智能路由 + reduce 归纳，均有确定性单测断言并发行为），不依赖框架原生 subagent 机制；`harness.subagent.enabled` 生产配置为 `false`。**GA 复核**：4 个 issue 截至 2026-07-10 仍全部 open，未修复，本次升级按既定优先级不处理，维持既有规避方案 |
| #1852 | DashScope 结构化输出解析在部分场景下静默失效 | 意图识别采用**规则快车道**（关键词命中直接判定意图，跳过模型调用）作为第一道防线；模型判断失败走 `onErrorResume` 兜底到默认意图，不让单次结构化输出失败导致整条链路挂死；叠加上面第三节的告警指标，失效可观测 |

## 五、部署侧规避（生产配置基线）

以下风险通过**生产环境配置调整**规避，落地在 [`customer-work-app-server/src/main/resources/application-prod.yml`](../customer-work-app-server/src/main/resources/application-prod.yml)（`customer-channel` 模块另有独立的
[`application-prod.yml`](../customer-channel/src/main/resources/application-prod.yml)，收敛 admin 控制台的暴露面）：

| Issue / 风险来源 | 风险描述 | 生产配置调整 |
|---|---|---|
| #1979（**GA 已修复**）/ #1985（仍 open） | `ClasspathSkillRepository` 在 fat-jar 中按 classpath 资源枚举/读取技能目录会失败。#1979 已由 [#1981](https://github.com/agentscope-ai/agentscope-java/pull/1981) 于 2026-07-06 修复合入 GA；#1985（`agentscope-builder` 模块本地运行 skill 加载报错）是另一个不同模块的独立 bug，本项目未使用 `agentscope-builder`，不适用 | `customer-work.skill.repository: filesystem`，技能目录外置到独立路径（环境变量注入）。**GA 后维持此配置的理由已变**：不再是规避 #1979（已修复，classpath 模式本身在 GA 下可用），而是 Skill **自进化写回**（`SkillCurator`，见 功能与配置全量参考.md §6.10）本就需要可写文件系统，classpath 只读天然不满足这个更根本的需求 |
| #1769 | JSON 会话持久化模式（`JsonFileAgentStateStore`）每次整份重写，长会话下文件膨胀、写放大 | `customer-work.session.mode: redis`（或 `mysql`，二选一，注释中说明取舍） |
| #1954 等 | 子智能体编排的多个已知问题（详见第四节） | `customer-work.harness.subagent.enabled: false` |
| #1740 | Compaction 单次判断不循环，阈值设置不当会漏压缩 | `customer-work.context.compression-enabled: true`，阈值保持默认保守值，注释提醒不要顶格设置 |
| #1741 | SSE 连接泄漏 | `customer-work.stream.idle-timeout-seconds: 120` |
| 应用层：审批端点身份伪造 | `operator` 曾是客户端自报的 query 参数，任何持有通用 API Key 的调用方都能冒充任意坐席放行退款 | `security.approval-auth.enabled: true`（配套 `ApprovalAuthWebFilter`，操作员身份改由服务端按 token 解析；真实 token→姓名映射经运维侧独立配置下发，不进代码仓库） |
| 应用层：审批/槽位收集/对话阶段的多实例一致性 | 三者默认进程内存储，多实例部署下请求被负载均衡到不同实例会导致查不到工单/收集进度重来/对话阶段归零（详见下方"多实例部署注意事项"） | `human-approval.store-mode: jdbc`、`slot-filling.store-mode: jdbc`、`dialog.store-mode: jdbc`，三者复用 `session.mysql.*` 连接配置 |
| 应用层：Actuator 暴露面 | 默认 `application.yml`（尤其 `customer-channel`）为方便调试暴露了全部管理端点（`exposure.include: "*"`） | prod 两处 yml 均收敛为 `management.endpoints.web.exposure.include: health,prometheus`，`health.show-details: when-authorized` |
| 应用层：鉴权默认值 | `security.auth.enabled` 非 prod 环境默认 `false`，容易在生产忘记显式开启 | prod yml 翻转默认值为 `${AUTH_ENABLED:true}`（fail-safe：忘记设置环境变量时默认拦截而非放行） |

### 多实例部署注意事项（诚实声明：以下能力当前实现是进程内统计/存储）

| 组件 | 现状 | 多实例影响 | 应对 |
|---|---|---|---|
| `security.rate-limit` 限流 | 进程内计数器 | N 实例横向扩容 = 实际总配额被放大为 N 倍 | 需要全局精确限流时在网关层（Higress 等）做全局限流，或改造为 Redis 计数 |
| `model.cost-control` 模型成本熔断 | 进程内 `AtomicLong` 计数（本项目 prod 基线默认未开启） | 同上，按实例数放大 | 同上；开启前需评估是否要求全局精确 |
| `CustomerServiceService` 会话级串行锁 | 进程内 `Semaphore`（`ConcurrentHashMap<sessionId, Semaphore>`） | 只在同一实例内生效，同一 `sessionId` 的并发请求若被负载均衡到不同实例，锁不能跨实例互斥 | 生产建议网关层为同一 `sessionId` 配置会话粘性路由（sticky session），不依赖跨实例分布式锁 |
| `PendingApprovalService` / `SlotFillingService` / `DialogStageService` | 均已提供 `store-mode=jdbc` 可插拔实现（见上表） | 切 jdbc 后可跨实例共享，问题已解决 | 生产按上表配置 `store-mode: jdbc` |
| `ComplaintBackend`（投诉工单） | 默认 `MockComplaintBackend` 进程内 `Map`；已提供 `MybatisComplaintBackend`（落库 `cw_complaint`，经 `ComplaintMapper`）作为 `customer-work.tool-backend.mode=jdbc` 时的可插拔实现，问题已解决 | 生产按 `customer-work.tool-backend.mode: jdbc` 配置即可跨实例共享，无需自行对接工单系统 |

## 六、仍受框架限制、需等待修复的风险（诚实声明）

以下问题**没有完美的应用层规避方案**，只能通过部署边界声明或上线前人工验收来控制风险，需要持续关注框架修复进展：

| Issue | 风险描述 | 当前应对 |
|---|---|---|
| #1966 / #1764 | Channel（钉钉/飞书/企业微信）与 AG-UI inbound 链路，框架暂无法把 IM 平台侧的真实用户身份映射进 `RuntimeContext`（即 Channel 收到的消息识别不到"是哪个平台用户在说话"这一层身份） | Channel 面**按单租户群部署**并在文档中显式声明边界（多用户共享同一个群时存在上下文串扰风险）；不在多租户共享群场景下依赖框架自动身份隔离，详见 [`docs/customer-channel操作文档.md`](customer-channel操作文档.md) 的"生产边界"说明 |
| #1968（**GA 已修复**）/ #1683（仍 open） | 原描述"中断后的状态保存、Harness `interrupt` 信号转发存在不确定性"实际是两个独立 bug：#1968（中断后状态未落盘）已由 [#1970](https://github.com/agentscope-ai/agentscope-java/pull/1970) 于 2026-07-08 修复合入 GA；#1683（`HarnessAgent` 不转发 `ReActAgent` 的按会话 `interrupt` 方法）截至 GA 仍 open，性质不同、不能一并视为已解决 | #1968 已随框架修复，可放宽；#1683 仍需**上线验收阶段实测**"中断 → 再次对话"真实场景，尤其经 `HarnessAgentFactory` 构建的智能体（走 `HarnessAgent` 路径），确认业务可接受的行为边界后再放量 |
| #1695 | `ToolResultEviction`（超大工具结果落盘/占位）在部分路径下不驱逐，未能达到预期的上下文瘦身效果 | 不把这个能力当作"防上下文膨胀"的可靠手段依赖；上下文治理主要依赖第五节的 Compaction（阈值保守配置），`ToolResultEviction` 仅作为锦上添花，不作为兜底假设 |
| **（GA 新增）** [#1988](https://github.com/agentscope-ai/agentscope-java/issues/1988) / [#1989](https://github.com/agentscope-ai/agentscope-java/issues/1989)（2026-07-02 提交，均 open） | 中间件回调（如 `MiddlewareBase.onModelCall`）内调用 `agent.interrupt()`，若调用携带的 `RuntimeContext.sessionId` 与 agent 的 `defaultSessionId` 不同，中断**静默失效**（无异常、无日志） | 排查确认：本项目自研的 5 段 Middleware（`ToolGuardMiddleware` 等）**均不在回调内调用 `agent.interrupt()`**，中断统一由 `CustomerServiceService`/`ChatService` 在 REST 层直接对 agent 实例发起，不落入该 bug 的触发路径；仅作为**边界风险记录**，若未来有中间件需要主动中断，需先确认 `RuntimeContext.sessionId` 与 agent 默认会话一致 |
| **（GA 新增）** [#1906](https://github.com/agentscope-ai/agentscope-java/issues/1906)（2026-06-25 提交，open） | 框架 `SkillBox#uploadSkillFiles()` 解析 `skillId` 时，若技能目录下 `SKILL.md` 同级存在其他文件（如 `SOUL.md`），会因路径解析错误导致该技能不可用 | 本项目 Skill 上传功能（`customer-admin-server` 批次六新增）是**自研的 `SkillService#parseUploadContent`**（按扩展名分流 + `ZipInputStream` 解 zip），未调用框架 `SkillBox#uploadSkillFiles()`，不触发此 bug；但内置技能目录 `resources/skills/refund-handling/` 若未来新增非 `SKILL.md` 的伴生文件，需留意此限制仍存在于框架侧 |
| **（GA 新增）** [#2075](https://github.com/agentscope-ai/agentscope-java/issues/2075)（2026-07-09 提交，open，Feature/安全） | 框架依赖的 Java MCP SDK 0.17 存在已披露安全漏洞，待升级 | 本项目 `mcp.enabled` 默认关闭，MCP 为可选扩展点；**若生产环境开启 MCP，需跟踪此 issue 修复进度**，修复前评估是否接受该 SDK 层已知漏洞的风险敞口 |

# 生产就绪评估（agentscope-java 120 open issues 交叉核对）

> 评估分支：`rc2.0`（基于 `io.agentscope:agentscope-harness:2.0.0-RC4`）
> 结论性质：**缓解 / 规避，不是"已解决"**——框架 bug 的最终修复权在上游仓库，本项目只能在应用层规避风险或降低触发概率。

---

## 一、评估范围

对 `agentscope-java` 仓库当时的 **120 个 open issues** 做了全量筛查，逐条与 `customer-work`（本项目）的实际调用链路交叉核对：哪些issue 在本项目的用法下会被触发、哪些不会、哪些已有应用层规避手段。

前提声明：框架本身处于 **RC4，尚未 GA**（对照 #1961 / #1836 / #1704 等版本成熟度相关 issue），意味着：
- 后续 RC5 / GA 版本行为可能发生变化（含 issue 修复、也含新引入的行为变更）；
- 本评估的所有结论都锚定在 **RC4 这个具体版本**，升级版本后需要重新走一遍验证（见"七、版本策略"）。

---

## 二、已实测排除的风险（P0 探针，commit `3128108`）

以下 issue 描述的现象，在本项目实际调用路径下**编写探针测试并实测未复现**：

| Issue | 描述的风险 | 实测结论 |
|---|---|---|
| #1941 / #1675 | 同步 `call()` 不触发 `onAgent` 中间件钩子 | **未复现**。实测 `call()` 与 `streamEvents()` 均触发 `onAgent`（各 1 次），主链路挂载在 `onAgent` 上的脱敏（Masking）、可观测（Observability）等中间件正常生效。 |
| #1681 / #1619 / #1623 | 多租户状态被错误归入 `_default`/`default` 命名空间，导致跨租户状态泄漏 | **未复现**。状态按 `(userId, sessionId)` 正确隔离，落盘路径为 `<root>/<userId>/<sessionId>/agent_state.json`，跨租户不可见，未观察到 `_default`/`default` 命名空间污染。 |

对应测试：
- `MiddlewareInvocationVerificationTest`
- `TenantIsolationVerificationTest`

这两个探针已经**固化为回归测试**，随每次 `mvn test` 常态化运行。其价值不止是"证明当前版本没问题"，更重要的是：**升级到 RC5 / GA 时，如果上游改动导致这两个行为发生漂移（钩子不触发了，或者隔离失效了），测试会立刻红，起到显式的行为漂移告警作用**，不需要靠线上事故才能发现。

## 三、已加固缓解（commit `7f31801`）

以下四项是在应用层做的主动加固，用来降低对应 issue 组合场景下的影响面：

| Issue | 风险描述 | 缓解手段 | 配置键 |
|---|---|---|---|
| #1644 | `HarnessAgent.Builder` 未显式设置 `generateOptions` 时，`streamEvents()` 会抛 NPE | `HarnessAgentFactory` 在构建 Harness Agent 时显式补齐默认 `generateOptions`，避免落入未设置分支 | 无独立开关（构造期兜底，恒生效） |
| #1898 / #1896 | 沙箱执行环境下工具可删除 `.agentscope/workspace` 沙箱工作区，或跨用户越权写 | `ToolGuardMiddleware.onActing` 新增**破坏性命令拦截**：对工具字符串入参匹配危险正则（默认覆盖 `rm -rf`、删 `.agentscope/workspace`、Windows `del /f\|/s`、`format `），命中即改写为安全占位 `[BLOCKED_BY_TOOL_GUARD]` 并计数告警 | `hooks.tool-guard.destructive-patterns`（可整体覆盖默认正则列表） |
| #1852 / #1699 | DashScope 结构化输出（意图分类等）存在静默失效场景，出错不易被发现 | `CustomerServiceService` 在意图分类失败、chat 兜底路径新增 Micrometer 计数指标，可选注入 `MeterRegistry`（未接入监控则 no-op），便于告警面板及时发现异常升高 | 指标名 `customerwork.intent.classify.errors`、`customerwork.chat.fallback` |
| #1741 | SSE 流在下游长时间无数据时无法自行关闭，导致连接泄漏 | `chatStream()` 增加**空闲超时**：相邻两个流元素间隔超过阈值即以友好收尾消息（`STREAM_IDLE_TIMEOUT`）结束流，而不是无限挂起 | `customer-work.stream.idle-timeout-seconds`（默认 120，`<=0` 禁用） |

以上四项加固均有对应单元测试覆盖（详见 `CHANGELOG.md` Unreleased 段），当前 **202 tests 全绿**。

## 四、靠架构决策天然规避的风险

以下几类风险不是靠"打补丁"规避的，而是本项目在架构设计阶段就选择了不依赖框架对应能力，因此这些 issue 描述的缺陷天然不在本项目主链路上：

| Issue | 框架侧的问题 | 本项目的架构决策 |
|---|---|---|
| #1726 | AG-UI 协议下框架无法完成"权限确认"闭环（前端拿不到标准的确认交互） | 人工审批闭环（HITL）不绑定框架的 `CONFIRM_SINK_KEY`，而是落在**应用层**：新增 `approval` 包（`PendingApprovalService` + `ApprovalRequest` 状态机）与 `ApprovalController`（`GET /approvals`、`POST /approvals/{id}/approve\|deny`），退款等高风险工具登记待审单、人工放行后回调执行，形成"挂起 → 人工决策 → 生效"的完整闭环，不依赖框架尚未打通的 Web 友好确认 API |
| #1850 | 框架内置 `ReActAgent.Builder.fallbackModel(...)` 存在已知缺陷，实际不工作 | 使用**自研 `FallbackChatModel`**（模型调用装饰器：主模型失败时切换到兜底模型），行为由 `FallbackChatModelTest` 覆盖，不依赖框架内置实现 |
| #1954 / #1953 / #1700 / #1911 | Harness 子智能体（subagent）存在跳过执行、父子上下文不传递、资源不回收等问题 | 生产环境下需要的"可控并行多专家协作"，改走本项目自研的 **`MultiAgentOrchestrator`**（真并发 fanout + 智能路由 + reduce 归纳，均有确定性单测断言并发行为），不依赖框架原生 subagent 机制；`harness.subagent.enabled` 生产配置为 `false` |
| #1852 | DashScope 结构化输出解析在部分场景下静默失效 | 意图识别采用**规则快车道**（关键词命中直接判定意图，跳过模型调用）作为第一道防线；模型判断失败走 `onErrorResume` 兜底到默认意图，不让单次结构化输出失败导致整条链路挂死；叠加上面第三节的告警指标，失效可观测 |

## 五、部署侧规避（生产配置基线）

以下风险通过**生产环境配置调整**规避，落地在 [`customer-work-example/src/main/resources/application-prod.yml`](../customer-work-example/src/main/resources/application-prod.yml)：

| Issue | 风险描述 | 生产配置调整 |
|---|---|---|
| #1979 / #1985 | `ClasspathSkillRepository` 在 fat-jar 中按 classpath 资源枚举/读取技能目录会失败 | `customer-work.skill.repository: filesystem`，技能目录外置到独立路径（环境变量注入） |
| #1769 | JSON 会话持久化模式（`JsonFileAgentStateStore`）每次整份重写，长会话下文件膨胀、写放大 | `customer-work.session.mode: redis`（或 `mysql`，二选一，注释中说明取舍） |
| #1954 等 | 子智能体编排的多个已知问题（详见第四节） | `customer-work.harness.subagent.enabled: false` |
| #1740 | Compaction 单次判断不循环，阈值设置不当会漏压缩 | `customer-work.context.compression-enabled: true`，阈值保持默认保守值，注释提醒不要顶格设置 |
| #1741 | SSE 连接泄漏 | `customer-work.stream.idle-timeout-seconds: 120` |

## 六、仍受框架限制、需等待修复的风险（诚实声明）

以下问题**没有完美的应用层规避方案**，只能通过部署边界声明或上线前人工验收来控制风险，需要持续关注框架修复进展：

| Issue | 风险描述 | 当前应对 |
|---|---|---|
| #1966 / #1764 | Channel（钉钉/飞书/企业微信）与 AG-UI inbound 链路，框架暂无法把 IM 平台侧的真实用户身份映射进 `RuntimeContext`（即 Channel 收到的消息识别不到"是哪个平台用户在说话"这一层身份） | Channel 面**按单租户群部署**并在文档中显式声明边界（多用户共享同一个群时存在上下文串扰风险）；不在多租户共享群场景下依赖框架自动身份隔离，详见 [`docs/customer-web操作文档.md`](customer-web操作文档.md) 的"生产边界"说明 |
| #1968 / #1683 | 中断后的状态保存、Harness `interrupt` 信号转发存在不确定性（中断时机与状态落盘时机的竞态） | **上线验收阶段必须实测**"中断 → 再次对话"的真实场景（而不是只跑离线单测），确认业务可接受的行为边界后再放量 |
| #1695 | `ToolResultEviction`（超大工具结果落盘/占位）在部分路径下不驱逐，未能达到预期的上下文瘦身效果 | 不把这个能力当作"防上下文膨胀"的可靠手段依赖；上下文治理主要依赖第五节的 Compaction（阈值保守配置），`ToolResultEviction` 仅作为锦上添花，不作为兜底假设 |

## 七、版本策略

- **当前锁定 RC4**，不追新 RC。
- 升级到 RC5 / GA 时，回归闸门为：
  1. **202 个测试**全绿（含第二节固化的两个探针回归测试——behavior drift 会直接体现为测试变红）；
  2. **意图评测集**（`IntentEvalRunner` + `eval/intent-eval-cases.json`）跑一遍，确认规则快车道/模型分诊的准确率、覆盖率没有因为框架升级而劣化。
- 任何一次框架版本升级，都应该重新过一遍本文档第二～六节的结论，而不是假设旧结论自动适用于新版本。

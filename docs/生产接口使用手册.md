## 一、调用总则(先读)

### 1.1 鉴权:所有业务接口带 `X-API-Key`

生产环境 `security.auth.enabled=true`(prod profile 默认),除以下免鉴权路径外,**所有请求必须带请求头 `X-API-Key`**,值为运维下发的 `AUTH_API_KEYS` 之一:

```
免鉴权路径:/actuator/**、/api/customer/health、/swagger-ui/**、/v3/api-docs/**、/webjars/**
```

Key 比对为常量时间比较(防时序侧信道),错误或缺失返回 **401**。请求头名可经 `security.auth.header-name` 改,默认 `X-API-Key`。

### 1.2 限流:超限返回 429

`security.rate-limit` 按客户端维度限流(**优先按 API Key,无 Key 按远端 IP**),默认 120 次/分钟(`RATE_LIMIT_RPM`),超限返回 **429 Too Many Requests**。注意这是单实例进程内计数,多实例部署时全局限流应在网关层做(见部署手册第七节)。

### 1.3 请求追踪:`X-Request-Id`

每个响应都会带 `X-Request-Id` 响应头(调用方传入则透传,否则服务端生成)。**排查问题时请拿着这个值找运维查日志**——该请求在反应式链路上流经的每条日志都通过 MDC 自动带上 `requestId`(以及已知会话时的 `sessionId`),运维用它一次检索即可捞出全链路日志。出错时(4xx/5xx)错误响应体里也会带 `requestId` 字段,用户报障时直接截图即可提供定位凭据(见 §9)。

若上游(API 网关/调用方)已跑分布式追踪并传入 W3C `traceparent` 请求头,本服务会解析其 **trace-id** 并一并写入日志 MDC(键 `traceId`)、回写 `X-Trace-Id` 响应头——本服务日志因此与上游 Jaeger/Tempo 链路共享同一 traceId,可交叉关联(`observability.trace-correlation-enabled`,默认开)。注:进程内真正采集 span 并导出到 OTLP 需引入 OpenTelemetry SDK(当前构建未含),属基础设施扩展点。

### 1.4 sessionId 约定(重要)

`sessionId` 由调用方(网关/前端)生成并透传,承载三层语义:

| 写法 | 语义 |
|---|---|
| 留空 | 匿名会话,服务端生成 `anonymous-<uuid>` 并在响应中回填,后续请求须回传 |
| `conv-123` | 普通会话:多轮上下文在该 ID 下持续累积 |
| `u1001:conv-123` | **租户:会话** 二段式(分隔符 `memory.tenant-delimiter`,默认 `:`):同一租户前缀的多个会话**共享长期记忆**(用户画像/历史事实),会话内上下文仍互相隔离 |

约束:长度 ≤ 128;`message` 必填且 ≤ 4000 字符。

**同一 sessionId 的并发请求会在服务端串行排队执行**(会话级锁,防状态覆盖)。多实例部署时该锁只在单实例内生效,网关必须按 sessionId 做粘性路由——接入方不要对同一 sessionId 并发发请求,收到回复再发下一条。

### 1.5 接口文档自助查看

Swagger UI 免鉴权开放:`GET /swagger-ui/index.html`(OpenAPI 描述在 `/v3/api-docs`)。本手册与 Swagger 的差异以代码为准。

## 三、对话类接口

### 3.1 同步对话 `POST /api/customer/chat`

最简单的接入方式,阻塞等完整回复,适合内部系统联调与非实时场景。

```bash
curl -X POST https://<host>/api/customer/chat \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "u1001:conv-1", "message": "帮我查一下订单 20260613001 的状态"}'
```

```json
{"sessionId": "u1001:conv-1", "reply": "订单 20260613001:状态=已发货,金额=299.00 元。"}
```

匿名请求(`sessionId` 留空)时响应会回填服务端生成的 ID,**调用方必须保存并在后续请求回传**,否则每轮都是新会话。

### 3.2 流式对话 `POST /api/customer/chat/stream`(SSE)

面向用户的前端首选,逐 token 推送,体验等同打字机效果。

```bash
curl -N -X POST https://<host>/api/customer/chat/stream \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "u1001:conv-1", "message": "退货流程是什么"}'
```

事件流格式(`text/event-stream`):

```
event: message
data: 您好,退货流程

event: message
data: 分为三步……

event: done
data: [DONE]
```

客户端处理规则:
- 累积所有 `event: message` 的 `data` 拼成完整回复;收到 `event: done` 表示正常结束。
- **服务端空闲超时 120 秒**(`stream.idle-timeout-seconds`):超过该时长无新数据服务端会主动断流,客户端应视为异常结束并允许用户重发。
- 网关/负载均衡器需关闭对该路径的响应缓冲(如 Nginx `proxy_buffering off`),否则流式退化为一次性输出。

### 3.3 结构化意图识别 `POST /api/customer/intent`

不产生对话回复,返回强类型意图结果,供上游路由系统(工单分派/技能组分流)直接消费:

```json
{
  "intent": "refund",
  "orderId": "20260613001",
  "urgent": true,
  "summary": "用户要求对订单退款"
}
```

`intent` 枚举:`presale`(售前导购) / `consult`(咨询) / `order`(订单) / `refund`(售后退款) / `complaint`(投诉) / `other`。`urgent=true` 表示建议尽快人工介入。

### 3.4 多 Agent 协作咨询 `POST /api/customer/consult`

把一个复杂问题分发给订单 / 售后 / 知识库多个专家 Agent 处理后聚合结论。请求体同 `ChatRequest`,响应为聚合后的纯文本。适合"这个订单能不能退、怎么退、退多少"这类横跨多域的问题;简单问题用 `/chat` 即可(consult 成本更高)。

内部行为由配置决定(接入方无需关心,但对延迟有感知):`multi-agent.routing-enabled`(先意图分诊,只派发相关专家)、`max-concurrency`(真并行 fanout)、`reduce-enabled`(汇总归纳)、`timeout-seconds`(单专家超时)。

### 3.5 AG-UI 协议对话 `POST /api/customer/agui`(SSE)

输出符合 [AG-UI 协议](https://docs.ag-ui.com/) 的标准 Agent-UI 事件流(RUN_STARTED / TEXT_MESSAGE_CONTENT / TOOL_CALL 等 JSON 事件)。**只有已使用 AG-UI 兼容前端组件的团队需要接这个**;普通前端用 §3.2 的 `/chat/stream` 更简单。

### 3.6 安全中断 `POST /api/customer/session/{sessionId}/interrupt`

终止该会话正在执行的 Agent(如模型陷入长时间工具循环),**上下文保留**,用户可继续对话。幂等:无活跃任务时返回提示文本,不报错。给"停止生成"按钮用。

### 3.7 结束会话 `DELETE /api/customer/session/{sessionId}`

清理会话:移除热 Agent 缓存 + 删除持久化状态 + 释放会话锁。用户明确关闭会话窗口时调用;不调用也有兜底(`session.idle-timeout-minutes` 配置的空闲自动清理,prod 需显式开启)。**调用后该 sessionId 的历史上下文不可恢复**。

## 四、退款闭环(核心业务流程)

退款是全系统唯一的资金动作,设计为**双层防线 + 人工终审**,任何路径都不存在"AI 直接打款":

```
用户提出退款
   │
   ├─ 路径 A:自然对话(/chat)──> Agent 决定调用 submitRefund 工具
   │        └─ Permission ASK 闸门(工具调用层,第一层防线)
   │             └─ AfterSalesTools.submitRefund → 生成 PENDING 审批单(不打款)
   │
   └─ 路径 B:结构化表单(/forms/refund)──> 多轮槽位收集
            └─ 收齐 订单号+原因 → 生成 PENDING 审批单(不打款)
   
   PENDING 审批单(两条路径在此汇合)
   │
   ├─ 人工坐席 approve(带 X-Approval-Token,第二层防线)→ APPROVED → 触发下游执行(打款)
   │      └─ 执行失败 → EXECUTE_FAILED → 定时补偿重试(最多 3 次)
   ├─ 人工坐席 deny → DENIED(终态)
   └─ 超时未决策 → 按 timeout-action 升级告警或自动拒绝(默认不启用)
```

### 4.1 路径 A:对话内自然触发

用户在 `/chat` 里说"订单 20260613001 质量有问题,我要退款",Agent 自主决定调用退款工具,生成审批单后**回复用户"已提交退款申请,等待人工审核"**——对接入方透明,无需额外开发。若要在自己的坐席系统里跟进这张单,轮询 §5.1 的列表接口(按 `sessionId` 关联)。

### 4.2 路径 B:多轮表单收集 `POST /api/customer/forms/refund`

结构化收集入口(适合 App 内"申请退款"按钮场景),同一 `sessionId` 连续 POST 推进同一张表单:

```bash
# 第 1 轮:用户只说了意图
curl -X POST https://<host>/api/customer/forms/refund \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "refund-u1001", "message": "我要退款"}'
```
```json
{
  "sessionId": "refund-u1001",
  "complete": false,
  "nextPrompt": "请提供需要退款的订单号。",
  "collected": {}
}
```

接入方把 `nextPrompt` 展示给用户,拿到回答后再 POST;收齐 **orderId(带格式校验)+ reason** 两个槽位后:

```json
{
  "sessionId": "refund-u1001",
  "complete": true,
  "collected": {"orderId": "20260613001", "reason": "质量问题"},
  "approvalId": "APR-xxxx",
  "message": "信息已收齐,已生成待人工审批退款单 APR-xxxx,人工坐席放行后执行打款。"
}
```

- `complete=false` → 按 `nextPrompt` 继续追问;`complete=true` → 表单结束,保存 `approvalId` 供跟进。
- 收集进度落 MySQL(prod 下 `slot-filling.store-mode=jdbc`),**中途应用重启或换实例不丢进度**。
- 订单号不符合格式时不会推进,`nextPrompt` 会重新要求提供,不限次数。

## 五、人工审批接口

供**坐席工作台/审批后台**对接。查询接口只需 `X-API-Key`;approve/deny 两个资金端点额外要求操作员令牌。

### 5.1 查询

```bash
# 待审列表(status 可选:pending / approved / denied,大小写不敏感;不传返回全部)
curl -H "X-API-Key: <key>" "https://<host>/api/customer/approvals?status=pending"
# 单条详情
curl -H "X-API-Key: <key>" "https://<host>/api/customer/approvals/APR-xxxx"
```

审批单 JSON 完整字段:

| 字段 | 说明 |
|---|---|
| `id` / `type` | 单号 / 类型(当前仅 `REFUND`) |
| `sessionId` / `orderId` / `amount` / `reason` | 来源会话 / 订单号 / 金额 / 申请原因 |
| `status` | `PENDING` → `APPROVED` / `DENIED`(终态,状态机保证不可再变) |
| `operator` / `decisionNote` / `decidedAtMs` | 决策人 / 备注 / 决策时间(毫秒时间戳) |
| `executionStatus` | 下游执行状态:`NOT_APPLICABLE`(未放行) / `EXECUTED`(打款成功) / `EXECUTE_FAILED`(打款失败,待补偿) |
| `executionFailureReason` / `executionAttempts` | 失败原因 / 已重试次数 |
| `createdAtMs` | 创建时间 |

**坐席端展示要点**:`status=APPROVED` 不等于钱已到账——真正的完成态是 `status=APPROVED && executionStatus=EXECUTED`。`EXECUTE_FAILED` 的单会被定时任务自动重试(上限 `human-approval.max-execution-retry-attempts`,默认 3),重试耗尽仍失败的需人工介入处理。

### 5.2 放行 / 拒绝(需操作员令牌)

生产环境 `security.approval-auth.enabled=true`,这两个端点**必须带 `X-Approval-Token` 请求头**,值为运维给每个坐席单独下发的令牌。服务端按令牌解析出操作员姓名并记入审计——**URL 里的 `operator` 参数在生产环境被忽略**(防调用方自报任意身份放行退款),仅本地开发(鉴权关闭)时才生效。

```bash
# 放行(触发下游打款)
curl -X POST -H "X-API-Key: <key>" -H "X-Approval-Token: <坐席个人令牌>" \
  "https://<host>/api/customer/approvals/APR-xxxx/approve"

# 拒绝(note 备注可选,会记入审计)
curl -X POST -H "X-API-Key: <key>" -H "X-Approval-Token: <坐席个人令牌>" \
  "https://<host>/api/customer/approvals/APR-xxxx/deny?note=不符合七天无理由条件"
```

行为约定:
- 响应即决策后的审批单全量 JSON(approve 的响应里已能看到 `executionStatus` 首次执行结果)。
- **重复决策返回 409 Conflict**(状态机拒绝对终态二次决策)——坐席端把 409 当"已被他人处理"提示即可,支持多坐席安全并发操作同一队列。
- 单号不存在返回 404;令牌无效或缺失返回 401/403。
- 每次决策写入 `cw_audit_log` 审计表(谁/何时/对哪张单/什么决策/备注),合规可追溯。
- deny 的下游回调失败**不影响拒绝结果**(仅记日志);approve 的执行失败进入 `EXECUTE_FAILED` 补偿流程。

## 六、坐席辅助与会话质检

### 6.1 坐席辅助 `POST /api/customer/assist`

人工坐席接管会话时,输入用户消息,返回话术建议——**只给坐席参考,不会发给用户**:

```bash
curl -X POST -H "X-API-Key: <key>" \
  "https://<host>/api/customer/assist?message=你们的东西质量太差了我要投诉"
```
```json
{
  "suggestedReply": "非常抱歉给您带来不好的体验……",
  "knowledgeHint": "投诉处理 SOP:先安抚情绪,再核实订单……",
  "recommendedTool": "createComplaint"
}
```

注意 `message` 是 **query 参数**,不是 JSON body,特殊字符需 URL 编码。

### 6.2 会话质检 `POST /api/customer/quality/inspect`

对一组回复(坐席或 Agent 的)做合规质检。body 是 **JSON 字符串数组**,`sessionId` 为 query 参数(可选,建议传——不通过的记录按它归档租户):

```bash
curl -X POST -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  "https://<host>/api/customer/quality/inspect?sessionId=u1001:conv-1" \
  -d '["您的退款我保证今天一定到账","请您稍等"]'
```
```json
{"score": 60, "passed": false, "issues": ["检测到资金类违规承诺:保证……到账"]}
```

业务逻辑:规则质检(资金违规承诺等硬红线判不通过)。**`passed=false` 时系统自动把这条质检结果沉淀为事实流水(FactLog,按租户分文件)**,供质量团队离线复盘与训练数据筛选——这是"记录",不会自动改变线上 Agent 行为。

典型接入方式:会话结束(§3.7)时由业务侧把该会话的 Agent 回复批量送检,形成常态化质量抽样。

## 七、主动服务通知

由**订单系统事件 / 定时任务 / 运营后台**触发(不是终端用户调用),全部 query 参数:

```bash
# 订单状态变更主动通知(target 为渠道侧的推送目标标识,如飞书群/用户 open_id)
curl -X POST -H "X-API-Key: <key>" \
  "https://<host>/api/customer/notify/order-status?orderId=20260613001&status=已发货&target=<target>"

# 满意度回访
curl -X POST -H "X-API-Key: <key>" \
  "https://<host>/api/customer/notify/survey?orderId=20260613001&target=<target>"
```

推送走 `NotificationChannel` 抽象:部署了 customer-web 且配置飞书 webhook 时经飞书推送;**未配置真实渠道时降级为仅记日志**(接口仍返回成功)——生产接入前确认渠道实现已就位,`target` 的取值语义由所接渠道决定。

### 7.5 会话故障诊断(运维/坐席后台专用)

线上定位专用:把散落在 6 处存储的会话现场一次拉齐,把"用户报障 → 定位根因"从人肉查多张表缩短为一次调用。受 `X-API-Key` 保护,面向运维,不对终端用户开放。

```bash
curl -H "X-API-Key: <key>" \
  "https://<host>/api/customer/diagnostics/session/u1001:conv-1?auditLimit=20&factLimit=20"
```
```json
{
  "sessionId": "u1001:conv-1",
  "tenantId": "u1001",
  "stateExists": true,
  "dialogStage": "PROCESSING",
  "slotFilling": {"orderId": "20260613001"},
  "slotFillingAsking": "reason",
  "approvals": [{"id": "APR-xxx", "status": "APPROVED", "executionStatus": "EXECUTE_FAILED", "...": "..."}],
  "auditAvailable": true,
  "recentAudit": [{"eventType": "tool-call", "agentName": "CustomerServiceAgent-u1001:conv-1", "eventData": "{...}", "createdAtMs": 1751000000000}],
  "qualityFacts": ["{\"type\":\"quality-failure\",\"sessionId\":\"u1001:conv-1\",...}"],
  "degradedSources": []
}
```

字段要点:
- **`degradedSources`**:诚实标注哪些数据源采集失败/不可用(如 `["state: db down"]`)。**它非空时,对应字段的"空"是"没查到"而非"确实没有"**——排障时先看这个,避免误判。
- **`auditAvailable`**:`false` 表示未接入可查询的审计后端(默认 `LoggingAuditSink` 只写日志不可查),此时 `recentAudit` 恒空;要用审计下钻须配置 `JdbcAuditSink`(写 `cw_audit_log`)。
- **`recentAudit`**:按 `agentName` 后缀匹配 sessionId,时间倒序。审批决策类审计不在此段(在 `approvals` 段已含决策人/时间)。
- **`qualityFacts`**:该会话相关的质检失败事实(JSONL 原文),取最近 `factLimit` 条。
- 审计事件下钻(更大 limit):`GET /api/customer/diagnostics/session/{sessionId}/audit?limit=100`。

诊断读取涉及 JDBC/文件 IO,已统一在 `boundedElastic` 线程执行,不阻塞事件循环。

## 八、对话背后的内部逻辑(接入方须知)

这些机制在 `/chat`、`/chat/stream` 内部自动生效,接入方不直接调用,但会影响观察到的行为:

1. **意图快车道(fast-route)**:消息命中关键词规则且指向唯一意图时跳过 LLM 分诊直接路由,**该类请求显著更快**——同类问题延迟不一致是正常现象,不是故障。
2. **对话阶段状态机**:会话在 GREETING → 需求澄清 → 处理 → 收尾 等阶段间流转,系统按当前阶段动态调整 Agent 的系统提示词(分阶段聚焦)。阶段状态 prod 下落 MySQL(`dialog.store-mode=jdbc`),重启/换实例不"归零"。
3. **上下文压缩(Compaction)**:长会话超过阈值(8000 token / 40 条消息)时自动摘要压缩、保留最近 10 条——超长会话中 Agent 对很早之前细节的记忆是"摘要级"的,属预期行为。
4. **权限闸门(Permission ASK)**:`submitRefund` / `transferToHuman` 两个工具被配置为需确认,是退款双层防线的第一层(见 §4)。
5. **模型兜底与重试**:主模型(DashScope)失败自动重试(2 次,500ms 退避)后切兜底模型;触发兜底时监控指标 `customerwork.chat.fallback` 上升,回复质量可能下降——运维应关注该指标告警。
6. **敏感信息脱敏**:日志中的手机号/订单敏感字段自动掩码,排查问题时日志里看到 `138****5678` 属正常。
7. **审计**:审批决策等关键动作写入 `cw_audit_log`;对话内容本身不进审计表(在会话存储与可观测链路里)。

## 九、错误码与故障排查

| 状态码 | 场景 | 接入方处理 |
|---|---|---|
| 400 | 参数校验失败(message 为空/超 4000;status 枚举非法) | 检查请求体,响应 body 有具体字段错误信息 |
| 401 | `X-API-Key` 缺失或错误;`X-Approval-Token` 无效 | 核对运维下发的 Key/令牌 |
| 404 | 审批单不存在 | 单号错误或查询了未生成的单 |
| 409 | 审批单重复决策 | 该单已被其他坐席处理,刷新列表即可 |
| 429 | 触发限流(默认 120 次/分钟/Key) | 退避重试;长期不够找运维调 `RATE_LIMIT_RPM` |
| 5xx | 服务端异常 | 用响应头 `X-Request-Id` 或错误体里的 `requestId` 字段找运维查日志(两者同值) |

**流式接口专项**:

| 现象 | 原因 | 处理 |
|---|---|---|
| SSE 一次性输出全部内容 | 网关/LB 开了响应缓冲 | 关闭该路径的 proxy buffering |
| SSE 中途断开且无 `done` 事件 | 空闲超 120s 被服务端断流,或网关超时更短 | 网关读超时须 > `stream.idle-timeout-seconds`;客户端视为异常结束 |
| 回复变慢、质量下降 | 主模型故障切了兜底模型 | 观察 `customerwork.chat.fallback` 指标,联系运维 |
| 同一会话回复串行变慢 | 会话锁排队(同 sessionId 并发请求) | 客户端收到回复后再发下一条 |

**接入自检清单**(新调用方上线前过一遍):

- [ ] 所有请求带 `X-API-Key`;坐席系统的 approve/deny 额外带 `X-Approval-Token`
- [ ] sessionId 采用 `租户:会话` 二段式(需要跨会话长期记忆时)且 ≤128 字符
- [ ] 匿名会话回填的 sessionId 已保存并在后续请求回传
- [ ] SSE 客户端正确处理 `message`/`done` 两类事件与中途断流
- [ ] 同一 sessionId 不并发发送
- [ ] 审批单完成态判断使用 `status + executionStatus` 双字段
- [ ] 409/429 有对应的用户侧提示与退避逻辑

## 一、调用总则(先读)

### 1.1 鉴权:所有业务接口带 `X-API-Key`

生产环境 `security.auth.enabled=true`(prod profile 默认),除以下免鉴权路径外,**所有请求必须带请求头 `X-API-Key`**,值为运维下发的 `AUTH_API_KEYS` 之一:

```
免鉴权路径:/actuator/**、/api/customer/health、/swagger-ui/**、/v3/api-docs/**、/webjars/**
```

Key 比对为常量时间比较(防时序侧信道),错误或缺失返回 **401**。请求头名可经 `security.auth.header-name` 改,默认 `X-API-Key`。

### 1.2 限流:超限返回 429

`security.rate-limit` 按客户端维度限流(**优先按 API Key,无 Key 按远端 IP**),默认 120 次/分钟(`RATE_LIMIT_RPM`),超限返回 **429 Too Many Requests**。注意这是单实例进程内计数,多实例部署时全局限流应在网关层做(见部署手册第七节)。

### 1.3 请求追踪:`X-Request-Id`

每个响应都会带 `X-Request-Id` 响应头(调用方传入则透传,否则服务端生成)。**排查问题时请拿着这个值找运维查日志**——该请求在反应式链路上流经的每条日志都通过 MDC 自动带上 `requestId`(以及已知会话时的 `sessionId`),运维用它一次检索即可捞出全链路日志。出错时(4xx/5xx)错误响应体里也会带 `requestId` 字段,用户报障时直接截图即可提供定位凭据(见 §10)。

若上游(API 网关/调用方)已跑分布式追踪并传入 W3C `traceparent` 请求头,本服务会解析其 **trace-id** 并一并写入日志 MDC(键 `traceId`)、回写 `X-Trace-Id` 响应头——本服务日志因此与上游 Jaeger/Tempo 链路共享同一 traceId,可交叉关联(`observability.trace-correlation-enabled`,默认开)。注:进程内真正采集 span 并导出到 OTLP **已落地**——开启 `customer-work.observability.otel.enabled`(starter)/
`admin.observability.otel.enabled`(admin)后装配 OpenTelemetry SDK 与 OTLP exporter,按 agent/model/tool
(starter 另加 HTTP 入口)三段出 span;关闭时整组 Bean 不装配,启动零开销。配套一键监控栈见
[docker/observability/README.md](../docker/observability/README.md)。

### 1.4 sessionId 约定(重要)

`sessionId` 由调用方(网关/前端)生成并透传,承载三层语义:

| 写法 | 语义 |
|---|---|
| 留空 | 匿名会话,服务端生成 `anonymous-<uuid>` 并在响应中回填,后续请求须回传 |
| `conv-123` | 普通会话:多轮上下文在该 ID 下持续累积 |
| `u1001:conv-123` | **租户:会话** 二段式(分隔符 `memory.tenant-delimiter`,默认 `:`):同一租户前缀的多个会话**共享长期记忆**(用户画像/历史事实),会话内上下文仍互相隔离 |

约束:长度 ≤ 128;`message` 必填且 ≤ 4000 字符。

**同一 sessionId 的并发请求会在服务端串行排队执行**(会话级锁,防状态覆盖)。多实例部署时该锁只在单实例内生效,网关必须按 sessionId 做粘性路由——接入方不要对同一 sessionId 并发发请求,收到回复再发下一条。

### 1.5 接口文档自助查看

Swagger UI 免鉴权开放:`GET /swagger-ui/index.html`(OpenAPI 描述在 `/v3/api-docs`)。本手册与 Swagger 的差异以代码为准。

## 三、对话类接口

### 3.1 同步对话 `POST /api/customer/chat`

最简单的接入方式,阻塞等完整回复,适合内部系统联调与非实时场景。

```bash
curl -X POST https://<host>/api/customer/chat \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "u1001:conv-1", "message": "帮我查一下订单 20260613001 的状态"}'
```

```json
{"sessionId": "u1001:conv-1", "reply": "订单 20260613001:状态=已发货,金额=299.00 元。", "messageId": "MSG-4bf92f35-77b3-4da6-a3ce"}
```

匿名请求(`sessionId` 留空)时响应会回填服务端生成的 ID,**调用方必须保存并在后续请求回传**,否则每轮都是新会话。`messageId` 供 §3.8 提交点赞/点踩反馈时引用。

### 3.2 流式对话 `POST /api/customer/chat/stream`(SSE)

面向用户的前端首选,逐 token 推送,体验等同打字机效果。

```bash
curl -N -X POST https://<host>/api/customer/chat/stream \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "u1001:conv-1", "message": "退货流程是什么"}'
```

事件流格式(`text/event-stream`):

```
event: message
data: 您好,退货流程

event: message
data: 分为三步……

event: done
data: [DONE]
```

客户端处理规则:
- 累积所有 `event: message` 的 `data` 拼成完整回复;收到 `event: done` 表示正常结束。
- **服务端空闲超时 120 秒**(`stream.idle-timeout-seconds`):超过该时长无新数据服务端会主动断流,客户端应视为异常结束并允许用户重发。
- 网关/负载均衡器需关闭对该路径的响应缓冲(如 Nginx `proxy_buffering off`),否则流式退化为一次性输出。

### 3.3 结构化意图识别 `POST /api/customer/intent`

不产生对话回复,返回强类型意图结果,供上游路由系统(工单分派/技能组分流)直接消费:

```json
{
  "intent": "refund",
  "orderId": "20260613001",
  "urgent": true,
  "summary": "用户要求对订单退款"
}
```

`intent` 枚举:`presale`(售前导购) / `consult`(咨询) / `order`(订单) / `refund`(售后退款) / `complaint`(投诉) / `other`。`urgent=true` 表示建议尽快人工介入。

### 3.4 多 Agent 协作咨询 `POST /api/customer/consult`

把一个复杂问题分发给订单 / 售后 / 知识库多个专家 Agent 处理后聚合结论。请求体同 `ChatRequest`,响应为聚合后的纯文本。适合"这个订单能不能退、怎么退、退多少"这类横跨多域的问题;简单问题用 `/chat` 即可(consult 成本更高)。

内部行为由配置决定(接入方无需关心,但对延迟有感知):`multi-agent.routing-enabled`(先意图分诊,只派发相关专家)、`max-concurrency`(真并行 fanout)、`reduce-enabled`(汇总归纳)、`timeout-seconds`(单专家超时)。

### 3.5 AG-UI 协议对话 `POST /api/customer/agui`(SSE)

输出符合 [AG-UI 协议](https://docs.ag-ui.com/) 的标准 Agent-UI 事件流(RUN_STARTED / TEXT_MESSAGE_CONTENT / TOOL_CALL 等 JSON 事件)。**只有已使用 AG-UI 兼容前端组件的团队需要接这个**;普通前端用 §3.2 的 `/chat/stream` 更简单。

### 3.6 安全中断 `POST /api/customer/session/{sessionId}/interrupt`

终止该会话正在执行的 Agent(如模型陷入长时间工具循环),**上下文保留**,用户可继续对话。幂等:无活跃任务时返回提示文本,不报错。给"停止生成"按钮用。

### 3.7 结束会话 `DELETE /api/customer/session/{sessionId}`

清理会话:移除热 Agent 缓存 + 删除持久化状态 + 释放会话锁。用户明确关闭会话窗口时调用;不调用也有兜底(`session.idle-timeout-minutes` 配置的空闲自动清理,prod 需显式开启)。**调用后该 sessionId 的历史上下文不可恢复**。

### 3.8 消息级反馈 `POST /api/customer/feedback`

对具体一条回复提交点赞/点踩,`messageId` 取自 `/chat` 响应体(见 §3.1)。**仅覆盖非流式 `/chat`**——`/chat/stream` 逐 token 输出没有单一终态对象可挂 `messageId`,暂不支持。

```bash
curl -X POST https://<host>/api/customer/feedback \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId":"u1001:conv-1","messageId":"MSG-xxxx","type":"DOWN","comment":"答非所问"}'
```

行为约定:
- `type` 仅 `UP`/`DOWN`;同一 `messageId` 重复提交按最新一次覆盖(用户改主意允许更正)。
- **`DOWN` 类型自动沉淀事实到 FactLog**(与会话质检 §7.2 不通过时的落盘同一机制),供离线复盘/回流知识库——只做"记录",筛选回流是离线人工职责。
- 查询:`GET /api/customer/feedback/{messageId}` 单条;`GET /api/customer/feedback?sessionId=` 某会话全部反馈(时间正序)。
- 单条查询不存在返回 404。

## 四、退款闭环(核心业务流程)

退款是全系统唯一的资金动作,设计为**双层防线 + 人工终审**,任何路径都不存在"AI 直接打款":

```
用户提出退款
   │
   ├─ 路径 A:自然对话(/chat)──> Agent 决定调用 submitRefund 工具
   │        └─ Permission ASK 闸门(工具调用层,第一层防线)
   │             └─ AfterSalesTools.submitRefund → 生成 PENDING 审批单(不打款)
   │
   └─ 路径 B:结构化表单(/forms/refund)──> 多轮槽位收集
            └─ 收齐 订单号+原因 → 生成 PENDING 审批单(不打款)
   
   PENDING 审批单(两条路径在此汇合)
   │
   ├─ 人工坐席 approve(带 X-Approval-Token,第二层防线)→ APPROVED → 触发下游执行(打款)
   │      └─ 执行失败 → EXECUTE_FAILED → 定时补偿重试(最多 3 次)
   ├─ 人工坐席 deny → DENIED(终态)
   └─ 超时未决策 → 按 timeout-action 升级告警或自动拒绝(默认不启用)
```

### 4.1 路径 A:对话内自然触发

用户在 `/chat` 里说"订单 20260613001 质量有问题,我要退款",Agent 自主决定调用退款工具,生成审批单后**回复用户"已提交退款申请,等待人工审核"**——对接入方透明,无需额外开发。若要在自己的坐席系统里跟进这张单,轮询 §5.1 的列表接口(按 `sessionId` 关联)。人工转接场景则轮询 §6.1 的人机切换工单列表。

### 4.2 路径 B:多轮表单收集 `POST /api/customer/forms/refund`

结构化收集入口(适合 App 内"申请退款"按钮场景),同一 `sessionId` 连续 POST 推进同一张表单:

```bash
# 第 1 轮:用户只说了意图
curl -X POST https://<host>/api/customer/forms/refund \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{"sessionId": "refund-u1001", "message": "我要退款"}'
```
```json
{
  "sessionId": "refund-u1001",
  "complete": false,
  "nextPrompt": "请提供需要退款的订单号。",
  "collected": {}
}
```

接入方把 `nextPrompt` 展示给用户,拿到回答后再 POST;收齐 **orderId(带格式校验)+ reason** 两个槽位后:

```json
{
  "sessionId": "refund-u1001",
  "complete": true,
  "collected": {"orderId": "20260613001", "reason": "质量问题"},
  "approvalId": "APR-xxxx",
  "message": "信息已收齐,已生成待人工审批退款单 APR-xxxx,人工坐席放行后执行打款。"
}
```

- `complete=false` → 按 `nextPrompt` 继续追问;`complete=true` → 表单结束,保存 `approvalId` 供跟进。
- 收集进度落 MySQL(prod 下 `slot-filling.store-mode=jdbc`),**中途应用重启或换实例不丢进度**。
- 订单号不符合格式时不会推进,`nextPrompt` 会重新要求提供,不限次数。

## 五、人工审批接口

供**坐席工作台/审批后台**对接。查询接口只需 `X-API-Key`;approve/deny 两个资金端点额外要求操作员令牌。

### 5.1 查询

```bash
# 待审列表(status 可选:pending / approved / denied,大小写不敏感;不传返回全部)
curl -H "X-API-Key: <key>" "https://<host>/api/customer/approvals?status=pending"
# 单条详情
curl -H "X-API-Key: <key>" "https://<host>/api/customer/approvals/APR-xxxx"
```

审批单 JSON 完整字段:

| 字段 | 说明 |
|---|---|
| `id` / `type` | 单号 / 类型(当前仅 `REFUND`) |
| `sessionId` / `orderId` / `amount` / `reason` | 来源会话 / 订单号 / 金额 / 申请原因 |
| `status` | `PENDING` → `APPROVED` / `DENIED`(终态,状态机保证不可再变) |
| `operator` / `decisionNote` / `decidedAtMs` | 决策人 / 备注 / 决策时间(毫秒时间戳) |
| `executionStatus` | 下游执行状态:`NOT_APPLICABLE`(未放行) / `EXECUTED`(打款成功) / `EXECUTE_FAILED`(打款失败,待补偿) |
| `executionFailureReason` / `executionAttempts` | 失败原因 / 已重试次数 |
| `createdAtMs` | 创建时间 |

**坐席端展示要点**:`status=APPROVED` 不等于钱已到账——真正的完成态是 `status=APPROVED && executionStatus=EXECUTED`。`EXECUTE_FAILED` 的单会被定时任务自动重试(上限 `human-approval.max-execution-retry-attempts`,默认 3),重试耗尽仍失败的需人工介入处理。

### 5.2 放行 / 拒绝(需操作员令牌)

生产环境 `security.approval-auth.enabled=true`,这两个端点**必须带 `X-Approval-Token` 请求头**,值为运维给每个坐席单独下发的令牌。服务端按令牌解析出操作员姓名并记入审计——**URL 里的 `operator` 参数在生产环境被忽略**(防调用方自报任意身份放行退款),仅本地开发(鉴权关闭)时才生效。

```bash
# 放行(触发下游打款)
curl -X POST -H "X-API-Key: <key>" -H "X-Approval-Token: <坐席个人令牌>" \
  "https://<host>/api/customer/approvals/APR-xxxx/approve"

# 拒绝(note 备注可选,会记入审计)
curl -X POST -H "X-API-Key: <key>" -H "X-Approval-Token: <坐席个人令牌>" \
  "https://<host>/api/customer/approvals/APR-xxxx/deny?note=不符合七天无理由条件"
```

行为约定:
- 响应即决策后的审批单全量 JSON(approve 的响应里已能看到 `executionStatus` 首次执行结果)。
- **重复决策返回 409 Conflict**(状态机拒绝对终态二次决策)——坐席端把 409 当"已被他人处理"提示即可,支持多坐席安全并发操作同一队列。
- 单号不存在返回 404;令牌无效或缺失返回 401/403。
- 每次决策写入 `cw_audit_log` 审计表(谁/何时/对哪张单/什么决策/备注),合规可追溯。
- deny 的下游回调失败**不影响拒绝结果**(仅记日志);approve 的执行失败进入 `EXECUTE_FAILED` 补偿流程。

## 六、人机切换接口

供**坐席工作台**对接。取代此前 `transferToHuman` 只打日志、生成不落库的随机字符串工单号的空实现——
转人工现登记为可查询、可流转的工单:AI 转出生成 `PENDING` → 坐席 `claim` 接单(`CLAIMED`)→ 处理完毕
`resolve` 结案(`RESOLVED`,会话可回收给 AI 续接)。

### 6.1 查询

```bash
# 待接单列表(status 可选:pending / claimed / resolved,大小写不敏感;不传返回全部)
curl -H "X-API-Key: <key>" "https://<host>/api/customer/handoffs?status=pending"
# 单条详情
curl -H "X-API-Key: <key>" "https://<host>/api/customer/handoffs/HO-xxxx"
```

工单 JSON 完整字段:

| 字段 | 说明 |
|---|---|
| `id` / `sessionId` / `reason` | 工单号 / 关联会话(见下方已知限制) / 转人工原因 |
| `status` | `PENDING` → `CLAIMED` → `RESOLVED`(终态,状态机保证不可再变) |
| `claimedBy` / `claimedAtMs` | 接单坐席 / 接单时间(毫秒时间戳) |
| `resolutionNote` / `resolvedAtMs` | 处理结果备注 / 结案时间(毫秒时间戳) |
| `createdAtMs` | 创建时间 |

**已知限制**:框架当前的工具调用未打通 RuntimeContext 注入,`sessionId` 字段目前恒为占位值
`"agent-tool"`(与 §4 退款工具 `submitRefund` 同一限制),暂无法据此精确关联到发起会话——坐席端
按工单号(而非 sessionId)跟单即可,不影响接单/结案流程。

### 6.2 接单 / 结案

```bash
# 坐席接单
curl -X POST -H "X-API-Key: <key>" \
  "https://<host>/api/customer/handoffs/HO-xxxx/claim?operator=alice"

# 结案回收给 AI(note 备注可选,会记入审计)
curl -X POST -H "X-API-Key: <key>" \
  "https://<host>/api/customer/handoffs/HO-xxxx/resolve?note=已安抚，问题解决"
```

行为约定:
- 响应即流转后的工单全量 JSON。
- **重复接单 / 未接单先结案返回 409 Conflict**(状态机拒绝非法流转)——坐席端把 409 当"已被他人处理"
  或"尚未接单"提示即可,支持多坐席安全并发操作同一待接单队列。
- 单号不存在返回 404。
- 每次流转写入 `cw_audit_log` 审计表(谁/何时/对哪张单/什么决策),合规可追溯。
- 与 `ApprovalController` 的资金端点不同,接单/结案不产生资金动作,未接入同等强度的操作员令牌鉴权
  (仅信任请求参数 `operator`)。

### 7.1 坐席辅助 `POST /api/customer/assist`

```bash
curl -X POST -H "X-API-Key: <key>" \
```

```json
  "recommendedTool": "createComplaint"

```

注意 `message` 是 **query 参数**,不是 JSON body,特殊字符需 URL 编码。

### 7.2 会话质检 `POST /api/customer/quality/inspect`

对一组回复(坐席或 Agent 的)做合规质检。body 是 **JSON 字符串数组**,`sessionId` 为 query 参数(可选,建议传——不通过的记录按它归档租户):

```bash
curl -X POST -H "X-API-Key: <key>" -H "Content-Type: application/json" \
```

典型接入方式:会话结束(§3.7)时由业务侧把该会话的 Agent 回复批量送检,形成常态化质量抽样。

```bash
# 订单状态变更主动通知(target 为渠道侧的推送目标标识,如飞书群/用户 open_id)

```

推送走 `NotificationChannel` 抽象:部署了 customer-channel 且配置飞书 webhook 时经飞书推送;**未配置真实渠道时降级为仅记日志**(接口仍返回成功)——生产接入前确认渠道实现已就位,`target` 的取值语义由所接渠道决定。

### 8.5 会话故障诊断(运维/坐席后台专用)

线上定位专用:把散落在 6 处存储的会话现场一次拉齐,把"用户报障 → 定位根因"从人肉查多张表缩短为一次调用。受 `X-API-Key` 保护,面向运维,不对终端用户开放。

```bash
curl -H "X-API-Key: <key>" \
  "https://<host>/api/customer/diagnostics/session/u1001:conv-1?auditLimit=20&factLimit=20"
```
```json
{
  "sessionId": "u1001:conv-1",
  "tenantId": "u1001",
  "stateExists": true,
  "dialogStage": "PROCESSING",
  "slotFilling": {"orderId": "20260613001"},
  "slotFillingAsking": "reason",
  "approvals": [{"id": "APR-xxx", "status": "APPROVED", "executionStatus": "EXECUTE_FAILED", "...": "..."}],
  "auditAvailable": true,
  "recentAudit": [{"eventType": "tool-call", "agentName": "CustomerServiceAgent-u1001:conv-1", "eventData": "{...}", "createdAtMs": 1751000000000}],
  "qualityFacts": ["{\"type\":\"quality-failure\",\"sessionId\":\"u1001:conv-1\",...}"],
  "degradedSources": []
}
```

字段要点:
- **`degradedSources`**:诚实标注哪些数据源采集失败/不可用(如 `["state: db down"]`)。**它非空时,对应字段的"空"是"没查到"而非"确实没有"**——排障时先看这个,避免误判。
- **`auditAvailable`**:`false` 表示未接入可查询的审计后端(默认 `LoggingAuditSink` 只写日志不可查),此时 `recentAudit` 恒空;要用审计下钻须配置 `MybatisAuditSink`(写 `cw_audit_log`)。
- **`recentAudit`**:按 `agentName` 后缀匹配 sessionId,时间倒序。审批决策类审计不在此段(在 `approvals` 段已含决策人/时间)。
- **`qualityFacts`**:该会话相关的质检失败事实(JSONL 原文),取最近 `factLimit` 条。
- 审计事件下钻(更大 limit):`GET /api/customer/diagnostics/session/{sessionId}/audit?limit=100`。

诊断读取涉及 JDBC/文件 IO,已统一在 `boundedElastic` 线程执行,不阻塞事件循环。

### 8.6 业务数据分析报表(运维/运营专用)

按时间窗口聚合审批 / 人机切换 / 质检三个业务维度,回答"这段时间业务运转得怎么样"——区别于 §8.5 按 sessionId 聚合单会话现场。受 `X-API-Key` 保护。

```bash
# windowStartMs/windowEndMs 缺省时默认最近 24 小时;tenantId 缺省时质检维度返回空占位
curl -H "X-API-Key: <key>" "https://<host>/api/customer/analytics/business?tenantId=u1001"
```
```json
{
  "windowStartMs": 1751513600000,
  "windowEndMs": 1751600000000,
  "approval": {
    "totalInWindow": 12,
    "countByStatus": {"APPROVED": 8, "DENIED": 2, "PENDING": 2},
    "approvalRate": 0.8,
    "avgDecisionSeconds": 145.3,
    "currentPendingBacklog": 5
  },
  "handoff": {
    "totalInWindow": 7,
    "countByStatus": {"RESOLVED": 4, "CLAIMED": 1, "PENDING": 2},
    "avgTimeToClaimSeconds": 38.2,
    "avgTimeToResolveSeconds": 612.0,
    "currentPendingBacklog": 3,
    "currentClaimedBacklog": 1
  },
  "quality": {"tenantId": "u1001", "failureCountInWindow": 3, "avgScore": 62.5}
}
```

字段要点:
- **`approvalRate`**:放行率 = APPROVED / (APPROVED + DENIED);窗口内无已决策单时为 `0.0`(非 NaN,可直接展示)。`avgDecisionSeconds` 此时为 `null`。
- **`currentPendingBacklog`/`currentClaimedBacklog`**:**不受 window 参数影响**的当前积压快照——"周期内新增了多少"和"现在卡着多少"是两个不同的运维问题,分别看 `totalInWindow`/`countByStatus` 和 `current*Backlog`。
- **`quality`**:`tenantId` 未指定时整段为空占位(`tenantId=null, failureCountInWindow=0, avgScore=null`)——`FactLog` 按租户分文件存储,无法跨租户汇总,需要按租户逐个查询。
- **诚实边界**:不提供"转人工率"(handoff 量 / 会话总量)——没有可靠的"时间窗内会话总量"数据源(已结束会话已从状态存储删除,无法反推历史开启量),不编造不可靠的分母。

## 九、对话背后的内部逻辑(接入方须知)

这些机制在 `/chat`、`/chat/stream` 内部自动生效,接入方不直接调用,但会影响观察到的行为:

1. **意图快车道(fast-route)**:消息命中关键词规则且指向唯一意图时跳过 LLM 分诊直接路由,**该类请求显著更快**——同类问题延迟不一致是正常现象,不是故障。
2. **对话阶段状态机**:会话在 GREETING → 需求澄清 → 处理 → 收尾 等阶段间流转,系统按当前阶段动态调整 Agent 的系统提示词(分阶段聚焦)。阶段状态 prod 下落 MySQL(`dialog.store-mode=jdbc`),重启/换实例不"归零"。
3. **上下文压缩(Compaction)**:长会话超过阈值(8000 token / 40 条消息)时自动摘要压缩、保留最近 10 条——超长会话中 Agent 对很早之前细节的记忆是"摘要级"的,属预期行为。
4. **权限闸门(Permission ASK)**:`submitRefund` / `transferToHuman` 两个工具被配置为需确认,是退款双层防线的第一层(见 §4)。`transferToHuman` 触发的转人工现已登记为可查询工单(见 §6)。
5. **模型兜底与重试**:主模型(DashScope)失败自动重试(2 次,500ms 退避)后切兜底模型;触发兜底时监控指标 `customerwork.chat.fallback` 上升,回复质量可能下降——运维应关注该指标告警。
6. **敏感信息脱敏**:日志中的手机号/订单敏感字段自动掩码,排查问题时日志里看到 `138****5678` 属正常。
7. **审计**:审批决策等关键动作写入 `cw_audit_log`;对话内容本身不进审计表(在会话存储与可观测链路里)。
8. **入站防注入围栏**(需显式开启 `hooks.prompt-guard.enabled=true`,默认关闭):开启后命中中英文常见提示词注入/越狱模式(如"忽略之前的指令"/套取系统提示词)的消息会被**直接拒绝、不产生模型调用**,`/chat`/`/chat/stream` 均会收到统一拒绝话术而非正常回复——这不是故障,是安全围栏生效。

## 十、错误码与故障排查

| 状态码 | 场景 | 接入方处理 |
|---|---|---|
| 400 | 参数校验失败(message 为空/超 4000;status 枚举非法) | 检查请求体,响应 body 有具体字段错误信息 |
| 401 | `X-API-Key` 缺失或错误;`X-Approval-Token` 无效 | 核对运维下发的 Key/令牌 |
| 404 | 审批单/工单不存在 | 单号错误或查询了未生成的单 |
| 409 | 审批单重复决策;人机切换工单重复接单或未接单先结案 | 该单已被其他坐席处理,刷新列表即可 |
| 429 | 触发限流(默认 120 次/分钟/Key) | 退避重试;长期不够找运维调 `RATE_LIMIT_RPM` |
| 5xx | 服务端异常 | 用响应头 `X-Request-Id` 或错误体里的 `requestId` 字段找运维查日志(两者同值) |

**流式接口专项**:

| 现象 | 原因 | 处理 |
|---|---|---|
| SSE 一次性输出全部内容 | 网关/LB 开了响应缓冲 | 关闭该路径的 proxy buffering |
| SSE 中途断开且无 `done` 事件 | 空闲超 120s 被服务端断流,或网关超时更短 | 网关读超时须 > `stream.idle-timeout-seconds`;客户端视为异常结束 |
| 回复变慢、质量下降 | 主模型故障切了兜底模型 | 观察 `customerwork.chat.fallback` 指标,联系运维 |
| 同一会话回复串行变慢 | 会话锁排队(同 sessionId 并发请求) | 客户端收到回复后再发下一条 |

**接入自检清单**(新调用方上线前过一遍):

- [ ] 所有请求带 `X-API-Key`;坐席系统的 approve/deny 额外带 `X-Approval-Token`
- [ ] sessionId 采用 `租户:会话` 二段式(需要跨会话长期记忆时)且 ≤128 字符
- [ ] 匿名会话回填的 sessionId 已保存并在后续请求回传
- [ ] SSE 客户端正确处理 `message`/`done` 两类事件与中途断流
- [ ] 同一 sessionId 不并发发送
- [ ] 审批单完成态判断使用 `status + executionStatus` 双字段
- [ ] 坐席系统跟进人机切换工单按工单号(而非 sessionId)——sessionId 字段暂为占位值
- [ ] 409/429 有对应的用户侧提示与退避逻辑

## 十一、用户认证接口(用户工单系统)

面向**终端用户端**(如 `customer-work-app` H5、自建 App)。这组接口与 §3~§10 的运维/坐席接口是两套鉴权体系:
用户接口用 **JWT**(`Authorization: Bearer <token>`)而非 `X-API-Key`。JWT 由 `UserJwtService` 用 **HS256** 签发,
密钥来自 env `CW_USER_JWT_SECRET`(开发有默认值,生产必须覆盖),默认有效期 **7 天**(`user-auth.jwt-expire-hours=168`)。

> 说明:开启 `security.auth.enabled` 时,`/api/customer/auth/**` 与 `/api/customer/user/**` 是否需要额外的
> `X-API-Key` 取决于网关放行策略;JWT 是这组接口自身的身份来源,承载 `userId`。

### 11.1 注册 `POST /api/customer/auth/register`

```bash
curl -X POST https://<host>/api/customer/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"secret123","nickname":"爱丽丝","phone":"13800000000"}'
```
```json
{"userId": "U-3f2a9c7e-..."}
```
- `username` 3~64 位、`password` 6~64 位(BCrypt 加盐存储,不可逆);`nickname`/`phone` 可选。
- **用户名重复返回 409**;字段校验失败返回 400。

### 11.2 登录 `POST /api/customer/auth/login`

```bash
curl -X POST https://<host>/api/customer/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"secret123"}'
```
```json
{"token": "eyJhbGciOiJIUzI1NiJ9...", "userId": "U-3f2a9c7e-...", "nickname": "爱丽丝", "expiresAtMs": 1752200000000}
```
- **用户名或密码错误统一返回 401**(不区分"用户不存在"与"密码错",防用户名枚举);账户停用同样 401。
- `token` 供后续所有用户接口与 `/ws/user` 使用;`expiresAtMs` 为过期毫秒时间戳,客户端据此提前续登。

### 11.3 当前用户 `GET /api/customer/auth/me`

```bash
curl https://<host>/api/customer/auth/me -H "Authorization: Bearer <token>"
```
```json
{"userId": "U-3f2a9c7e-...", "username": "alice", "nickname": "爱丽丝", "phone": "13800000000"}
```
- 缺 Bearer / 令牌无效 / 用户不存在均返回 **401**。

## 十二、用户端工单接口

前缀 `/api/customer/user/**`,由 `UserAuthWebFilter` 校验 JWT。**主体身份从令牌解析,服务端不信任客户端自报的 userId**;
一切工单归属校验以令牌里的 `userId` 为准,越权访问他人工单返回 **403**,非法状态流转返回 **409**。

### 12.1 开会话 `POST /api/customer/user/sessions`

```bash
curl -X POST https://<host>/api/customer/user/sessions -H "Authorization: Bearer <token>"
```
```json
{"sessionId": "u<userId>:conv-<uuid>", "ticketId": "TK-..."}
```
- 生成会话号 `u<userId>:conv-<uuid>`(冒号前缀复用租户隔离机制,同一用户多会话共享长期记忆);同时建一张
  category=`CONSULT`、status=`AI_SERVING` 的工单。**保存 `sessionId` 用于连 `/ws/user` 与查消息**。

### 12.2 我的工单列表 `GET /api/customer/user/tickets`

```bash
curl "https://<host>/api/customer/user/tickets?status=WAITING_AGENT&page=1&size=20" \
```

```json
{"total": 3, "items": [{"id":"TK-...","status":"WAITING_AGENT","priority":"NORMAL","category":"CONSULT","title":"...","createdAtMs":1752100000000}]}
```
- `status` 可选(工单状态枚举,非法值 400);`page` 默认 1、`size` 默认 20。只返回当前用户自己的工单。

### 12.3 工单详情 `GET /api/customer/user/tickets/{id}`

```json
{"ticket": {"id":"TK-...","status":"PROCESSING","assignee":"agent-01","reopenCount":0,"...":"..."},
 "events": [{"eventType":"CREATE","fromStatus":null,"toStatus":"AI_SERVING","actorType":"SYSTEM","createdAtMs":1752100000000},
            {"eventType":"REQUEST_HANDOFF","fromStatus":"AI_SERVING","toStatus":"WAITING_AGENT","actorType":"USER","...":"..."}]}
```
- 返回工单主体 + 全量事件轨迹(时间正序)。**非本人工单返回 403**,不存在返回 404。

### 12.4 会话消息历史 `GET /api/customer/user/sessions/{sessionId}/messages`

```bash
curl "https://<host>/api/customer/user/sessions/u123:conv-abc/messages?beforeId=1050&limit=50" \

```

```json
[{"id":1048,"messageId":"MSG-...","sessionId":"u123:conv-abc","ticketId":"TK-...","senderType":"USER","senderId":"U-...","content":"你好","createdAtMs":1752100000000},
```

### 12.5 工单流转(用户侧)

| 端点 | 动作 | 允许的前态 → 后态 |
|---|---|---|
| `POST /user/tickets/{id}/handoff` | 转人工 | `AI_SERVING` → `WAITING_AGENT` |
| `POST /user/tickets/{id}/confirm` | 确认解决 | `WAITING_CONFIRM` → `RESOLVED` |
| `POST /user/tickets/{id}/reject` | 驳回 | `WAITING_CONFIRM` → `PROCESSING` |
| `POST /user/tickets/{id}/reopen` | 重开 | `RESOLVED`\|`CLOSED` → `WAITING_AGENT`(计数) |
| `POST /user/tickets/{id}/close` | 关单 | `AI_SERVING`\|`WAITING_CONFIRM`\|`RESOLVED` → `CLOSED` |

```bash
# 请求体可带可选 reason;返回流转后的工单全量 JSON
curl -X POST https://<host>/api/customer/user/tickets/TK-xxx/handoff \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"reason":"AI 没解决我的问题"}'
```
- **非法状态流转返回 409**(如对 `PROCESSING` 工单 confirm);**非本人工单 403**;不存在 404。

## 十三、坐席端工单接口

前缀 `/api/customer/agent/**`,由 `AgentAuthWebFilter` 校验请求头 **`X-Agent-Token`**(HMAC-SHA256 凭证,
格式 `agentId:expiresAtMs:签名`,由 `AgentAccessCredential` 签发,密钥 env `CW_AGENT_WS_SECRET`)。缺失/无效/过期返回 **401**。
坐席工作台通常经 §14 的 8082 代理调用这组接口,无需自己签令牌。

### 13.1 工单池筛选 `GET /api/customer/agent/tickets`

```bash
curl "https://<host>/api/customer/agent/tickets?status=WAITING_AGENT&priority=HIGH&category=AFTER_SALE&page=1&size=20" \
  -H "X-Agent-Token: <凭证>"
```
```json
{"total": 12, "items": [{"id":"TK-...","status":"WAITING_AGENT","priority":"HIGH","userId":"U-...","...":"..."}]}
```
- 可选筛选:`status` / `assignee` / `category` / `priority`(非法枚举 400)。

### 13.2 详情与消息

- `GET /api/customer/agent/tickets/{id}` → `{ticket, events}`(同 §12.3 结构,不存在 404)。
- `GET /api/customer/agent/tickets/{id}/messages?beforeId=&limit=` → 消息数组(游标分页,同 §12.4)。

### 13.3 接单与流转

| 端点 | 动作 | 说明 / 状态码 |
|---|---|---|
| `POST .../{id}/claim` | 接单 | `WAITING_AGENT`→`PROCESSING`,**乐观锁抢单,已被抢占返回 409** |
| `POST .../{id}/reply` | 回复用户 | body `{content}`,返回落库的 `ChatMessage`;**非受理坐席 403**;用户离线时仅落库不报错 |
| `POST .../{id}/hold` | 挂起 | `PROCESSING`→`ON_HOLD`,body 可带 `{reason, note}` |
| `POST .../{id}/resume` | 恢复 | `ON_HOLD`→`PROCESSING` |
| `POST .../{id}/transfer` | 转派 | body `{toAgent}`:空→转回队列(`WAITING_AGENT`),非空→换绑指定坐席 |
| `POST .../{id}/resolve` | 提交解决 | `PROCESSING`→`WAITING_CONFIRM`,body 可带 `{note}` |
| `POST .../{id}/close` | 关单 | body 可带 `{reason}` |
| `PUT .../{id}/priority` | 改优先级 | body `{priority}`(LOW/NORMAL/HIGH/URGENT),空 400 |
| `PUT .../{id}/category` | 改分类 | body `{category}`(CONSULT/ORDER/AFTER_SALE/COMPLAINT/OTHER),空 400 |

```bash
# 接单
curl -X POST https://<host>/api/customer/agent/tickets/TK-xxx/claim -H "X-Agent-Token: <凭证>"
# 回复用户(消息经 WebSocket 实时推送给在线用户)
curl -X POST https://<host>/api/customer/agent/tickets/TK-xxx/reply \
  -H "X-Agent-Token: <凭证>" -H "Content-Type: application/json" -d '{"content":"您好,已为您处理"}'
```
- 所有非法状态流转返回 **409**;工单不存在 404。

### 13.4 坐席订单接口 `GET/POST /api/customer/agent/orders/**`

同前缀 `/api/customer/agent/**`,鉴权同 §13(`X-Agent-Token`)。`tool-backend.mode!=jdbc`(无订单数据源)时
整组接口返回 **503**。

| 端点 | 说明 |
|---|---|
| `GET /api/customer/agent/orders` | 分页查询,过滤参数 `userId`/`username`(模糊)/`orderId`/`status`(均可选) + `page`/`size`(默认 1/20),按下单时间倒序,返回含 `username` |
| `GET /api/customer/agent/orders/{orderId}` | 详情,含 `logisticsTrace`(物流轨迹);不存在 **404** |
| `POST /api/customer/agent/orders/{orderId}/modify-address` | 改收货地址,body `{"newAddress":"..."}`;`newAddress` 为空 **400** |
| `POST /api/customer/agent/orders/{orderId}/cancel` | 取消订单,body 可选 `{"reason":"..."}`;**仅"待支付/已支付/待发货"(未发货)可取消**,已发货及之后状态返回 **409** |

```bash
# 分页查询(按用户名模糊 + 状态过滤)
curl "https://<host>/api/customer/agent/orders?username=张三&status=待发货&page=1&size=20" \
  -H "X-Agent-Token: <凭证>"
```
```json
{"total": 3, "items": [{"orderId":"O-20260613001","userId":"U-...","username":"张三","productId":"P001",
  "productName":"...","amount":"199.00","status":"待发货","receiverAddr":"...","createdAtMs":1752300000000}]}
```
```bash
# 改址
curl -X POST https://<host>/api/customer/agent/orders/O-20260613001/modify-address \
  -H "X-Agent-Token: <凭证>" -H "Content-Type: application/json" -d '{"newAddress":"北京市朝阳区xxx"}'
# 取消(状态不允许时返回 409)
curl -X POST https://<host>/api/customer/agent/orders/O-20260613001/cancel \
  -H "X-Agent-Token: <凭证>" -H "Content-Type: application/json" -d '{"reason":"用户主动取消"}'
```
- 金额字段统一格式化为两位小数字符串(如 `"199.00"`)。

## 十四、admin 代理接口(customer-admin-server, 8082)

坐席工作台前端(`customer-admin-web`)不直接持有 `CW_AGENT_WS_SECRET`,而是经后台管理系统 8082 的
`/api/ticket/**` 代理坐席 API:8082 用 `RestClient` **每次请求现签** `X-Agent-Token`(TTL 120s)转发到 8080,
前置 **Sa-Token 权限点**校验,响应统一 `Result<T>` 包装,写操作带 `@OperationLog` 审计。

| 8082 端点 | 转发到 8080 | Sa-Token 权限点 |
|---|---|---|
| `GET /api/ticket/page` | `GET /agent/tickets` | `user-ticket:view` |
| `GET /api/ticket/{id}` · `/{id}/messages` | 同名 | `user-ticket:view` |
| `POST /api/ticket/{id}/claim` | `/{id}/claim` | `user-ticket:claim` |
| `POST /api/ticket/{id}/reply` | `/{id}/reply` | `user-ticket:reply` |
| `POST /api/ticket/{id}/transfer` | `/{id}/transfer` | `user-ticket:transfer` |
| `POST /api/ticket/{id}/resolve` | `/{id}/resolve` | `user-ticket:resolve` |
| `POST /api/ticket/{id}/close` | `/{id}/close` | `user-ticket:close` |
| `POST /api/ticket/{id}/hold` · `/resume`、`PUT /{id}/priority` · `/category` | 同名 | `user-ticket:edit` |
| `GET /api/ticket/ws-credential` | — | `user-ticket:view` |
| `GET /api/ticket/orders/page` | `GET /agent/orders` | `user-order:view` |
| `GET /api/ticket/orders/{orderId}` | `GET /agent/orders/{orderId}` | `user-order:view` |

| `POST /api/ticket/orders/{orderId}/cancel` | `POST /agent/orders/{orderId}/cancel` | `user-order:edit` |

- **用户订单管理**(`user-order:*`,Flyway `V20__user_orders_menu.sql`,菜单 id=139 挂 `客服工单`分组、按钮
  140/141):`UserOrderController`/`UserOrderService` 薄委托给同一个 `CustomerWorkTicketClient`,直接透传 8080
  的分页契约(`{"total":n,"items":[...]}`),本模块不建订单业务表。`CustomerWorkTicketClient` 把 8080 的
  404/409 翻译为订单专属错误码:404→`ORDER_NOT_FOUND`(40013,"订单不存在"),409→`ORDER_STATE_CONFLICT`
  (40014,"订单当前状态不允许该操作"),经 `GlobalExceptionHandler` 转标准 `Result` 响应体。

```bash
# 8082 分页(query 参数用 pageNum/pageSize,内部映射为 8080 的 page/size)
curl "https://<admin-host>/api/ticket/orders/page?username=张三&status=待发货&pageNum=1&pageSize=20" \
  -H "Authorization: Bearer <后台登录令牌>"
# 8082 取消(订单已发货时 8080 返回 409,客户端翻译为 ORDER_STATE_CONFLICT)
curl -X POST https://<admin-host>/api/ticket/orders/O-20260613001/cancel \
  -H "Authorization: Bearer <后台登录令牌>" -H "Content-Type: application/json" -d '{"reason":"客服代取消"}'
```
```json
{"code": 40014, "message": "订单当前状态不允许该操作", "data": null, "timestamp": 1752300000000}
```

- **`GET /api/ticket/ws-credential`** 签发坐席 WebSocket 凭证,供浏览器**直连** 8080 的 `/ws/agent`(长连接不经 8082):

```json
{"token": "agent-01:1752200000000:xxxxx", "wsUrl": "ws://<8080host>/ws/agent", "expiresAtMs": 1752200000000, "agentId": "agent-01"}
```
- 8080 侧异常翻译:工单接口 409→`TICKET_STATE_CONFLICT`;订单接口 404→`ORDER_NOT_FOUND`、409→`ORDER_STATE_CONFLICT`;
  两者共用 401→`CUSTOMER_WORK_AUTH_FAILED`、IO/超时→`CUSTOMER_WORK_UNAVAILABLE`(均包成 `BizException`)。
- 配置前缀 `admin.customer-work.*`:`base-url`(默认 `http://localhost:8080`)、`ws-url`(默认 `ws://localhost:8080/ws/agent`)、
  `agent-secret`(**必须与 8080 共享同一 env `CW_AGENT_WS_SECRET`**)、`credential-expire-hours`(默认 12)。

## 十五、WebSocket 接入说明

两个原生 WebFlux WebSocket 端点,统一帧协议 `{"type": "...", "data": {...}}`(JSON)。握手鉴权失败以
`POLICY_VIOLATION`(1008)关闭连接;同一身份重复连接会**顶号**(旧连接被服务端正常收尾)。

### 15.1 连接方式

| 端点 | 鉴权 | 连接示例 |
|---|---|---|
| `/ws/user?token=<JWT>` | 用户 JWT(§11) | `new WebSocket("wss://<host>/ws/user?token=" + jwt)` |
| `/ws/agent?token=<HMAC凭证>` | 坐席 HMAC 凭证(§14 领取) | `new WebSocket("ws://<8080host>/ws/agent?token=" + credential)` |

### 15.2 上行帧(客户端 → 服务端)

```json
// 用户发消息
{"type": "chat", "data": {"sessionId": "u123:conv-abc", "content": "帮我查订单 20260613001"}}
// 用户主动转人工
{"type": "handoff", "data": {"sessionId": "u123:conv-abc", "reason": "要人工"}}
// 坐席回复(坐席端;须为该工单受理坐席)
{"type": "chat", "data": {"ticketId": "TK-xxx", "content": "您好,已为您处理"}}
// 心跳(双端)
{"type": "ping"}
```

### 15.3 下行帧(服务端 → 客户端)

```json
// 一条完整消息(坐席回复 / 转发 / 用户回显)
{"type": "chat", "data": {"messageId":"MSG-...","sessionId":"u123:conv-abc","ticketId":"TK-...","senderType":"AGENT","senderId":"agent-01","content":"...","ts":1752100000000}}
// AI 流式增量(打字机)
{"type": "chat_chunk", "data": {"content": "您好,"}}
// AI 流式定稿(全文,已落库)
{"type": "chat_done", "data": {"messageId":"MSG-...","content":"您好,请问...","ts":1752100000000}}
// 工单流转事件(推给相关用户与坐席)
{"type": "ticket_event", "data": {"ticketId":"TK-...","eventType":"CLAIM","fromStatus":"WAITING_AGENT","toStatus":"PROCESSING","actorType":"AGENT","status":"PROCESSING","assignee":"agent-01","ts":1752100000000}}
// 新工单进池(广播全体在线坐席,唤起抢单)
{"type": "ticket_new", "data": {"ticketId":"TK-...","userId":"U-...","title":"...","priority":"NORMAL","category":"CONSULT","ts":1752100000000}}
// 系统提示
{"type": "system", "data": {"content": "客服正在赶来的路上,请稍候", "ts": 1752100000000}}
// 帧级错误(不断开连接)
{"type": "error", "data": {"code": "CHAT-NOT-ASSIGNEE", "message": "..."}}
// 心跳应答
{"type": "pong"}
```

### 15.4 客户端处理要点

- `senderType` 取值 `USER`/`BOT`/`AGENT`/`SYSTEM`,前端据此渲染不同气泡。
- AI 回复走 `chat_chunk` 增量拼接 + `chat_done` 定稿;坐席回复/转发直接走单条 `chat`。
- 收到 `ticket_event` 应刷新工单状态与可用操作按钮;坐席端收到 `ticket_new` 提示有新工单可抢。
- `error` 帧不断开连接(如帧格式错 `CHAT-FRAME-INVALID`、非受理坐席 `CHAT-NOT-ASSIGNEE`、会话越权 `CHAT-SESSION-DENIED`);
  只有握手鉴权失败才会 `POLICY_VIOLATION` 关闭。
- 离线期间的消息不会漏:重连后经 `GET .../messages?beforeId=&limit=` 拉历史补齐即可。

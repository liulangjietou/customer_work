## 1. 项目总览

这是一个把"大模型智能体"工程化落地为**可上生产的客服系统**的参考实现。核心理念贯穿全项目：

> **每个能力 = 一个配置开关 + 一个可替换实现。** 内置实现保证离线开箱即用、单测可过；生产改一行配置或提供一个 Bean，即可切到云端 / 私有化后端，业务代码零改动。

## 2. 技术栈原理与优缺点

| 技术 | 在本项目的角色 | 原理简述 | 优点 | 缺点 / 注意 |
|---|---|---|---|---|
| **Spring Boot 3.2 (WebFlux)** | Web 框架 + 依赖注入 | 基于 Reactor 的异步非阻塞 Web 栈，事件循环少量线程处理高并发 | 高吞吐、与 Agent 的响应式天然契合、SSE 流式友好 | 调试链路较命令式难；`block()` 误用会拖垮事件循环；MDC 透传需借助 Reactor Context |
| **Project Reactor** | 异步编程模型（`Mono`/`Flux`） | 声明式数据流 + 背压；`retryWhen`/`onErrorResume`/`contextWrite` 等算子 | 组合性强、背压、内建重试/超时 | 学习曲线陡；冷热流、订阅时机易踩坑（本项目重试 bug 即源于此，见 §6） |
| **AgentScope Java 1.0.12** | 智能体框架 | ReActAgent（推理-行动循环）+ Toolkit + Memory + Session/State + Hook + Model 抽象 | 纯 Java、Spring 友好、抽象完整可插拔 | 高速迭代，部分能力需扩展依赖；流式协议等细节仍在演进 |
| **DashScope（百炼）** | 默认大模型 | 通义千问 OpenAI 兼容/原生协议；`stream` 增量返回 | 国产、合规、Embedding/TTS 齐全 | 需 API Key、计费；联网搜索/思考为厂商特有参数 |
| **Jedis** | Redis 会话存储 | `UnifiedJedis` 连接池，惰性连接 | 多实例共享会话 | 单机限流不分布式（见 §13） |
| **HikariCP + MySQL** | MySQL 会话存储 | JDBC 连接池；`MysqlSession` 自动建表 | 强一致、可审计 | 需运维 DB |
| **Nacos Client 3.0.2** | 配置中心 | `ConfigService` 长轮询监听配置变更 | 提示词热更新、灰度 | AI/A2A API 需更高版本（见 §16） |
| **Micrometer + Actuator** | 指标 / 健康 | 维度化指标 + `/actuator` 端点 | Prometheus 生态、运维就绪 | 指标基数需控制 |
| **springdoc-openapi 2.3** | API 文档 | 扫描注解生成 OpenAPI + Swagger UI | 在线调试、契约 | 与 Boot 版本需匹配 |
| **okhttp** | Mem0/ReMe 客户端依赖 | HTTP 客户端 | 框架记忆扩展所需 | 仅特定 provider 用 |
| **JaCoCo** | 覆盖率 | 字节码插桩统计 | 质量度量 | 报告非门禁（本项目仅产出报告） |

## 3. 整体架构

### 3.0 工程模块（多模块 Maven 工程）

```mermaid
flowchart LR
    PARENT["customer-work-parent (pom)"] --> ST["customer-work-spring-boot-starter<br/>可复用 starter（含 @AutoConfiguration）"]
    PARENT --> EX["customer-work-example<br/>可运行客服示例 (包 ...customerworkapp)"]
    EX -->|依赖| ST
    DOWN["任意下游工程 (任意包名)"] -->|引入 starter 依赖| ST
    note["下游零扫描：引入 starter + 写自己的 *Backend Bean / Controller，即得完整能力"]
```

- `starter`：配置/装配/模型层/记忆/RAG/工具 SPI/安全/可观测/Nacos 等**可复用基础设施**，
  通过 `@AutoConfiguration`（`CustomerWorkAutoConfiguration`，注册于
  `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）自动装配。
- `example`：`CustomerWorkApplication`（包 `com.richard.fyoung.customerworkapp`）+ Controller + 业务资源。

**自动装配原理与边界**：

```mermaid
flowchart TB
    BOOT["下游 @SpringBootApplication 启动"] --> AC["Spring Boot 读取<br/>AutoConfiguration.imports"]
    AC --> CWA["CustomerWorkAutoConfiguration<br/>@ComponentScan(com.richard.fyoung.customerwork)<br/>@EnableConfigurationProperties + @EnableScheduling"]
    CWA --> BEANS["装配 starter 全部 Bean"]
    APP["下游自身 @SpringBootApplication<br/>扫描自身包(如 ...customerworkapp)"] --> OWN["装配下游自己的 Controller/Backend"]
    BEANS -. 包名不重叠, 无重复装配 .- OWN
```

- starter 固定扫描自身包 `com.richard.fyoung.customerwork`；example 在独立包 `com.richard.fyoung.customerworkapp`，
  两者不重叠 → 下游自身扫描与 starter 自动装配各管各的，**不会重复注册**。
- starter 用 **HikariCP** 而非 `spring-jdbc`，因此不触发 `DataSourceAutoConfiguration`，下游无需排除它。

## 5. 一次请求的全流程时序

### 5.1 同步对话 `POST /chat`

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant F as 过滤器链<br/>(RequestId→Auth→RateLimit)
    participant Ctrl as Controller
    participant Svc as CustomerServiceService
    participant Fac as AgentFactory
    participant Ag as ReActAgent
    participant M as Model(可能含Retry/Fallback)
    participant T as Toolkit→Backend

    C->>F: HTTP 请求(+X-API-Key)
    F->>F: 生成 X-Request-Id / 校验Key / 限流
    F->>Ctrl: 放行
    Ctrl->>Svc: chat(sessionId, message)
    Svc->>Svc: resolveAgent(sid)<br/>computeIfAbsent + loadIfExists
    alt 会话首次出现
        Svc->>Fac: createAgent(sid)
        Fac-->>Svc: 装配好的 ReActAgent
        Svc->>Ag: loadIfExists(session,key) 恢复历史
    end
    Svc->>Ag: call(userMsg)
    loop ReAct 循环 (≤ maxIters)
        Ag->>M: stream(推理)
        M-->>Ag: 文本/工具调用决策
        opt 需要工具
            Ag->>T: 执行工具(委托后端)
            T-->>Ag: 工具结果
        end
    end
    Ag-->>Svc: 最终回复 Msg
    Svc->>Svc: persist(sid) 异步 saveTo (boundedElastic)
    Svc-->>Ctrl: reply 文本
    Ctrl-->>C: ChatResponse(JSON)
```

## 6. 模型层

`ModelConfig.chatModel()` 用**装饰器模式**按配置层层包装：`Retry( Fallback( Provider ) )`。

```mermaid
flowchart LR
    P["按 provider 构建<br/>dashscope/openai/anthropic/gemini/ollama"] --> FBQ{fallback.enabled?}
    FBQ -- 是 --> FB["FallbackChatModel(primary, 兜底)"]
    FBQ -- 否 --> RTQ
    FB --> RTQ{retry.enabled?}
    RTQ -- 是 --> RT["ResilientChatModel(退避重试)"]
    RTQ -- 否 --> OUT
    RT --> OUT["@Bean Model"]
```

**调用期行为**（兜底 + 重试叠加）：

```mermaid
sequenceDiagram
    participant A as ReActAgent
    participant R as ResilientChatModel
    participant FB as FallbackChatModel
    participant P as 主模型
    participant S as 兜底模型(Ollama)
    A->>R: stream()
    R->>FB: Flux.defer(每次重试重新发起)
    FB->>P: stream()
    alt 主模型成功
        P-->>FB: 结果
    else 主模型出错
        FB->>S: onErrorResume 切兜底
        S-->>FB: 结果
    end
    FB-->>R: 结果/错误
    Note over R: 出错则 retryWhen(backoff) 重订阅 defer
```

> **原理要点（也是踩坑点）**：Reactor 的 `retryWhen` 会**重订阅同一个上游**。若直接 `delegate.stream().retryWhen()`，重试只是重订阅"已失败的同一个流"，对真实调用无效。本项目用 `Flux.defer(() -> delegate.stream(...))` 保证**每次重试重新发起底层调用**——这正是 `ResilientChatModelTest` 守护的语义。
> **优点**：统一抽象屏蔽厂商差异；私有化兜底满足数据主权；重试提升高可用。**缺点/边界**：anthropic/gemini 需各自 SDK；多模态/工具 schema 在不同厂商表现有差异，切换需回归评估（见 `docs/EVAL.md`）。

## 7. Agent 装配与 ReAct 循环

`CustomerServiceAgentFactory.createAgent(sessionId)` 是装配中枢：

```mermaid

    START["createAgent(sessionId)"] --> TK["buildToolkit()<br/>ToolRegistrar+分组 / MetaTool / MCP / Higress"]
    START --> SP["systemPrompt()<br/>Nacos 下发 ↔ 内置回退"]
    START --> B["ReActAgent.builder()"]
    TK --> B
    SP --> B
    B --> MEM["memory: ContextMemoryFactory<br/>(InMemory / AutoContext)"]
    B --> H1["hook: ObservabilityHook(+token护栏)"]
    B --> H2{humanApproval.enabled?}
    H2 -- 是 --> HA["hook: HumanApprovalHook"]
    B --> H3{observability.trace?}
    H3 -- 是 --> TR["hook: JsonlTraceExporter"]
    B --> H4{protocol.tts?}
    H4 -- 是 --> TTS["hook: TTSHook"]
    B --> PTR["enablePendingToolRecovery(中断恢复)"]
    B --> PLAN{plan.enabled?}

    B --> LTMC{memory.longTermEnabled?}
    LTMC -- 是 --> LTM["longTermMemory(provider) + mode BOTH"]
    B --> RAGC{rag.enabled?}
    RAGC -- 是 --> KN["knowledge(provider) + ragMode AGENTIC"]
    B --> SKC{skill.enabled?}
    SKC -- 是 --> SB["skillBox(classpath/filesystem +可选代码执行)"]
    B --> BUILD["build() → ReActAgent"]
```

**ReAct（Reasoning + Acting）原理**：让 LLM 做"大脑"，循环【推理→决定调工具→观察结果→再推理】，直到给出最终答复或达 `maxIters` 上限。相比写死的 Workflow，自主性强、能吃模型能力红利；本项目用 `maxIters`、`HumanApprovalHook`（高风险工具暂停）、`interrupt()`（安全中断）、`enablePendingToolRecovery`（中断恢复）四件套约束其"自主性失控"风险。

## 8. 会话持久化

`SessionConfig` 按 `session.mode` 提供 `Session` Bean；`CustomerServiceService` 进程内缓存热 Agent，并用框架 `State` 能力跨请求/跨进程恢复。

```mermaid
flowchart LR
    MODE{session.mode} -->|memory| IM[InMemorySession]
    MODE -->|json| JS[JsonSession 落盘]
    MODE -->|redis| RS[RedisSession via Jedis]
    MODE -->|mysql| MS[MysqlSession via HikariCP<br/>表 agentscope_sessions 自动建]
```

```mermaid
stateDiagram-v2
    [*] --> 新会话: 请求到达
    新会话 --> 装配: createAgent
    装配 --> 恢复: loadIfExists(session,key)
    恢复 --> 活跃
    活跃 --> 活跃: chat()每轮 → persist saveTo
    活跃 --> 已清理: endSession() / session.delete
    已清理 --> [*]
```

> `SessionStateManager` 进一步用框架 `SessionManager` 把多个 `StateModule`（记忆/计划/工具状态）作为整体 save/load，替代逐个手工编排。**优点**：内存零运维、json 单机可恢复、redis 多实例共享、mysql 强一致可审计。**边界**：redis/mysql 需运维；持久化在 `boundedElastic` 异步执行避免阻塞事件循环。

## 11. 工具体系与可替换后端

这是"改成你自己的业务 Agent"的关键。工具壳只承载暴露给 LLM 的 **Schema**，业务逻辑委托给接口后端：

```mermaid
flowchart LR
    LLM[LLM 决定调用工具] --> Tools["OrderTools/AfterSalesTools/KnowledgeBaseTools<br/>(@Tool Schema 壳)"]
    Tools --> BE{后端接口}
    BE -->|默认| MOCK["MockXxxBackend<br/>@ConditionalOnMissingBean"]
    BE -->|你的实现| MINE["MyXxxBackend<br/>(WebClient 调真实微服务)"]
```

**扩展方式**（零改框架）：
```java
@Component
public class MyOrderBackend implements OrderBackend {
    public Mono<String> queryOrder(String id) { /* 调你的订单服务 */ }
    public Mono<String> queryLogistics(String id) { /* ... */ }
}
```
`ToolBackendConfig` 的默认 `@Bean` 标了 `@ConditionalOnMissingBean`，你的 Bean 一出现，默认 Mock 自动让位。

> **原理**：`@ConditionalOnMissingBean` 只在 `@Bean` 方法（配置类）上可靠生效，不能放在 `@Component` 扫描类上——这是本项目修过的真实 bug（冒烟测试 `ApplicationContextTest` 抓到）。
> 工具组（Tool Group）+ 可选 Meta-Tool 让 Agent 在大量工具时按需激活，缓解上下文窗口压力。

## 12. 多 Agent 编排

`MultiAgentOrchestrator` 构建订单/售后/知识库三个专家 Agent，用框架 `Pipelines` 编排：

## 13. 接入层安全与请求治理

WebFilter 按 `@Order` 串成链（数字越小越先）：

```mermaid
flowchart LR
    REQ[请求] --> F0["RequestIdWebFilter<br/>HIGHEST_PRECEDENCE"]
    F0 --> F1["ApiKeyAuthWebFilter<br/>+10"]
    F1 --> F2["RateLimitWebFilter<br/>+20"]
    F2 --> CTRL[Controller]
    F0 -. 写回 X-Request-Id + Reactor 上下文 .-> RESP
    F1 -. 401 .-> RESP[响应]
    F2 -. 429 .-> RESP
```

- **鉴权**：校验 `X-API-Key`；健康/Actuator/Swagger 路径豁免。
- **限流**：固定时间窗，按 API Key 或客户端 IP 计数，超限 429。分布式部署应换 Redis 限流（接口不变可平滑替换）。
- **请求关联**：生成/透传 `X-Request-Id` 进响应头与 Reactor Context，便于全链路排障。
- 默认鉴权/限流关闭，生产开启（见 README §6.14）。

## 18. 设计取舍与边界

- **响应式全链路无 `.block()`**：业务链路严格异步；仅持久化落盘放 `boundedElastic`，演示/测试边界处除外。
- **配置开关 + 可替换实现**：以少量"默认 Mock"换取离线可跑、可测、易采用；代价是初次阅读需理解 provider/配置分发。
- **效果非确定性**：AI 输出不确定，单测覆盖"工程正确性"，"效果正确性"靠评估（`docs/EVAL.md`）。
- **框架版本**：锁定 `agentscope 1.0.12`；Harness 等 1.1+ 能力为升级后扩展点。
- **安全**：仓库零密钥，全部环境变量注入；生产建议 Vault/KMS/K8s Secret。

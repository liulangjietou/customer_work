## 1. 项目总览

这是一个把"大模型智能体"工程化落地为**可上生产的客服系统**的参考实现，已迁移到 **AgentScope 2.0**。核心理念贯穿全项目：

> **每个能力 = 一个配置开关 + 一个可替换实现。** 内置实现保证离线开箱即用、单测可过；生产改一行配置或提供一个 Bean，即可切到云端 / 私有化后端，业务代码零改动。

2.0 带来的架构升级（相对 1.x）：

> **Agent 无状态化**：状态按 `(userId, sessionId)` 外置到 `AgentStateStore`，单实例并发服务多租户多会话；
> **五段 Middleware** 取代松散 Hook；**HarnessAgent** 在 ReActAgent 之上叠加 Plan Mode / Compaction / Sandbox / Subagent；
> **Permission System** 成为框架原生的工具权限闸门。

## 2. 技术栈原理与优缺点

| 技术 | 在本项目的角色 | 原理简述 | 优点 | 缺点 / 注意 |
|---|---|---|---|---|
| **Spring Boot 3.2 (WebFlux)** | Web 框架 + 依赖注入 | 基于 Reactor 的异步非阻塞 Web 栈 | 高吞吐、与 Agent 响应式契合、SSE 友好 | `block()` 误用拖垮事件循环；MDC 需 Reactor Context 透传 |
| **Project Reactor** | 异步编程模型（`Mono`/`Flux`） | 声明式数据流 + 背压；中间件链即 `Function<Input, Flux<AgentEvent>>` | 组合性强、背压、内建重试/超时 | 学习曲线陡；冷热流易踩坑（见 §6 重试） |
| **AgentScope Java 2.0.0 GA (`agentscope-harness`)** | 智能体框架 | ReActAgent + HarnessAgent + Toolkit + **AgentStateStore** + **Middleware** + Permission + Sandbox + Model 抽象 | 纯 Java、Spring 友好、无状态可横扩、Harness 工程底座完整、已 GA | 部分扩展（远端沙箱/k8s 等）需引扩展坐标；内置模型实现（OpenAI/DashScope/Anthropic/Gemini/Ollama）自 GA 起拆分为独立 `agentscope-extensions-model-*` 模块 |
| **DashScope（百炼）** | 默认大模型 | 通义千问 OpenAI 兼容/原生协议；`stream` 增量返回 | 国产、合规、Embedding 齐全 | 需 API Key、计费 |
| **Jedis** | Redis 状态存储 | `JedisPool` 连接池 → `JedisAgentStateStore` | 多实例共享会话状态 | 单机限流不分布式（见 §15） |
| **HikariCP + MySQL** | MySQL 状态存储 | JDBC 连接池 → `MysqlAgentStateStore` 自动建表 | 强一致、可审计 | 需运维 DB |
| **Nacos Client 3.0.2** | 配置中心 | `ConfigService` 长轮询监听 | 提示词热更新 | AI/A2A API 需更高版本 |
| **Micrometer + Actuator** | 指标 / 健康 | 维度化指标 + `/actuator` | Prometheus 生态 | 指标基数需控制 |
| **springdoc-openapi 2.3** | API 文档 | 扫描注解生成 OpenAPI + Swagger UI | 在线调试 | 与 Boot 版本需匹配 |
| **JaCoCo** | 覆盖率 | 字节码插桩 | 质量度量 | 报告非门禁 |

> **依赖编排**：`agentscope-bom` 统一管理 core/harness/extensions 版本；扩展能力（Redis/MySQL 状态、
> Mem0/ReMe/百炼记忆、Dify/百炼 RAG、AG-UI、Higress、Studio、Nacos 提示词）走 `agentscope-extensions-*`，
> 且多数沿用 `io.agentscope.core.*` 包名，迁移时整合层代码零改动。

## 3. 整体架构

### 3.0 工程模块（多模块 Maven 工程）

```mermaid
flowchart LR
    PARENT["customer-work-parent (pom)<br/>引入 agentscope-bom"] --> ST["customer-work-starter<br/>可复用 starter（含 @AutoConfiguration）"]
    PARENT --> EX["customer-work-app-server<br/>可运行客服示例 (包 ...customerworkapp)"]
    EX -->|依赖| ST
    DOWN["任意下游工程 (任意包名)"] -->|引入 starter 依赖| ST
    note["下游零扫描：引入 starter + 写自己的 *Backend Bean / Controller，即得完整能力"]
```

- `starter`：配置/装配/模型层/记忆/RAG/工具 SPI/**五段 Middleware**/**Permission**/安全/可观测/Nacos 等可复用基础设施，
  通过 `@AutoConfiguration`（`CustomerWorkAutoConfiguration`）自动装配。
- `app`：`CustomerWorkApplication`（包 `com.richard.fyoung.customerworkapp`）+ Controller + 业务资源。
- starter 固定扫描自身包 `com.richard.fyoung.customerwork`；与 app 包名不重叠 → 无重复装配。
- starter 用 **HikariCP** 而非 `spring-jdbc`，不触发 `DataSourceAutoConfiguration`，下游零排除即插即用。

## 5. 一次请求的全流程时序

### 5.1 同步对话 `POST /chat`（2.0）

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant F as 过滤器链<br/>(RequestId→Auth→RateLimit)
    participant Ctrl as Controller
    participant Svc as CustomerServiceService
    participant Fac as AgentFactory
    participant Ag as ReActAgent
    participant Store as AgentStateStore
    participant M as Model(可能含Retry/Fallback)
    participant T as Toolkit→Backend

    C->>F: HTTP 请求(+X-API-Key)
    F->>F: 生成 X-Request-Id / 校验Key / 限流
    F->>Ctrl: 放行
    Ctrl->>Svc: chat(sessionId, message)
    Svc->>Fac: createAgent(sid) [缓存未命中时]
    Svc->>Fac: contextFor(sid) → RuntimeContext(userId,sessionId[,org])
    Svc->>Ag: call(text, ctx)
    Ag->>Store: 按 (userId,sessionId) 自动加载历史 AgentState
    loop ReAct 循环 (≤ maxIters)
        Ag->>M: stream(推理)
        M-->>Ag: 文本/工具调用决策
        opt 需要工具
            Note over Ag: Permission 校验 + onActing 中间件链
            Ag->>T: 执行工具(委托后端)
            T-->>Ag: 工具结果
        end
    end
    Ag->>Store: 自动持久化更新后的 AgentState
    Ag-->>Svc: 最终回复 Msg
    Svc-->>Ctrl: reply 文本
    Ctrl-->>C: ChatResponse(JSON)
```

> 与 1.x 的差异：**无 `loadIfExists/saveTo` 手工调用**；加载/持久化由框架在 `call` 链路按 `RuntimeContext`
> 自动完成。热 Agent 缓存仅用于摊薄"按会话装配 Agent"的构建开销，淘汰不丢数据（状态在 Store）。

### 5.2 流式对话 `POST /chat/stream`（SSE）

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant Ctrl as Controller
    participant Svc as Service
    participant Ag as ReActAgent
    C->>Ctrl: POST /chat/stream
    Ctrl->>Svc: chatStream(sid, text)
    Svc->>Ag: stream(List.of(msg), StreamOptions[REASONING,AGENT_RESULT], ctx)
    loop 逐事件
        Ag-->>Svc: Event(增量文本)
        Svc-->>Ctrl: 文本片段
        Ctrl-->>C: SSE event: message / data
    end
    Note over Ag: 流结束 → 框架自动持久化状态
    Ctrl-->>C: SSE event: done / [DONE]
```

## 6. 模型层

`ModelConfig.chatModel()` 用**装饰器模式**按配置层层包装：`Retry( Fallback( Provider ) )`。

```mermaid
flowchart LR
    P["按 provider 构建<br/>dashscope/openai/anthropic/gemini/ollama"] --> FBQ{fallback.enabled?}
    FBQ -- 是 --> FB["FailoverModel(候选链, 熔断)"]
    FBQ -- 否 --> RTQ
    FB --> RTQ{retry.enabled?}
    RTQ -- 是 --> RT["ResilientChatModel(退避重试)"]
    RTQ -- 否 --> OUT
    RT --> OUT["@Bean Model"]
```

> **原理要点（也是踩坑点）**：Reactor 的 `retryWhen` 会**重订阅同一个上游**。若直接
> `delegate.stream().retryWhen()`，重试只是重订阅"已失败的同一个流"，对真实调用无效。本项目用
> `Flux.defer(() -> delegate.stream(...))` 保证**每次重试重新发起底层调用**——`ResilientChatModelTest` 守护此语义。
>
> **2.0 内置替代**：`ReActAgent/HarnessAgent.Builder` 原生支持 `.maxRetries(int)` 与 `.fallbackModel(Model/String)`，
> 可替代自研装饰器。本项目保留自研版以演示"装饰器组合"原理，二者择一即可。
>
> **优点**：统一抽象屏蔽厂商差异；私有化兜底满足数据主权；重试提升高可用。**缺点/边界**：anthropic/gemini
> 需各自 SDK；多模态/工具 schema 在不同厂商表现有差异，切换厂商后需用 `IntentEvalRunner` + 真实链路抽检做回归评估，避免效果劣化。

## 13. 多 Agent 编排与子智能体

### 13.1 进程内多专家（Reactor 编排）

`MultiAgentOrchestrator` 构建订单/售后/知识库三专家 Agent，用 **Reactor 直接编排**（取代已移除的 `Pipelines`）：

```mermaid
flowchart TB
    Q[用户问题] --> MODE{multi-agent.mode}
    MODE -->|fanout| RT["智能路由 RouterAgent<br/>IntentResult → 相关专家子集"]
    RT --> FO["真并行 fanout<br/>flatMap(call.subscribeOn(boundedElastic), maxConcurrency)"]
    FO --> RD["reduce 归纳 ReducerAgent<br/>多专家结论 → 统一口径回复"]
    MODE -->|sequential| SE["Mono 链式：依次流过逐步细化"]
    RD --> R[回复]
    SE --> R
```

**路由 → 并行 → 归纳**三段（fanout 模式）：

| 段 | 开关 | 行为 | 退化 |
|---|---|---|---|
| 智能路由（快车道）| `fast-route-enabled` | 关键词规则命中**唯一**意图→直路由，跳过 LLM | 命中多类/无命中 → 交慢车道 |
| 智能路由（慢车道）| `routing-enabled` | RouterAgent 分诊意图，`expertsForIntent` 纯映射只挑相关专家 | 分诊失败 / other → 广播全部，保证不漏 |
| 真并行 fanout | 总是 | 各专家 `subscribeOn(boundedElastic)` 真并发 + 限流 + 超时/错误隔离 | 单专家时即一个任务 |
| reduce 归纳 | `reduce-enabled` | ReducerAgent 把多结论合成统一口径回复（去重/消解冲突） | 单专家 / 关闭 → `aggregate` 拼接 |

> **可观测**（Micrometer → `/actuator/prometheus`）：`customerwork.mas.route{intent}`、
> `customerwork.mas.fanout.experts`、`customerwork.mas.expert{expert,outcome=success/timeout/failure}`、
> `customerwork.mas.reduce{triggered}`，无 Micrometer 时降级为 no-op。此外 `CustomerServiceService` 还埋了
> `customerwork.intent.classify.errors`（意图分类失败计数）与 `customerwork.chat.fallback`（对话兜底触发计数）
> 两个计数器，用于监控分类稳定性与兜底占比。

**真并行的关键（第一性原理）**：`agent.call()` 返回 `Mono<Msg>`，但底层模型调用很可能是**阻塞式**。若只写
`flatMap(agent -> agent.call(...))`，三个专家会在同一条订阅线程上**依次阻塞**——是"并行的写法、串行的执行"。
本编排器给每个任务挂 `subscribeOn(Schedulers.boundedElastic())`，把阻塞调用挪到独立线程，才是**真并发**；
再叠加三道工程保障：

| 机制 | 实现 | 作用 |
|---|---|---|
| 并发限流 | `flatMap(task, maxConcurrency)` | 同时在跑的专家数上限（默认 8），防资源打满 |
| 超时隔离 | `.timeout(timeoutSeconds)` | 慢专家不无限拖累整体 |
| 错误隔离 | `.onErrorResume(→占位 Msg)` | 单专家失败降级为"暂不可用"占位，其余照常聚合 |

> 离线确定性单测（`MultiAgentOrchestratorTest`）：用可控阻塞 `Mono` 记录运行期**峰值并发度**——
> `fanout` 断言峰值 ≥ 2（证明真并发），`concurrency=1` 断言峰值 == 1（限流退化为串行），并验证错误隔离。
>
> **备注（测试边界）**：单测证明的是"并发是真实发生的"（峰值并发度 ≥ 2），不依赖网络、确定性可重复；
> 但**三专家同时打真实大模型的端到端墙钟加速比**需配置真实 `DASHSCOPE_API_KEY` 跑 `POST /consult` 现场观测——
> 离线覆盖的是**并发度**，而非真实网络延迟下的**加速倍数**（后者随模型 RTT、限流与重试波动，不适合做断言）。

### 13.2 HarnessAgent 子智能体（spawn/send）

HarnessAgent 默认开启子智能体：`subagentFactory` 注册命名专家，框架经 `AgentSpawnTool`（`agent_spawn`）
按需派生、`InboxMiddleware` 做反向推送（`agent_send`），支持同步与后台委派。

> **优点**：主从分层、职责单一、可后台委派。**边界与并行说明**：HarnessAgent 的子智能体由主智能体在
> ReAct 循环里**自行逐个 spawn**，本质串行、不可编程控制其并发；需要"主 + 子智能体"**可控并行**会诊时，
> 走 §13.1 的 `MultiAgentOrchestrator`（它构造的正是注册为 subagent 的同一批专家）。跨进程多 Agent 互通需
> A2A + Nacos 注册发现（扩展点，见 §19）。

### 13.4 自动化意图评测框架（借鉴 AliGo 测评系统）

`IntentEvalRunner` 对 classpath 评测集 `eval/intent-eval-cases.json` 逐用例打分，量化**规则快车道**质量：

| 指标 | 含义 |
|---|---|
| accuracy | 判定正确数 / 总用例（明确用例命中正确意图 + 模糊用例正确地交 LLM）|
| fastLaneCoverage | 快车道命中数 / 明确意图用例数（规则能直接处理的占比）|

- **离线确定性**（只用 `fastRouteIntent`，不触发模型）、可 CI 跑、可版本对比；`EvalReport.format()` 输出文本报告。
- 评测集外置 JSON = AliGo 强调的"用例沉淀复用"；新增用例只改 JSON、不动代码。
- **边界**：真实回复的相关性/准确性评测需 LLM-as-judge（真实模型 Key），不在离线评测范围。
- 测试：`IntentEvalRunnerTest`（数据集加载 + 准确率≥95% / 覆盖率≥80% 质量基线）。

### 13.5 对话阶段状态机（动态 Prompt，借鉴 AliGo）

AliGo 把"全量规则塞一个大 Prompt"改为"状态机式动态组装"，是其准确率 50%→90% 的关键之一。本项目用
`onSystemPrompt` 中间件落地：`DialogStageService` 按会话维护 `DialogStage`，`DialogStageMiddleware`
在每次调用前把**当前阶段**的聚焦指令片段动态追加到系统提示词。

```mermaid
stateDiagram-v2
    [*] --> GREETING: 接待识别
    GREETING --> COLLECTING: 信息收集
    COLLECTING --> PROCESSING: 业务处理
    PROCESSING --> CONFIRMING: 确认收尾
    GREETING --> ESCALATED: 转人工
    COLLECTING --> ESCALATED
    PROCESSING --> ESCALATED
```

- 每阶段只注入"当前主链路"指令（如 COLLECTING 阶段："缺什么问什么，一次只问最关键一项"），而非全量规则——降 token、提准。
- 阶段流转由业务事件驱动（`set`）或主链路顺序推进（`advance`）；与 `TenantContextMiddleware` 同段叠加。
- 测试：`DialogStageServiceTest`（默认态 / 流转 / 片段非空 / 中间件注入当前阶段片段）。

### 13.6 主动服务（订单通知 / 满意度回访，复用 Channel 推送）

`ProactiveNotificationService` 组装主动消息，推送委托给可替换的 `NotificationChannel`：

```mermaid
flowchart LR
    EV["订单状态变更 / 定时任务 / 运营后台"] --> SVC["ProactiveNotificationService<br/>notifyOrderStatus / sendSatisfactionSurvey"]
    SVC --> CH{NotificationChannel}
    CH -->|生产配置| WH["WebhookNotificationChannel<br/>Idempotency-Key"]
    CH -->|失败| DLQ[(cw_dead_letter)]
    DLQ -->|指数退避，同 operationId| CH
    CH -->|非生产未配置| LOG["LoggingNotificationChannel（仅日志）"]
```

- 配置 `customer-work.notification.webhook-url` 后装配真实 Webhook 通道；prod 门禁要求同时配置认证令牌。
- 出站失败可靠写死信，恢复后由 `ProactiveNotificationDeadLetterHandler` 重放；通知网关按稳定 operationId 幂等。
- 端点：`POST /api/customer/notify/order-status|survey`。测试：`ProactiveNotificationServiceTest`、
  `WebhookNotificationChannelTest`（故障入队、恢复重放与幂等头）。

### 13.7 坐席辅助 + 会话质检（借鉴 AliGo 坐席辅助 / 质检）

- **坐席辅助** `AgentAssistService`：按用户消息规则匹配，给人工坐席输出「建议话术 + 知识提示 + 推荐工具」
  （旁挂提示，不直接发用户）。端点 `POST /api/customer/assist`。
- **会话质检** `QualityInspectionService`：对坐席/Agent 回复做合规打分——**资金违规承诺**（已打款/马上到账/保证退）
  单条 -40 且直接判不通过，绝对化表述 -10、服务禁语 -15；输出 `QualityReport(score, passed, issues)`。
  端点 `POST /api/customer/quality/inspect`。
- 均规则化、离线确定性。测试：`AgentAssistServiceTest`、`QualityInspectionServiceTest`。

**数据飞轮闭环** `QualityFeedbackRecorder`：质检不通过时把回复内容 + 扣分项作为事实写入
`FactLog`（三层记忆体系 L3，按 sessionId 解析出的租户分文件追加），供离线复盘。`AgentAssistController`
的 `/quality/inspect` 已接入本类而非直接调用 `QualityInspectionService`。

> **诚实边界**：本类只做"记录"——把失败会话沉淀为可查询的事实流水；"从事实流水筛选、
> 回流知识库/评测集"是离线人工或独立批处理任务的职责，不在本类自动完成。
> 测试：`QualityFeedbackRecorderTest`（不通过记录 / 通过不记录 / 租户解析）。

## 14. 权限系统 / Plan Mode / 沙箱（Harness 新能力）

### 14.1 Permission System（三态权限）

`PermissionConfig` 把 `customer-work.harness.permission` 映射为框架原生 `PermissionContextState`，注入主 ReActAgent：

```mermaid
flowchart LR
    TOOL[工具调用] --> ENG{PermissionEngine}
    ENG -->|allow 规则| OK[直接放行]
    ENG -->|ask 规则| CONFIRM[人工确认 RequireUserConfirm]
    ENG -->|deny 规则| BLOCK[拒绝]
    ENG -->|mode| MODE["default/acceptEdits/explore/bypass/dontAsk"]
```

- 三态决策：**允许 / 询问(审批) / 拒绝**；ask 规则默认覆盖 `submitRefund`、`transferToHuman`。
- 与 `HumanApprovalMiddleware` 形成"声明式权限 + 可观测确认"双层，HITL 上升为框架原生能力。

#### 14.1.1 人工审批闭环（退款放行，应用层 HITL）

Permission ASK 把关"是否允许 Agent 调用退款工具"，但**工单生成后是否真打款**需要第二道人工闸门。
`PendingApprovalService` + `ApprovalController` 提供这道闭环：

```mermaid
flowchart LR
    T["submitRefund 工具"] -->|生成待审单 AP-xxx| ST[(PendingApprovalService<br/>PENDING)]
    ST --> Q["GET /approvals?status=pending"]
    Q --> H{人工坐席}
    H -->|approve CAS| AP["APPROVED → 执行租约 → ApprovalExecutionHandler"]
    H -->|deny| DN["DENIED"]
```

| 设计点 | 说明 |
|---|---|
| 状态机 | `ApprovalRequest` 充血，`PENDING → APPROVED/DENIED` 终态不可变；重复决策 fast-fail（HTTP 409） |
| 互补双层 | Permission ASK（工具调用层）+ 审批闭环（资金执行层），各司其职 |
| 为何应用层 | 框架运行时确认（`RequireUserConfirmEvent` / `ReActAgent.CONFIRM_SINK_KEY`）在 2.0.0 GA 仍**未暴露 Web 友好的公共回填 API**（RC4→GA 升级时核对过 `ReActAgent`/`AgentBase` 源码，此处无变化），绑定其内部协议脆弱；而"退款先生成待确认工单、人工放行后执行"本就是更稳健的领域建模 |
| 资金安全 | 生产强制装配 `ApprovalExecutionHandler`；决策 CAS 只允许一人成功，执行租约 + fencing token 防并发旧 worker 回写，下游按审批单号幂等 |

> 测试：`PendingApprovalServiceTest`（并发决策、崩溃租约回收、fencing 与幂等键）、`AfterSalesToolsApprovalTest`（退款登记待审单 / 无服务降级）。

### 14.2 Plan Mode（只读规划期）

`HarnessAgent.enablePlanMode()`：先以只读方式产出 markdown 计划（持久化到 `workspace/plans`），获批后再进入写
执行，让"意图与动作解耦"。`allowShellInPlanMode` 控制规划期是否允许 Shell。

### 14.3 安全沙箱执行

## 15. 接入层安全与请求治理

WebFilter 按 `@Order` 串成链（数字越小越先）：

```mermaid
flowchart LR
    REQ[请求] --> F0["RequestIdWebFilter HIGHEST_PRECEDENCE"]
    F0 --> F1["ApiKeyAuthWebFilter +10"]
    F1 --> F2["RateLimitWebFilter +20"]
    F2 --> CTRL[Controller]
    F1 -. 401 .-> RESP[响应]
    F2 -. 429 .-> RESP
```

- **鉴权**：校验 `X-API-Key`；健康/Actuator/Swagger 路径豁免。
- **限流**：固定时间窗，按 API Key 或客户端 IP 计数，超限 429。分布式部署应换 Redis 限流。
- **请求关联**：生成/透传 `X-Request-Id` 进响应头与 Reactor Context。
- 默认鉴权/限流关闭，生产开启。

## 20. 设计取舍与边界

- **Agent 无状态 + 状态外置**：单实例并发服务多租户多会话、零停机滚动发布；代价是状态语义上移到 `AgentStateStore`，
  需理解 `(userId, sessionId)` 维度。
- **响应式全链路无 `.block()`**：业务链路严格异步；中间件即 `Function<Input, Flux<AgentEvent>>` 组合。
- **配置开关 + 可替换实现**：以少量"默认 Mock"换取离线可跑、可测、易采用。
- **效果非确定性**：AI 输出不确定，单测覆盖"工程正确性"，"效果正确性"靠回归评估（`IntentEvalRunner` + classpath 评测集 `eval/intent-eval-cases.json`，提示词/模型变更后应重跑）。
- **框架版本**：锁定 `agentscope-harness 2.0.0`（GA）；远端沙箱 / A2A / 调度等为引扩展坐标后的扩展点。
- **不可迁移**：核心移除的 TTS、`PlanNotebook`、`Pipelines`、`SessionManager/StateModule` 见 [MIGRATION-2.0.md](MIGRATION-2.0.md)。
- **安全**：仓库零密钥，全部环境变量注入；生产建议 Vault/KMS/K8s Secret。

## 20.1 生产部署基线

`ga2.0` 分支（承接 `rc2.0` 时期）已对照 `agentscope-java` 框架 RC4 时点的 120 个 open issues 做过一轮全量交叉核对，结论沉淀在
[`docs/生产就绪评估.md`](生产就绪评估.md)，生产配置基线固化在
[`customer-work-app-server/src/main/resources/application-prod.yml`](../customer-work-app-server/src/main/resources/application-prod.yml)。
措辞上一律是**缓解 / 规避**，不是"已解决"——框架 bug 的最终修复权在上游仓库。核心结论：

- **已实测排除的 P0 风险**：#1941/#1675（同步 `call()` 不触发 `onAgent`）与 #1681/#1619（多租户状态误入默认命名空间）
  经探针测试实测**未复现**，两个探针（`MiddlewareInvocationVerificationTest`/`TenantIsolationVerificationTest`）已固化为回归测试，
  升级框架版本时行为漂移会直接体现为测试变红。
- **四项应用层加固**：`generateOptions` 显式兜底（缓解 #1644 NPE）、`ToolGuardMiddleware` 破坏性命令拦截
  （缓解 #1898/#1896）、意图分类失败/对话兜底告警指标（缓解 #1852/#1699）、SSE 空闲超时
  （缓解 #1741 连接泄漏），均有单测覆盖。
- **部署配置基线**：`skill.repository: filesystem`（规避 #1979/#1985 fat-jar 下 classpath 技能枚举失败）、
  `session.mode: redis`（规避 #1769 JSON 持久化写放大）、`harness.subagent.enabled: false`
  （规避子智能体一组已知问题）、`context.compression-enabled: true` 且阈值保守（规避 #1740 Compaction 漏压缩）。
- **仍受框架限制、需人工把关的遗留限制**：#1966（Channel 场景框架暂无法把 IM 用户身份映射进
  `RuntimeContext`，需按单租户群部署并显式声明边界）、#1968（中断后状态保存存在竞态，上线前必须实测
  "中断→再次对话"）、#1695（`ToolResultEviction` 部分路径不驱逐，不作为上下文治理的兜底假设）。

## 22. 用户工单系统

在既有"AI 客服 + 人机切换"能力之上，本模块补齐了**面向真实终端用户的完整工单闭环**：终端用户注册登录后开会话与
AI 对话，命中转人工或按状态机流转给人工坐席处理，全程消息经 WebSocket 实时双向推送并落库。它与 §6.11 的旧
handoff 域**共存**：旧域服务"AI 工具（`transferToHuman`）触发的转人工工单"，新 ticket 域服务"真实用户会话工单"。

### 22.1 架构总览

```mermaid
flowchart LR
    subgraph 用户端
      MOBILE["customer-work-app<br/>Vue3+Vant4 H5 (5175)"]
    end
    subgraph 坐席端
      ADMINWEB["customer-admin-web<br/>坐席工作台 (5174)"]
    end
    APP["customer-work-app-server (8080, WebFlux)<br/>REST + WebSocket"]
    ADMINSRV["customer-admin-server (8082)<br/>RestClient 代理 + Sa-Token 权限"]
    DB[("agent_scope_customer_work<br/>cw_user / cw_ticket / cw_ticket_event<br/>cw_chat_message / cw_order / cw_product")]

    MOBILE -->|"REST(JWT) + /ws/user"| APP
    ADMINWEB -->|"REST"| ADMINSRV
    ADMINSRV -->|"RestClient 现签 X-Agent-Token<br/>/api/customer/agent/**"| APP
    ADMINWEB -.->|"领取 WS 凭证后浏览器直连<br/>/ws/agent?token=HMAC"| APP
    APP --> DB
```

- **两服务不共库、HTTP 互调**：数据全部落 8080 的 `agent_scope_customer_work` 库；8082（`customer_admin` 库）
  不直接读 8080 的业务表，而是经 `RestClient` 调 8080 坐席 API，鉴权用**现签**的 `X-Agent-Token`（每次请求
  用 `AgentAccessCredential.sign(agentId, now+120s, secret)` 生成短时令牌）。
- **WebSocket 分两类接入**：用户端浏览器/H5 用 JWT 直连 `/ws/user`；坐席端先经 8082 的
  `GET /api/ticket/ws-credential` 领取 HMAC 凭证，再由浏览器**直连** 8080 的 `/ws/agent`（不经 8082 转发，
  避免长连接穿透代理）。
- **相关代码**：starter `com.richard.fyoung.customerwork.{data.ticket,data.user,data.chatlog,safety.security}`、app
  `com.richard.fyoung.customerworkapp.{controller,security,ws,chat}`、admin
  `com.richard.fyoung.customeradmin.ticket`。

### 22.2 七态工单状态机

`Ticket`（`com.richard.fyoung.customerwork.data.ticket.Ticket`）是充血实体，状态流转方法内建前后态校验，非法流转
一律 `IllegalStateException`（fast-fail，映射为 HTTP 409）。

```

        │                                                                            │

   │AI_SERVING│ ───────────────▶ │WAITING_AGENT │ ───────▶ │ PROCESSING │ ──────▶ │ ON_HOLD │
   └─────────┘ ◀─────────────── └──────────────┘         └────────────┘ ◀────── └─────────┘
       │        cancelHandoff          ▲   ▲                  │  │  resume
       │                               │   │  transferToPool  │  │
       │            reject（退回）      │   └──────────────────┘  │ markResolved
       │        ┌──────────────────────┘                         ▼
       │        │                                        ┌────────────────┐
       │   ┌──────────────┐        confirm               │ WAITING_CONFIRM│
       │   │   (用户端)    │ ◀──────────────────────────  └────────────────┘
       │   └──────────────┘                                       │ confirm
       │                                                          ▼
       │  close                                            ┌────────────┐
       └────────────────────────────────────────────────▶ │  RESOLVED  │
                                                           └────────────┘
                                                                  │ close / SLA auto-close
                                                                  ▼
                                                           ┌────────────┐
                                                           │   CLOSED   │
                                                           └────────────┘
```

每条流转的方法、前后态与触发者：

| 方法 | 前态 → 后态 | 触发者 | 说明 |
|---|---|---|---|
| `create` | — → `AI_SERVING` | 系统（开会话） | 建单，默认 priority=NORMAL、category 空则 OTHER |
| `requestHandoff(reason)` | `AI_SERVING` → `WAITING_AGENT` | 用户 / 系统（关键词命中） | 已在 WAITING_AGENT/PROCESSING/ON_HOLD 时幂等返回 false |
| `cancelHandoff()` | `WAITING_AGENT` → `AI_SERVING` | 系统 | 撤回转人工、回到 AI 服务 |
| `claim(agentId)` | `WAITING_AGENT` → `PROCESSING` | 坐席 | 走 `store.claimAtomically` 乐观锁，抢单失败 409 |
| `hold()` / `resume()` | `PROCESSING` ⇄ `ON_HOLD` | 坐席 | 挂起 / 恢复 |
| `transferToPool()` | `PROCESSING`\|`ON_HOLD` → `WAITING_AGENT` | 坐席 | 转回队列（清 assignee） |
| `transferToAgent(agentId)` | `PROCESSING`（状态不变） | 坐席 | 换绑受理坐席 |
| `markResolved(note)` | `PROCESSING` → `WAITING_CONFIRM` | 坐席 | 提交待用户确认 |
| `confirm()` | `WAITING_CONFIRM` → `RESOLVED` | 用户 / SLA 自动 | 用户确认解决 |
| `reject(reason)` | `WAITING_CONFIRM` → `PROCESSING` | 用户 | 驳回，退回人工处理 |
| `close(reason)` | `AI_SERVING`\|`WAITING_CONFIRM`\|`RESOLVED` → `CLOSED` | 用户 / 坐席 / SLA 自动 | 关单归档 |
| `reopen(reason)` | `RESOLVED`\|`CLOSED` → `WAITING_AGENT` | 用户 | 重开，`reopenCount++` |
| `changePriority` / `changeCategory` | 任意非 `CLOSED` 态 | 坐席 | 改优先级 / 分类（非流转） |

- 优先级 `TicketPriority`：`LOW / NORMAL / HIGH / URGENT`；分类 `TicketCategory`：`CONSULT / ORDER / AFTER_SALE / COMPLAINT / OTHER`。
- 事件类型 `TicketEventType`（14 种）：`CREATE / REQUEST_HANDOFF / CANCEL_HANDOFF / CLAIM / HOLD / RESUME / TRANSFER / MARK_RESOLVED / CONFIRM / REJECT / CLOSE / REOPEN / PRIORITY_CHANGE / CATEGORY_CHANGE`。
- 参与者 `TicketActorType`：`USER / AGENT / BOT / SYSTEM`。

### 22.3 数据模型（6 张表）

全部落 `agent_scope_customer_work` 库，持久层为贫血 DO（`entity/`）+ `BaseMapper`（`mapper/`）+ 复杂 SQL 写在
`resources/customerwork/mapper/*.xml`，建表与种子由 starter 的 Flyway 统一执行；V1 是冻结基线，V2 接管并
修复历史存量结构，V3 增加可靠投递表与租约字段。开关为 `session.mysql.migration-enabled`，迁移失败阻断启动，
不再各 Store 内分散 `ensureTable`。

| 表 | 归属 | 关键字段 | 索引 |
|---|---|---|---|
| `cw_user` | 用户账户 | id(`U-<uuid>`), username, password_hash(BCrypt), nickname, phone, status(ACTIVE/DISABLED), created_at_ms | 唯一键 `uk_user_username` |
| `cw_ticket` | 工单主表 | id(`TK-<uuid>`), session_id, user_id, title, category, priority, status, assignee, handoff_reason, resolve_note, reopen_count, created_at_ms / updated_at_ms / handoff_at_ms / claimed_at_ms / resolved_at_ms / closed_at_ms | idx_ticket_session / _user / _status / _assignee |
| `cw_ticket_event` | 工单事件轨迹 | id(自增), ticket_id, event_type, from_status, to_status, actor_type, actor_id, note, created_at_ms | 按 ticket_id |
| `cw_chat_message` | 聊天消息 | id(自增，游标主键), message_id(`MSG-<uuid>`), session_id, ticket_id, sender_type, sender_id, content, created_at_ms | 唯一键 `uk_chat_message_id` + idx_chat_session / _ticket |
| `cw_order` | 订单业务后端 | order_id(PK), user_id, product_id, product_name, amount, status, receiver_addr, logistics_trace, created_at_ms | 含种子 20260613001~004 |
| `cw_product` | 商品业务后端 | product_id(PK), name, category, price, stock, description, promotion, status(ON_SALE/OFF_SALE) | 含种子 P001~P003 |

- **会话号 `u<userId>:conv-<uuid>` 与租户隔离**：用户开会话时 `UserTicketController` 生成
  `u<userId>:conv-<uuid>`，冒号前缀复用 §6/记忆体系的**租户隔离机制**（`memory.tenant-delimiter=":"`）——
  同一用户的多个会话共享长期记忆、跨用户严格隔离；WebSocket 的 `ChatDispatchService` 校验 sessionId 前缀，
  不匹配返回 error 帧 `CHAT-SESSION-DENIED`；HTTP 附件、反馈、满意度与消息回放统一由 `UserSessionGuard`
  回溯 `cw_ticket` 根资源，未知与非本人均返回 404。
- **一会话一活跃工单约束**：`TicketService.findActiveBySession(sessionId)` 只返回非 `RESOLVED`/`CLOSED` 的工单；
  用户 `POST /user/sessions` 时若无活跃工单则 `createForSession(CONSULT)` 建单，保证一条会话同时只有一张进行中工单。

### 22.4 WebSocket 帧协议

统一帧结构 `WsFrame(type, data)`（`com.richard.fyoung.customerwork.infra.ws.WsFrame`，随通用 WS 基建下沉 starter；
app 侧只保留 `AgentChatWebSocketHandler`/`UserChatWebSocketHandler`/`WebSocketConfig`），JSON 编码。

**上行帧**（客户端 → 服务端）：

| type | 方向 | data 字段 | 说明 |
|---|---|---|---|
| `chat` | 用户端 | `{sessionId, content}` | 用户发消息，经 `ChatDispatchService.onUserMessage` |
| `chat` | 坐席端 | `{ticketId, content}` | 坐席回复，经 `onAgentMessage`，校验受理坐席 |
| `handoff` | 用户端 | `{sessionId, reason}` | 用户主动转人工 |
| `ping` | 双端 | — | 心跳，服务端回 `pong` |

**下行帧**（服务端 → 客户端）：

| type | data 字段 | 说明 |
|---|---|---|
| `chat` | `{messageId, sessionId, ticketId, senderType(USER\|BOT\|AGENT\|SYSTEM), senderId, content, ts}` | 一条完整消息（坐席回复 / 转发） |
| `chat_chunk` | `{content}` | AI 流式增量（打字机效果） |
| `chat_done` | `{messageId, content, ts}` | AI 流式定稿全文（聚合后落库的 BOT 消息） |
| `ticket_event` | 工单事件（eventId/ticketId/eventType/fromStatus/toStatus/actorType/status/assignee/ts） | 工单流转实时推送用户与坐席；eventId 用于客户端去重 |
| `ticket_new` | `{eventId, ticketId, userId, title, priority, category, ts}` | 新工单进池，广播全体在线坐席唤起抢单；eventId 用于去重 |
| `system` | `{content, ts}` | 系统提示（如"客服正在赶来"） |
| `error` | `{code, message}` | 帧级错误（如 `CHAT-FRAME-INVALID`、`CHAT-NOT-ASSIGNEE`），**不断连接** |
| `pong` | `null` | 心跳应答 |

- 握手鉴权失败以 `CloseStatus.POLICY_VIOLATION` 关闭连接（用户端验 JWT、坐席端验 HMAC 凭证）。
- 同身份重复连接**顶号**：`WsSessionRegistry` 为每连接建一个 unicast `Sinks.many`，新连接登记时对旧 sink
  `tryEmitComplete()`（旧连接下行流正常收尾），保证一个身份只有一条活跃下行。

```mermaid
sequenceDiagram

    participant KW as HandoffKeywordDetector
    participant TS as TicketService
    participant CS as CustomerServiceService

    U->>DISP: chat {sessionId, content}
    DISP->>DISP: 校验 sessionId 前缀 u<userId>:
    DISP->>TS: findActiveBySession / createForSession(CONSULT)

    DISP->>KW: 关键词命中?

        TS-->>A: ticket_new 广播抢单

        else WAITING_CONFIRM

        else 其它(含 WAITING_AGENT)
            DISP-->>U: system "客服正在赶来的路上"
        end
    end

    A->>DISP: chat {ticketId, content}（坐席回复）
    DISP->>DISP: 校验 agentId == ticket.assignee（否则 error CHAT-NOT-ASSIGNEE）
    DISP->>DISP: 落库 AGENT 消息
    DISP-->>U: chat（用户在线则推送；离线仅落库，上线拉历史补齐）
```

### 22.6 鉴权体系

| 通道 | 机制 | 密钥来源 | 校验点 |
|---|---|---|---|
| 用户 REST（`/api/customer/user/**`）| JWT HS256（`UserJwtService`，任意长度密钥经 SHA-256 派生 256bit）| env `CW_USER_JWT_SECRET`，默认 7 天 | `UserAuthWebFilter`（`Authorization: Bearer`），失败 401 |
| 用户 WS（`/ws/user`）| 同一 JWT（query `token`）| 同上 | 握手 `jwtService.verify`，失败 POLICY_VIOLATION |
| 坐席 REST（`/api/customer/agent/**`）| HMAC-SHA256 凭证（`AgentAccessCredential`，`agentId:expiresAtMs:签名`）| env `CW_AGENT_WS_SECRET` | `AgentAuthWebFilter`（`X-Agent-Token`），失败 401 |
| 旧人机切换 REST（`/api/customer/handoffs/**`）| 同一 HMAC-SHA256 凭证 | 同上 | 同一过滤器保护查询/接单/结案；操作员只取验签身份 |
| 坐席 WS（`/ws/agent`）| 同一 HMAC 凭证（query `token`）| 同上 | 握手 `AgentAccessCredential.verify` |
| admin 代理（8082 → 8080）| `RestClient` 拦截器**现签** `X-Agent-Token`（TTL 120s）| `admin.customer-work.agent-secret`（与 8080 共享 `CW_AGENT_WS_SECRET`）| 前置 Sa-Token `user-ticket:*` 权限 |

坐席凭证签发有两处：8082 的 `GET /api/ticket/ws-credential`（`UserTicketService.issueWsCredential`，
按 `credential-expire-hours` 签发供浏览器直连 WS）；以及 8082 每次 `RestClient` 请求由拦截器现签短时令牌。
密钥 `CW_AGENT_WS_SECRET` 必须 8080 与 8082 一致，否则坐席全链路 401。

### 22.7 并发与可靠性

```mermaid
sequenceDiagram
    participant API as TicketService
    participant TX as CustomerWorkTransactionExecutor
    participant DB as MySQL
    participant D as OutboxDispatcher
    participant H as OutboxHandler

    API->>TX: 执行一次工单命令
    TX->>DB: BEGIN
    TX->>DB: 更新 cw_ticket + 写 cw_ticket_event
    TX->>DB: 写 cw_outbox_message(PENDING)
    TX->>DB: COMMIT
    D->>DB: CAS 抢占租约(PENDING/过期 PROCESSING)
    D->>H: 至少一次投递(稳定 eventId)
    alt 成功
        D->>DB: SUCCEEDED
    else 失败
        D->>DB: PENDING + 指数退避 / ABANDONED
    end
```

- **抢单乐观锁**：`MybatisTicketStore` 的 `claim` 用条件 UPDATE
  `UPDATE cw_ticket SET status='PROCESSING', assignee=?, ... WHERE id=? AND status='WAITING_AGENT'`，靠影响
  行数判定成功，多实例/多坐席并发抢同一单只有一个胜出，其余抛 `IllegalStateException`（HTTP 409）。跨实例安全。
- **顶号策略**：同身份 WS 重复连接以新顶旧（见 §22.4），避免一个坐席多标签页分裂下行；旧连接正常收尾而非报错。
- **离线落库**：用户或坐席任一方离线时，消息仍落 `cw_chat_message`，仅跳过实时推送；对端上线后经
  `GET .../messages?beforeId=&limit=` 游标分页拉历史补齐（`MybatisChatMessageStore` 按 id 倒序取、翻转为升序返回）。
- **SLA 自动流转 vs 旧 handoff 域"只告警"的差异**：`TicketSlaScheduler` 对
  `WAITING_AGENT`（超 `sla-waiting-seconds`）/`PROCESSING`（超 `sla-processing-seconds`）**仅 error 告警**
  （无合理自动兜底，同旧 `HandoffSlaScheduler` §6.11 的设计语言）；但对
  `WAITING_CONFIRM`（超 `auto-confirm-seconds`）**自动 confirm**、`RESOLVED`（超 `auto-close-seconds`）
  **自动 close**——这两态存在合理的"用户长时间不响应即视同认可/归档"兜底语义，故做自动流转。单张工单自动
  流转异常只 error（`TICKET-SLA-AUTOFLOW-FAIL`）不影响其余。
- **本地事务**：jdbc 模式下 `TicketService` 把工单主表、事件轨迹和 Outbox 消息放入同一
  `TransactionTemplate`，任一步失败整笔回滚，避免“状态已变但事件丢失”。memory 模式使用同一事务 SPI 的直通实现。
- **至少一次事件投递**：Outbox 调度器用条件 UPDATE 抢占带超时的租约，成功后调用按类型注册的
  `OutboxHandler`；失败按指数退避重试，耗尽保留为 `ABANDONED`。无 Handler 的类型不累计次数，避免配置遗漏
  被伪装成业务失败。实例崩溃后租约到期可由其他副本接管，因此监听器与前端都按 eventId 幂等去重。
- **多租户调度**：扫描租约是明确的跨租户运维动作，集中走 `CrossTenantOperations`；消息记录自己的
  `tenant_id`，调用 Handler 前恢复该租户上下文，结束后还原，避免调度线程无请求上下文时 fail-closed，
  也避免处理 A 租户消息时误用 B 租户数据。
- **与旧 handoff 域共存**：`HumanHandoffTools.transferToHuman` 打通真实 `sessionId` 后**双写** ticket 域与旧
  handoff 域（`cw_handoff_ticket`），两域数据独立、互不覆盖，坐席工作台可分别查询。

### 22.8 用户订单管理（坐席查询/改址/取消）

在工单闭环之外，坐席还需要直接操作用户订单（改址、取消），链路横跨 `customer-admin-web` → 8082 代理 →
8080 坐席 API → starter 的 `OrderDirectoryService` → `OrderMapper`：

```mermaid
flowchart LR
    WEB["customer-admin-web<br/>用户订单管理页"] -->|GET/POST /api/ticket/orders/**| ADM["customer-admin-server(8082)<br/>UserOrderController→UserOrderService"]
    ADM -->|RestClient 现签 X-Agent-Token| APP["customer-work-app-server(8080)<br/>AgentOrderController"]
    APP --> SVC["OrderDirectoryService"]
    SVC -->|OrderMapper| DB[("cw_order JOIN cw_user")]
```

- **8080 坐席订单 API**（`AgentOrderController`，`/api/customer/agent/orders`，鉴权同 §22.6 坐席 REST）：
  - `GET`：分页查询，支持 `userId`/`username`/`orderId`/`status` 任意组合过滤，`OrderMapper.pageForAgent`
    对 `cw_order` 与 `cw_user` 按 `user_id` JOIN 回填 `username`，按下单时间倒序。
  - `GET /{orderId}`：详情，额外含 `logisticsTrace`；不存在 404。
  - `POST /{orderId}/modify-address`：改收货地址，`newAddress` 非空校验（400）。
  - `POST /{orderId}/cancel`：取消订单，**仅“待支付/已支付/待发货”（未发货阶段）可取消**，其余状态
    （已发货及之后）返回 `OrderMutationResult.STATE_CONFLICT` → HTTP 409；订单不存在 404；
    `tool-backend.mode!=jdbc`（无 `OrderMapper` Bean）时 `isEnabled()=false`，整组接口降级返回 503。
  - 金额字段对外统一格式化为两位小数字符串（`BigDecimal.setScale(2, HALF_UP)`）。
- **8082 admin 代理**（`UserOrderController`，`/api/ticket/orders`）：`page`/`detail` 需 `user-order:view`，
  `modify-address`/`cancel` 需 `user-order:edit`（Flyway `V20__user_orders_menu.sql`，菜单 id=139 挂在
  §22 用户工单同一分组“客服工单”下，按钮 140/141）；`UserOrderService` 薄委托给 `CustomerWorkTicketClient`
  透传 8080 的分页契约（`{total,items}`），本模块不建订单业务表。8080 侧 404/409 由客户端统一翻译为
  `BizException`，经 `GlobalExceptionHandler` 转标准 `Result` 响应体（同 §22.6 坐席工单代理的异常翻译约定）。
- 测试：starter `OrderDirectoryServiceTest`；app `AgentOrderControllerTest`；admin
  `CustomerWorkTicketClientTest` / `UserOrderServiceTest`。

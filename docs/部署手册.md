## 一、部署架构与组件清单

| 部署单元 | 模块 | 说明 | 是否必须 |
|---|---|---|---|

## 二、基础设施准备

| 依赖 | 用途 | 注意事项 |
|---|---|---|
| **Redis** | `session.mode=redis` 会话持久化 | 多实例共享会话状态;规避 #1769(JSON 文件模式整份重写、写放大) |
| **MySQL** | 5 个 `store-mode=jdbc` 的状态存储 + 审计日志 | **即使 session 选了 redis,MySQL 也必须部署**——`session.mysql.*` 连接配置被 human-approval / slot-filling / dialog / human-handoff / feedback 五个 JDBC store 复用,各自建独立连接池 |
| **技能目录磁盘** | `SKILL_DIRECTORY`(默认 `/data/customer-work/skills`) | filesystem 仓库规避 fat-jar 内 classpath 枚举失败(#1979/#1985);建议挂共享存储或独立数据盘 |
| **DashScope** | 主模型 | 确认账号配额与 QPS 上限;生产 Key 与开发 Key 分离 |
| **兜底模型** | `model.fallback.*` | prod 基线默认指向 ollama/qwen2.5。二选一:部署真实兜底模型并配好 `MODEL_FALLBACK_BASE_URL`,或显式设 `fallback.enabled: false`。**不要留一个指向不存在服务的默认值上线** |

**技能文件预置**:把仓库 `customer-work-app-server/src/main/resources/skills/` 下的技能目录整体拷贝到 `SKILL_DIRECTORY` 指向的路径,应用启动时从磁盘读取。`writable: true` 意味着 SkillCurator 会写回该目录,多实例部署时该目录应为共享存储。

## 三、数据库初始化

生产基线 `session.mysql.auto-create: false`——**应用不自动建表**,由 DBA 按 [mysql/01-agent-scope-customer-work/customer-work-schema.sql](../mysql/01-agent-scope-customer-work/customer-work-schema.sql) 走变更流程建以下 19 张表(前 7 张为原有能力,中 4 张为用户工单系统,后 8 张为 JDBC 业务工具后端演示表):

| 表名 | 归属功能 | 写入方 |
|---|---|---|
| `agentscope_sessions` | 会话持久化(仅 `session.mode=mysql` 时使用) | MysqlSessionRepository |
| `cw_audit_log` | 审计日志(含审批/工单决策留痕) | MybatisAuditSink |
| `cw_approval` | HITL 审批工单(资金类,含执行状态/重试计数) | MybatisApprovalStore |
| `cw_slot_filling_progress` | 多轮槽位收集进度 | MybatisSlotFillingStore |
| `cw_dialog_stage` | 对话阶段状态机 | MybatisDialogStageStore |
| `cw_handoff_ticket` | 人机切换工单(AI 工具触发的转人工闭环) | MybatisHandoffStore |
| `cw_message_feedback` | 消息级用户反馈(点赞/点踩) | MybatisFeedbackStore |
| `cw_user` | 终端用户账户(BCrypt 密码) | MybatisUserAccountStore |
| `cw_ticket` | 用户工单主表(7 态状态机) | MybatisTicketStore |
| `cw_ticket_event` | 工单事件轨迹 | MybatisTicketStore |
| `cw_chat_message` | 聊天消息(一行一条,双维度游标分页) | MybatisChatMessageStore |
| `cw_order` | 订单业务后端(含种子数据) | MybatisOrderBackend |
| `cw_product` | 商品业务后端(含种子数据) | MybatisProductBackend |
| `cw_refund` | 售后工单(退款/退货/换货共表,含种子数据) | MybatisAfterSalesBackend |
| `cw_invoice_request` | 发票申请 | MybatisAfterSalesBackend |
| `cw_member` | 会员积分/等级(含种子数据) | MybatisMemberBackend |
| `cw_member_account_log` | 会员账户问题处理日志 | MybatisMemberBackend |
| `cw_complaint` | 投诉工单(含种子数据) | MybatisComplaintBackend |
| `cw_knowledge` | 知识库 FAQ(含种子数据) | MybatisKnowledgeBackend |

权限建议:应用账号只授 DML(SELECT/INSERT/UPDATE/DELETE),不授 DDL。

> 上述 15 个持久化类均为贫血 DO(`entity/`)+ `BaseMapper`(`mapper/`)+ 复杂 SQL 写在
> `resources/customerwork/mapper/*.xml` 的 MyBatis-Plus 实现,建表已收敛为统一的
> **`SchemaInitializer`**(执行 `resources/customerwork/schema/customer-work-schema.sql`,与本节
> `mysql/01-agent-scope-customer-work/customer-work-schema.sql` 内容一致),不再由各 Store/Backend 类各自分散 `ensureTable`。
>
> 开发/测试环境可以开 `auto-create: true` 让应用自动建表,生产不建议(表结构变更应走 DBA 流程留痕)。仓库默认 `application.yml`(开发取向)已是 `session.mode=mysql` + `auto-create: true`,启动即由 `SchemaInitializer` 自动建齐上述 19 张表(其中 8 张业务工具后端表仅 `customer-work.tool-backend.mode=jdbc` 时才装配对应 Mapper Bean,但建表脚本本身不区分开关、随 `SchemaInitializer` 一并执行);`cw_order`/`cw_product`/`cw_refund`/`cw_member`/`cw_complaint`/`cw_knowledge` 用 `INSERT IGNORE` 灌入种子数据(订单 `20260613001`~`004`、商品 `P001`~`P003`、会员 `U-demo-1`/`U-demo-2`、退货/发票/运费 FAQ 等),生产接入真实业务系统后应替换或清理种子。

## 四、环境变量清单

### customer-work-app-server 必填项

无默认值、或默认值不可用于生产,缺任何一项会导致启动失败或核心链路不通:

| 环境变量 | 说明 |
|---|---|
| `SPRING_PROFILES_ACTIVE` | 固定 `prod` |
| `DASHSCOPE_API_KEY` | 主模型 API Key |
| `AUTH_API_KEYS` | API 鉴权 Key,逗号分隔多个(如 `key1,key2`) |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_DATABASE` / `MYSQL_USERNAME` / `MYSQL_PASSWORD` | 五个 JDBC store + 审计 + 用户工单 4 张 + JDBC 业务后端 8 张表共用 |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | 会话持久化 |
| `CW_USER_JWT_SECRET` | 用户工单系统:终端用户 JWT 签名密钥(HS256)。开发有默认值 `dev-secret-change-me-in-production-0001`,**生产必须覆盖**为高强度随机串,泄露等于可伪造任意用户身份 |
| `CW_AGENT_WS_SECRET` | 用户工单系统:坐席 HMAC 接入凭证密钥。**8080 与 8082(`admin.customer-work.agent-secret`)必须同值**,否则坐席全链路 401;开发默认 `dev-agent-secret-change-me-0001`,生产必须覆盖 |

> **fail-safe 提醒**:prod profile 下 `security.auth.enabled` 默认是 **true**(与非 prod 环境相反)。忘记配 `AUTH_API_KEYS` 的结果是所有请求被鉴权拦下(需要运维介入排查),而不是接口裸奔——这是有意的安全默认值,不要为了图省事把它翻回去。

### 运行时配置热更新(admin 8082 → 8080,默认关闭)

后台管理系统改动「已绑定为客服机器人运行配置」的智能体/模型后,把运行时配置(模型链/兜底/重试/系统提示词/MCP/maxIters)发布到 Nacos,8080 监听热生效——**模型链原子热替换 + 会话 Agent 重建,无需重启**。两侧默认全关,开启后按下表配置。**关键约束:两端 AES 密钥必须同值,dataId 必须一致**,否则密文解不开/订阅不到,整份配置被判失败并保留旧配置(不影响可用性)。

| 环境变量 | 侧 | 默认值 | 说明 |
|---|---|---|---|
| `CUSTOMER_WORK_RUNTIME_CONFIG_ENABLED` | 8080 消费端 | `false` | 置 `true` 启用运行时配置监听 |
| `CUSTOMER_WORK_CONFIG_AES_KEY` | 8080 消费端 | 空 | API Key 密文 AES 解密密钥(16/24/32 字节)。**必须与 admin 的 `ADMIN_AES_SECRET_KEY` 同值** |
| `NACOS_SERVER_ADDR` / `NACOS_NAMESPACE` / `NACOS_USERNAME` / `NACOS_PASSWORD` | 8080 消费端 | localhost:8848 / customer-work / nacos / nacos | 复用 `customer-work.nacos.*` 连接配置;`runtime-config-data-id` 默认 `customer-work-runtime-config` |
| `ADMIN_RUNTIME_PUBLISH_NACOS_ENABLED` | 8082 发布端 | `false` | 置 `true` 启用运行时配置发布 |
| `ADMIN_RUNTIME_PUBLISH_NACOS_SERVER_ADDR` / `_NAMESPACE` / `_GROUP` / `_USERNAME` / `_PASSWORD` | 8082 发布端 | localhost:8848 / 空 / DEFAULT_GROUP / 空 / 空 | Nacos 连接 |
| `ADMIN_RUNTIME_PUBLISH_NACOS_DATA_ID` | 8082 发布端 | `customer-work-runtime-config` | **必须与 8080 的 `customer-work.nacos.runtime-config-data-id` 一致** |

> 端到端:admin「渠道绑定」页把某渠道绑定到一个智能体 → 改动该智能体或其模型并通过连通性探测 → admin 组装配置(API Key 密文原样携带)发布 Nacos → 8080 监听回调解密并热应用。发布前强制连通性探测,探测不过拒绝发布;下发失败可在渠道绑定页「重新发布」。

#### 后台登录态持久化(Sa-Token + Redis)

后台登录态存 Redis(`AdminSaTokenDaoConfig`),**服务重启/滚动发布不会把在线用户踢下线**,多实例部署也天然共享同一份登录态。Redis 对 8082 因此从"可选的读缓存"升级为**登录必须依赖**:Redis 不可达时鉴权 fail-closed(请求 401),这是登录态该有的安全语义(与历史对话读缓存"连不上就回源 MySQL"刻意相反)。

| 环境变量 / 配置 | 默认 | 说明 |
|---|---|---|
| `ADMIN_REDIS_HOST` / `ADMIN_REDIS_PORT` / `ADMIN_REDIS_PASSWORD` | `localhost` / `6379` / 空 | 登录态存储 Redis(同一实例同时供历史对话读缓存、分布式锁复用);生产必填且必须配密码 |
| `ADMIN_SATOKEN_TIMEOUT_SECONDS`(`sa-token.timeout`) | `86400` | 登录态有效期(秒),默认 24 小时。**绝对过期**(`activity-timeout: -1`,不按活跃续期),从登录那一刻算起,与进程生命周期无关 |
| `ADMIN_REMEMBER_ME_TIMEOUT_SECONDS` | `604800` | 登录时勾选"记住我"的有效期(秒),默认 7 天;不勾选走上面的 24 小时 |
| `ADMIN_SATOKEN_REDIS_PERSISTENT` | `true` | 应急开关。置 `false` 退回 Sa-Token 内存 DAO——**仅在 Redis 故障需要先把后台救回来时用**,代价是重启即全员掉线、多实例互不认 token |

> 多实例部署注意:各实例必须指向**同一个** Redis,否则各签各的 token,负载均衡轮到另一台就 401。

> **Docker 模式产物同步(P1-3,bind mount 挂 agent 工作区根)**:docker 模式下后端把宿主机 agent 工作区根
> `./data/admin-workspace/{agentCode}` 以 `docker run -v` 挂进容器 `/workspace`,会话产物(`sessions/{sessionId}/`)、
> 跨会话记忆(`MEMORY.md`)、Plan Mode 计划文件(`plans/`)全部实时落宿主机——文件树 / file_change / Git 助手 /
> 一键回滚 / test_report 与 local 模式等价可用,无需 docker cp。同时自动注入 `--user <宿主机 uid:gid>`
> (启动时 `id -u`/`id -g` 探测)并显式 `HOME=/workspace`,容器写出的产物属主与 admin-server 进程用户一致,
> 原生 Linux Docker 上回滚(`git checkout/clean`)/文件保存不会撞 root 属主。
> 部署注意:① **宿主机工作区目录须在 Docker 的文件共享白名单内**(macOS Docker Desktop 默认共享 `/Users`;
> 自定义路径需在 Docker Desktop 设置里加共享);② **uid 探测失败的回退**(如非 POSIX 环境、`id` 命令不可用,
> 启动日志有 `host uid/gid unresolved` 提示):容器回退为镜像默认用户(通常 root),Linux 上产物会归 root:root,
> 需自行保证 uid 对齐——自定义镜像内建同 uid 用户,或 Docker 守护进程开 `userns-remap`;macOS Docker Desktop
> 有属主映射,无此问题;③ 工作区目录由后端预建,建目录失败会直接快速失败(fast fail)而非交给 docker 以 root 补建。

> HITL 挂起态只存进程内存、**服务重启即失效**(重启后 `/plan/confirm` 找不到挂起项直接 fast fail;正在挂起的 SSE 连接也随重启断开)——单实例语义,多实例部署需自行把确认注册表外部化(如 Redis),当前不支持。
>
> **护栏不可绕过(设计意图)**:catastrophic 级命令(如 `rm -rf`、触碰 `.git`、访问 `/etc` `/root`)**即使在 HITL 里被人工批准,仍会被内层 `SandboxGuardMiddleware` 最终改写拦截**——护栏是不可绕过的最后防线,HITL 与护栏是叠加关系而非替代关系;人工批准真正放行的是 HITL 独有的确认级操作(`mvn clean`、修改依赖文件、批量修改等)。

## 五、秘密配置(operators 映射)

审批放行端点(`POST /api/customer/approvals/{id}/approve|deny`)由 `ApprovalAuthWebFilter` 守护:操作员身份由服务端按 `security.approval-auth.operators`(token → 坐席姓名映射)解析请求头 `X-Approval-Token`,**不信任客户端传的 operator 参数**。

- prod yml 只提交了开关 `approval-auth.enabled: true`,operators 映射**刻意留空**——每个坐席的真实凭证不进代码仓库。
- 部署时通过独立的运维侧配置下发,例如 K8s Secret 挂载的 `application-prod-secrets.yml`,或 Spring Cloud Config:

```yaml
# application-prod-secrets.yml(运维侧管理,严禁提交进仓库)
customer-work:
  security:
    approval-auth:
      operators:
        "tok-a1b2c3d4": "张三"
        "tok-e5f6g7h8": "李四"
```

> **硬阻塞提醒**:开关开着但 operators 为空时,所有 approve/deny 请求会被拒绝——退款人工放行闭环走不通。**不下发这份映射,不要放开真实流量。**

## 七、多实例部署注意事项

以下三项默认是**进程内实现**(单实例下更快也更简单),横向扩容前必须逐条切换,否则"扩容"会同时放大配额、打乱会话:

1. **限流与成本熔断**:默认进程内计数,N 个实例下实际总配额被放大为 N 倍。多副本部署设 `customer-work.distributed.counter-mode: redis`,两者共用同一个计数器实现,一个开关同时生效。
2. **会话级串行锁**:默认进程内 Semaphore,只在同一实例内生效,同一 `sessionId` 的并发请求落到不同实例就没有互斥,对话历史会被交叉覆盖。两种做法二选一——网关层为 sessionId 配置会话粘性路由(sticky session),**或**设 `customer-work.distributed.session-lock-mode: redis`(切了之后不再依赖 sticky,才能真正自由扩缩容)。
3. **审批 / 槽位 / 对话阶段已切 jdbc,跨实例安全**:三者共享状态落 MySQL,应用重启、多实例路由均不受影响——前提是[第三节](#三数据库初始化)的表已建好。

Redis 连接复用 `customer-work.distributed-lock.redis.*`。三者的 Redis 实现在 **Redis 不可达时降级为进程内**而非直接放行:保护性能力在基础设施故障时全放行等于保护消失,退回单机配额仍拦得住单实例上的失控流量。

**Kubernetes 部署**:`deploy/k8s/` 提供了 Deployment / Service / HPA / PDB / 探针 / 优雅停机的完整清单,其 ConfigMap 已把上述三项全部切成 Redis。注意 `terminationGracePeriodSeconds`(45)必须大于应用的 `runtime.shutdown-timeout-seconds`(30),否则处理中的对话会被 SIGKILL 打断。

## 八、安全暴露面收口

- **Actuator**:prod yml 已收敛为只暴露 `health,prometheus`(`show-details: when-authorized`)。确认部署环境没有其他配置源(配置中心/启动参数)把 exposure 覆盖回 `*`。

## 十一、回滚预案

- **代码版本回滚**:三个 jdbc store 的表是纯新增,回滚应用版本不影响已有数据。
- **`store-mode` 从 jdbc 切回 memory**:进行中的审批单会从视图中"消失"(数据仍在 `cw_approval` 表里,只是不再读取)。**回滚窗口内确保没有未决审批单**,或先人工处理完再切。
- **鉴权回滚**:如 `approval-auth` 导致坐席无法操作(通常是 operators 未下发),临时缓解是运维侧下发正确的 secrets 覆盖,而不是关掉 `approval-auth.enabled`——关掉等于重新打开身份伪造漏洞。

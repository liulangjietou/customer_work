## 一、部署架构与组件清单

| 部署单元 | 模块 | 说明 | 是否必须 |
|---|---|---|---|
| 客服主应用 | `customer-work-app-server` | 对外 API(chat / approvals / refund-form / assist 等)+ 用户工单 REST/WebSocket | 必须 |
| 管理控制台 | `customer-channel` | admin / Studio / Channel(钉钉·飞书·企业微信)/ AG-UI | 可选 |
| 后台管理系统 | `customer-admin-server`(8082)+ `customer-admin-web`(5174) | RBAC + AI 配置 + **坐席工单工作台**(代理 8080 坐席 API) | 部署用户工单系统时必须 |
| 用户端 H5 | `customer-work-app`(静态站) | 终端用户登录/聊天/我的工单(直连 8080) | 部署用户工单系统时必须 |
| Redis | 外部依赖 | 会话持久化(多实例共享) | 必须 |
| MySQL | 外部依赖 | 审批工单 / 槽位进度 / 对话阶段 / 审计日志 | 必须 |
| 网关(如 Higress/Nginx) | 外部依赖 | TLS 终结、全局限流、会话粘性路由 | 强烈建议 |
| Prometheus + Grafana + Tempo | 外部依赖 | 指标采集/告警/链路追踪,一键栈见 `docker/observability/`(详见[第九节](#九可观测性与告警)) | 强烈建议 |

两个应用各自带一份 `application-prod.yml` 生产基线(键名已逐一对照 `CustomerWorkProperties` 核实),激活方式统一为 `SPRING_PROFILES_ACTIVE=prod`:

- [customer-work-app-server/src/main/resources/application-prod.yml](../customer-work-app-server/src/main/resources/application-prod.yml)
- [customer-channel/src/main/resources/application-prod.yml](../customer-channel/src/main/resources/application-prod.yml)

两份文件的语法与关键键值均有离线测试守护(`ProdProfileConfigTest`,两模块各一份),改动 prod yml 后跑测试即可发现低级错误。

## 二、基础设施准备

| 依赖 | 用途 | 注意事项 |
|---|---|---|
| **Redis** | `session.mode=redis` 会话持久化 | 多实例共享会话状态;规避 #1769(JSON 文件模式整份重写、写放大) |
| **MySQL** | 全部 JDBC Store、审计、Outbox、死信与技能权威数据 | **即使 session 选了 redis,MySQL 也必须部署**；所有域复用 starter 的独立 `customerWorkDataSource` 与事务管理器 |
| **运行时临时目录** | 技能/Memory/Harness 等框架所需的可重建物化文件 | 统一落 `${java.io.tmpdir}/customer-work/`，不需要持久卷；权威数据在 MySQL，文件在 MinIO |
| **DashScope** | 主模型 | 确认账号配额与 QPS 上限;生产 Key 与开发 Key 分离 |
| **兜底模型** | `model.fallback.*` | prod 基线默认指向 ollama/qwen2.5。二选一:部署真实兜底模型并配好 `MODEL_FALLBACK_BASE_URL`,或显式设 `fallback.enabled: false`。**不要留一个指向不存在服务的默认值上线** |

**技能库**：prod 使用 `skill.repository=mysql`，启动时从 MySQL 全量物化到临时目录供框架读取；临时目录可随时重建，
不得当成权威数据或挂持久卷。

## 三、数据库初始化

客服业务库由 starter 内置 Flyway 管理，生产基线固定开启
`customer-work.session.mysql.migration-enabled=true`。迁移失败会阻断启动，不能把结构错误拖到第一笔真实请求。
存量非空库首次接管时 Flyway 自动登记版本 `0`，随后执行 V1 之后的增量迁移；不会删除或重建既有业务表。
首次上线前必须备份，并用只读核对确认表数量与关键数据量。

[mysql/01-agent-scope-customer-work/customer-work-schema.sql](../mysql/01-agent-scope-customer-work/customer-work-schema.sql)
是空库手工初始化/CI 建库的完整镜像；运行时权威迁移位于
`customer-work-starter/src/main/resources/db/customerwork/migration/`。两者变更必须同步。

代表性表如下（完整清单以 V1 基线为准）：

| 表名 | 归属功能 | 写入方 |

应用账号必须具备 Flyway 所需 DDL 权限；若组织要求运行账号仅有 DML，请在发布阶段用独立迁移账号先执行
同版本迁移并验证，再以 `migration-enabled=false` 启动运行账号。禁止长期关闭迁移却不建立替代发布流程。

升级顺序：备份 → 单实例执行迁移 → 检查 `flyway_schema_history` 与 `/actuator/health` → 验证 Outbox/死信积压 →
再滚动其余实例。V1 只作为冻结基线，后续结构变化必须新增版本，禁止修改已发布迁移。

## 四、环境变量清单

### customer-work-app-server 必填项

无默认值、或默认值不可用于生产,缺任何一项会导致启动失败或核心链路不通:

| 环境变量 | 说明 |
|---|---|
| `SPRING_PROFILES_ACTIVE` | 固定 `prod` |
| `DASHSCOPE_API_KEY` | 主模型 API Key |
| `AUTH_KEY_ID` | 稳定 API Key 标识；轮换 secret 时保持不变 |
| `AUTH_KEY_HASH` | 原始 API Key 的完整 SHA-256 小写摘要（64 位），服务端不保存明文 |
| `AUTH_KEY_TENANT_ID` / `AUTH_KEY_SCOPES` / `AUTH_KEY_EPOCH` | 凭据租户、权限范围与轮换版本；scope 支持 `*`、路径和 `METHOD:/path/**` |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_DATABASE` / `MYSQL_USERNAME` / `MYSQL_PASSWORD` | 五个 JDBC store + 审计 + 用户工单 4 张 + JDBC 业务后端 8 张表共用 |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | 会话持久化 |
| `CW_USER_JWT_SECRET` | 用户工单系统:终端用户 JWT 签名密钥(HS256)。开发有默认值 `dev-secret-change-me-in-production-0001`,**生产必须覆盖**为高强度随机串,泄露等于可伪造任意用户身份 |
| `CW_AGENT_WS_SECRET` | 用户工单系统:坐席 HMAC 接入凭证密钥。**8080 与 8082(`admin.customer-work.agent-secret`)必须同值**,否则坐席全链路 401;开发默认 `dev-agent-secret-change-me-0001`,生产必须覆盖 |

> **fail-safe 提醒**:prod profile 下 `security.auth.enabled` 默认是 **true**，且生产门禁拒绝旧的明文
> `api-keys/tenant-keys`。忘记配置合法的 `AUTH_KEY_ID/AUTH_KEY_HASH` 会阻断启动，而不是接口裸奔。
> 摘要可用 `printf %s "$RAW_API_KEY" | shasum -a 256` 生成；原始值只交给调用方。

轮换时为同一 `keyId` 并存不同 `epoch` 的哈希凭据；调用方全部切换后提高
`customer-work.security.auth.minimum-epochs.<keyId>`，旧 epoch 立即失效。`expires-at` 使用 ISO-8601
时间；生产启动门禁会拒绝无 scope、格式错误、过期或低于最小 epoch 的启用凭据。

### 运行时配置热更新(admin 8082 → 8080,默认关闭)

后台管理系统改动「已绑定为客服机器人运行配置」的智能体/模型后,把运行时配置(模型链/兜底/重试/系统提示词/MCP/maxIters)发布到 Nacos,8080 监听热生效——**模型链原子热替换 + 会话 Agent 重建,无需重启**。两侧默认全关,开启后按下表配置。**关键约束:两端 AES 密钥必须同值,dataId 必须一致**,否则密文解不开/订阅不到,整份配置被判失败并保留旧配置(不影响可用性)。

|---|---|---|---|

| `CUSTOMER_WORK_CONFIG_AES_KEY` | 8080 消费端 | 空 | API Key 密文 AES 解密密钥(16/24/32 字节)。**必须与 admin 的 `ADMIN_AES_SECRET_KEY` 同值** |

> 端到端:admin「渠道绑定」页把某渠道绑定到一个智能体 → 改动智能体或其资产时，同事务写 `ai_runtime_publish_task` 并冻结该 revision 的 ACK 实例集合 → worker 从权威表重建配置，模型密钥与 MCP headers 均只携带 AES-GCM 密文，随后签名并发布 Nacos → 8080 先验 contentHash/HMAC，再解密并原子热应用 → 通过 `cw_outbox_message` 回传 ACK → 冻结集合全部 APPLIED 后任务才进入 `APPLIED`。任务表不复制配置正文或密文。

> ACK 入口只接受 `X-Runtime-Config-Ack-Token`：服务端先把 token 映射到固定租户与 instanceId，再核对正文中的
> instanceId、revision 和 contentHash。通用 `X-Open-Api-Token` 不能访问该入口，同一实例重复回执只做 upsert，
> 不能靠伪造多个 instanceId 凑够阈值。

> MCP 管理页的分页接口不返回 `config`；编辑详情需要 `mcp:edit`，敏感键和 headers 叶子值只返回占位符，
> 只有连接目标未变化时才会按相同 JSON 路径合并旧值；换 URL/命令必须重填凭据。远程 URL 禁止
> userInfo/query/fragment，最终客户端与发布任务会再次校验，历史危险 URL 在配置版本详情中整段脱敏。
> `debug/call` 会真实调用下游，因此同样要求 `mcp:edit` 并写操作审计。
> 敏感叶子已经从 `ai_mcp.config` 提取到 SecretRef；数据库 config 只留不可执行占位符，发布载荷只含
> `headersCipher`。生产启动会拒绝仍在启用且含内联凭据的存量 MCP，须先在编辑页重新保存完成迁移。

> 模型健康状态变化会为所有引用 Agent 同事务登记 `HEALTH_OVERLAY` 可靠任务。该意图用于故障切换，跳过
> 连通性、认证与 Eval 发布门禁，但不会绕过权威表重建、fencing、contentHash/HMAC 校验和冻结目标 ACK。
> `UNHEALTHY/RECOVERING` 从普通兜底、策略路由与实验臂候选中剔除；`DEGRADED` 仍可路由。
> 人工 `FORCE_HEALTHY/FORCE_UNHEALTHY` 必须具备 `model:health-override`、填写原因和到期时间，最长有效期由
> `ADMIN_MODEL_HEALTH_MAX_OVERRIDE_HOURS` 限制，到期后自动回到探测事实。

> 新任务入队时把该租户配置的 ACK instanceId 排序去重后冻结到任务；集合内任一实例未回执或 REJECTED 都不会
> 进入 `APPLIED`，集合外实例回执会被拒绝。`minimum-ack-count` 只保留给迁移前没有冻结快照的历史任务。

> 8080 使用发布端共享的 `RuntimeConfigContentHasher` 重算业务正文 SHA-256；算法排除
> `publishedAt`、`revision`、`contentHash`。声明 hash 缺失、格式错误或与正文不一致时回传 `REJECTED`，
> 保留旧配置且不清语义缓存、不进入 applier。随后用 keyId 对 revision/contentHash/publishedAt/schemaVersion
> 验 HMAC-SHA256；未知 key、缺签名或篡改都在解密前拒绝。Nacos ACL 与 TLS 仍需保留，但不再单独承担来源认证。

> runtime `contentHash` 变化时，8080 先阻断当前租户缓存读写并清理旧代际，再应用新配置。每个请求在入口捕获
> generation，旧在途请求完成后因代际不匹配会拒绝回写；清理或配置应用失败则回滚旧 generation 并保留旧配置。

> 冻结/退租经独立租户访问快照投递；8080 应用限制快照或 ACTIVE `accessEpoch` 递增后会主动断开该租户已有的
> 用户和坐席 WebSocket，新 epoch 凭据可重新握手。新请求与新握手均 fail-closed。跨运行时仍存在 Nacos
> 投递、监听和主动回读延迟，发布任务未送达前不得宣称
> 已在全部运行时完成撤权。

> 多租户开启时，worker 强制写 `<dataId>-tenant-<tenantId>`，8080 实例必须把
> `customer-work.nacos.tenant-code` 配成同一租户。消费者只读/监听该租户 key；缺失或删除会保留最后安全配置，
> 不回落也不响应主 dataId。主 dataId 只用于 `tenant.enabled=false` 且未配 tenant-code 的单租户部署。

> **历史平台租户切换到 `default`**：必须在维护窗把 `NACOS_TENANT_CODE` 改为 `default`，并将
> `<dataId>-tenant-__platform__` 的有效内容重新发布到 `<dataId>-tenant-default`，核对 revision、content hash
> 与全部实例 ACK 后再恢复流量。新版消费端不会读取旧 dataId，也不会自动复制；若升级前的历史环境或非生产环境曾启用
> Mem0、ReMe、百炼等远端记忆，还必须按提供方能力把远端 userId 从旧租户值导出/导入或建立迁移别名；
> 当前 prod 门禁不会允许这些 Provider 重新上线，直到补齐导出/擦除回执 SPI。数据库 V8 只负责 MySQL 长期记忆、
> 事实日志和语义缓存。完整的数据库、Redis、MinIO、凭据切换顺序见 `docs/多租户架构设计.md` §5。

> 一个 dataId 只代表一份全局运行时配置：多个渠道可以绑定同一个智能体，但后台会拒绝在同一 dataId 下
> 同时启用不同智能体，避免“最后一次发布覆盖前一智能体”。确需运行不同智能体时，部署独立的 admin/8080
> 配置对并使用不同 dataId。

#### 后台登录态持久化(Sa-Token + Redis)

后台登录态存 Redis(`AdminSaTokenDaoConfig`),**服务重启/滚动发布不会把在线用户踢下线**,多实例部署也天然共享同一份登录态。Redis 对 8082 因此从"可选的读缓存"升级为**登录必须依赖**:Redis 不可达时鉴权 fail-closed(请求 401),这是登录态该有的安全语义(与历史对话读缓存"连不上就回源 MySQL"刻意相反)。

| 环境变量 / 配置 | 默认 | 说明 |
|---|---|---|
| `ADMIN_REDIS_HOST` / `ADMIN_REDIS_PORT` / `ADMIN_REDIS_PASSWORD` | `localhost` / `6379` / 空 | 登录态存储 Redis(同一实例同时供历史对话读缓存、分布式锁复用);生产必填且必须配密码 |
| `ADMIN_SATOKEN_TIMEOUT_SECONDS`(`sa-token.timeout`) | `86400` | 登录态有效期(秒),默认 24 小时。**绝对过期**(`activity-timeout: -1`,不按活跃续期),从登录那一刻算起,与进程生命周期无关 |
| `ADMIN_REMEMBER_ME_TIMEOUT_SECONDS` | `604800` | 登录时勾选"记住我"的有效期(秒),默认 7 天;不勾选走上面的 24 小时 |
| `ADMIN_SATOKEN_REDIS_PERSISTENT` | `true` | 应急开关。置 `false` 退回 Sa-Token 内存 DAO——**仅在 Redis 故障需要先把后台救回来时用**,代价是重启即全员掉线、多实例互不认 token |

> 多实例部署注意:各实例必须指向**同一个** Redis,否则各签各的 token,负载均衡轮到另一台就 401。
> 同时必须设置 `ADMIN_AGENT_TASK_CLEANUP_ORPHANS_ON_STARTUP=false`：现有后台任务执行器没有实例租约，
> 启动时全局清理只适用于单实例；多副本滚动发布若保持默认值，会把其它 Pod 正在执行的任务误标为失败。

> `${java.io.tmpdir}/customer-work/admin-workspace/{agentCode}` 以 `docker run -v` 挂进容器 `/workspace`,会话产物(`sessions/{sessionId}/`)、
> 跨会话记忆(`MEMORY.md`)、Plan Mode 计划文件(`plans/`)全部实时落宿主机——文件树 / file_change / Git 助手 /
> 一键回滚 / test_report 与 local 模式等价可用,无需 docker cp。同时自动注入 `--user <宿主机 uid:gid>`
> (启动时 `id -u`/`id -g` 探测)并显式 `HOME=/workspace`,容器写出的产物属主与 admin-server 进程用户一致,
> 原生 Linux Docker 上回滚(`git checkout/clean`)/文件保存不会撞 root 属主。
> 部署注意:① **宿主机工作区目录须在 Docker 的文件共享白名单内**(macOS Docker Desktop 默认共享 `/Users`;
> 自定义路径需在 Docker Desktop 设置里加共享);② **uid 探测失败的回退**(如非 POSIX 环境、`id` 命令不可用,
> 启动日志有 `host uid/gid unresolved` 提示):容器回退为镜像默认用户(通常 root),Linux 上产物会归 root:root,
> 需自行保证 uid 对齐——自定义镜像内建同 uid 用户,或 Docker 守护进程开 `userns-remap`;macOS Docker Desktop
> 有属主映射,无此问题;③ 工作区目录由后端预建,建目录失败会直接快速失败(fast fail)而非交给 docker 以 root 补建。

> HITL 挂起态只存进程内存、**服务重启即失效**(重启后 `/plan/confirm` 找不到挂起项直接 fast fail;正在挂起的 SSE 连接也随重启断开)——单实例语义,多实例部署需自行把确认注册表外部化(如 Redis),当前不支持。
>
> **护栏不可绕过(设计意图)**:catastrophic 级命令(如 `rm -rf`、触碰 `.git`、访问 `/etc` `/root`)**即使在 HITL 里被人工批准,仍会被内层 `SandboxGuardMiddleware` 最终改写拦截**——护栏是不可绕过的最后防线,HITL 与护栏是叠加关系而非替代关系;人工批准真正放行的是 HITL 独有的确认级操作(`mvn clean`、修改依赖文件、批量修改等)。

## 五、秘密配置(operators 映射)

审批放行端点(`POST /api/customer/approvals/{id}/approve|deny`)由 `ApprovalAuthWebFilter` 守护:操作员身份由服务端按 `security.approval-auth.operators`(token → 坐席姓名映射)解析请求头 `X-Approval-Token`,**不信任客户端传的 operator 参数**。

- prod yml 只提交了开关 `approval-auth.enabled: true`,operators 映射**刻意留空**——每个坐席的真实凭证不进代码仓库。
- 部署时通过独立的运维侧配置下发,例如 K8s Secret 挂载的 `application-prod-secrets.yml`,或 Spring Cloud Config:

```yaml
# application-prod-secrets.yml(运维侧管理,严禁提交进仓库)
customer-work:
  security:
    approval-auth:
      operators:
        "tok-a1b2c3d4": "张三"
        "tok-e5f6g7h8": "李四"
```

> **硬阻塞提醒**:开关开着但 operators 为空时,所有 approve/deny 请求会被拒绝——退款人工放行闭环走不通。**不下发这份映射,不要放开真实流量。**

## 七、多实例部署注意事项

以下三项默认是**进程内实现**(单实例下更快也更简单),横向扩容前必须逐条切换,否则"扩容"会同时放大配额、打乱会话:

1. **限流、租户配额与主体配额**:默认进程内计数,N 个实例下实际总配额被放大为 N 倍。多副本部署设 `customer-work.distributed.counter-mode: redis`,三类保护共用同一个计数器实现。`ModelCostCircuitBreaker` 当前没有生产调用方，不能作为部署门禁。
2. **会话级串行锁**:默认进程内 Semaphore,只在同一实例内生效,同一 `sessionId` 的并发请求落到不同实例就没有互斥,对话历史会被交叉覆盖。两种做法二选一——网关层为 sessionId 配置会话粘性路由(sticky session),**或**设 `customer-work.distributed.session-lock-mode: redis`(切了之后不再依赖 sticky,才能真正自由扩缩容)。
3. **审批 / 槽位 / 对话阶段已切 jdbc,跨实例安全**:三者共享状态落 MySQL。审批决策通过 PENDING 条件更新抢占，资金执行通过执行租约与 fencing token 防并发/崩溃重放——前提是[第三节](#三数据库初始化)的表已建好，且部署提供真实 `ApprovalExecutionHandler`。

Redis 连接复用 `customer-work.distributed-lock.redis.*`。三者的 Redis 实现在 **Redis 不可达时降级为进程内**而非直接放行:保护性能力在基础设施故障时全放行等于保护消失,退回单机配额仍拦得住单实例上的失控流量。

**Kubernetes 部署**:`deploy/k8s/` 提供了 Deployment / Service / HPA / PDB / 探针 / 优雅停机的完整清单,其 ConfigMap 已把上述三项全部切成 Redis。注意 `terminationGracePeriodSeconds`(45)必须大于应用的 `runtime.shutdown-timeout-seconds`(30),否则处理中的对话会被 SIGKILL 打断。

## 八、安全暴露面收口

- **Actuator**:prod yml 已收敛为只暴露 `health,prometheus`(`show-details: when-authorized`)。确认部署环境没有其他配置源(配置中心/启动参数)把 exposure 覆盖回 `*`。
- **OpenAPI**:prod 默认 `SPRINGDOC_ENABLED=false`，只有在受控内网确有调试需求时临时开启。
- **网络**:应用端口不直接暴露公网,前置网关做 TLS 终结。
- **响应头**:应用统一返回 `nosniff`、`DENY`、`no-referrer`、`Permissions-Policy`；HTTPS 下附加 HSTS，API/Actuator 响应禁止缓存。
- **工具层防线不要关**:`hooks.tool-guard`(破坏性命令拦截)与 Harness Permission ASK(`submitRefund` / `transferToHuman` 需确认)在 prod 基线均为开启状态。它们与应用层 HITL 审批闭环是**双层防线**,不要为了"少一次确认"关掉任何一层。
- **凭证分离**:生产 `DASHSCOPE_API_KEY` / 结构化 API Key / `ADMIN_WRITE_TOKEN` / operators token 全部与开发环境隔离,定期轮换。
- **提交前密钥扫描**:运行 `scripts/verify-no-committed-secrets.sh`；CI 同样执行。任何已经进入 Git 历史的密钥都必须在提供方控制台吊销/轮换，单纯删除当前文件不构成止损。

#### 登录拼图验证码

本地登录与 OA 登录共用同一条准入链：`challenge → 随机拼图 → 落点与轨迹核验 → 一次性 proof → 登录原子消费`。
登录请求只携带 proof，不携带客户端的“已验证”布尔值或原始轨迹；proof 在用户查询、BCrypt 和 LDAP Bind
之前消费，密码错误、域控不可用或账号禁用都不会返还。challenge 与 proof 同时绑定来源 IP 和归一化
User-Agent，因而不能直接搬到另一浏览器或网络环境重放。

challenge 响应包含服务端即时生成的背景图、拼图块 data URI 及画布尺寸，目标横坐标只保存在服务端；客户端
提交的 `placementX` 和轨迹横坐标都按 `canvasWidth-pieceWidth` 的可移动行程归一化到 `0..1000`。服务端原子
消费 challenge 后，同时校验落点是否命中随机目标、轨迹终点是否与落点一致，以及时长、采样数和中间点质量；
失败的 challenge 不可复用，前端会签发新题。验证成功后前端直接续接登录，不要求用户再次点击登录按钮。

落点校验在读取 challenge 前就按可信来源 IP 占用滑动窗口预算，默认每小时 3 次；
换 User-Agent 不会获得新预算。题目看不清而刷新只占用签发额度，不占用落点猜测额度；一旦提交校验，
无论 challenge 已过期、指纹不匹配、落点/轨迹失败还是成功签发 proof，都会保留这次计数直到窗口滑出。
`rate-limit-window-seconds` 在启动时强制不小于 `challenge-ttl-seconds`，避免预签发的题目跨窗口叠加猜测机会。

验证预算刻意按解析后的来源 IP 聚合，因此企业 NAT、统一代理或 CGNAT 下的用户会共享这 3 次额度；同一出口内
任意调用方都可能让其他用户在窗口内暂时无法验证。正式部署前必须确认来源 IP 的实际分布，并监控
`LOGIN_CAPTCHA_TOO_FREQUENT` 是否集中命中单个出口。共享出口是常态时，应在网关叠加更高额度的纯 IP 防洪桶，
并把低额度猜测预算绑定到服务端签发的浏览器会话；不要只把 `max-verify-per-window` 调大，否则会同步放大盲猜概率。

后台没有 Redisson Bean 时使用有容量上限的进程内存储，适合单实例开发；一旦启动时选中 Redis，
保存或消费响应不确定都 **fail-closed**，运行期不会再切到内存副本。这样会牺牲 Redis 瞬时故障期间的登录
可用性，但避免“Redis 已成功写入/删除、客户端却收到超时”时同一 challenge 或 proof 在两处复活。

从旧版固定终点滑块升级时，禁止让新旧节点同时处理 `/api/auth/login-captcha/challenge` 与
`/api/auth/login-captcha/verify`：challenge 状态已升级为 `v2`，但 proof 为承接在途登录仍保持兼容编码，旧节点
签发的弱验证 proof 可被新节点消费。发布时先将这两个接口只路由到新节点，旧节点可以暂时继续处理普通登录；
至少等待一个 challenge TTL（默认 120 秒）后再下掉旧节点。网关不能按路径分流时，必须先摘流并排空旧节点，
再启动新版本，不能直接无隔离滚动混跑。

这仍是一道低成本自动化准入门槛，不是身份认证或完整风险引擎。随机目标能阻断只按固定终点伪造轨迹的脚本，
一次性凭据与来源绑定用于阻断省略验证、重放和跨来源搬运；面向高风险公网对抗时仍应叠加网关/WAF、登录限流、
设备与行为风险判定，或接入专业第三方风控，不能把拼图验证码宣传成单独完备的反机器人方案。

#### 成本闸门

`AdminProductionReadinessValidator` 在 prod profile 下会强制校验(不满足直接拒绝启动):

- `admin.subject-quota.enabled=true` — 注册者是陌生人,不限量等于把平台的模型账单交给公众
- `admin.subject-quota.default-level` 不能是 `admin-default` — 那是按内部员工定的 1 小时 200 万 token,对外用客服端库 `V23` 种子里的 `public-trial`(1 小时 / 20 万 token / 50 次)
- `admin.tenant.enabled=true`
- 自助注册开着时 `admin.notification.mail.enabled=true` 且 host 非空(邮箱验证码是注册的硬前提)

#### 注册流程:邮箱验证码

> **这一节适用于所有部署形态**,不只是对外实例:邮箱必填与邮箱验证码没有关闭开关,
> 判定在 `RegistrationGuard#admit` 一处无条件执行。放在本章只是因为它与开放注册相关。

自助注册一律走邮箱验证码,注册者必须先证明自己控制着填写的那个邮箱——只"填了邮箱"不等于"这邮箱是他的",
不验证的话审核结果与密码重置都会发到别人手里。内网实例若确实不需要自助注册,应当关掉
`ADMIN_REGISTRATION_SELF_SERVICE`(只由管理员预建账号),而不是把验证配成关。

```
填邮箱 → 填图形验证码 → 点「获取验证码」→ 收信 → 填 6 位数字码 → 提交注册
```

**两道验证码各在各的位置,不是叠加**:

| 位置 | 用的是 | 挡的是 |
|---|---|---|
| `POST /api/auth/email-code` 发码 | 图形验证码 | 无人值守的脚本。**发信是唯一会向站外第三方产生副作用的匿名操作**——服务端替调用者给任意地址发一封信,这里才是最该先挡住脚本的地方 |
| `POST /api/auth/register` 注册 | 邮箱验证码 | 冒用他人邮箱。此时不再要图形码:手里的邮箱码是比它强得多的证据,再要一次只是多一个输入框 |

**发码接口的四道防线**(逐条挡一种滥用,见 `EmailVerificationService`):

| 防线 | 默认值 | 挡的打法 |
|---|---|---|
| 图形验证码 | 对外强制 | 无人值守的脚本 |
| 来源 IP 限流 | 10 次/小时 | 一个来源换着邮箱轰炸 |
| 单邮箱重发冷却 | 60 秒 | 对同一个受害者的高频轰炸 |
| 单邮箱每日总量 | 10 封/天 | "每 60 秒一封发一整天"——冷却对这种打法完全无效 |

验证码本身:6 位数字、10 分钟有效、允许 5 次输错后作废。**输错不立刻作废**是刻意的——
错一位就要求重新收信,而每一次重发都是一封真实的外部邮件;但也不能不限,6 位数字在无限次尝试下可以直接猜穿。
失败计数写回时**保持原有过期时刻**,否则不断试错就能让验证码永不过期。

自助注册创建的账号 `sys_user.email_verified` 恒为 1;为 0 的只可能是 LDAP 影子账号、管理员预建账号,
或本能力上线前的存量数据。

**开着自助注册就必须配好 SMTP**:`AdminProductionReadinessValidator` 只要
`admin.registration.self-service-enabled=true` 就强制校验 `admin.notification.mail.enabled` 与 host;
运行时 `sendCode` 另有 fail-closed 兜底,但那时用户已经站在注册页上了。这是邮箱验证不可配的代价——
不想配 SMTP 的实例应当关掉自助注册,而不是关掉验证。

#### 审核流程

1. 用户在登录页注册(必须先通过邮箱验证码) → 创建 `PENDING`、零角色、暂落 `default` 的账号(拿不到任何权限点)
2. 管理员进「系统管理 → 用户管理」,按审核状态筛 `PENDING`
3. 点「审核」,选归属方式:
   - **新开租户**(对外实例的常态):填租户编码与名称,系统自动建租户、生成租户管理员角色并授予本租户内全部权限
   - **并入已有租户**:选租户 + 至少一个角色;对外实例上不允许选 `default`
4. 提交后自动递增 `auth_epoch` 踢掉旧会话,并在事务提交后发出站内信与邮件
5. 用户重新登录即获得权限


### 8.2 建库与部署验收(实测流程)

只部署服务、只同步表结构、不带业务数据时的完整流程。下面每一步都在临时库上实测过。

#### 1. 建库

```bash
# 客服端库:完整镜像一次建好(含所有结构与系统种子)
mysql --default-character-set=utf8mb4 -h<host> -uroot -p \
  -e "source mysql/01-agent-scope-customer-work/customer-work-schema.sql"

# 后台库:必须走这个脚本,不要 for f in mysql/02-customer-admin/*.sql
scripts/apply-admin-schema-mirror.sh customer_admin
```

**后台库为什么必须走脚本**:那个目录的约定是"文件名前缀 = 版本号,排序即执行序",
但 shell glob 与 `ls` 用的是**字典序**,版本号进三位数后两者分叉:

```
... 09-V9, 10-V10, 100-V100, 101-V101, 11-V11, ... 99-V99
```

V100/V101 会跑在 V11 之前。实测后果分两种,**后一种更阴险**:V101 直接报
`Unknown column 'r.control_plane'`(V63 才加的列);而 V100 逐表守卫、表不存在就跳过,
于是**静默什么都没做**——建出来的库排序规则始终没对齐,且没有任何报错。
脚本内部用 `sort -V` 修正,CI 也已改用它。

#### 2. 清演示数据

完整镜像自带一批 demo 业务数据(`U-demo-1`、"旗舰款无线降噪耳机"、"退款专员-小赵"这类
假订单/会员/商品/坐席/知识条目)。本地跑 demo 有用,上生产就是脏数据——
**客服智能体会拿它们当真实业务回答问题**。

```bash
scripts/clear-demo-data.sh agent_scope_customer_work customer_admin --public
```

划界的判据是"系统缺了它会不会坏":

| | 表 |
|---|---|
| **清** | `cw_order` `cw_refund` `cw_complaint` `cw_member` `cw_product` `cw_seat_agent` `cw_knowledge`;`--public` 时另清 `sql_datasource` / `sql_define` / `sql_define_param` / `sql_field_transform`(SQL 查询功能对外已下架) |
| **留** | `cw_subject_quota_level`(限流按 `level_code` 查,缺了直接 fail-closed)、`cw_dict_*`、`cw_sensitive_word`;后台的 `sys_permission`(菜单权限)、`sys_role`、`sys_tenant`、`sys_user`、`ai_model_price`、`ai_system_tool` |

#### 3. 验收核对

```sql
-- 结构:应与 mysql/schema-snapshot/ 一致
SELECT COUNT(*) FROM information_schema.tables
 WHERE table_schema='customer_admin' AND table_type='BASE TABLE';           -- 88
SELECT COUNT(*) FROM information_schema.tables
 WHERE table_schema='agent_scope_customer_work' AND table_type='BASE TABLE';-- 48（47 + 框架自建的 agentscope_sessions）

-- 排序规则:应为 0,不为 0 说明建库路径没走对
SELECT COUNT(*) FROM information_schema.tables
 WHERE table_schema IN ('customer_admin','agent_scope_customer_work')
   AND table_type='BASE TABLE' AND table_collation<>'utf8mb4_unicode_ci';

-- 菜单数据在、演示数据已清
SELECT COUNT(*) FROM customer_admin.sys_permission;      -- 166
SELECT COUNT(*) FROM agent_scope_customer_work.cw_order; -- 0
```

**登录后按这条路径走一遍**:admin 账号登录(`super_admin` 走特判,直接获得全部权限,
不依赖 `sys_role_permission`)→ 注册一个陌生账号 → 确认登录后菜单为空 →
超管审核并新开租户 → 重登逐个菜单点一遍 → 直接调 `/api/sql/query/adhoc` 应返回 403。

#### 4. 关于 V101 对既有部署的影响

**全新库上 V101 不是空操作**——实测对照:V99 种子给 `tenant_admin`(租户开通模板角色)授了
140 条权限,V101 回收了其中 **70 条**,按族分布:

```
model 8  skill 6  mcp 5  sql-datasource 5  sql-define 5  dict 4  model-experiment 4
rate-limit-rule 4  slo 4  workbench-site 4  ai-audit 2  dead-letter 2  devtools 2
governance 2  semantic-cache 2  sql-console 2  sql-query 2  billing 1  improvement 1
sensitive-hit-log 1  sensitive-word 1  sql-config 1  subject-quota 1  workbench 1
```

这是**预期且必要**的:`tenant_admin` 本就不该持有全平台一份的模型配置、能挂外部 MCP、

既有内网部署升级后同样会被回收——若你给普通角色配过这些权限,升级后需由控制面用户重新授权。

## 十、上线流程与灰度

1. **预发环境跑 MySQL 门控测试**:`MybatisApprovalStoreTest` / `MybatisSlotFillingStoreTest` / `MybatisDialogStageStoreTest` / `MybatisHandoffStoreTest` / `MybatisFeedbackStoreTest` / `MybatisAuditSinkQueryTest` 等在有 MySQL 的环境会执行真实 round-trip,无 MySQL 时自动 `assumeTrue` 跳过。**这些持久化类已在 GA 升级验证时于真实 MySQL 上跑通(并借此暴露修复了两个既有 bug:JDBC URL `characterEncoding` 非法值、审计查询的 `ESCAPE` 转义错误,详见 [MIGRATION-2.0.md §9.4](MIGRATION-2.0.md)),但仍强烈建议每次上线前在预发环境复跑一遍,确认目标库/账号可正常 round-trip**:

   ```bash
   # 预发环境(有 MySQL)执行,JDK 17;凭据经环境变量注入(测试硬编码 root/root)
   mvn -gs scripts/settings-central-direct.xml -s scripts/settings-central-direct.xml test
   # 期望:0 failures,MySQL 门控测试不再 skip
   ```

2. **单实例灰度**:先单实例 + 小比例真实流量,端到端验证审批闭环——提交退款 → 坐席带 `X-Approval-Token` 放行 → 下游执行 → `cw_audit_log` 留痕,四步全通再扩容。
3. **验证执行失败补偿**:`PendingApprovalService.retryExecutionFailures`(由 `ApprovalTimeoutScheduler` 定时驱动,上限 `human-approval.max-execution-retry-attempts`,默认 3)会回收过期执行租约并重试。生产必须提供 `ApprovalExecutionHandler`；`ApprovalExecutionContext.idempotencyKey` 固定为审批单号、fencing token 每次尝试变化。**下游资金系统必须持久化消费记录并按 idempotencyKey 幂等**；fencing token 用于阻止旧 worker 回写本地执行状态。否则进程在“下游成功、状态回写前”崩溃时仍可能重复打款。
4. **可靠投递验证**：创建并流转一张工单，确认 `cw_ticket`、`cw_ticket_event`、`cw_outbox_message` 同时提交，
   Outbox 最终进入 `SUCCEEDED`；消费端按事件 ID 去重，接受至少一次投递。
5. **多实例扩容**:确认共享计数器/会话锁及 Outbox 租约接管正常后再横向扩容。

## 十一、回滚预案

- **代码版本回滚**:先停止新版本写入，再回滚应用；Flyway 迁移默认不做自动 down。新增表/列保留通常不影响旧版，
  若存在不兼容 DDL，必须使用上线前备份和经评审的前向修复脚本，禁止直接删除生产表。
- **`store-mode` 从 jdbc 切回 memory**:进行中的审批单会从视图中"消失"(数据仍在 `cw_approval` 表里,只是不再读取)。**回滚窗口内确保没有未决审批单**,或先人工处理完再切。
- **鉴权回滚**:如 `approval-auth` 导致坐席无法操作(通常是 operators 未下发),临时缓解是运维侧下发正确的 secrets 覆盖,而不是关掉 `approval-auth.enabled`——关掉等于重新打开身份伪造漏洞。
